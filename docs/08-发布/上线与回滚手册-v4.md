## 四、回滚：分三层，从轻到重

先判断问题在哪一层，只回滚那一层。每次回滚都要产品负责人在聊天里同意，执行后写进发布记录。

### 第 1 层：网页有问题 → Pages 回到上一次部署
适用：页面打不开、按钮坏了、样式错了；数据没问题。
1. Cloudflare 控制台 → Workers & Pages → 柠檬记的 Pages 项目 → Deployments。
2. 在正式环境（Production）的列表里找到上一次成功的部署（发布前第二节第 9 项记下的编号）。
3. 点它右边的“⋯” → Rollback to this deployment（回滚到这次部署）。
4. Pages Function（语言分流、`/sb/` 转发）跟着一起回滚。如果转发是独立 Worker：Worker 页面 → Deployments → 选上一版本 → 回滚。
5. 确认：打开 `/app/version.json`，版本号是旧的；手机上关掉再打开 App，Service Worker 会换回旧版。
6. exe：R-105 起页面打包在 exe 里，Pages 回滚**不会改变已安装 exe 里的页面**；`latest.json` 回到旧版，但已经装了新 exe 的电脑不会自动降级。exe 本身有问题时，用旧代码打一个更高的版本号（如 4.0.1），重新走 desktop 流水线。

**4.0.0 首发时没有“上一次部署”**：第 1 层不可用，网页有大问题时直接走第五节“撤回 3.0.1 只读版”。

### 第 2 层：服务器函数有问题 → 重新部署上一个 tag 的函数
适用：提醒不推、AI 识别出错、登录或邀请码报错，查明是 Edge Function 的问题。
1. 办法 A（首选）：GitHub → Actions → deploy-prod → 找到上一个 tag 那次的运行 → Re-run all jobs → 产品负责人点“批准”。它会重新部署那个 tag 的函数和网页；数据库迁移只增不改，`db push` 不会有变化。
2. 办法 B（GitHub 用不了时）：运维在本机 `git checkout <上一个 tag>` → `npm ci` → 按 deploy-prod 里“复制 shared”那一步，把 `/shared/` 复制到 `supabase/functions/_shared/gen/`（架构 2.5、8.3；原来的 `build.py --target fn` 已取消）→ `supabase functions deploy <函数名> --project-ref <正式项目>`，逐个部署出问题的函数 → 切回主干。这一步要用正式项目的令牌，**由产品负责人本人在自己的 PowerShell 窗口里执行**：运维写好完整命令（不含令牌），本人把令牌放进这个窗口的环境变量、运行、关掉窗口。例外由运维执行时，本人临时生成一把新令牌，用完立即吊销并记进过程记录（人员名单第七节第 5 条）。
3. 数据库**不做回退**：架构 8.3 约定迁移只做向后兼容的变更，旧函数能直接用新表结构。不要手写删列、删表的回退 SQL。
4. 确认：设一条 2 分钟后的提醒，能准时收到；跑一次 AI 识别。

### 第 3 层：数据错了 → 按用户从 JSON 恢复
适用：搬家导错、程序写坏了某个人的数据。这一层会**丢掉备份时间之后的改动**，只在前两层解决不了时用。
1. **先止损**：找到写坏数据的原因，先用第 1 或第 2 层回滚代码，避免恢复后又被写坏。
2. **选备份**：服务器备份保留 7 天（`backups/<日期>/<user_id>/`）；本机每日备份保留 30 天（`E:\柠檬记-备份\每日\<日期>\<user_id>\`，以架构第 10 节为准）；版本前、发布前的永久保留。选出问题之前最近的一份。
3. **先在预览环境试**：把这份备份导入预览项目，QA 核对条数、抽查 10 条，隐私记能用同一把 VAULT_KEY 解开。
4. **告诉受影响的人**：恢复期间不要记东西；备份时间之后记的内容会丢，先截图或抄下来。
5. **正式恢复**：用恢复脚本（`tools/backup/` 下，后端在 B7a 前写好、演练过；名字以实现为准），**只针对这一个 user_id**，先 `--dry-run` 看要改多少条，再正式执行。要用 service role key，所以**由产品负责人本人在自己的 PowerShell 窗口里运行**，把条数告诉后端；例外由 AI 执行时，用完立即轮换这把密钥。备份文件是 7-Zip 加密的，恢复时临时解开，用完删掉明文。
6. **核对**：QA 核对条数、抽查；本人在 iPhone 上整表重拉后看一遍。
7. **图片和附件**：服务器备份不含图片和附件；图片（含纪念日头像）从本机 `E:\柠檬记-备份\图片\<user_id>\`、附件从 `E:\柠檬记-备份\附件\<user_id>\`（都是每周增量）找回，临时解开、上传后删明文。向量不用恢复，会自动重算。
8. 记进发布记录：恢复了谁、用的哪天的备份、丢了多长时间的改动。

### 回滚做不到的一件事：已经交给微软的链接
预览 PPT 时，文件以短时签名链接交给微软在线预览（含隐私记的 PPT，R-118）。**链接一旦发出就没法提前作废，微软那边可能还有缓存**，任何一层回滚都收不回来。万一预览错了文件：
1. 马上删掉原文件（隐私记的 PPT，临时对象按架构的规则会在链接到期后被清掉，也要确认已删）；
2. 记进事故记录（哪个文件、什么时候、谁预览的）；
3. 告诉产品负责人。能做的只有这些。

## 五、3.0.1 只读版：撤回办法

3.0.1 是搬家后留在 claude.ai 上的旧版，只能看，顶部提示去新版。有两种“撤回”：

### A. 4.0.0 出了大问题，要退回旧版继续用（30 天内）
适用：上线后发现 4.0.0 不能用，第 1、2 层回滚也解决不了（首发时尤其如此）。
1. 产品负责人同意退回。
2. 把 v3 最后一版（`archive/releases/v3/planner.html`）重新发布到 claude.ai 的**同一个地址**，覆盖 3.0.1 只读版。旧版的数据还在 claude.ai 的数据库里，没有删。
3. 重新开启 Claude 定时任务 `planner-daily-snapshot`。
4. **搬家之后在 4.0.0 里新记的东西不会自动回到旧版**。从 4.0.0 导出这段时间的记录，交给产品负责人看，手动补进旧版（数量少时）；没有自动的反向搬家工具。所以越早决定越好。
5. 4.0.0 的网站：Cloudflare 上把 `/app/` 换成“维护中”页面，或者暂停 Pages 项目，避免两边同时记。
6. 修好以后重新走一遍第三节（搬家要先清掉 4.0.0 里那个账号的旧导入，或者导入时按 legacy_id 去重）。

### B. 30 天到了，正常下线 3.0.1
1. 第 30 天由主持人提醒产品负责人。
2. 产品负责人确认新版用得没问题。
3. 把 claude.ai 上的页面换成一页“已停用，请用 https://lemomemo.com/app/”；要彻底删掉页面，必须产品负责人本人同意。
4. 本机归档永久保留（`archive/releases/`、`E:\柠檬记-备份\` 下的“迁移前”文件夹）。
5. 之后 v3 的构建脚本移进 `archive/v3-build/`，主干只剩 Vite 构建（架构 8.1）。
