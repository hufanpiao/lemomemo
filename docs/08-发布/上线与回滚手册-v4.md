## 四、回滚：分三层，从轻到重

先判断问题在哪一层，只回滚那一层。每次回滚都要产品负责人在聊天里同意，执行后写进发布记录。

### 第 1 层：网页有问题 → Pages 回到上一次部署
适用：页面打不开、按钮坏了、样式错了；数据没问题。
1. Cloudflare 控制台 → Workers & Pages → 柠檬记的 Pages 项目 → Deployments。
2. 在正式环境（Production）的列表里找到上一次成功的部署（发布前第二节第 9 项记下的编号）。
3. 点它右边的“⋯” → Rollback to this deployment（回滚到这次部署）。
4. Pages Function（语言分流、`/sb/` 转发）跟着一起回滚。如果转发是独立 Worker：Worker 页面 → Deployments → 选上一版本 → 回滚。
5. 确认：打开 `/app/version.json`，版本号是旧的；手机上关掉再打开 App，Service Worker 会换回旧版。
6. exe：R-105 起页面打包在 exe 里，Pages 回滚**不会改变已安装 exe 里的页面**；`latest.json` 回到旧版，但已经装了新 exe 的电脑不会自动降级。exe 本身有问题时，用旧代码打一个更高的版本号（如 4.0.1），重新走 desktop 流水线。

**4.0.0 首发时没有“上一次部署”**：第 1 层不可用；R-208 起也没有 v3 可退（第五节已删）。网页有大问题时，在 Cloudflare 上把 `/app/` 换成一页“维护中”（或暂停 Pages 项目），修好再发 4.0.1。

### 第 2 层：服务器函数有问题 → 重新部署上一个 tag 的函数
适用：提醒不推、AI 识别出错、登录或邀请码报错，查明是 Edge Function 的问题。
1. 办法 A（首选）：产品负责人用冻结副本运行 `publish.ps1 -Tag <上一个 tag> -Only functions`（R-206；产物从上一个 tag 那次 release-build 下载，Actions 产物保留 90 天，过期了就在那个 tag 上重跑 release-build）。它只重新部署那个 tag 的函数；数据库迁移只增不改，不用 `db push`。网页也要回到上一版时用第 1 层。
2. 办法 B（GitHub 用不了时）：运维在本机 `git checkout <上一个 tag>` → `npm ci` → 按 release-build 里“复制 shared”那一步，把 `/shared/` 复制到 `supabase/functions/_shared/gen/`（架构 2.5、8.3；原来的 `build.py --target fn` 已取消）→ `supabase functions deploy <函数名> --project-ref <正式项目>`，逐个部署出问题的函数 → 切回主干。这一步要用正式项目的令牌，**由产品负责人本人在自己的 PowerShell 窗口里执行**：运维写好完整命令（不含令牌），本人把令牌放进这个窗口的环境变量、运行、关掉窗口。例外由运维执行时，本人临时生成一把新令牌，用完立即吊销并记进过程记录（人员名单第七节第 5 条）。
3. 数据库**不做回退**：架构 8.3 约定迁移只做向后兼容的变更，旧函数能直接用新表结构。不要手写删列、删表的回退 SQL。
4. 确认：设一条 2 分钟后的提醒，能准时收到；跑一次 AI 识别。

### 第 3 层：数据错了 → 按用户从 JSON 恢复
适用：程序写坏了某个人的数据。这一层会**丢掉备份时间之后的改动**，只在前两层解决不了时用。
1. **先止损**：找到写坏数据的原因，先用第 1 或第 2 层回滚代码，避免恢复后又被写坏。
2. **选备份**：服务器备份保留 7 天（`backups/<日期>/<user_id>/`）；本机每日备份保留 30 天（`E:\柠檬记-备份\每日\<日期>\<user_id>\`，以架构第 10 节为准）；版本前、发布前的永久保留。选出问题之前最近的一份。
3. **先在预览环境试**：把这份备份导入预览项目，QA 核对条数、抽查 10 条，隐私记能用同一把 VAULT_KEY 解开。
4. **告诉受影响的人**：恢复期间不要记东西；备份时间之后记的内容会丢，先截图或抄下来。
5. **正式恢复**：用恢复脚本（`tools/backup/` 下，后端在 B7a 前写好、演练过；名字以实现为准），**只针对这一个 user_id**，先 `--dry-run` 看要改多少条，再正式执行。要用 service role key，所以**由产品负责人本人在自己的 PowerShell 窗口里运行**，把条数告诉后端；例外由 AI 执行时，用完立即轮换这把密钥。备份是明文（R-209、R-210），直接用；恢复时复制出来的临时文件夹用完删掉。
6. **核对**：QA 核对条数、抽查；本人在 iPhone 上整表重拉后看一遍。
7. **图片和附件**：服务器备份不含图片和附件；图片（含纪念日头像）从本机 `E:\柠檬记-备份\图片\<user_id>\`、附件从 `E:\柠檬记-备份\附件\<user_id>\`（都是每周增量）找回（明文，R-210），上传后删掉临时副本。向量不用恢复，会自动重算。
8. 记进发布记录：恢复了谁、用的哪天的备份、丢了多长时间的改动。

### R2 不可用（照片和附件存不进、打不开；架构 0.32、12 风险 23）

> 运维 10-28 起草（B0 R2 任务单 O-6，原定 B7a 前写，提前写好）；B7a 审手册时代码审查员、安全审查员一并看，标“待实测”的在 B7 恢复演练里核实。

适用：照片、头像、附件显示占位、上传一直失败，**文字照常能记、能同步**（数据库在 Supabase，不受影响）。R2 本身没有备份，本机每周拉取是唯一副本（架构第 10 节）。

**先判断是哪一种**（按从常见到少见）：

| 现象 | 多半是 | 怎么办 |
|---|---|---|
| 所有人、所有图片都打不开，`/files` 返回 5xx；Cloudflare 后台 R2 › 存储桶的“指标”里请求在报错 | **令牌到期或被删**（R2 令牌建议 90 天到期，环境清单第四节）、令牌被误改了权限 | 下面第 1 条 |
| 同上，且 [Cloudflare 状态页](https://www.cloudflarestatus.com/) 上 R2 标着故障 | **R2 故障** | 下面第 2 条 |
| Cloudflare 后台提示账单问题、账号受限 | **账单**（卡过期、扣款失败） | 负责人本人在 管理账户 › 账单 里处理；处理好后不用改任何配置 |
| 只有某几张打不开（占位），别的正常 | 对象丢了或行和对象对不上 | 不是“R2 不可用”：按第 3 层第 7 步从本机备份找回这几个文件；先跑一遍 file-check 补扫看有多少 |
| 怀疑令牌或 `FILES_URL_SECRET` 泄露 | — | 下面第 3 条 |

1. **令牌到期或被删**（最常见）：
   1. 负责人在 R2 › API 令牌里看是哪一把（`/files` 用的“柠檬记 正式 files”、函数用的“柠檬记 正式 functions”）过期或不在了；
   2. 照[负责人 B0 网页操作清单](../00-团队/负责人B0网页操作清单.md) ⑫ C 重新生成那一把，运行 `set-r2-tokens.ps1 -Target production`（两把都要粘贴，没过期的那把粘原值即可）；
   3. Supabase 的 secrets 改了立即对函数生效；**Pages 的变量只对之后的部署生效**，所以要重新部署一次当前版本：负责人运行 `publish.ps1 -Tag <当前 tag>`（同一个 tag 再发一次，迁移和函数没有变化）；
   4. 确认：手机上打开有图片的随手记，能显示；传一张新图能成功；
   5. 记进发布记录；到期提醒改到下次到期前一周（主持人）。
2. **R2 故障**：没有可回滚的东西，**不切换**。
   1. 在聊天里告诉用户“照片和附件暂时打不开，文字照常记”；
   2. 等 Cloudflare 恢复；恢复后看一眼 file-check 有没有卡住的 pending（上传失败的附件会留在 pending，按架构 5.13 的重试和清理处理）；
   3. 超过 24 小时还没恢复，或 Cloudflare 宣布长时间故障、账号被封：负责人决定要不要走下一节“切回 Supabase 存储”。
3. **怀疑泄露**：
   1. `R2_FILES_*` / `R2_FN_*`：负责人马上在 R2 › API 令牌里**删掉那一把**（删了立即失效），再按第 1 条生成新的并写入；删和写之间这段时间 `/files` 会报错，属于预期；
   2. `FILES_URL_SECRET`：重新运行 `set-r2-tokens.ps1 -Target production`（每次都会换一个新的），重新部署后所有没过期的图片链接立即作废（最长 10 分钟的影响，App 会重新签）；
   3. 看 R2 › 存储桶 › 指标，有没有不寻常的读取量；记进事故记录；
   4. 对象被删或被改：按第 3 层第 7 步，从本机 `E:\柠檬记-备份\图片\`、`附件\` 用 `tools/backup/restore-files.ps1` 传回（临时写令牌，用完立即吊销，架构第 10 节；脚本 B7 写，**待实测**）。

### 切回 Supabase 存储（R2 长期不能用、或决定不用 R2 时）

> 这是**开发改动加一次发布**，不是点几下就能切回去的开关：架构 0.32 的方案估约 **3～5 人日**（[方案](../10-架构/方案-文件存储改用R2.md)第 8 节）。由负责人决定做不做；做的话主持人排进开发，按普通发布流程上线。下面是运维写的顺序，**各步都待实测**，B7a 审手册时请架构师核对。

**先知道的代价**：
- **Supabase 免费版文件存储只有 1 GB**（和数据库等共用告警口径，架构 0.32 第 8 条），而 R-217 定负责人上限 5 GB：切回前要么把每人上限调到装得下（`private.user_limits.media_mb`），要么升级 Supabase Pro（每月 25 美元起，以官网为准）。负责人先定这一条。
- Supabase Storage 的 S3 访问密钥**不能按桶限权**（架构第 10 节原来的“需核实”），`/files` 和服务器函数要共用一把全权限的，安全审查员要重新看。
- `If-None-Match: *` 条件写在 Supabase 的 S3 接口上支不支持**没有核实**；不支持就用架构 3.3 G 的退路（先 HEAD 再写，file-check 的 etag 兜底）。

**顺序**：
1. **暂停上传**：发一版让 `/files` 的上传返回“暂时不能上传”（具体开关由前端 B 在 B7a 审手册时补；只读照常），避免切换期间两边各有一部分新文件。
2. **建回四个桶和权限**：后端写一个**新迁移**（迁移只增不改，不改 0003、0004、0006），建 `images`、`files`、`vault-images`、`vault-files` 四个桶、大小和类型上限；客户端不直接访问存储，所以不用恢复原来的 `img_*`、`file_*` 存储策略（`/files` 照旧是唯一出入口）。
3. **复制对象**：用 R2 的只读令牌（或 R2 不可用时用本机 `E:\柠檬记-备份\图片\`、`附件\`）把四个桶的对象按原路径复制到 Supabase（`rclone copy`，S3 接口对 S3 接口；`--checksum`）。数条数、抽查 sha256；file-check 全量补扫一遍。
4. **改配置不改代码**（`shared/objstore.ts` 和 `/files` 是唯一出入口，架构 12 风险 23 的退路）：
   - Pages：`R2_ENDPOINT` 改成 `https://<正式 ref>.supabase.co/storage/v1/s3`，`R2_FILES_*` 换成 Supabase 的 S3 访问密钥（Supabase › Storage › S3 Connection 生成，**负责人本人**生成并运行 `set-r2-tokens.ps1`；脚本对格式的检查要放宽，运维那时改）；
   - Supabase secrets：`R2_ENDPOINT`、`R2_FN_*` 同样换；
   - 签名的区域改成项目所在区域（`ap-northeast-2`），由前端 B 确认 objstore 的区域可配；
   - 清单的 `store` 改回 `'supabase'`、D1 跟着改（后端）。
5. **发布**：按 `publish.ps1` 正常发一版（含第 2 步的迁移）；打开上传。
6. **核对**：传一张图、开一个附件、注销一个测试账号后四个桶里这个人的前缀为 0（预览环境先完整走一遍）。
7. **收尾**：本机每周拉取改用 Supabase 的 S3 只读访问（`pull.ps1` 改地址和凭据）；隐私说明里“照片和附件存放在境外”一项按实际改回（15.7 第 21 项）；R2 里的对象确认 Supabase 这边齐了以后再由负责人决定删不删；1 美元账单提醒留着。
8. 记进发布记录和架构（新开一个 0.x 变更记录）。

### 回滚做不到的一件事：已经交给微软的链接
预览 PPT 时，文件以短时签名链接交给微软在线预览（含隐私记的 PPT，R-118）。**链接一旦发出就没法提前作废，微软那边可能还有缓存**，任何一层回滚都收不回来。万一预览错了文件：
1. 马上删掉原文件（隐私记的 PPT，临时对象按架构的规则会在链接到期后被清掉，也要确认已删）；
2. 记进事故记录（哪个文件、什么时候、谁预览的）；
3. 告诉产品负责人。能做的只有这些。
