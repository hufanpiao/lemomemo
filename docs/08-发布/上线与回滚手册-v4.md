  10-30 起（OPS-deploy ②③⑤⑥⑦⑧，审查通过）脚本还会：① 第 4 步 `npm ci` 之后删掉 `node_modules\.bin` 和 `.package-lock.json`，算 wrangler 整棵依赖树的哈希，和 `tools\release\wrangler-tree.lock` 对不上就停（第 5 步输令牌前再算一次；升级 wrangler 或改 `tools\deploy` 的锁文件时要一起重算，`-DryRun` 对不上会打印实际值）；② 令牌只在脚本内存里（SecureString），每个子进程启动前才把**它要的那几把**设进环境变量、结束就清（link 和 db push 拿 Supabase 令牌和数据库密码，functions deploy 只拿 Supabase 令牌，wrangler 只拿 Cloudflare 令牌和 Account ID，`-DryRun` 一把都不给）；窗口里预先有这几个环境变量，第 1 步就停；③ 改库之前用 `wrangler secret list` 只读核对 lemo-ops 的六个密钥名字都在（只取名字、不打印），缺一个就停——所以**发布前要先把六个密钥设齐**；④ 第 3 步之后给 `node_modules\aws4fetch` 记哈希，改库前、部署网页前各比一次；⑤ 第 3 步核对后把 `dist\web` 复制到临时工作目录，之后的指纹复核和 `pages deploy` 都用这份（当前目录仍是仓库根，所以 `functions\` 照旧）；⑥ 全局 git 配置（global 一级及它 include 的文件）里有 `filter.*`、`core.attributesfile`，或 `git var GIT_ATTR_GLOBAL` 指的属性文件不为空，就停；system 一级（10-30 第五批，R-264、R-265，待审查）只放行 Git for Windows 自带的 4 项 `filter.lfs.clean`、`filter.lfs.smudge`、`filter.lfs.process`、`filter.lfs.required`（名字和值都要和默认一字不差），其余 `filter.*` 和 `core.attributesfile` 照停；脚本第一次调 git 前在本进程设 `GIT_ATTR_NOSYSTEM=1`，git 和它的子进程都不读 Git 自带的系统属性文件，没生效（`git var GIT_ATTR_SYSTEM` 仍答出路径）就停；`GIT_CONFIG_SYSTEM` 不再是禁止的环境变量（system 一级检查读的就是 git 实际用的那份）。**Git 要 2.42 以上**，更老的版本 `git var` 不认这两项，脚本会停下提示升级。
- **停在 lemo-ops 这一步时**（屏幕上是“发布停止：lemo-ops 部署失败……”）：数据库迁移已推、服务器函数已是新版，lemo-ops 和网页还是旧版。这种状态能用，只是上面“同一次部署”说的 ② 没生效（Resend 用量读到坏数据时，在报的告警仍可能被悄悄删掉）。处理：修好原因（常见是令牌少了 Workers Scripts: Edit、KV id 不对、六个密钥没设）后，**用同一个 tag、同样的参数原样重跑 `publish.ps1 -Tag v4.0.0 -Ops`**——迁移演练会显示没有新迁移，函数和 lemo-ops 重新部署一遍，再部署网页。回滚（`-Only functions -Ops`）停在这一步也一样原样重跑。

```powershell
# 在冻结副本根目录（已切到这次发布的 tag），开一个新的 PowerShell 窗口
# 先演练（不要令牌、不部署）：看 lemo-ops 打包演练里 OPS_STATE 绑定的是真的命名空间 ID
powershell -NoProfile -ExecutionPolicy Bypass -File E:\柠檬记-发布\publish-v4.0.0.ps1 -Tag v4.0.0 -Ops -DryRun
# 正式发布（网页、服务器函数、lemo-ops 一次部署）
powershell -NoProfile -ExecutionPolicy Bypass -File E:\柠檬记-发布\publish-v4.0.0.ps1 -Tag v4.0.0 -Ops
# 做完关掉这个窗口
```

- 怎么确认成功：Cloudflare 控制台 Workers → lemo-ops 的部署记录是刚才这一次（版本标签是这次的 tag、说明是 `<tag>@<提交前 12 位>`）、两个 Cron Trigger（`*/15 * * * *`、`7 0 * * *`）都在；15 分钟后看一次它的日志没有报错。

上线后观察：
- 当天：每个整点看一次推送是否准时、Worker 有没有报错。
- 前 7 天：每天看一次备份、保活、用量。
- 有问题按第四节处理。

## 四、回滚：分三层，从轻到重

先判断问题在哪一层，只回滚那一层。每次回滚都要产品负责人在聊天里同意，执行后写进发布记录。

### 第 1 层：网页有问题 → Pages 回到上一次部署
适用：页面打不开、按钮坏了、样式错了；数据没问题。
1. Cloudflare 控制台 → Workers & Pages → 柠檬记的 Pages 项目 → Deployments。
2. 在正式环境（Production）的列表里找到上一次成功的部署（发布前第二节第 9 项记下的编号）。
3. 点它右边的“⋯” → Rollback to this deployment（回滚到这次部署）。
4. Pages Function（语言分流、`/sb/` 转发）跟着一起回滚。如果转发是独立 Worker：Worker 页面 → Deployments → 选上一版本 → 回滚。
5. 确认：打开 `/app/version.json`，版本号是旧的；手机上关掉再打开 App，Service Worker 会换回旧版。
6. exe：R-105 起页面打包在 exe 里，Pages 回滚**不会改变已安装 exe 里的页面**；`latest.json` 回到旧版，但已经装了新 exe 的电脑不会自动降级。exe 本身有问题时，用旧代码打一个更高的版本号（如 4.0.1），重新走 desktop 流水线。

**4.0.0 首发时没有“上一次部署”**：第 1 层不可用；R-208 起也没有 v3 可退（第五节已删）。网页有大问题时，在 Cloudflare 上把 `/app/` 换成一页“维护中”（或暂停 Pages 项目），修好再发 4.0.1。

### 第 2 层：服务器函数有问题 → 重新部署上一个 tag 的函数
适用：提醒不推、AI 识别出错、登录或邀请码报错，查明是 Edge Function 的问题。
1. 办法 A（首选，10-29 起可用）：产品负责人在冻结副本里切到上一个 tag（`git switch --detach <上一个 tag>`），运行 `publish.ps1 -Tag <上一个 tag> -Only functions -Ops`（可以先加 `-DryRun` 演练一遍，不要令牌）。这一层同样会在部署前核对 lemo-ops 的六个密钥名字（10-30 起，第三节）。它只重新部署那个 tag 的服务器函数，紧接着把 lemo-ops 也部署成同一个 tag 的版本（第 2b 条）；不构建网页、不 `db push`、不部署 Pages，所以**不要数据库密码**，只要正式 Supabase 令牌和正式 Cloudflare 令牌（Workers Scripts: Edit）。这个 tag 里有 usage-report 和 lemo-ops 时，不加 `-Ops` 脚本第 1 步就停。**不要不带 `-Only` 跑整套 `publish.ps1 -Tag <上一个 tag>`**：它会连 `db push` 和 Pages 一起动。数据库迁移只增不改，不用 `db push`；网页也要回到上一版时用第 1 层。原定做法里“产物从上一个 tag 那次 release-build 下载”（R-206、架构 0.31 第 24 条，Actions 产物保留 90 天，过期了就在那个 tag 上重跑 release-build）等 B6-exe 期间脚本改成下载 CI 产物以后才有；现在用的是冻结副本里这个 tag 的源码。
2. 办法 B（GitHub 用不了时）：运维在本机 `git checkout <上一个 tag>` → `npm ci` → 按 release-build 里“复制 shared”那一步，把 `/shared/` 复制到 `supabase/functions/_shared/gen/`（架构 2.5、8.3；原来的 `build.py --target fn` 已取消）→ `supabase functions deploy <函数名> --project-ref <正式项目>`，逐个部署出问题的函数 → 切回主干。运行 `supabase functions deploy` 之前，先确认 `supabase\.env*` 和仓库根目录的 `.env*` 都不存在（`Get-ChildItem -Force supabase\.env*, .env*` 什么都不列；Supabase CLI 会自动读这些文件，里面的设置可能把令牌带到别的服务器；`.env.production.local` 是构建用的公开值，也先移出仓库目录），并在同一个窗口里设 `$env:SUPABASE_API_URL='https://api.supabase.com'`（进程里的值优先于这些文件）。这一步要用正式项目的令牌，**由产品负责人本人在自己的 PowerShell 窗口里执行**：运维写好完整命令（不含令牌），本人把令牌放进这个窗口的环境变量、运行、关掉窗口。例外由运维执行时，本人临时生成一把新令牌，用完立即吊销并记进过程记录（人员名单第七节第 5 条）。
2b. **lemo-ops 跟着回滚到同一个 tag**：回滚了 usage-report（或整批函数）时，lemo-ops 也要回到同一个 tag（两者对 `resend_unreadable` 的约定是一起改的，见第三节“usage-report 和 lemo-ops 必须同一次部署”）。用办法 A 时 `-Ops` 已经做了这一步；用 `-Only functions -Ops` 回滚后，lemo-ops 的“线上网页版本和 lemo-ops 的 tag 核对不通过”告警会一直响（6 小时一封“仍未恢复”），直到网页也回到同一个 tag，属预期（见本条末尾）；用办法 B 时，在同一个 `git checkout <上一个 tag>` 的副本里由产品负责人本人手工部署（10-29 运维已在临时目录用同样的命令 `--dry-run` 跑通，wrangler 4.150.0）：

   先确认 Windows 剪贴板历史关着（设置 › 系统 › 剪贴板），窗口里没有代理、`NODE_OPTIONS`、`CLOUDFLARE_API_KEY` 这类环境变量（见第三节“部署 lemo-ops”），仓库目录和各级父目录没有 `wrangler.toml` 之类的文件。

   ```powershell
   # 在已切到上一个 tag 的副本根目录，开一个新的 PowerShell 窗口
   # 和第三节“设六个密钥”那段一样（10-30 起，OPS-deploy-sugg ⑤）：按锁文件把 wrangler 4.150.0 装到临时目录（不装项目依赖、不跑项目脚本），
   # 删掉 node_modules\.bin 和 node_modules\.package-lock.json，核对整棵依赖树和 tools\release\wrangler-tree.lock 一致了才往下走；
   # 用 node 直接跑 node_modules\wrangler\bin\wrangler.js（不用 .bin\wrangler.cmd）。先不要令牌做一次 --dry-run 看绑定，再问令牌部署。
   # 整段从 & { 到 } 一起粘贴：中间哪一步不对整段就停；不论成功失败，最后都清掉令牌、剪贴板和临时目录
   & {
     $ErrorActionPreference = 'Stop'
     foreach ($n in 'HTTPS_PROXY', 'HTTP_PROXY', 'ALL_PROXY', 'NODE_OPTIONS', 'NODE_TLS_REJECT_UNAUTHORIZED', 'NODE_EXTRA_CA_CERTS', 'CLOUDFLARE_API_KEY', 'CLOUDFLARE_EMAIL', 'CLOUDFLARE_API_TOKEN') {
       if ([Environment]::GetEnvironmentVariable($n, 'Process')) { throw "这个窗口里有 $n，先关掉窗口、从系统环境变量里删掉再来" }
     }
     $tag = (Read-Host '要回到的 tag（例如 v4.0.0，就是这个副本现在检出的那个）').Trim()
     if ($tag -cnotmatch '^v[0-9]+\.[0-9]+\.[0-9]+\z') { throw 'tag 要写成 vX.Y.Z（小写 v、半角数字）' }
     # 核对这个副本检出的就是这个 tag 的提交（R-266）：不一致就停，免得把别的代码当成这个 tag 部署上去
     $tagCommit = git rev-parse --verify --quiet "$tag^{commit}"
     if ($LASTEXITCODE -ne 0 -or -not $tagCommit) { throw "这个副本里没有 tag $tag" }
     $headCommit = git rev-parse HEAD
     if ($LASTEXITCODE -ne 0 -or -not $headCommit) { throw 'git rev-parse HEAD 失败' }
     if ([string]$headCommit -cne [string]$tagCommit) { throw "这个副本检出的不是 $tag（HEAD 是 $headCommit，$tag 指向 $tagCommit）：先 git checkout $tag 再来" }
     $t = Join-Path $env:TEMP ('lemo-wrangler-' + [guid]::NewGuid().ToString('N'))
     New-Item -ItemType Directory -Path $t | Out-Null
     try {
       Copy-Item -LiteralPath 'tools\deploy\package.json', 'tools\deploy\package-lock.json' -Destination $t
       Push-Location $t
       try { npm.cmd ci --ignore-scripts --no-audit --no-fund } finally { Pop-Location }
       if ($LASTEXITCODE -ne 0) { throw "npm ci 失败（退出码 $LASTEXITCODE）" }
       # 核对依赖树。锁文件里唯一不以 # 开头的那一行：package-lock.json 的 SHA-256、文件数、树哈希。
       # 树哈希的算法和 publish.ps1 的 Get-DistHash 一样：每个文件一行“SHA-256␠␠相对路径（/ 分隔）\n”，按路径排序后整体再算 SHA-256
       $lock = @(Get-Content -LiteralPath 'tools\release\wrangler-tree.lock' -Encoding UTF8 | ForEach-Object { $_.Trim() } | Where-Object { $_ -and -not $_.StartsWith('#') })
       $want = @($lock[0] -split '\s+')
       if ($lock.Count -ne 1 -or $want.Count -ne 3) { throw 'tools\release\wrangler-tree.lock 的格式不对' }
       if ((Get-FileHash -LiteralPath (Join-Path $t 'package-lock.json') -Algorithm SHA256).Hash.ToLower() -cne $want[0]) { throw 'tools\deploy\package-lock.json 和 wrangler-tree.lock 记的不是同一份' }
       $nm = (Resolve-Path -LiteralPath (Join-Path $t 'node_modules')).ProviderPath
       Remove-Item -LiteralPath (Join-Path $nm '.bin'), (Join-Path $nm '.package-lock.json') -Recurse -Force -ErrorAction SilentlyContinue
       $all = @(Get-ChildItem -LiteralPath $nm -Recurse -Force)
       if (@($all | Where-Object { $_.Attributes -band [IO.FileAttributes]::ReparsePoint }).Count -gt 0) { throw 'node_modules 里有符号链接或联接' }
       $files = @($all | Where-Object { -not $_.PSIsContainer })
       $rels = [string[]]@($files | ForEach-Object { $_.FullName.Substring($nm.Length + 1).Replace('\', '/') })
       $rows = [string[]]@($files | ForEach-Object { (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash.ToLower() })
       for ($i = 0; $i -lt $rows.Count; $i++) { $rows[$i] = $rows[$i] + '  ' + $rels[$i] + "`n" }
       [Array]::Sort($rels, $rows, [StringComparer]::Ordinal)   # 只适用于 ASCII 路径（现在的依赖树全是 ASCII）
       $total = (Get-FileHash -InputStream ([IO.MemoryStream]::new([Text.Encoding]::UTF8.GetBytes(-join $rows))) -Algorithm SHA256).Hash.ToLower()
       if ($files.Count -ne [int]$want[1] -or $total -cne $want[2]) { throw "装好的 wrangler 依赖树和 wrangler-tree.lock 对不上（实际 $($files.Count) 个文件、树哈希 $total）。还没输令牌：停下来，在聊天里告诉运维" }
       Write-Host "wrangler 依赖树和 tools\release\wrangler-tree.lock 一致（$($files.Count) 个文件）"
       $w = Join-Path $nm 'wrangler\bin\wrangler.js'
       $empty = Join-Path $t 'empty.env'
       New-Item -ItemType File -Path $empty | Out-Null
       # 和 publish.ps1 的 Set-WranglerEnv 一样：API 地址固定为官方、不写日志文件、不发统计和错误报告、不打印横幅（不去 npm 查新版本）、不查 skills 更新
       $env:CLOUDFLARE_API_BASE_URL = 'https://api.cloudflare.com/client/v4'
       $env:WRANGLER_WRITE_LOGS = 'false'; $env:WRANGLER_LOG_PATH = Join-Path $t 'wrangler-logs'
       $env:WRANGLER_SEND_METRICS = 'false'; $env:DO_NOT_TRACK = '1'; $env:WRANGLER_SEND_ERROR_REPORTS = 'false'
       $env:WRANGLER_HIDE_BANNER = 'true'; $env:WRANGLER_NO_SKILLS_UPDATE_PROMPTS = 'true'
       # 先看绑定（不要令牌、不上传）：OPS_STATE 不能是 REPLACE_WITH_KV_NAMESPACE_ID
       node $w deploy --config workers\lemo-ops\wrangler.toml --env-file $empty --dry-run --outdir (Join-Path $t 'dry')
       if ($LASTEXITCODE -ne 0) { throw "wrangler deploy --dry-run 失败（退出码 $LASTEXITCODE）" }
       $ok = (Read-Host '上面 OPS_STATE 绑定的是真的命名空间 ID 吗？是就输入“继续”').Trim()
       if ($ok -ne '继续') { throw '没有输入「继续」，已取消' }
       $acct = (Read-Host 'Cloudflare Account ID（32 位，Cloudflare 首页右侧，不是密钥）').Trim()
       if ($acct -notmatch '^[0-9a-f]{32}$') { throw 'Account ID 的格式不对' }
       $s = Read-Host -AsSecureString '粘贴正式 Cloudflare 令牌'   # 在这里粘贴令牌，屏幕不显示
       Set-Clipboard -Value ' '
       if ($s.Length -lt 8) { $s.Dispose(); throw '令牌太短，像是没粘贴上' }
       $env:CLOUDFLARE_API_TOKEN = [Net.NetworkCredential]::new('', $s).Password
       $s.Dispose()
       $env:CLOUDFLARE_ACCOUNT_ID = $acct
       node $w deploy --config workers\lemo-ops\wrangler.toml --env-file $empty --tag $tag
       if ($LASTEXITCODE -ne 0) { throw "wrangler deploy 失败（退出码 $LASTEXITCODE）" }
     } finally {
       foreach ($n in 'CLOUDFLARE_API_TOKEN', 'CLOUDFLARE_ACCOUNT_ID', 'CLOUDFLARE_API_BASE_URL', 'WRANGLER_WRITE_LOGS', 'WRANGLER_LOG_PATH', 'WRANGLER_SEND_METRICS', 'DO_NOT_TRACK', 'WRANGLER_SEND_ERROR_REPORTS', 'WRANGLER_HIDE_BANNER', 'WRANGLER_NO_SKILLS_UPDATE_PROMPTS') {
         [Environment]::SetEnvironmentVariable($n, $null, 'Process')
       }
       Set-Clipboard -Value ' '
       Remove-Item -LiteralPath $t -Recurse -Force -ErrorAction SilentlyContinue
     }
   }
   # 做完关掉这个窗口（令牌的托管副本还在这个窗口的内存里，关掉才没有）
   ```

   **回滚后会收到“线上网页版本和 lemo-ops 的 tag 核对不通过”（R-270，10-30 起）**：lemo-ops 每 15 分钟把自己这一版的 tag（`wrangler deploy --tag`，经 `version_metadata` 绑定读到）去掉开头的 v 后，和 `https://lemomemo.com/app/version.json` 的版本号逐字比对，连续 2 轮（约 30 分钟）对不上、取不到或格式不对就发信。如果刚按回滚手册只回滚了函数，属预期（网页还是新版、lemo-ops 已回到旧 tag），网页也回到同一个 tag 或重新发布后连续 2 轮一致会发“已恢复”。另外，`wrangler secret put` 或在控制台改 lemo-ops 设置生成的新版本可能不带 tag，也会触发这封信（信里写“这一版没有 tag”；运维没在正式账号上实测过），这时由产品负责人在冻结副本里先 `git switch --detach <线上那个 tag>`（publish.ps1 和上面这段命令都要求检出的正好是这个 tag），再用上面 2b 这段只部署 lemo-ops 的命令重新部署一次（问 tag 时填线上那个）。也可以用 `publish.ps1 -Tag <线上那个 tag> -Only functions -Ops`：它会把 Supabase 函数按同一个 tag 整批重新部署一遍，版本不变，没有害处。这条告警只抓误发和发布半途停下，挡不住有人故意改 tag 或伪造 version.json。
3. 数据库**不做回退**：架构 8.3 约定迁移只做向后兼容的变更，旧函数能直接用新表结构。不要手写删列、删表的回退 SQL。
4. 确认：设一条 2 分钟后的提醒，能准时收到；跑一次 AI 识别。

### 第 3 层：数据错了 → 按用户从 JSON 恢复
适用：程序写坏了某个人的数据。这一层会**丢掉备份时间之后的改动**，只在前两层解决不了时用。
1. **先止损**：找到写坏数据的原因，先用第 1 或第 2 层回滚代码，避免恢复后又被写坏。
2. **选备份**：服务器备份保留 7 天（`backups/<日期>/<user_id>/`）；本机每日备份保留 30 天（`E:\柠檬记-备份\每日\<日期>\<user_id>\`，以架构第 10 节为准）；版本前、发布前的永久保留。选出问题之前最近的一份。
3. **先在预览环境试**：把这份备份导入预览项目，QA 核对条数、抽查 10 条，隐私记能用同一把 VAULT_KEY 解开。
4. **告诉受影响的人**：恢复期间不要记东西；备份时间之后记的内容会丢，先截图或抄下来。
5. **正式恢复**：用恢复脚本（`tools/backup/` 下，后端在 B7a 前写好、演练过；名字以实现为准），**只针对这一个 user_id**，先 `--dry-run` 看要改多少条，再正式执行。要用 service role key，所以**由产品负责人本人在自己的 PowerShell 窗口里运行**，把条数告诉后端；例外由 AI 执行时，用完立即轮换这把密钥。备份是明文（R-209、R-210），直接用；恢复时复制出来的临时文件夹用完删掉。
6. **核对**：QA 核对条数、抽查；本人在 iPhone 上整表重拉后看一遍。
7. **图片和附件**：服务器备份不含图片和附件；图片（含纪念日头像）从本机 `E:\柠檬记-备份\图片\<user_id>\`、附件从 `E:\柠檬记-备份\附件\<user_id>\`（都是每周增量）找回（明文，R-210），上传后删掉临时副本。向量不用恢复，会自动重算。
8. 记进发布记录：恢复了谁、用的哪天的备份、丢了多长时间的改动。

### R2 不可用（照片和附件存不进、打不开；架构 0.32、12 风险 23）

> 运维 10-28 起草（B0 R2 任务单 O-6，原定 B7a 前写，提前写好）；B7a 审手册时代码审查员、安全审查员一并看，标“待实测”的在 B7 恢复演练里核实。

适用：照片、头像、附件显示占位、上传一直失败，**文字照常能记、能同步**（数据库在 Supabase，不受影响）。R2 本身没有备份，本机每周拉取是唯一副本（架构第 10 节）。

**先判断是哪一种**（按从常见到少见）：

| 现象 | 多半是 | 怎么办 |
|---|---|---|
| 所有人、所有图片都打不开，`/files` 返回 5xx；Cloudflare 后台 R2 › 存储桶的“指标”里请求在报错 | **令牌到期或被删**（R2 令牌建议 90 天到期，环境清单第四节）、令牌被误改了权限 | 下面第 1 条 |
| 同上，且 [Cloudflare 状态页](https://www.cloudflarestatus.com/) 上 R2 标着故障 | **R2 故障** | 下面第 2 条 |
| Cloudflare 后台提示账单问题、账号受限 | **账单**（卡过期、扣款失败） | 负责人本人在 管理账户 › 账单 里处理；处理好后不用改任何配置 |
| 只有某几张打不开（占位），别的正常 | 对象丢了或行和对象对不上 | 不是“R2 不可用”：按第 3 层第 7 步从本机备份找回这几个文件；先跑一遍 file-check 补扫看有多少 |
| 怀疑令牌或 `FILES_URL_SECRET` 泄露 | — | 下面第 3 条 |

1. **令牌到期或被删**（最常见）：
   1. 负责人在 R2 › API 令牌里看是哪一把（`/files` 用的“柠檬记 正式 files”、函数用的“柠檬记 正式 functions”）过期或不在了；
   2. 照[负责人 B0 网页操作清单](../00-团队/负责人B0网页操作清单.md) ⑫ C 重新生成那一把，运行 `set-r2-tokens.ps1 -Target production`（两把都要粘贴，没过期的那把粘原值即可）；
   3. Supabase 的 secrets 改了立即对函数生效；**Pages 的变量只对之后的部署生效**，所以要重新部署一次当前版本：负责人运行 `publish.ps1 -Tag <当前 tag>`（同一个 tag 再发一次，迁移和函数没有变化）；
   4. 确认：手机上打开有图片的随手记，能显示；传一张新图能成功；
   5. 记进发布记录；到期提醒改到下次到期前一周（主持人）。
2. **R2 故障**：没有可回滚的东西，**不切换**。
   1. 在聊天里告诉用户“照片和附件暂时打不开，文字照常记”；
   2. 等 Cloudflare 恢复；恢复后看一眼 file-check 有没有卡住的 pending（上传失败的附件会留在 pending，按架构 5.13 的重试和清理处理）；
   3. 超过 24 小时还没恢复，或 Cloudflare 宣布长时间故障、账号被封：负责人决定要不要走下一节“切回 Supabase 存储”。
3. **怀疑泄露**：
   1. `R2_FILES_*` / `R2_FN_*`：负责人马上在 R2 › API 令牌里**删掉那一把**（删了立即失效），再按第 1 条生成新的并写入；删和写之间这段时间 `/files` 会报错，属于预期；
   2. `FILES_URL_SECRET`：重新运行 `set-r2-tokens.ps1 -Target production`（每次都会换一个新的），重新部署后所有没过期的图片链接立即作废（最长 10 分钟的影响，App 会重新签）；
   3. 看 R2 › 存储桶 › 指标，有没有不寻常的读取量；记进事故记录；
   4. 对象被删或被改：按第 3 层第 7 步，从本机 `E:\柠檬记-备份\图片\`、`附件\` 用 `tools/backup/restore-files.ps1` 传回（临时写令牌，用完立即吊销，架构第 10 节；脚本 B7 写，**待实测**）。

### 切回 Supabase 存储（R2 长期不能用、或决定不用 R2 时）

> 这是**开发改动加一次发布**，不是点几下就能切回去的开关：架构 0.32 的方案估约 **3～5 人日**（[方案](../10-架构/方案-文件存储改用R2.md)第 8 节）。由负责人决定做不做；做的话主持人排进开发，按普通发布流程上线。下面是运维写的顺序，**各步都待实测**，B7a 审手册时请架构师核对。

**先知道的代价**：
- **Supabase 免费版文件存储只有 1 GB**（和数据库等共用告警口径，架构 0.32 第 8 条），而 R-217 定负责人上限 5 GB：切回前要么把每人上限调到装得下（`private.user_limits.media_mb`），要么升级 Supabase Pro（每月 25 美元起，以官网为准）。负责人先定这一条。
- Supabase Storage 的 S3 访问密钥**不能按桶限权**（架构第 10 节原来的“需核实”），`/files` 和服务器函数要共用一把全权限的，安全审查员要重新看。
- `If-None-Match: *` 条件写在 Supabase 的 S3 接口上支不支持**没有核实**；不支持就用架构 3.3 G 的退路（先 HEAD 再写，file-check 的 etag 兜底）。

**顺序**：
1. **暂停上传**：发一版让 `/files` 的上传返回“暂时不能上传”（具体开关由前端 B 在 B7a 审手册时补；只读照常），避免切换期间两边各有一部分新文件。
2. **建回四个桶和权限**：后端写一个**新迁移**（迁移只增不改，不改 0003、0004、0006），建 `images`、`files`、`vault-images`、`vault-files` 四个桶、大小和类型上限；客户端不直接访问存储，所以不用恢复原来的 `img_*`、`file_*` 存储策略（`/files` 照旧是唯一出入口）。
3. **复制对象**：用 R2 的只读令牌（或 R2 不可用时用本机 `E:\柠檬记-备份\图片\`、`附件\`）把四个桶的对象按原路径复制到 Supabase（`rclone copy`，S3 接口对 S3 接口；`--checksum`）。数条数、抽查 sha256；file-check 全量补扫一遍。
4. **改配置不改代码**（`shared/objstore.ts` 和 `/files` 是唯一出入口，架构 12 风险 23 的退路）：
   - Pages：`R2_ENDPOINT` 改成 `https://<正式 ref>.supabase.co/storage/v1/s3`，`R2_FILES_*` 换成 Supabase 的 S3 访问密钥（Supabase › Storage › S3 Connection 生成，**负责人本人**生成并运行 `set-r2-tokens.ps1`；脚本对格式的检查要放宽，运维那时改）；
   - Supabase secrets：`R2_ENDPOINT`、`R2_FN_*` 同样换；
   - 签名的区域改成项目所在区域（`ap-northeast-2`），由前端 B 确认 objstore 的区域可配；
   - 清单的 `store` 改回 `'supabase'`、D1 跟着改（后端）。
5. **发布**：按 `publish.ps1` 正常发一版（含第 2 步的迁移）；打开上传。
6. **核对**：传一张图、开一个附件、注销一个测试账号后四个桶里这个人的前缀为 0（预览环境先完整走一遍）。
7. **收尾**：本机每周拉取改用 Supabase 的 S3 只读访问（`pull.ps1` 改地址和凭据）；隐私说明里“照片和附件存放在境外”一项按实际改回（15.7 第 21 项）；R2 里的对象确认 Supabase 这边齐了以后再由负责人决定删不删；1 美元账单提醒留着。
8. 记进发布记录和架构（新开一个 0.x 变更记录）。

## 七、例行维护

### auth.audit_log_entries 的增长和清理

- 依据：B1 接手清单 OPS-mail-sugg ④。lemo-ops 的“发信量读不到”告警正文指到这里（本节标题不要改，改了要同步改 `workers/lemo-ops/src/rules.ts` 里的引用）。

**为什么要管**：验证码发信量告警（架构 0.38 第 12 条、15.6 第 4d 条 ①）的 auth_1h 来自这张表（迁移 `20261029230000` 的 `private.auth_mail_counts()`）。这张表有三个特点：

- **只增不减**：Supabase Auth（GoTrue）每次登录、发验证码、刷新令牌、退出都记一行，自己从不清理，Supabase 也不替我们清；
- **没有 `created_at` 索引**：表归 `supabase_auth_admin`，我们不加索引（迁移里写明了），所以按时间筛也是**扫全表**；
- **每 15 分钟扫一遍**：lemo-ops 每 15 分钟调一次 usage-report {part: heartbeat}，每次都跑一次 `auth_mail_counts()`。

表越大，这一扫越慢、越占数据库额度（免费版 500 MB 是整个库共用的）。最先出现的信号是：usage-report 读发信量超过 2 秒（`AUTH_MAIL_TIMEOUT_MS`），函数日志记 `auth_mail:timeout`，lemo-ops 发“发信量读不到”。

**什么时候清（R-274，负责人 10-30 定，依据安全说明 v4 第二节建议 1）**：**每月固定清一次**，在每月第一周和第六节那项“查一次 `auth.audit_log_entries` 的行数和大小”一起做：先查行数和大小，再跑下面现成的分批删除语句，删 **90 天前** 的行，删完再查一次。不再等到阈值才清。

**提前查看的信号**（不用等到下个月第一周，出现任一条就先按下面查一次行数和大小、看看是不是有人在刷，必要时提前清一次）：

| 指标 | 信号 | 说明 |
|---|---|---|
| 行数 | **超过 100 万行** | 按现在的人数（每人每台设备每小时一次刷新令牌约 1 行），每月清到只剩 90 天的量，远到不了；到了说明人多了或有人在刷 |
| 表大小（含 TOAST） | **超过 100 MB** | 占免费版整个库的五分之一 |
| 发信量读取超时 | **一周内出现 2 次以上 `auth_mail:timeout`**（不是数据库整体连不上的那种） | 说明扫全表已经接近 2 秒 |

**清理什么**：只删 **90 天前** 的旧行。**绝不能删最近 24 小时的**（`auth_mail_counts()` 数的是最近 1 小时 / 24 小时，删了告警就不准）；90 天也给安全排查留出时间。保留天数要改，先问安全审查员。**表里含邮箱和 IP**：保留 90 天、每月清一次，一条记录最长约 90 天加最多约 5 周（两次清理最多相隔约 37 天），也就是**最长约 4 个月**后删除，和隐私说明“保存多久”的写法一致（R-274；接手清单 OPS-mail-sugg ⑦）。哪个月漏清了，隐私说明的说法就兑现不了，下个月第一周补上，并记进过程记录。

**谁来做**：

- 运维每月第一周提醒，查行数和大小、清理，记进过程记录（删前删后的行数和大小、删了几批）。
- **正式项目由产品负责人本人执行**（正式项目的令牌只在负责人本机，R-105）：在 Supabase 面板正式项目的 SQL Editor 里粘贴下面的语句；**预览项目可以由运维执行**。
- 第一次清理前先在**预览项目**跑一遍；报 `permission denied` 就停下，不要换别的办法绕，交给架构师定。

**怎么查行数和大小**（只读，随时可以跑）：

```sql
-- 估计行数（不扫表，秒回；autovacuum / analyze 之后才准；结果是 -1 表示这张表还没 analyze 过，看下面的准确行数）
select reltuples::bigint as approx_rows
  from pg_class where oid = 'auth.audit_log_entries'::regclass;

-- 准确行数（扫全表，表大时要几秒，别在高峰跑）
select count(*) from auth.audit_log_entries;

-- 表大小（含索引和 TOAST）
select pg_size_pretty(pg_total_relation_size('auth.audit_log_entries'));

-- 90 天前的有多少（清理前估算批数）
select count(*) from auth.audit_log_entries where created_at < now() - interval '90 days';
```

**清理语句**（只写在本手册里，**不做成迁移**：表不归我们，什么时候清、清多少由人决定）：

```sql
-- 一次删一批（5 万行），返回这一批删了多少行；返回 0 时停。一批一个短事务，
-- 免得一次删太多锁太久、触发 lemo-ops 的“长事务”告警（超过 4 分钟）或拖慢登录
with d as (
  delete from auth.audit_log_entries
   where id in (
     select id from auth.audit_log_entries
      where created_at < now() - interval '90 days'
      limit 50000
   )
  returning 1
)
select count(*) from d;
```

- 每批之间隔几秒；全部删完后跑一次 `vacuum (analyze) auth.audit_log_entries;`（不锁表，让空间能被重用、估计行数变准）。这句要**单独执行**（SQL Editor 里只放这一句，不和别的语句一起选中运行：`vacuum` 不能在事务块里跑）。看到 `WARNING:  skipping "audit_log_entries" --- only table or database owner can vacuum it` 这类 skipping 的警告就算了，不用想办法绕，交给 autovacuum 自己做。**不要跑 `vacuum full`**：它锁全表，期间所有登录都会卡住。
- 删完再跑一次上面的查行数和大小，记进过程记录（删了多少行、删前删后大小）。
- 清理不影响发信量告警（只删 90 天前的）；做完后下一轮 lemo-ops 照常，不需要重启或重新部署任何东西。

> 附：Resend 那项“读不到”和“没接”（OPS-mail-sugg ②）。usage-report 读到坏的 Resend 用量时，lemo-ops 报“Resend 用量读不到”、已在报的“Resend 当天额度用了超过 70%”原样保留；**真没接时（Resend 用量一直为 null、不带标记），连已发过的“Resend 用量读不到”一起悄悄删掉、不发“已恢复”——这是有意的**：没接就不再查这一项，谈不上恢复。

## 八、出事时的手动处理

### 告警邮件发不出去（R-261，10-30）

- 依据：架构 15.6 第 4d 条 ①：告警邮件本身可能因为 Resend 额度用完或出错发不出，所以 lemo-ops 另记一笔。
- 去哪看：Cloudflare 控制台 → Workers KV → `lemo-ops-state` → 键 `mail-fail:v1`。
  - `count` > 0：上次发成功以后发失败了这么多次（每次发失败算一次，同一件事重试几轮就算几次，不等于丢了几件事）；
  - `first_at`：这一串失败里第一封的时刻；`last_at`、`last_status`：最近一次失败的时刻和 Resend 回的 HTTP 码，`null` 表示超时或网络出错、没有回应；
  - `last_ok_at`：最近一次发成功的时刻。键里不记收件人、标题、正文。
- 提示只带在之后第一封发成功的告警信末尾（中韩两句），发成功后计数清零，同一轮后面的信和以后的信都不带。
- Workers Logs（lemo-ops 已开 observability）里能搜到这几个错误码：`mail_send_failed`、`mail_fail_write_failed`、`mail_fail_read_failed`、`kv_write_failed`；日志里只有错误码，没有邮箱。
- 处理：按 `last_status` 查 Resend 后台（429 多半是额度用完，401/403 是密钥失效，按 R-220 重新生成），修好后等下一轮告警发出来，看 `count` 清零。

### 验证码发信额度被耗尽

- 依据：架构 15.6 第 4d 条 ③（0.38 第 12 条）。lemo-ops 的“验证码邮件一小时内发得太多”“Resend 当天额度用了超过 70%”两封告警正文都指到这里。
- 执行：**产品负责人**在 Supabase 后台（正式项目）操作；运维在旁边看告警、查记录、写过程记录。
- **现象**：Auth 的发信上限是**全项目共用**的每小时 30 封（`config.toml` `[auth.rate_limit] email_sent = 30`，线上同），Resend 免费版另有每天 100 封。有人拿一个已注册的邮箱反复发验证码，就能让所有人在这一小时里收不到验证码；连着干一天还会把 Resend 当天的 100 封用完（注册、注销、告警邮件也发不出）。**影响只在新登录**：已经登录的设备照常（刷新令牌不发信），不泄露数据。

**处理步骤**：

1. **确认是被刷，找出被拿来刷的账号**：在 SQL Editor 里看过去 1 小时谁请求了验证码（只看计数，结果里有邮箱，不要截图外发、不要贴进 AI 会话）：

   ```sql
   select e.payload->>'actor_username' as email, count(*) as n
     from auth.audit_log_entries e
    where e.created_at > now() - interval '1 hour'
      and e.payload->>'action' = 'user_recovery_requested'
    group by 1 order by n desc limit 10;
   ```

   一个邮箱占了大头就是被拿来刷的；分散在很多邮箱、人数又对得上，可能只是真的有很多人在登录（例如刚开放给朋友），不用往下做。
2. **先封第 1 步查出的账号**（或者和第 3 步同时做）：给这个账号设 `banned_until`，后台 Authentication → Users 里该用户的封禁操作，或在 SQL Editor 跑下面这句；**报 `permission denied` 就改用后台 Users 页面封禁**，不要换别的办法绕（上线前的预览演练会先跑一次这句，见第二节第 8 项）。被封的账号还会不会收到验证码**还没实测**（架构要求 B1 实测，结论写进过程记录）；如果封了还在发，看第 4 步。

   ```sql
   update auth.users set banned_until = now() + interval '24 hours'
    where email = '<第 1 步查出的邮箱>';
   ```

   这个账号是朋友的（被人冒用），事后告诉本人，解封时把 `banned_until` 改回 null。
3. **封了还不够，再临时调高 `email_sent`**（补充手段，不单独用）：这一小时的额度已经被刷完、正常的人还在等验证码时，Supabase 后台 Authentication → Rate Limits，把每小时发信上限临时调高。**Resend 每天 100 封是硬上限，调高只能撑当天**；事情过去后**改回 30**，并在过程记录里写明调高、改回的时间。
4. **必要时临时关 Email 登录方式几个小时**：后台 Authentication → Sign In / Providers 里关掉 Email。期间**所有人都登不了新设备**，已登录的不受影响。刷的人停了就打开，打开后自己发一次码确认能收到。

**不做的事**：**不调高默认额度**（5.6“不调高”不变：额度越高，被刷时 Resend 的每日额度越快用完）；第 3 步只是临时的，事后一定改回。

**有意接受**（架构原文）：一个肯花钱打码的人仍能让新登录停一阵，靠告警尽快发现、手动处理；人少、影响只在新登录，接受。

**事后**：过程记录写一段（几点收到告警、刷了多少封、做了第几步、几点恢复）；同一个人反复来，交给架构师看要不要加 `/sb` 对 `POST /auth/v1/otp` 的每 IP 限流（架构 15.6 第 4d 条 ②）。

### 邀请注册留下没有 profile 的账号（orphan_user、orphan_suspect，B1 10-31）

- 依据：架构 0.38 第 29 条、5.6；B1 接手清单 INVITE-late-commit、INVITE-auth-timeout、ORPHAN-alert。
- 执行：**产品负责人**在 Supabase 后台（正式项目）操作；删用户是永久删除，由负责人本人确认、本人点。
- **现象**：lemo-ops 告警“没有 profile 的账号”大于 0（ORPHAN-alert 接上之前，只能在 Edge 函数日志里看到 `orphan_user:<id 前 8 位>` 或 `orphan_suspect`）。两种都是“auth 里有用户、profiles 里没有行”：建号后补 profile 失败、删用户也失败（orphan_user）；或建号超时晚到建成、用户之后没再重试（orphan_suspect 之一）。没有 profile 的用户一律当停用，登不进来，也没有任何业务数据。

**处理步骤**：

1. Supabase 控制台 → Edge Functions → invite-signup → Logs，搜 `orphan_`，记下时刻（免费版日志保留时间短，以告警为准）。
2. SQL Editor 跑（结果里有邮箱，只在后台看，不往别处贴）：

   ```sql
   select u.id, u.email, u.created_at
     from auth.users u
     left join public.profiles p on p.user_id = u.id
    where p.user_id is null
      and u.created_at < now() - interval '10 minutes'
    order by u.created_at desc;
   ```

   创建时刻和日志时刻对得上的那一行就是（orphan_user 再对 id 前 8 位）。
3. 控制台 Authentication → Users 删掉这个用户；用 invite-admin 给这个邮箱的人重发一个新邀请码。旧码不必退（一次性码，已占的那一次作废）。

**查不到的情况**：`orphan_suspect` 也可能是这个邮箱本来就有一个正常账号（上面的 SQL 查不到它）。这时告诉对方“已经注册过，直接用邮箱验证码登录”即可，不删任何账号；这个邮箱残留的那行 pending（注册成功但删 pending 失败、又换了别的码再验证时会出现）等它过期自动清掉，或在 SQL Editor 手工删掉这一行。

**事后**：过程记录写一段（几点收到告警、哪种、做了第几步）。同一周出现两次以上，交给架构师查 Auth 接口是不是经常超时。
