## 一、现状（读代码确认过的，同第一版）

| 事情 | 现在的代码 | 对方案的影响 |
|---|---|---|
| 冲突事件 | `send.ts` 收到 `conflict` / `forked` 后，先 `outbox.ack`，再 `emit({type:'conflict', status, table, id, conflicts, old, forkId})` | 服务器**已经应用了本机的修改**。`old` 只在内存里 |

## 二、界面放在哪：方案 A，首屏 0 字节

### 2.1 结构

```
首屏（main 块）             不改
        │ 画完以后 startAfterPaint 下载
        ▼
after-paint 块：sync-wiring.ts ── wireSync() 末尾调 startSyncNotices(facade, boot)
        │  新文件 src/app/sync-notice-gate.ts（静态并进 after-paint 块，目标约 1 KB）
        │  ① 预建容器 <div data-sync-notice role="region" aria-label="同步提示">，加在 body 末尾；
        │     里面先放一个常驻的空 <div role="status" aria-live="polite">（M3）
        │  ② facade.onEvent：收 conflict / forked
        │  ③ 读 gone 项（时机见 4.1）
        │  有要显示的东西了才往下
        ▼
按需分包：features/sync-notice 的 SyncNoticeHost（卡片、对话框、文案、字段描述）
        对预建的容器 createRoot；live region 不重建，只往里写文字
```

- **首屏 0 字节**：gate 跟着 after-paint 块加载，宿主是单独分包。`first-paint-graph` 加断言：main 闭包里没有 `sync-notice-gate.ts`，也没有 `features/sync-notice/**`。
- **不碰 App.tsx、main.tsx、各列表页。**
- 容器的 `aria-label` 跟界面语言走，不写死中文：gate 不进词典，由宿主挂上以后补上；挂上之前容器是空的，没有标签也不影响读屏。
- `role="region"` 加 `aria-label`：读屏用户可以按地标跳到 gone 卡上。
- gate 只静态 import `features/sync-notice/index.ts` 里的**类型**，宿主一律用 `import()` 加载。

### 2.2 和主 App 的衔接（评审第三节第 1 点）

### 2.3 跨标签页（已定：B2 不做）

- 冲突卡只在同步主页标签页出现。主页标签页隐藏时会主动放锁（4.3b），所以可见的标签页通常就是主页。
- gone 卡各标签页都会出现（从 outbox 读）。
- 跨标签页广播登记为接手清单 K8-tab-broadcast（B3）。

## 三、交互、视觉和文案

### 3.1 提示卡

- **样式**：照视觉稿的 dock toast，两行字：`t1` 标题、`t2` 说明，按钮在右下。
  - 只共用 UndoToast 的颜色、圆角、磨砂令牌，布局另写（L2）：标题可换行；窄屏（≤ 360 px）时按钮换到第二行、右对齐；按钮点击区 44 px。
  - 标题里只截断 `{title}`，最多 12 个字加“…”。“已在另一台设备上删除”这半句不截。
- **位置和叠放（主持人已定；复审一 R1 改正）**：
  - 从下到上依次是：底栏、撤销条、提示卡。
  - **两个变量由前端 B 在 `src/styles/base.css` 的 `:root` 定义**（主持人定的分工），就是把现在的位置原样提出来：
    ```css
    --dock-bottom: max(calc(env(safe-area-inset-bottom) + 118px), var(--kb, 0px)); /* 现有浮条位置，含键盘避让 */
    --undo-h: 56px; /* 撤销条高度：44px 按钮 + 上下各 6px 内边距，和 UndoToast 现在一样 */
    ```
    - 宽屏（≥ 900px，FA-7 切侧栏、底部没有底栏）那一档：由前端 B 在切侧栏的**同一个媒体查询**里覆盖 `--dock-bottom`，提示卡、撤销条、提醒按钮条跟着一起走。
    - **不拿 `--tabbar-h` 推算浮条位置**：它是全局渐进模糊带的高度（126px），定义在 `:root` 上，没有底栏的页面也不是 0。第二版那个公式作废。
  - **K8 实现时，6 处浮条一起改用 `var(--dock-bottom)`**，值不变、现有视觉不变：
    1. kit `UndoToast.module.css`；
    2. `Remind.module.css` 里的提醒按钮条两处；
    3. 今天页；
    4. 待办页；
    5. 最近删除页。

    `--undo-h` 加一条组件测试，锁住它等于 UndoToast 的实际高度。
  - 提示卡平时在 `bottom: var(--dock-bottom)`。撤销条开着时，提示卡往上让一条：给 kit `UndoToast` 根元素加属性 `data-undo-toast`（主持人已批），宿主样式写成：
    ```css
    [data-sync-notice] { bottom: var(--dock-bottom); }
    body:has([data-undo-toast]) [data-sync-notice] { bottom: calc(var(--dock-bottom) + var(--undo-h) + 8px); }
    ```
    `:has()` 要 iOS 15.4 以上，和同步选主要求的 Web Locks 起步版本一致。
  - 文件分工：base.css 的两个变量和宽屏覆盖归前端 B；6 处浮条改用变量、`data-undo-toast`、提示卡样式归前端 A（K8 实现时做）。前端 B 的变量先合入，前端 A 再改 6 处。
- **主 App 弹层打开时（M4）**：
  - 用一条 CSS 隐藏提示卡，不加 JS：`:root.scroll-locked [data-sync-notice] { visibility: hidden }`。kit `Dialog` 打开时已经会在 `<html>` 上加 `scroll-locked`。
  - 计时那边用一个 MutationObserver 看 `<html>` 的 class 是否含 `scroll-locked`，有就暂停。不动 Dialog 的 lockCount。
  - 提示卡自己打开的对话框也会加 `scroll-locked`：宿主自己开对话框时先记一个标记，这时不隐藏卡，也不算“别的弹层”。
- **路由（L4）**：
  - 告知页（ConsentPage）、整页提醒（`#/remind`）不显示提示卡，卡先排队。
  - 编辑页照常显示，正在改的就是这一条记录时也显示，这正是用户最需要知道的时候。
- **排队**：
  - 一次只显示一张。冲突卡排在 gone 卡前面；gone 卡不会自动收起，始终排在最后。
  - 有排队时，在说明下面另起一行写“还有 {n} 条”（K-15）。这一行只在数量变化时更新，不会反复播报。
- **合并**：
  - 冲突按 `table:id` 合并：`conflicts` 取并集，`old` 逐列以最新的为准（L1）。
  - gone 按 `table:id` 合并（H1，见 4.1）。
- **计时（M3、M4）**：
  - 冲突卡 8 秒后自动收起（同 `UNDO_TOAST_MS`）。
  - 只在以下条件**都满足**时才计时：`document.visibilityState === 'visible'`、卡确实在显示（不是排队中、没有被路由或弹层藏起来）、指针不在卡上、焦点不在卡里。
  - gone 卡不自动收起。
- **读屏（M3）**：
  - 预建的 live region 由 gate 在 after-paint 时就放进页面。宿主挂上后，**等下一帧**再往里写“标题 + 说明”，保证第一次也会播报。
  - 卡片本身不抢焦点。“看另一台设备的版本”用 kit `Dialog`，焦点进出由它负责。

### 3.3 “看另一台设备的版本”（不加“用另一台设备的版本”，负责人已定）

- **conflict**：用 kit `Dialog`，逐行列出 `conflicts` 里每一列，格式是“字段名：另一台设备上的值”（值取自合并后的 `old`）。
- **字段描述（H3）**：集中放在 `src/features/sync-notice/data/fields.ts`。
  - 按表列出“列 → 字段名词条 + 格式”。格式：日期；时刻（日程按这一行的 `tz` 列，A15）；提醒选项；长文本截两行加“…”；对象、数组按字段描述格式化（L8）。

## 四、数据流和失败处理

### 4.1 收集

- **出卡表白名单（H2）**：
  - `NOTICE_TABLES = ['events', 'todos', 'anniversaries', 'categories', 'notes']`，写成常量并配单测。
  - 名单外的表（`settings`、`devices`、`note_images`、`note_files`）：
    - conflict 不出卡，现有的 `sync_conflict` 日志照旧；
    - gone 静默丢弃：调 `write.resolveGone(table, id, 'drop')`，记日志 `sync_gone_drop`（只记 coll，不记 id、内容）。devices 由 device-reg 自己处理；settings 以服务器为准。
- **conflict**：`facade.onEvent` 收到后放进内存队列，按 `table:id` 合并（L1）。重启后就没了：修改已经保存，这只是提示。
- **gone**：
  - 读法：`outbox.list()` 筛出 `state === 'failed' && error === 'gone'` 的项，**按 `table:id` 分组成一张卡**（H1）。卡上记下这一组的 op_id 集合，只用于显示；真正动手时以 core 在事务里重新读到的为准（4.3）。
  - 读的时机（L6）：
    - gate 启动时；
    - `outbox.subscribe` 通知时；
    - 收到 gone 事件时；
    - 页面回到前台（`visibilitychange` 变成 visible）时。
    - 只靠计数变化可能漏一次通知，但点按时 core 会复查，最多是显示晚一点，不会做错。
  - 一组项读出来以后先合并 data（按 seq 从小到大，后面的覆盖前面的；gate 只用合并结果判 undone 和取标题，不受 mergePatch 的提醒例外影响）。合并后 `undone === true` 的（M1：用户自己的修改就是撤销，两边都要这条消失），不出卡，直接 `resolveGone(..., 'drop')`。
- **按钮怎么对应**：恢复是 `write.resolveGone(table, id, 'restore')`，“不用了”是 `write.resolveGone(table, id, 'drop')`。功能层不再直接调 `outbox.discard`（M2，架构 4.1）。

### 4.2 卡上按钮的结果

| `resolveGone` 返回 | 卡上怎么办 |
|---|---|
| `{ ok: true, done: 'restored', opId }` | 收起，记下 opId（4.4）。这一行回到列表（新入队的 patch 进了 view） |
| `{ ok: true, done: 'dropped' }` | 收起。这一行留在“最近删除” |
| `{ ok: true, done: 'nothing' }`（已经没有 gone 项：别的标签页处理掉了、行被硬删了） | 收起，不提示 |
| `{ ok: false, reason: 'local_unavailable' \| 'closing' }` | 卡留着，说明换成“没能恢复，请稍后再试。”，两个按钮都在，可以再点 |
| `{ ok: false, reason: 'switching' }` | 不提示。页面随即重载，卡不会带到新账号 |
| 恢复 patch 已入队、卡已收起，之后服务器回 `not_found`（这一行在恢复前已被彻底删除：硬删、30 天清理；复审三 P2） | core 照旧把这一项当 drop 丢掉、整表重拉（send.ts、outbox-send.ts 现有逻辑），并发 outbox 事件 `{ type: 'rejected', item, code: 'not_found' }`。gate 订阅 `outbox.onEvent`，见 4.4 第 3 点：是“刚恢复”的那条记录就在底部出一句轻提示“这条已彻底删除，无法恢复。”，几秒后自动消失，经常驻 live region 播报；不出卡、不留在队列里 |
| `{ ok: false, reason: 'rejected', code }`（严格校验拒收，比如 `readonly_row`、`invalid_row`，M8；以及 core 拒绝恢复撤销项的 `undone`，正常不会走到，gate 先 drop 了） | 说明换成“这台设备上没法恢复这一条。”，只留“不用了”。记 `sync_gone_restore_fail`（coll、code） |

### 4.3 core 新入口 `write.resolveGone`（M2、M7；需要另过代码审查）

这是 core 改动，由前端 A 做，单独送代码审查。下面的签名是**实际落点**（代码审查 L1 改：原稿写的 write.ts 加入口、Outbox 接口加方法会进首屏，已作废，不要照原稿加回去）。

> **实现时的落点（首屏余量只剩 0.3 KB，实测后定）**：入口不放进 `write.ts`，也不给 `Outbox` 接口加方法——这两个都在首屏块里，
> 方法包装或首屏里的 `import()` 实测 +72～100 B gzip。实际是：
> - 入口 `src/core/write-gone.ts` 的 `resolveGone(table, id, mode)`，属于 write.* 一族，只有 sync-notice 按需加载时用；
> - 实现 `src/core/outbox-gone.ts` 的 `resolveGoneImpl(ctx, …)`；
> - ctx 经 `outbox.ts` 导出的 `outboxCtx`（WeakMap，createOutbox 登记）取。
> 首屏实测 127018 B，对照 127020 B，没有增加。first-paint-graph 守着这三个文件不进首屏静态闭包。
> 返回值、拒收码、事务规则同下文；`outbox.resolveGone` 的写法读作 `resolveGoneImpl(outboxCtx.get(outbox), …)`。

```ts
// src/core/write-gone.ts（入口，write.* 一族；不在首屏，只有 sync-notice 按需加载时用）
export type ResolveGoneResult =
  | { ok: true; done: 'restored' | 'dropped' | 'nothing'; opId: string | null }   // opId：恢复项的 op_id，只有 restored 有
  | { ok: false; reason: WriteFailReason | 'rejected'; code?: string };
export async function resolveGone(table: string, id: string, mode: 'restore' | 'drop'): Promise<ResolveGoneResult>;

// src/core/outbox-gone.ts（实现；只准 write-gone.ts 引，tests/build/k8-gone-imports.test.ts 守着）
export async function resolveGoneImpl(ctx: Ctx, table: string, id: string, mode: 'restore' | 'drop',
  opts?: ResolveGoneOptions /* { remindOf?(merged, patch): boolean } */): Promise<ResolveGoneReport /* { done, opId } */>;

// src/core/outbox.ts：ctx 从这里取，同样只准 write-gone.ts 引
export const outboxCtx: WeakMap<Outbox, Ctx>;
```

**先做一步重构（复审一 R2 ①）**：把 `enqueueImpl` 里“建新项”那一段提成 outbox.ts 内部函数，`enqueue` 和 `resolveGone` 共用，不手写第二份：

```ts
/** 建一项新的 outbox 项（enqueueImpl、resolveGoneImpl 共用）：op_id、base_rev、own_revs、client_ts、v、app、seq、remind、deps 的规则只在这里 */
function newItem(ctx: Ctx, input: EnqueueInput, row: CachedRow | undefined, mine: readonly OutboxItem[], all: readonly OutboxItem[]): OutboxItem;
```

- 规则照现在的 `enqueueImpl` 原样搬过去：
  - 前面有没确认的 insert（`afterInsert`）时，`base_rev` 为 null、`own_revs` 为空；
  - 否则 `base_rev` 取本机 `server.rev`，`own_revs` 拷 `row.own_revs`；
  - `client_ts` 取 `ctx.now()`；`v`、`app` 取当前值；`seq` 取全队列最大值加 1；`deps` 照传。
- 重构单独一个提交：enqueue 的现有单测全部不改、照样通过，作为不改行为的证据。

实现步骤（restore）：

1. **事务外先读、先校验**（同 `enqueueImpl`：严格校验的代码按需加载，不能放进 IDB 事务里等）：
   - 读这条记录的项，分出两组：
     - gone 组：`state === 'failed' && error === 'gone'`；
     - **跟随组（复审一 R2 ②）**：seq 在 gone 组之后、还没发出（`state === 'pending'` 且没有 `sent`）的 patch。比如编辑页开着时用户又存了一次。不并进来的话，恢复项排在它后面（gone 项排在这条记录最前时 sendOrder 会把整条挡住，跟随组本来就发不出去；代码审查 L4 更正：原稿写的“它会先发出去、又回 gone”与代码不符）。
     - 已发出的、在途的（`sent` 或 `inflight`）不动，回来照样走 gone 流程，最多再出一张卡。
   - 两组按 seq 逐项用 `rows.mergePatch` 合并 data，得到 `merged`（代码审查 M1：和普通入队同一套规则，前一项换了提醒、后一项是旧提醒的“知道了”时不把旧 notified_for 并进来，R4-L1）。严格校验的代码（loadRowSchemas）因此在合并之前加载。
   - 恢复项的 `deps` 取两组各项 deps 的并集，去掉这条记录自己、去重（代码审查 M2：不带的话带提醒整条提前发时可能排到它依赖的 insert 前面）。
   - **core 自己拒绝恢复撤销项（复审一 R2 ④）**：`merged.undone === true` 时，restore 不入队，返回 `{ ok: false, reason: 'rejected', code: 'undone' }`。gate 照旧在出卡前就走 drop（4.1），这一层是给别的调用方兜底，免得复活两边都要删的记录。
   - `patch = { ...merged, deleted_at: null }`；服务器行（`row.server`）的 `undone === true` 时再加 `undone: false`（M1）。
   - `validateWrite(patch)`，不通过就抛 `OutboxRejectError`，由 write 转成 `rejected`。
   - `remind = opts.remindOf?.(本机 view 和 patch 合起来的行)`。`remindOf` 由 write 层用 shared 的 `remindAtOf` 现算，传这一行的 `tz`（A15），非空即为 true（M7，和各编辑页同一个写法）。
2. **写事务**（`[table, OUTBOX]`，readwrite）：
   - 重新读这条记录的 gone 组和跟随组。op_id 集合和第 1 步不一样（别的标签页处理过、又来了新的 gone、跟随组被发出去了）时，**抛内部哨兵错误 `GoneChanged`，让整个事务回滚**（复审一 R2 ③）。不能读到不一致就 `return`：那时事务可能已经写了一部分。
   - 一项都没有了：同样抛 `GoneChanged`，交给事务外判断。
   - 再判一次 `row.ro`，是只读就抛 `OutboxRejectError('readonly_row')`。
   - 用 `newItem(...)` 建恢复项（data = `patch`，`remind` 用第 1 步算出的），`put` 进队列。
   - 删掉 gone 组和跟随组的全部项。
   - `rewriteRow` 重算 view。
3. **事务外处理 `GoneChanged`**：捕获后回到第 1 步**重读一次**（重新合并、重新校验）再走第 2 步；第二次还是 `GoneChanged`，返回 `{ ok: true, done: 'nothing' }`（卡收起，界面按 outbox 现状重新出卡）。
4. 事务提交后：`notify(table)`、`ctx.refresh()`。
5. **drop**：
   - 只删 gone 组，跟随组不动：跟随组是用户之后的新修改，“不用了”只放弃 gone 的那部分。跟随组发出去回 gone，再出一张卡；
   - 不需要校验；
   - 事务内同样按 op_id 集合比对，不一致就抛 `GoneChanged`、重读一次。

恢复以后的事件（复审三 P2）：不新增 core 事件。恢复 patch 发出去以后回 `not_found` 时，`failImpl` 已经按 drop 处理并发 `{ type: 'rejected', item, code: 'not_found' }`（outbox-send.ts），`item` 就是恢复项（`data.deleted_at === null`）。gate 直接订阅 `boot.outbox.onEvent` 接住它（4.4）。

失败语义：
- 事务要么全成要么全不成，所以不会出现“入队了但 gone 项还在”，也不会出现“gone 项删了但没入队”。第一版里“discard 失败后下次启动再出卡”的兜底不需要了（M2 ①）。
- 两个标签页一个点“恢复”、一个点“不用了”：只有先提交的那个生效。后提交的事务里读到的集合变了，抛 `GoneChanged`；重读后已经没有 gone 项，返回 `nothing`，收起卡（M2 ②）。
- `outbox_suspended` 和库关闭照 write.patch 的映射：分别返回 `switching`、`closing`。

单测（core，另过代码审查）：
- 重构：enqueue 现有单测不改、全部通过；`newItem` 在“前面有没确认的 insert”时 `base_rev` 为 null、`own_revs` 为空（R2 ①）；
- 同一条记录两个 gone 项，合并后一次入队、两项都删（H1）；
- gone 之后还有一个没发出的 patch：并进恢复项、一起删；已发出的不动（R2 ②）；
- 事务里集合变了：抛 `GoneChanged`、事务回滚（队列和 view 都没变）、重读一次后成功；连续两次变了返回 `nothing`（R2 ③）；
- 合并后 `undone === true`：restore 返回 `rejected` / `undone`，队列不变（R2 ④）；
- 两个“标签页”并发，一个 restore、一个 drop，只有一个生效（M2）；
- 只读行拒收；
- 带提醒的行，`remind` 为 true（M7）；
- drop 不动跟随组；
- 挂起、关库时的返回值；
- 代码审查补的：gone 组换提醒、跟随组“知道了”时 notified_for 仍是 null（M1）；恢复项 deps 取并集（M2）；pending 但 sent 的跟随项不并进来（S3）；readonly_row 的映射（S4）；
- 服务器口径（S1，src/core/sync/__tests__/send-gone-restore.test.ts）：补拉前恢复回 conflict 含 deleted_at、随手记恢复同时 forked、恢复后 not_found 的 rejected 事件，三条的 opId / item.op_id 都等于恢复项。

### 4.4 恢复后紧接着的冲突（M6）

- 恢复时如果补拉还没完成，本机的 `server.rev` 还是删除前的值，恢复 patch 会回 `conflict`，冲突列是 `deleted_at`。
- **“刚恢复”怎么认（复审四 L1，主持人已采纳）**：按恢复项的 op_id 认，不按时间窗口。`resolveGone` 返回 `{ ok: true, done: 'restored', opId }`，gate 记下这个 opId，直到这一项被确认或丢弃。冲突事件 `conflict` / `forked` 为此带上 `opId`（core/sync/send.ts、types.ts 加一个字段）；`rejected` 事件本来就带 `item`。清理：gate 每次读队列时，记下的 opId 已不在队列里，且连续两次读都不在才移除（确认后的事件在 ack 之后才发，读队列那一次可能先到）。这样离线很久之后再发也照样认得出（离线超过 5 分钟的用例钉住）。
- 处理：恢复项回 conflict 时，先从 `conflicts` 里去掉 `deleted_at`、`undone`：剩下为空就不出卡；剩下还有别的列，照常出卡（那是真冲突）。服务器这时照样已经把行恢复了（后端核查确认），所以不能把 `deleted_at` 当冲突弹卡。
- **随手记恢复时同时 forked（复审三 P1，主持人已定）**：随手记的恢复 patch 带着 title、body，服务器发现这两列也冲突时，会恢复原行并另存一条冲突副本（副本里是这台设备的标题和正文）。这时**不再弹“两台设备都改了内容”那张卡**：用户刚点过“恢复”，再弹一张卡只会让人困惑。冲突副本照常保留，随手记列表照常显示它。做法：恢复项（按 opId 认）收到 `forked` 事件，直接丢掉，不出卡（日志照旧记 `sync_conflict`）。
- **恢复时服务器回 not_found（复审三 P2，负责人已定）**：gate 订阅 `boot.outbox.onEvent`，收到 `{ type: 'rejected', code: 'not_found' }`、且 `item.op_id` 是记下的恢复项时，在底部出一句轻提示“这条已彻底删除，无法恢复。”，几秒后（同 `UNDO_TOAST_MS`）自动消失。不出卡，没有按钮，经预建的常驻 live region 播报。这个提示属于宿主分包，不进首屏；收到事件时宿主还没加载就先加载。不是恢复项的 not_found 照旧静默（同步引擎整表重拉）。

## 十、界面批的实际落点和偏差（前端 A，11-05）

- 文件：gate 是 `src/app/sync-notice-gate.ts`；队列、合并、刚恢复的认法拆到了 `src/app/sync-notice-store.ts`，gate 只管容器、订阅和挂宿主。宿主和文案在 `src/features/sync-notice/`，类型放在 `hooks/notice-types.ts`（ui 不能引 data，类型要让 ui 和 app 都能引）。
- 白名单：`index.ts` 里有一份 `NOTICE_TABLES` 字面量（A27：index 只准导出 lazy、字面量、类型），由 `notice-tables.test.ts` 钉住和 `data/notice-tables.ts` 一致。
- 暂停计时：告知页和别的弹层的判断用 250 ms 一拍的轮询（看 `html.scroll-locked`、`main[data-feature="onboarding"]`、页面是否可见），没有用 MutationObserver。
- 标题：纪念日取 `name`，分类也取 `name`，其余取 `title`。
- 订阅回调一律兜底：gate 挂在 `outbox.subscribe` 上，而这个回调在 enqueue 的 refresh 里是同步调的；提示出错只记 js_error，不能冒到写入链路里。
- 卸载时机改了（代码审查 K8 界面批 M1）：只在换账号时卸，也就是 `boot.switching` 设上的时候；被移除、停用、冷静期的退出都会先设它。不跟同步引擎的 stopped 走，因为主页标签页一隐藏就放锁，引擎就是 stopped，跟着卸的话回到前台也不再出卡。原来 2.x 里写的“同步停了就卸”作废。
- “已处理”的认法改了（M2）：按那一批 gone 项的 op_id 认，不再按整条记录认。同一条记录换了一批 gone，照常出卡；resolveGone 回 nothing 时不算处理过，重读一次。
- 换卡时清掉悬停、焦点（M3）；冲突列全是隐藏列时，不给“看另一台设备的版本”按钮。
- 轻提示（P2）拆成两个副作用：只认一次“计数变大”，播报和计时挂在单独的状态上。这样 t 换身份、StrictMode 重跑时不会丢掉计时。
- 浮条位置：kit 的 UndoToast 加了 `data-undo-toast`。它和 5 处页面浮条一起改用 `bottom: var(--dock-bottom)`。提示卡在 `body:has([data-undo-toast])` 时往上让出 `--undo-h + 8px`；e2e 实测撤销条高 56px，和 `--undo-h` 一致。
- 首屏：K8 只给首屏加了 31 B（gzip，就是 UndoToast 那个属性）；gate 和 store 跟 sync-wiring 块一起下载，宿主单独分包。
- e2e（`tests/e2e/b2-sync-notice.spec.ts`）：e2e 环境没有能用的同步后端，所以直接写本机库造出“gone 之后”的状态，覆盖恢复、不用了、叠在撤销条上面、别的对话框打开时隐藏四种情况。冲突卡要同步引擎发事件，e2e 造不出来，只在单测里测。
- 已知局限（代码审查 L1）：“刚恢复”那一项只记在内存里。恢复后、发出去之前刷新页面，再回来的 deleted_at 冲突还会出一张卡；按“这一页内”设计，可以接受。
- 顺手改的：store 逐个通知、各自兜底（L2）；容器只在有卡或轻提示时才有 aria-label（L3）；卡片按 key 换节点（R2-L1）；首屏图测试和 store 测试拆到 300 行以内。
- 遗留：两个日志 act（`sync_gone_drop`、`sync_gone_restore_fail`）要后端登记进数据字典 4.6。
