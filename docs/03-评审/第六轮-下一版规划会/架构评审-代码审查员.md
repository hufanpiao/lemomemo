## 0. 给产品负责人的一段话

**结论：修改后通过。** 整体方向没有问题：Supabase 加 Cloudflare、每人只能看自己的数据、库表一次建好再分三期交付、AI 能换服务商、离线先记后传，这些都和你拍板的决定一致。照这份文档能开工的部分约占七成。

不过有 **10 条“高”级问题**，开工前要先改进文档，其中最要紧的几条是：

1. **完全没写中韩双语界面（R-48）。** 现有代码里约 49 个文件、200 多处中文是写死的，要先定下“文字放在哪、怎么切换”，否则每写一个新界面都要返工。
2. **时间可能差 9 小时。** 提醒规则要同时在手机和服务器上运行，但现有的日期函数默认按“这台机器所在的时区”计算，而服务器用的是世界标准时间（UTC）。服务器替 Claude 代记、滚动纪念日提醒时，算出来的时刻会差 9 小时。
3. **几处权限写法看着对，实际不生效。** 例如“只允许改昵称和时区”这条，按文档的写法，任何登录用户都能把自己改成“管理员”，然后去发邀请码；另外有一处清理任务可能误删别人的图片。现在只有你一个人用，影响不大，但这正是第十一节定下的底线（行级权限），必须在开放给朋友之前改好。
4. **离线和多设备同步有几个没想透的地方。** 比如撤销刚记下的内容以后，另一台设备上可能一直留着这条；服务器发完推送，你在手机上改日程就会误报“已在另一台设备上改过”；电脑 exe 先弹了提醒，手机就收不到推送。
5. **两个关键数字核实了**（见第 4 节）：Gemini 免费版官方已经不公布次数，开发者实测 Flash 约每天 20 次（**不够用**），Flash-Lite 约每天 500 次（够你和十来个朋友用）；免费版的内容**会被谷歌用来改进产品，还可能有人工审阅**。Supabase 自带的发件**每小时只能发 2 封，而且只能发给项目团队成员**，也就是说朋友根本收不到验证码，不只是“慢”。

需要你决定的事项放在第 8 节，每条都附了我的推荐。

## 2. 问题清单

### 高（开工前必须改文档）

**H1　中韩双语界面（R-48）整体缺失**
- 位置：全文；2.1 分层、2.2 目录树、3.2 settings 和 profiles、5.3 推送文案、5.6 验证码邮件、8.1 构建、9 测试。
- 问题：
  - 没有定文字放在哪、谁负责翻译、怎么切换。现有代码里有 49 个 JS 文件含中文，字符串字面量约 215 处，而且散落在各层：`core/date.js` 的 `WK = ["周日",…]` 和 `md()` 生成的“10月23日”、`logic/remind.js` 的 `options()` 和 `label()`（“不提醒”“前一天 20:00”）、`logic/format.js`、`ui/*`，还有 `index.html` 里写死的文字。
  - 服务器上也有文案：推送“15:00 NEOX 会议”“明天是妈妈生日（60 岁）”、函数的错误提示、验证码邮件。服务器得知道每个用户用哪种语言，但 settings 和 profiles 里都没有“界面语言”这个字段。
  - 汉字的字形会跟着 `<html lang>` 变：中文和韩文里同一个汉字的写法略有不同，韩文界面里的汉字要按 `lang="ko"` 来渲染。
- 后果：4.0 新增的二十多个界面会接着写死中文，等到做韩文时要全部返工；而“共享给服务器的 logic”里也夹着中文，服务器推送也就没法出韩文版。
- 改法（建议新增一节“2.4 多语言”）：
  1. 新增 `core/i18n.js`，提供 `t(key, params, locale)` 和 `fmtDate(ms, tz, locale, style)`（内部用 `Intl.DateTimeFormat`，A1 不禁用 `Intl`）；词典放在 `src/i18n/zh-CN.js`、`src/i18n/ko-KR.js`，是纯数据，放在 core 层，这样 logic 和服务器都能用。
  2. logic 层不再返回成句的文案，改成返回 `{key, params}`，或者由调用方把 locale 传进来。`remind.options/label`、`format.*`、`date.WK/md` 都要改。
  3. 字段：settings 增加 `ui_locale`（`zh-CN` / `ko-KR`）。登录前没有 settings，由 `platform/prefs` 记一个本机值，默认按 `navigator.language`。push-dispatch 按 `ui_locale` 生成推送文案。界面语言和语音识别语言要分成两个设置。
  4. 验证码邮件：Supabase 的邮件模板支持 Go 模板语法，可以用 `{{ if eq .Data.locale "ko" }}…{{ end }}`。注册时把 locale 写进 user_metadata（invite-signup 调 createUser 时传 `user_metadata.locale`）。（模板语法见 Supabase 文档，具体用法上线前要实测。）
  5. `<html lang>` 跟着界面语言切换；字体栈按 `:lang(ko)` 和 `:lang(zh)` 分开；韩文一般比中文长 20–40%，按钮和提示条不能写死宽度。
  6. manifest.webmanifest 只能有一个名字，建议用不分语言的名字或中韩并列。节假日、节气、生肖的名称在数据表里存两种语言。
  7. check_arch 新增 **A20**：`ui/`、`logic/`、`data/`、`platform/` 的字符串字面量里出现汉字或谚文就报错（词典文件和测试除外）。注意现在的 check_arch 会先清空字符串内容再检查，A20 要单独扫原文。再加一个单元测试：zh 和 ko 两本词典的键必须完全一致，占位符也要一致。
  8. 工作量：把现有字符串抽进词典约 1.5–2 人日，加上韩文审校（R-48 已经注明需要审校）。要在第 12 节风险 8 里补进去。

**H2　共享给服务器的 logic 会按 UTC 计算时间，偏差 9 小时**
- 位置：8.1 `--target fn`、2.1“这几个 logic 文件也会打包给服务器函数用”、5.3 第 5 步、5.7 第 3 步、11“remind（加时区参数）”。
- 问题：`core/date.js` 的 `msAt`、`todayOf`、`minOfDay`、`hourOf`、`parse`、`addDays` 全都用 `new Date(y, m-1, d, …)` 和 `getHours()`，也就是按**运行环境的本地时区**来算。浏览器里没问题；但 Supabase Edge Functions（Deno）跑在 UTC。`logic/remind.computeRemindAt` 直接用 `msAt`，所以：
  - claude-intake 在服务器上替你记“明天 15:00 开会”，提醒会落在首尔时间 24:00 左右（差 9 小时）；
  - push-dispatch 第 5 步滚动纪念日的下一次提醒、anniv-roll 兜底重算，都会差 9 小时；
  - 服务器上算“今天”（例如日期校验时用的“今天前 1 年到后 5 年”）在 0:00–9:00 之间会算成前一天。
- 后果：推送的时刻全部错位，而且本机单元测试发现不了，因为开发机本来就在首尔时区。
- 改法：
  1. `core/tz.js` 不能只是“新增一个工具”，而是要**把 date.js 里和时刻有关的函数全部改成必须传 tz**：`msAt(dateStr, min, tz)`、`todayOf(ms, tz)`、`minOfDay(ms, tz)`。不涉及时刻的纯日期运算（`addDays`、`dayDiff`）改成按 UTC 算（`Date.UTC`），彻底不受运行环境影响。
  2. 规则 A15 加一条：共享文件里不能调用不带 tz 的时刻函数。
  3. 测试：`tests/run-all.mjs` 里所有 logic 测试分别在 `TZ=UTC`、`TZ=Asia/Seoul`、`TZ=America/Los_Angeles` 下各跑一遍（Node 可以用环境变量 `TZ` 控制），结果必须一样。这一条能一次性把漏掉的地方全找出来。

**H3　时区规则没有定义完整**
- 位置：3.2 events.tz、profiles.current_tz；5.4；13.8；纪要 13.14。
- 问题：
  1. **哪些是“固定时刻”、哪些“跟着人走”没有定。** 有时间的日程（“首尔 15:00 开会”）应该锁定在记录时的时区；全天日程、待办截止日的“当天 9:00 提醒”、纪念日的“9:00 推送”，按常理应该是**当地的 9:00**（人在上海就是上海的 9:00）。现在 remind_at 在保存时就算成绝对毫秒，换时区以后不会重算。结果是人到了上海，待办的提醒在 8:00 响，生日推送也在 8:00。
  2. 只有 events 有 `tz` 列，todos 和 anniversaries 没有。
  3. `profiles.current_tz` 由“客户端每次启动时上报”。家里的电脑在首尔、手机在上海，两边会来回覆盖，纪念日的提醒时刻也跟着来回跳。
  4. 免打扰时段按哪个时区判断，没写。
  5. 月历和“今天”页里，跨日的日程归到哪一天（首尔 00:30 等于上海前一天 23:30），没写。13.8 只说了在时间旁边加注。
- 后果：开发者只能自己猜，提醒时刻会不一致；这正是纪要 13.14 强调的“提醒时间不能错”。
- 改法：在第 4 节或单独一节写清楚“时区规则表”：
  - 有时间的日程：固定时刻，用 `tz` 列；显示时换算成设备所在时区，并加注原时区。
  - 全天日程、待办、纪念日：浮动时刻，以 `profiles.home_tz` 为准（不是 current_tz），三张表都加 `tz` 列，值可以为空，为空就表示浮动。
  - `home_tz` 的更新规则：只由“当前在前台、最近一次有用户操作的那台设备”上报，并且和上次的值不同、持续 30 分钟以上才更新；更新后由服务器函数（或客户端在下次启动时）批量重算浮动条目里未来的 remind_at。
  - 免打扰按 `home_tz` 判断。
  - `tz_mode = fixed` 时，`home_tz` 固定为首尔。
  - 真机验收 ⑬ 要分别测“固定日程”和“浮动待办”两种情况。

**H4　`notified_for` 一个字段承担了三种意思，会漏推送**
- 位置：5.3 第 2 步、5.3 末尾“桌面 exe 共用 notified_for”、4.4。
- 问题：
  - v3 里 `notifiedFor` 的意思是“用户点了知道了”（`write.ackReminder`），`logic/remind.due()` 看到它就不再弹提醒卡片。v4 里服务器**发推送之前**就写 notified_for，于是：
  - (a) 只要服务器一推送，其他设备 App 里的提醒卡片就不弹了，哪怕用户根本没看到推送；
  - (b) 4.2 的 exe 收不到 Web Push，靠本地每分钟检查。按“共用 notified_for”的设计，**exe 先弹了提醒、写了 notified_for，服务器就会跳过这一条，iPhone 收不到推送**。人不在电脑前时，这条提醒就漏了；
  - (c) 服务器每写一次 notified_for，rev 就加 1，这会触发 H9 的误报冲突。
- 改法：拆成两个字段。
  - `pushed_for`：只由服务器写，只用来给推送去重，**不加 rev**（见 H9）。
  - `notified_for`：保持 v3 的意思，表示用户已确认。
  - exe 和前台页面只按 notified_for 弹卡片，不写 pushed_for。
  - 服务器照常给所有设备推送；exe 弹出提醒后，用户点“知道了”就写 notified_for。iOS 不允许收到推送却不显示（见 L5），所以没法在手机端把“已经在电脑上确认过的”提醒静默掉。结论是**接受两端都会弹**，这比漏推送好（第 8 节第 9 条）。

**H5　RLS 的“只允许改某几列”和“读不到某列”写法不生效**
- 位置：3.3 D（api_tokens）、E（profiles）、B 的 `revoke select (body_enc)`、4.3 `select *`。
- 问题：
  1. **RLS 只能管“哪些行”，管不了“哪些列”。** E 写的“profiles 只允许改 display_name、tz_mode、current_tz”，用策略做不到。按现在的写法，用户可以 `update profiles set is_owner = true, disabled_at = null`，然后调 invite-admin 生成邀请码，**普通朋友就提权成了管理员**；被停用的账号也能自己解封。D 的“api_tokens 只允许改 revoked_at”也是同样的问题，用户可以给自己的钥匙加 scopes。
  2. 另外，表格 3.2 的 profiles 里根本没有 `is_owner` 这一列，5.6 却用到了它。
  3. `revoke select (body_enc) on notes from authenticated` 在 Supabase 默认配置下**不起作用**：默认给 authenticated 授的是整张表的 SELECT 权限，单独收回某一列没有效果。如果改成正确的写法（先收回整张表，再按列授权），那么 4.3 增量拉取用的 `select *` 和 supabase-js 默认的 `select()` 都会报“没有列权限”，Realtime 订阅也要求“列出的列必须是订阅角色可读的”（见 Supabase Postgres Changes 文档）。
- 后果：第 1 点是真正的提权漏洞，在“底线”范围内；第 3 点要么是假安全，要么一开工就报错。
- 改法：
  - profiles 和 api_tokens 用**列权限**：`revoke update on profiles from authenticated; grant update (display_name, tz_mode, home_tz) on profiles to authenticated;` api_tokens 同理，只授 `update (revoked_at)`。`is_owner`、`disabled_at` 加进表格，再加一个触发器兜底：非 service role 改这两列时报错。
  - `body_enc` 和 `token_hash`：**建议干脆不收回列权限**。body_enc 是用户自己的密文，密钥在服务器，读到也解不开；token_hash 是 256 位随机钥匙的哈希，没法反推。收回列权限换来的安全几乎为零，代价却是 REST、Realtime、适配器都得维护列清单。按 R-46“好用优先”，砍掉（见第 6 节）。
  - RLS 测试（第 9 节）补上“B 改自己的 is_owner、disabled_at、scopes 都失败”。

**H6　数据库函数默认谁都能调用，可能绕过 RLS**
- 位置：3.3“辅助函数 is_active() security definer”、4.4 `apply_patch`、6 `take_rate`。
- 问题：
  1. Postgres 新建的函数默认 `EXECUTE` 授给 PUBLIC，而 Supabase 会把 `public` schema 里的函数自动暴露成 `/rest/v1/rpc/<函数名>`，匿名用户和登录用户都能直接调用。
  2. `take_rate` 要写 rate_limits 表，而这张表没有策略，所以它只能写成 security definer。这样一来，任何人都能用任意 key 去调它，把别人或某个 IP 的额度刷满，比如让你一整天都用不了 AI。
  3. `apply_patch(table, id, patch, …)` 的表名和字段名都由调用方传进来，必然要用动态 SQL。文档没写表名白名单、字段白名单，也没写要用 `format('%I')`。如果哪天它被改成 security definer，就是一个完整的越权写入口；即使保持 security invoker，patch 里也能带上 `rev`、`changed`、`synced_at`、`deleted_at` 这些系统列。
  4. 文档没提视图。以后只要建一个视图（例如统计），在默认配置下它会以创建者身份运行，**绕过 RLS**。
- 改法：
  - 内部函数（take_rate、清理、迁移用的函数）放进不对外暴露的 `private` schema，并执行 `revoke execute … from public, anon, authenticated`，只授给 service_role。
  - `is_active()` 也放进 private，写上 `set search_path = ''`。
  - `apply_patch` 保持 security invoker，表名用白名单（`case` 枚举）；patch 的键按各表的“客户端可写列”白名单过滤，系统列一律去掉。
  - 架构约定里加一条：视图一律 `with (security_invoker = true)`。CI 里加一条 SQL 检查：public schema 里有任何 security definer 函数，或者没有设 security_invoker 的视图，就失败。

**H7　图片路径可以伪造，清理任务可能删掉别人的图片**
- 位置：3.3 G、3.4“同时删掉对应的图片对象”、3.3 A（note_images 走普通用户表策略）。
- 问题：
  - note_images 行由客户端插入，`bucket` 和 `path` 两列也由客户端填，没有任何约束。用户 B 可以插一行 `path = '<A 的 user_id>/…/x.webp'`，然后把这条随手记软删除；30 天后 pg_cron 以超级权限按 path 删除对象，**删掉的是 A 的图片**。account delete、backup 按 path 取图时也有同样的风险。
  - 另外，存储策略里 insert 应该写 `with check` 而不是 `using`；客户端如果用 upsert 重传，还需要 update 策略。
- 改法：
  - note_images 加约束 `check (bucket = 'images' and split_part(path, '/', 1) = user_id::text)`。vault-images 的行只能由函数插入，客户端的 insert 策略限定 `bucket = 'images'`。
  - 清理任务删除对象前，再核对一次路径前缀和 user_id 一致。
  - 存储策略：insert 用 `with check`；不开放 update（图片不可变，换图就换 id）。

**H8　离线队列和现有写入流程怎么接，没写清楚**
- 位置：4.2、11“store.js 新增 pull/patch”；对照 `src/scripts/data/write.js` 的 `run()`、`withTimeout`、`C.WRITE_TIMEOUT_MS`。
- 问题：
  1. 现在的 `write.run()` 是“10 秒没写成功或者失败，就回滚本地，发 error”。有了 outbox，离线写入**本来就不会**在 10 秒内成功，照现在的逻辑，断网时记的东西会被立刻回滚。文档没说 write.js 的语义要从“写存储”改成“写进队列”，也没说回滚改成只在 4xx 永久失败时才做。
  2. **服务器上的版本覆盖了本地还没发出去的修改。** Realtime 推来、或者增量拉到某一行时，如果这一行在 outbox 里还有没发送的 patch，文档没说要怎么合并。照“合并进缓存”的写法，本地刚改的内容会先被服务器的旧值盖掉，等 outbox 发出去以后再变回来，界面会闪一下，甚至丢数据。
  3. `apply_patch` 靠 op_id 去重，说“服务器记录 24 小时内用过的 op_id”，可是第 3.2 节没有这张表。
  4. outbox 的 `op: delete` 到底是硬删除还是软删除，没说清楚（3.4 说撤销用硬删除）。
  5. 现有的 `store.subscribe` 接口是“每次都给全量快照”，`data/subscribe.js` 和 `state.js` 都依赖这个。新的 cache 和 sync 是直接替代 subscribe，还是由 rest-adapter 模拟出全量快照？文档没定。
- 后果：data 层是 4.0 改动最大的地方，这几处不定，开发会在 write、subscribe、sync 三个文件之间来回返工。
- 改法（在 4.2 里补“和 v3 写入流程的衔接”）：
  - write.js 的 `run(op)` 改成 `outbox.enqueue(op)`：入队成功就当作成功；rollback 只在 outbox 报“永久失败”（4xx）时触发，并且由 data 发 `error` 事件。`WRITE_TIMEOUT_MS` 只用于“在线时 10 秒还没确认”，作用是在界面上显示“同步中”，不回滚。
  - sync 合并规则：收到服务器上的某一行后，先存成 `server_base`；如果 outbox 里有这条记录的待发 patch，就把这些 patch 依次叠加到 server_base 上，得到界面上显示的值（也就是 rebase）。
  - 新增表 `applied_ops(op_id uuid pk, user_id, at timestamptz)`，pg_cron 每天清理 24 小时以前的记录。
  - 定下接口：保留 `store.subscribe(coll)` 这个对外接口，由 data/sync 在内部用 cache 加增量拉取加 Realtime 拼出全量快照，交给现有的 subscribe.js。这样 state、normalize、各个 ui 都不用改。适配器契约测试里加上 `pull` 和 `patch` 的用例。

**H9　冲突检测会大量误报**
- 位置：4.4、3.1 `rev` 和 `changed`、5.2 和 5.3 里服务器写回的字段。
- 问题：
  1. 服务器自己也在写：push-dispatch 写 notified_for 和 remind_at，anniv-roll 写 next_date，ai-classify 写 category_id 和 ai_status，这些每次都会让 rev 加 1。
  2. 而现有 write.js **每次**保存都会带上 `updatedAt`，多数还带 `remindAt`。所以只要服务器推送过一次，或者纪念日滚动过一次，用户在任何设备上改这一条，都会和服务器改过的字段（remind_at、updated_at）重叠，结果按第 3 条报“已在另一台设备上改过”。
  3. “服务器只记得最近一次改了什么，rev − base_rev > 1 就当作冲突”，又进一步放大了误报。
  4. `changed` 列由 apply_patch 写，但客户端直接 PATCH、claude-intake、迁移脚本都不会去维护它。
- 后果：冲突提示变成家常便饭，用户就不再信任这个提示了。
- 改法：
  - 改成**按字段记版本**：加一列 `fv jsonb`，存 `{字段名: 最后修改它的 rev}`，由触发器 `trg_touch` 比较新旧值自动维护（这样所有写入路径都一致）。冲突的判断改成：patch 里任何一个字段的 `fv[字段] > base_rev`。这样“只记得最近一次”的限制也一并解决了。
  - 系统字段（pushed_for、synced_at、ai_status、ai_meta，还有 updated_at 本身）不参与冲突判断；remind_at、next_date 这类派生字段也不参与，改成服务器合并后按规则重新计算。
  - 前提是 H2 修好：服务器上算出来的 remind_at 和客户端一致，重算才可靠。

**H10　硬删除没法增量同步，其他设备会留下“幽灵条目”**
- 位置：3.4“撤销……直接硬删除”“硬删除以后增量同步就看不到”、4.3。
- 问题：
  - 增量拉取靠 `synced_at > cursor`，被硬删除的行不会出现在结果里。Realtime 虽然会推 DELETE 事件，但设备必须当时在线。
  - 撤销是 4.0 的核心流程（纪要 13.2）：在手机上说完一句话，又马上撤销，这时如果 iPad 或电脑离线、在后台，或者 iOS 已经断开了 WebSocket，那几条记录会一直留在它们的缓存里，直到 25 天后整表重拉。
- 改法：撤销也改成软删除，但在 `deleted_at` 之外再加一个 `purge = true`：界面直接隐藏，“最近删除”里也不显示，30 天清理时照常删除。这样增量同步就能看到。或者另建一张墓碑表 `tombstones(table, id, user_id, synced_at)`，由硬删除的触发器写入、增量拉取时一并读取。推荐前一种，改动更小。

说明：“自带发件发不到朋友”本来也可以算高，但纪要 13.21 已经定了“开放前接 Resend”，所以列为 M11。

### 中

**M1　阴历和节假日**
- 位置：2.2 `lunar-data.js`、5.4、9 lunar 测试、纪要 13.13。
- 问题：
  1. **腊月生日会跳过一年。** 5.4 写的是 `lunar.toSolar(今年, month, day, …)`，“已经过了就算明年”。阴历十一月、十二月的日子，往往落在下一个阳历年的 1、2 月。例如阴历 2025 年十二月二十（落在阳历 2026 年 2 月初）：在 2026 年 1 月调用 `toSolar(2026, 12, 20)`，得到的是 2027 年 1 月的日期，**中间那一次被跳过了**。正确的做法是阴历年 Y−1 和 Y 都算一遍，取不早于今天的最早那个日期。
  2. **中韩两套的差别是“整月”，不是“某一天”。** 两国定义每月初一时用的时区不同（中国按东八区，韩国按东九区），朔日正好在午夜附近时，**整个月**的初一会差一天，这个月里的每一天都跟着差一天。闰月的位置也可能不同，那就会差出整整一个月。所以“差异表”应该按“阴历年、月 → 这个月初一对应的阳历日期 + 是否闰月”来存，而不是一张“个别日期差一天”的补丁表。
  3. **没写数据来源和校验方法。** 建议：中国按紫金山天文台或香港天文台公布的历表；韩国按韩国天文研究院（KASI）的阴阳历数据。CI 里加一个测试，把两国已知有差异的年份（由生成数据的脚本从两份数据里自动列出来）逐月比对。
  4. 节假日：韩国的설날、추석（都是阴历节日）**必须**按韩国阴历算，中国的春节、中秋按中国农历算，**和每条记录的 lunar_variant 无关**。文档没写这一点，容易被写成“全部按设置里的默认值算”。
  5. “每年更新”的流程没写。韩国会临时宣布公休日（임시공휴일）和代替公休日，中国每年 11 月前后公布调休安排，这些都没法提前写死。建议把 holidays-data 做成按年份拆开的 JSON 静态文件（例如 `holidays/2027.json`），随网页一起发布、由 Service Worker 缓存；构建时检查“明年的数据有没有”，没有就给警告；中国的调休要另存“补班日”。
- 改法：按上面 1–5 条改 5.4 和 2.2；测试里补“腊月生日跨年”“闰月差异年”两类用例。

**M2　AI 的额度和调用顺序**
- 位置：5.1、6 ai-parse、12 风险 1、13.1、3.2 ai_config。
- 问题：
  1. `per_user_daily` 默认 30 次，而 Flash 免费版**全项目**实测每天约 20 次（见第 4 节）。一个人就能把全体的额度用光。
  2. 5.1 的流程是“除了离线、关了 AI、额度用完，**都先调 AI**”；第 12 节风险 1 的应对却写着“语音先跑本地规则，只有说法复杂时才调 AI”。两处矛盾，开发者不知道按哪个做。
  3. 7.3 的 parse 白名单允许输出 `note` 和 `anniv`，但 4.0 没有随手记和纪念日的界面（1.3）。在 4.0 里说“农历三月初五是妈妈生日”，就会往空表里写一行，用户在任何地方都看不到。
- 改法：
  - 模型默认用 **Flash-Lite**；上线第一天就在 AI Studio 里看本项目的真实额度，`global_daily` 取实际额度的 80%，`per_user_daily = global_daily / 预计人数`。
  - 调用顺序定为：先跑本地规则；本地规则“有把握”（只拆出一件、日期和时间都识别到了）就直接保存，**不调 AI**；只有拆出多件、或者识别不到日期，才调 AI。这样同时满足 13.15 的“AI 识别”和 13.16 的“0 元”。需要产品负责人确认（第 8 节第 2 条）。
  - ai-schema 的 kind 白名单由 `app_config.features` 决定：4.0 只放开 event 和 todo。

**M3　隐私记的 VAULT_KEY 方案（4.1）**
- 位置：5.5、8.4、5.2 末行。
- 问题：
  1. **邮箱重设等于没上锁。** 隐私记的作用按 R-46 是“防止别人翻看手机”。可拿到你手机的人，多半也能打开同一台手机上的 Gmail：点“忘记密码”，收验证码，重设，就能看到全部隐私记。现在的设计挡不住这种最常见的情况。
  2. **4 位密码可以在线慢慢试。** 每 15 分钟能试 5 次，1 万种组合最多试 2000 轮，约 21 天就能试遍。前提是对方手里有登录令牌，比如捡到一台没退出登录的设备。
  3. **bcrypt 在这里没有意义。** 4 位数字只有 1 万种组合，数据库泄露后，哪种哈希都能在一秒内试完。真正起保护作用的是“服务器计数”。bcrypt 在 Deno 里只能用纯 JS 实现，还会占用 Edge Function 的 CPU 时间（免费版每次请求有 CPU 时间上限）；argon2id 要用 WASM，内存也可能超限。
  4. **密文没有绑定行。** AES-GCM 没写 AAD（附加认证数据），能把 A 那条记录的密文复制到 B 那条记录里，照样能解开。
  5. **隐私记的明文会发给 Gemini 免费版**（5.2 末行）。核实结果：免费版的内容会被谷歌用来改进产品，可能有人工审阅，谷歌自己也提醒不要提交敏感或个人信息。R-46 虽然放宽了隐私要求，但“隐私记被拿去训练模型”和产品负责人设想的“隐私记”恐怕不是一回事，需要确认。
  6. 单把密钥的风险：VAULT_KEY 存在函数的环境变量里，任何能进 Supabase 控制台的人都能读到；函数代码里一句 `console.log` 就会让明文进日志。
- 改法：
  - 重设密码加一道“冷静期”：申请以后 **24 小时**才生效，期间所有设备都会收到推送“有人申请重设隐私记密码”，可以在 App 里取消；或者只允许在“已经登录超过 7 天的另一台设备”上发起。推荐冷静期（第 8 节第 4 条）。
  - 锁定时间逐级加长：15 分钟、1 小时、4 小时、24 小时；每次锁定都推送提醒。
  - 密码哈希改成 `HMAC-SHA256(VAULT_PIN_PEPPER, user_id || pin)`，用 WebCrypto 实现，省掉 bcrypt 依赖。
  - AES-GCM 用 `AAD = user_id || note_id || enc_key_id`；nonce 每次随机生成 96 位。
  - 隐私记默认**只用本地规则分类**，不送 Gemini 免费版，设置里另给一个开关（第 8 节第 5 条）。
  - 函数里禁止打印请求体；CI 里用 grep 检查 vault 函数里有没有 `console.log`。

**M4　免打扰和“只发 60 分钟内的提醒”互相冲突**
- 位置：5.3 第 1 步和末尾“免打扰时段……推迟到免打扰结束”。
- 问题：免打扰 23:00–7:00 的话，23:30 的提醒推迟到 7:00，那时已经过了 7.5 小时，按第 1 步“remind_at > now − 60 分钟”就被丢掉了。结果是免打扰期间的提醒全部消失。
- 改法：免打扰期间到点的条目，写一个 `defer_until = 免打扰结束时刻`；第 1 步的查询改成 `coalesce(defer_until, remind_at)` 加上 60 分钟窗口。免打扰按 `home_tz` 判断（H3）。

**M5　CSP 一上线就会让现有界面出问题**
- 位置：8.1 `_headers` 的 CSP。
- 问题：`default-src 'self'` 会同时限制 style-src 和 img-src。
  - 现有 `ui/dom.js:12` 用 `setAttribute("style", v)`，`src/index.html:53` 也有内联 style，这些都会被拦截；
  - 4.1 的图片来自 `https://<ref>.supabase.co/storage/...` 的签名链接，还有压缩时用的 `blob:`，也会被拦截；
  - Service Worker、字体都没有单独声明。
- 改法：先改代码，把 `h()` 的 `style` 参数改成用 `el.style.cssText`（通过 CSSOM 设置样式不受 CSP 限制），去掉 index.html 里的内联样式。CSP 补齐：`img-src 'self' blob: data: https://<ref>.supabase.co; worker-src 'self'; font-src 'self'; style-src 'self'`。Playwright 的 E2E 要在带 CSP 响应头的环境下跑，控制台出现 CSP 报错就算失败。

**M6　把 supabase-js 拼进 IIFE 会和 check_arch 冲突**
- 位置：2.2 `vendor-supabase.js`、8.1“沿用 IIFE 拼接”。
- 问题：
  - 现有 build.py 会把每个 script 各包一层函数作用域再拼起来，check_arch 对每个文件都要求有“职责 / 依赖”文件头（A6）、不超过 250 行（W1）。第三方库几千行，没有文件头，里面还有 `globalThis`、`localStorage` 等等。
  - 另外 supabase-js 要用 UMD 版（它会挂到全局 `supabase` 上），而 ESM 版拼不进 IIFE。
- 改法：manifest 新增 `vendor` 段，check_arch 对 vendor 段的文件全部跳过，只校验 sha256 和固定版本号（防止被替换）；用 `@supabase/supabase-js` 的 UMD 版，记下版本号；构建时把它放在 IIFE 前面，单独打包成 `vendor.<hash>.js`，这样它的缓存不会因为 App 代码改动而失效。

  - 4.2 开工前先做一个半天的技术验证：WebView2 里的语音识别、WebAuthn、本机通知。

**M8　先用 pages.dev、以后换域名，会丢一堆东西**
- 位置：1.1“xxx.pages.dev”、纪要第八节“域名可以先不买”、13.21“开放前买域名”。
- 问题：浏览器按“来源”（域名）来隔离数据。从 `xxx.pages.dev` 换到自己的域名以后：
  - 主屏幕上的 PWA 要删掉重装；
  - 推送订阅全部失效；
  - IndexedDB 缓存和登录会话全部没了，要重新登录；
  - Face ID 和 Windows Hello 的凭据（RP ID）全部作废。
  - 自己用的 2–4 周之后再换，你本人要重来一遍。另外 `pages.dev` 在中国大陆的访问一直不稳定（**未核实**，你常去中国，值得实测）。
- 改法：建议 4.0 上线前就买域名（每年约 10–15 美元，用 Cloudflare 注册还可以同时管理 DNS），网页直接放在自己的域名上；Resend 可以等开放给朋友时再接。需要产品负责人决定（第 8 节第 1 条）。

**M9　同一台设备换账号，推送会发到别人的手机上**
- 位置：3.2 devices（`push_endpoint unique`）、4.1“退出登录时清空整个库”。
- 问题：
  - 退出登录时文档只说了清空 IndexedDB，**没说要删掉服务器上这台设备的订阅**，所以 A 退出以后，A 的提醒仍会推到这台已经换成 B 登录的手机上；
  - B 在这台设备上订阅推送时，push_endpoint 和 A 的那一行重复，又因为 RLS 看不到 A 的行，upsert 会直接失败。
- 改法：退出登录时先调 `devices` 删除本机这一行，再清空本地数据；新增一个服务器函数（或 security definer 的 RPC，放在 private schema 里，只认当前用户）`claim_endpoint(endpoint)`：把旧主人的那一行删掉，再插入新的一行。

**M10　照着开工还缺的细节**
- 位置：3.2、3.3、6。
- 问题：
  - 3.2 只列了字段名，没写类型：date 是 `date` 还是 `text`？time 呢？done 是 boolean 吗？remind_offsets 有没有上限？开发者会各写各的。
  - 缺列：profiles.is_owner、settings.ui_locale（H1）、各表的 tz（H3）、pushed_for（H4）、fv（H9）、purge（H10）。缺表：applied_ops（H8）。
  - 迁移文件怎么切分（每个版本一个，还是每张表一个），没写。
  - 函数之间的复用（claude-intake “走 ai-parse 的同一套逻辑”）是直接 import `_shared`，还是函数调函数，没写。函数调函数会多一次冷启动，也会多算一次调用次数。
  - “每个邀请码 5 次失败后作废”：输错的人并不知道自己输的是哪个码，这一条要怎么计数？
- 改法：在附录里直接给出 `migrations/0001_init.sql` 的完整表结构（含类型、默认值、约束），这是最省返工的写法；函数之间一律通过 `_shared` 的模块复用，不互相调用。

**M11　Supabase 自带发件：不只是慢，而是发不到朋友**
- 位置：1.1 ⑦、12 风险 2。
- 问题：核实结果，自带发件每小时 2 封，并且**只发给项目团队成员的邮箱**，其他地址直接报错“Email address not authorized”；官方也说明它只适合测试和演示，没有送达保证。所以：
  - 朋友在开放之前根本收不到验证码；
  - 你自己如果一个小时内登录了两台设备，第三台就要等；
  - 隐私记重设密码、注销前重新验证，都会占用这 2 封的额度。
- 改法：第 12 节风险 2 的描述改正过来；预览环境的邀请注册测试只用团队成员邮箱或者本地 Mailpit；登录页上要明确提示“验证码一小时内最多发 2 封”，免得你以为软件坏了。跟 M8 一起决定什么时候接 Resend。

**M12　构建目标和共享代码的版本差**
- 位置：2.1“两个构建目标”、8.1、11。
- 问题：
  1. 现在的 build.py 有 `claude`、`staging`、`web` 三个目标，文档只字没提 staging 怎么处理。
  2. claude 目标只服务于“只读 30 天”的旧版，却要在主干上长期维护两套清单，再加上 A17 互斥检查。
  3. `logic.gen.js` 在 CI 部署时生成，函数和网页又分开部署。旧版客户端（尤其是不常更新的 exe）和新版服务器在提醒规则上可能不一致。4.4 的冲突规则写了两遍（JS 一份、SQL 一份），本质上不是同一份代码。
- 改法：
  - 搬完数据以后，claude 和 staging 目标**冻结**：在 3.x 的最后一个 tag 上打只读版，主干上删掉这两个目标，A17 也就不需要了；
  - 函数通过环境变量拿到 APP_VERSION，客户端调用时带上自己的版本号，服务器发现规则版本不一致时返回 `upgrade_required`，配合 `min_client_version` 使用；
  - 冲突规则只在 SQL 里实现一份，JS 那边不复制，通过契约测试直接打本地数据库来验证。

**M13　免费版暂停以后提醒就停了**
- 位置：12 风险 5、13.4。
- 问题：免费项目“7 天没人访问”会暂停，暂停期间 pg_cron 不会运行，也就不会有推送。你出门一周不打开 App，回来之前的提醒全都不会发。pg_cron 自己的活动算不算“有人访问”，**未核实**。
- 改法：本机每天的备份拉取（10 节）本身就会访问 API，前提是电脑开着；再加一个 GitHub Actions 的定时任务，每天调一次 `app_config`（几秒钟，几乎不占分钟数）。预览项目暂停了无所谓，但 deploy-preview 开头要先检查项目是否在运行，暂停了就先调管理接口恢复。

### 低

- **L1　“3.0.1 只读版”的命名**（13.6）：第十三节第 1 条写的是“不做 3.0.1”。只读版本身是合理的，建议叫“3.0.1（只读）”，并且请产品负责人确认这算不算违反第 1 条，或者改叫 3.0.2 以免混淆。
- **L2　ADR 要同步**：ADR-003（解析放在本地）、ADR-005（靠 Claude 定时推送）、ADR-001（单文件发布）都被 v4 推翻了，要写新的 ADR，并把旧的标成“已被取代”。
- **L3　RLS 写法和性能**：策略里写成 `(select auth.uid())`，避免每一行都调一次函数；`is_active()` 设 `stable` 和 `search_path`；notes 的 update 和 delete 策略缺了 `is_active()`，和其他表不一致。
- **L4　Realtime 的 DELETE 事件不经过 RLS**（官方文档原话的意思是：Postgres 没办法验证用户有没有权限看到一条已经删掉的记录）。客户端会收到别人那一行的主键，必须忽略缓存里没有的 id。泄露的只有 uuid，影响很小，但要写进 sync.js 的注释和测试。
- **L5　App 在前台时会提醒两次**：iOS 收到推送必须显示通知（不显示的话，几次之后系统会撤销订阅）。App 在前台时会同时出现系统通知和提醒卡片，可以接受，但卡片这边不要再响提示音。
- **L6　logs 不需要同步到其他设备**：4.1 写的是“每张表一个 store”，logs 只需要上传、不需要拉下来，否则每台设备都要缓存 90 天的日志。
- **L7　漏掉的配套**：皮肤对比度检查没有放进 CI（13.12）；功能文档快照没有放进发版流程（13.20）；“快捷键呼出记一件事”“未来 7 天的提醒清单”（纪要第五节）没有对应模块。
- **L8　注销账号和本机永久备份矛盾**：第九节第 5 条要求注销时删除全部数据，但第 10 节每周的备份在本机永久保留，里面会有朋友的数据。开放给朋友之前，要定下备份的保留期限，或者删除时按用户剔除。
- **L9　`supabase db dump` 要在本机装 Docker**（**未核实**，CLI 的 dump 一般依赖本地 pg_dump 或 Docker 容器）。每天的 JSON 备份已经足够，每周的整库 SQL 可以放在 GitHub Actions 里做（它的 Linux 机器上自带 Docker），产物加密后上传到私有桶，本机再拉下来。
- **L10　客户端的 `purgeDeleted` 要删掉**：v3 的 write.js 里由客户端负责清理 30 天前删除的内容，v4 改由 pg_cron 做，两边同时清理会重复操作。
- **L11　离线时不能用语音**：iOS 的 Web Speech 要联网，所以“离线也能记”只适用于打字。断网时长按“＋”要直接提示“请用键盘”。
- **L12　settings 整个放在一个 jsonb 里**：冲突时按整块 `data` 来算，两台设备分别改了皮肤和字号也会冲突。建议拍平成普通列，或者按“设置项”合并 jsonb 的键。
- **L13　GitHub Actions 的分钟数**：私有仓库每月有免费分钟数（Windows 机器按倍数计），每次 push 都跑 Docker 加两个浏览器的 E2E，开发密集的时候不够用。改成 PR 和 develop 跑完整流程、普通 push 只跑单元测试；另外 Playwright 的 webkit 不等于 iOS Safari，不能代替真机验收。
- **L14　增量游标**：`synced_at = now()` 取的是事务开始的时间，长事务提交时可能比游标还早；往回退 5 秒对这个规模够用，但要写明“只对短事务成立”，迁移脚本这类大批量导入完成后，要求设备整表重拉一次。

5. 如果两周后真的不够，再考虑每月不到 1 美元的付费模型，这需要产品负责人放开“0 元”的约束。

## 2. 新发现的问题

### 高

**N1　隐私记重设和注销账号的“刚验证过邮箱”检查，可以用刷新令牌绕过**
- 位置：5.5“服务器检查 JWT 的签发时间在 10 分钟以内，并且 amr 里有 otp”；6 account delete“10 分钟内重新验证过邮箱”。
- 问题：supabase-js 大约每小时会用刷新令牌自动换发一次新的 JWT。新 JWT 的签发时间（iat）是当前时间，而 `amr` 里仍然保留着当初登录用的 `otp` 那一项。所以，只要手里有一台已经登录的设备，等它刷新一次令牌（或者在控制台里手动调一次 `refreshSession()`），就能同时满足“10 分钟内签发”和“amr 含 otp”两个条件。这样**不用收邮件**就能重设隐私记密码，或者注销账号。按 R-46，隐私记要防的正是“拿着你手机的人”，而按 R-56，邮箱验证码就是重设时唯一的门槛。
- 改法（二选一，推荐 1）：
  1. 不再看 iat，改看 **amr 里 `method = "otp"` 那一项自带的 `timestamp`**：它记录的是这次验证码登录真正发生的时间，刷新令牌时不会变。要求这个时间在 10 分钟以内。（Supabase JWT 的 amr 每一项都带 method 和 timestamp，上线前用一个真实令牌确认一下字段名。）
  2. 或者由函数自己发起一次验证：vault 的 reset 改成两步，`reset_start` 由服务器调 `signInWithOtp` 给这个用户的邮箱发码，`reset_finish {code, new_pin}` 由服务器 `verifyOtp` 校验，通过后才换哈希。
- 测试：在函数测试里加上“刷新令牌以后调 reset 必须失败”。

### 中

**N2　private schema 的授权前后矛盾（H6 遗留）**
- 位置：3.3 通用规则（“`private.is_active()` 只授权给 authenticated”）、3.3 C 和附录 A 末行（`revoke execute on all functions in schema private from public, anon, authenticated`）、3.3 D（public 的 report_tz、claim_endpoint 是 security invoker，内部转调 private 里的 security definer 实现）、5.9 的 `my_ai_usage()`。
- 问题：
  - 每条 RLS 策略都要调 `private.is_active()`，public 里的转发函数也要调 private 里的实现。但附录 A 把 private 里所有函数对 authenticated 的执行权都收回了，也没写 `grant usage on schema private to authenticated`。照附录 A 写，**所有查询都会报 permission denied**，App 一条数据也读不出来。
  - 开发者遇到报错，最省事的“修法”就是把 private 整个授权出去，等于把 take_rate 也放开了。
  - 另外 `my_ai_usage` 没写进 D 的清单。
- 改法：附录 A 末尾写成明确的白名单：
  ```sql
  grant usage on schema private to authenticated;               -- 只授 usage，表仍然全部 revoke
  revoke execute on all functions in schema private from public, anon, authenticated;
  grant execute on function private.is_active() to authenticated;
  grant execute on function private.report_tz_impl(text, uuid, text),
                         private.claim_endpoint_impl(text, text, text, text, text),
                         private.my_ai_usage_impl() to authenticated;   -- 函数内部只认 auth.uid()
  grant execute on function private.take_rate(text, int, int) to service_role;
  ```
  - 确认 private 不在 API 暴露的 schema 列表里（这样上面这几个函数只能通过 RLS 和 public 转发间接用到）。
  - 既然转发函数什么都不做，也可以干脆把 report_tz 写成 public 里的 security definer，加上 `set search_path=''`，再把 CI 的“public 里不能有 security definer”改成白名单例外。两种写法选一种写死就行。
  - RLS 测试加上“B 直接调 `private.report_tz_impl` 时只能改到自己的行”。

**N3　重复事项只有字段，没有设计（R-63 并入以后的缺口）**
- 位置：1.3 末尾“重复事项”、附录 A 的 `repeat`、`repeat_skip`；5.3 推送；线框里没有重复事项的界面（全文只出现两次“重复”，都和这个功能无关）。
- 问题：
  - 每条记录只有一个 `remind_at`、`pushed_for`、`notified_for`，第一次提醒推送以后，下一次提醒由谁、在什么时候往后排？纪念日写了“推送后滚动”（5.3 第 6 步），重复事项没写。
  - 重复的待办打勾以后，是整条完成，还是把 due 推到下一次？
  - “只改这一次”是新建一条记录加上 `repeat_skip`，还是在原记录上加例外？撤销和冲突又怎么处理？
  - 月历和“今天”页要按 `expand()` 展开，展开出来的虚拟条目 id 怎么定（提醒、搜索、“错过的提醒”都要用 id 来定位）？
  - 这些不定，B6 做到一半会卡住，还可能回头改 B2 已经验收过的提醒逻辑。

  - 补一节“5.12 重复事项”：
    - 推送后由 push-dispatch 调 `logic/repeat.next(rule, after, tz)` 写回下一次的 remind_at；

**N5　从中国大陆上传 1.9 MB 的 WAV，20 秒内不一定传得完**
- 位置：5.11 第 1、2 点、14.5。
- 问题：WAV 没有压缩，60 秒约 1.9 MB。Cloudflare 免费版在大陆没有节点，从大陆上传的速度常常只有每秒几十到几百 KB（**未核实**，取决于运营商），较长的录音会经常超时，于是频繁走到“改用手机自带识别”，而自带识别又不支持中韩混说。韩国本地网络则没有这个问题。
- 改法（都不花钱）：
  1. 技术验证第一天优先测：Gemini 能不能直接收 iPhone 的 `audio/mp4`（AAC）、电脑的 `audio/webm`（Opus）。官方列表里有 AAC 和 OGG，容器不同，**不一定被拒**。能收的话，体积降到约四分之一（架构已列为“可以再省流量”，建议从“可选”升级为 B3 第一项）。
  2. 不能直接收，就在客户端把音频编成 **MP3（16 kHz、单声道、32 kbps）**，用纯 JS 编码器（如 lamejs，约 100 KB，放进 vendor 段），60 秒约 240 KB；MP3 在 Gemini 的支持列表里。
  3. 客户端超时按体积动态计算（比如每 100 KB 加 1 秒，封顶 30 秒），不要一律 20 秒。

**N6　复审时顺手核实的转发细节**（都不阻塞，B0 时落实）
- **supabase-js 的路径前缀（已核实，可行）**：当前源码里，`validateSupabaseUrl` 会先调 `ensureTrailingSlash` 给地址补上末尾的 `/`，各个服务的地址再用 `new URL('rest/v1', baseUrl)`、`new URL('auth/v1', baseUrl)`、`storage/v1`、`functions/v1`、`realtime/v1`（http 换成 ws）相对拼接。所以 `https://example.com/sb` 会变成 `https://example.com/sb/rest/v1` 等等，**路径前缀会保留**。旧的 v2 版本用的是字符串拼接 `${url}/rest/v1`，同样会保留。默认的登录存储键取的是主机名的第一段（`sb-example-auth-token`），和路径无关；预览环境的主机名是 `preview`，两个环境不会互相覆盖。来源：[SupabaseClient.ts](https://github.com/supabase/supabase-js/blob/master/packages/core/supabase-js/src/SupabaseClient.ts)、[helpers.ts](https://github.com/supabase/supabase-js/blob/master/packages/core/supabase-js/src/lib/helpers.ts)。要求：vendor 里固定的版本，B0 第一天用真实请求再确认一次。
- **函数固定区域（已核实）**：请求头 `x-region`，首尔的值是 `ap-northeast-2`；加不了请求头时，可以用查询参数 `forceFunctionRegion`；默认在“离请求方最近的区域”运行。来源：[Supabase: Regional invocations](https://supabase.com/docs/guides/functions/regional-invocation)。官方文档没写 pg_cron 和 pg_net 发起的调用在哪个区域运行，所以 **pg_net 调函数时也带上 `x-region`**，否则 ai-classify 万一落到不支持 Gemini 的区域就会失败。
- **存储签名链接不用改写**：按 storage-js 的实现，签名链接是“客户端配置的 storageUrl”加上服务器返回的相对路径，本来就是 `example.com/sb/storage/v1/...`（根据源码推断，B0 实测确认）。14.2 第 3 条可以降为“只校验、不改写”。
- **Worker 免费额度（已核实）**：每天 10 万次请求（UTC 午夜重置），每次 10 ms CPU，等待 fetch 的时间不算。超额时路由可以设成放行（绕过 Worker）或报错：**要设成报错**，因为放行的话，`/sb/*` 会落到 Pages，拿到一页 HTML，supabase-js 会报出看不懂的错误。来源：[Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/)。估算：大陆轮询模式下，一台前台设备每天约 2,900 次请求，几十台设备也在额度以内。
- **Edge Function 限制（已核实）**：每次请求 CPU 时间 2 秒（等待 I/O 不算）、内存 256 MB、免费版运行最长 150 秒；官方**没有公布请求体大小上限**，所以 5.11“技术验证时测 2.5 MB”这一步要保留。来源：[Supabase: Functions limits](https://supabase.com/docs/guides/functions/limits)。把 1.9 MB 编成 base64 的 CPU 开销远低于 2 秒。
- 建议：转发写成 Pages Functions（`functions/sb/[[path]].js`），和网页同一个项目、一起部署，就不用另外处理“Worker 路由和 Pages 谁先接到请求”的问题（Pages Functions 能不能透传 WebSocket，**未核实**，B0 测；不行就退回独立的 Worker 路由）。

### 低

## 2. 新带出的问题

**中 1 条（B2 开工前改进文档）：写 remind_queue 的触发器会被 N2 的授权挡住**
- 位置：4.5“一个触发器……把这条记录写进 `private.remind_queue`”；3.3 C 和附录 A 末尾的白名单。
- 问题：触发器函数默认以触发它的用户（authenticated）的身份执行。N2 已经把 private 里所有表对 authenticated 收回了，所以客户端每次改日期、时间或提醒设置，这个触发器往 `private.remind_queue` 插入时都会报 permission denied，**整条更新跟着失败**。这个触发器函数没有名字，也不在白名单的说明里，开发者很可能会按“不准把 private 授权出去”的规则卡住，或者反过来去放开 remind_queue 的写权限。另外，3.3 提到的“`disabled_at` 兜底触发器”也没有写明函数怎么定义。
- 改法：
  - 在附录 A 里写出 `private.enqueue_remind()`：`security definer set search_path = ''`，只做“插入 (table_name, id) on conflict do nothing”和清空 defer_until、pushed_for 这两件事。
  - `disabled_at` 的兜底触发器也同样写出函数定义。
  - 说明：触发器函数在触发时 Postgres 不检查 EXECUTE 权限，所以这两个函数**不进**白名单。顺带一提，白名单里那条 `grant execute on function private.touch() to authenticated` 其实也不需要，可以删掉，CI 白名单相应少一项。
  - RLS 测试里加一条：B 用自己的身份改自己日程的时间，能改成功，remind_queue 里多出一行。

**低 1 条：** `location` 写的是“提醒页里点一下就打开”。打开前只允许 `http:`、`https:`（以及需要的话 `tel:`）这几种开头，其他（比如 `javascript:`）一律按纯文本显示，防止链接执行脚本。数据只属于用户本人，所以列为低。

除以上两条外，没有发现新的高级或中级问题。
