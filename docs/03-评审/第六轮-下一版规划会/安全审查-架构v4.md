# 第六轮 · 安全审查：架构设计 v4（上服务器前）

- **审查对象**：`docs/10-架构/架构设计-v4.md`，第三轮修订稿，含 0.7 节。
- **尺度**：和《安全与隐私.md》一致，默认不通过。
- **已拍板、不推翻的决定**：
  - R-46：好用优先；
  - R-56：隐私记密码重设立即生效；
  - R-57：隐私记交给 AI；
  - R-60：注销后从所有备份删除；
  - R-62：录音交给 Gemini；
  - 推送里写标题和名字；
  - 邀请码注册，不做后台。

  这些决定带来的风险，本文只给不违背决定的补救办法。

## 0. 结论（产品负责人看）

**有条件通过**：可以按计划开工，但第 4 节的 P0 项没有全部完成之前，不能上正式服务器。

- **底线大体守住了**：
  - 行级权限、列级授权、private schema 白名单、存储路径约束都设计得很扎实；代码审查员三轮复审，把越权类问题基本堵上了；
  - AI、推送、隐私记的密钥都只放在服务器上；
  - 更新包签名已经进了流水线。
- **还有 1 个高级问题**：注销流程能把**你自己的全部备份**一起删掉，删的是本机备份。这条正好打在“备份”这条底线上，必须改。
- **另有 9 个中级问题**，集中在四个方面：
  - 登录防刷：所有请求经 Worker 转发后，Supabase 看到的是同一个 IP；
  - 隐私记的“首次设置”和“绑定 Face ID / Windows Hello”还缺身份校验；
  - 免费额度可能被单个账号写满；
  - 给朋友用之前的告知义务。

  每个问题都有不违背决定的补救办法。

## 1. 底线逐条核对

| 底线 | 结论 | 说明 |
|---|---|---|
| 行级权限 | **守住**，有 3 处要补 | 每张表都开了 RLS，`(select auth.uid())` 写法正确；系统列不授权（H5），private 按白名单授权（N2），视图用 security_invoker，图片路径受 CHECK 约束（H7），CI 也会检查。<br>要补的 3 处：<br>• note_images 能挂到别人的 note_id 上（低 3）；<br>• Realtime 的 DELETE 事件会泄露别人的 id（低 4）；<br>• 存储桶本身没设大小和类型上限（中 5） |
| 密钥只在服务器 | **守住**，有 2 处要补 | A14 和 gitleaks 会扫密钥特征，service role 不进仓库。<br>要补的 2 处：<br>• Claude 连接码会出现在 Claude 的聊天记录里（中 6）；<br>• exe 的登录令牌明文存在硬盘上（中 7） |
| 邀请码 | **基本守住** | 码只存哈希、只能用一次、7 天过期，并按 IP 和邮箱限流。但“按 IP 限流”依赖 Worker 传过来的真实 IP，而 Supabase 自己的验证码限流会被 Worker 合并成同一个 IP（中 1） |

| 更新包签名 | **守住**，有 1 处要补 | desktop.yml 里有签名步骤。签名私钥放在 GitHub secrets，要加审批保护（低 7） |

## 2. 问题清单

### 高

**高 1　注销会删掉本机的全部历史备份，而且没有“误删”和“被盗”的保护（R-60 与备份底线冲突）**
- **位置**：第 6 节 account delete、第 10 节第 3 步。
- **问题**：
  - 注销的门槛只有“10 分钟内用邮箱验证码登录过”。iPhone 上通常装着邮件 App，所以拿到你已解锁手机的人可以自己收验证码，然后注销**你的**账号。
  - 注销后，服务器上的 7 天备份会被删掉；第二天 pull.ps1 再按 `deleted_accounts` 把本机所有每日备份、版本前备份、发布前备份和图片都删掉。到这一步，数据**一份都不剩**。
  - 另外，pull.ps1 完全相信服务器返回的清单。只要 BACKUP_PULL_TOKEN 或服务器被攻破，对方就能让你的电脑删光所有人的备份。
- **补救**：下面几条都不违背 R-60，因为朋友注销时照样会删干净。
  1. **管理员账号**（也就是 `private.admins` 里的你）不能通过 App 注销，account 函数直接拒绝；你自己真要注销，到控制台里操作。
  2. pull.ps1 加三道保险：
     - 永远不删写在本机配置里的“受保护 user_id”（你自己）；
     - 一次清单里要删的账号超过 1 个，或者超过现有账号的 20%，就停下来写“需要人工确认.txt”，不执行删除；
     - 只删“已经不在当天备份名单里”的 user_id，两边对得上才删。
  3. 注销成功后，给这个账号的邮箱发一封“账号已注销”的通知（Resend），让本人知道。
  4. 顺序调整：先写 `deleted_accounts` 并标记 `disabled_at`，再删备份，最后删用户。backup-daily 要跳过已停用的账号，免得删到一半时又生成新备份。

### 中

**中 1　经 Worker 转发后，Supabase Auth 看到的所有用户都是同一个 IP（推断，B1 实测）**
- **依据**：Cloudflare 官方说明，Worker 跨域名调用另一个走 Cloudflare 的站点时，`CF-Connecting-IP` 会被固定成 `2a06:98c0:3600::103`（[Cloudflare 请求头](https://developers.cloudflare.com/fundamentals/reference/http-request-headers)）。supabase.co 是否也走 Cloudflare，**未核实**。
- **影响**：
  - Supabase 的“每个 IP 每 5 分钟最多校验 30 次验证码”变成了全体用户共用一个配额。一个人乱试，就能让所有人（包括你）一段时间内登录不了。
  - 反过来，如果 Worker 把客户端自带的 `X-Forwarded-For` 原样转发，而上游又信任这个头，就可以伪造 IP 绕过限流。
- **补救**：
  1. 在 Supabase Auth 打开 CAPTCHA，选 Cloudflare Turnstile。官方内置支持（[Supabase CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha)），`signInWithOtp` 时带上 captchaToken。Turnstile 在中国大陆能不能用**未核实**，要和 14.6 一起实测；不能用的话，只在大陆以外开，或者改用下面第 2 条。
  2. Worker 自己按真实 IP 给 `/sb/auth/v1/otp` 和 `/sb/auth/v1/verify` 限流：每个 IP 每 10 分钟最多 10 次。可以用 Cloudflare 免费版的 1 条速率限制规则，或者 Durable Objects 计数。
  3. Worker **删掉**客户端传来的 `x-client-ip`、`x-proxy-secret`、`x-forwarded-for`、`x-real-ip`，再由 Worker 自己用 `headers.set` 写入，不能用 append。
  4. Auth 设置里把验证码有效期从默认 1 小时缩短到 10 分钟。

**中 2　隐私记的“首次设置”和“绑定 Face ID / Windows Hello”没有写明身份校验**
- **位置**：5.5；第 6 节写着“vault：除 setup、unlock、reset 外还要 vault_token”。
- **问题**：
  - `setup` 不需要 vault_token。如果服务器没有检查“这个用户还没设过密码”，任何拿到登录状态的人都能直接重新 setup，等于绕过了密码。
  - 注册 WebAuthn 凭据（绑定 Face ID 或 Windows Hello）的步骤没写要什么条件。在你登录着的电脑前，别人可以绑上自己的 Windows Hello，以后就能直接解锁。
- **补救**：
  - setup 只在 `private.vault` 没有这个用户的记录时才执行，否则返回 `already_set`；
  - 注册凭据要求 vault_token 有效，并且当场再输一次密码；
  - unlock_webauthn 要校验以下几点：challenge 由服务器保存且只能用一次、origin、RP ID、credential_id 属于 JWT 里的这个用户、sign_count 递增；
  - 设置页列出已绑定的设备，可以删除；每次新绑定都推送通知。

**中 3　隐私记重设：拿着手机的人可以自己收验证码（R-56 的残余风险）**
- **问题**：N1 的修复是到位的：看 amr 里 otp 那一项的 timestamp，刷新令牌绕不过去。但重设立即生效，唯一门槛就是“能收到邮件”，而邮件 App 通常就在同一部手机上。现在的补救“推送给所有设备”，推送的正是被拿走的那部手机，作用有限。
- **补救**（不加冷静期，不违背“立即生效”）：
  - 重设成功后，另外**发一封邮件**到账号邮箱：“隐私记密码已于某时在某设备上重设”。电脑上的邮件也能看到。
  - 隐私记页面显示“上次重设时间”。
  - logs 记一条 `vault_reset`。
  - 建议你本人：iPhone 的邮件 App 打开 Face ID 锁（iOS 18 起可以给单个 App 上锁），这样拿着手机的人收不到验证码。

**中 4　免费版的不限行数写入，可能被一个账号写满全站**
- **问题**：
  - 客户端可以直接通过 REST 向 events、notes、logs、settings 插入数据（notes.body 一条最长 2 万字），这一层没有频率限制；
  - Supabase 免费版数据库约 500 MB（**未核实**，以官网为准），存储 1 GB；
  - 任何一个朋友的账号被盗，或者客户端出了死循环，都能把库写满，整个项目变成只读，所有人都受影响。
- **补救**：
  - 每张表加触发器做行数上限，例如每人每表最多 2 万行，logs 每人每天最多 2,000 条；
  - settings.value 限制在 4 KB 以内；
  - Cloudflare 定时任务每天查一次数据库和存储的用量，超过 70% 就推送提醒你。

**中 5　图片桶没有在“桶”这一层限制大小和类型**
- **问题**：note_images 表上限 10 MB，可存储策略只检查路径。客户端能往自己的文件夹里传任意大小、任意类型的文件，而且不用写 note_images 那一行，所以这些文件不会被清理。
- **补救**：
  - images、vault-images 两个桶设 `file_size_limit = 2 MB`（图片本来就压缩到约 300 KB），`allowed_mime_types = ['image/webp']`；
  - 每天清理一次没有对应 note_images 记录、并且超过 24 小时的对象；
  - 每人图片总量设上限，例如 200 MB。

**中 6　Claude 连接码会出现在 Claude 的聊天记录里；泄露后能刷推送、耗额度**
- **问题**：
  - 5.7 写的是 Claude 用 curl 带 `Authorization: Bearer <连接码>`，这条命令会原样留在 Claude 的会话记录里（本机和 Anthropic 都有），和“不贴进聊天”自相矛盾。
  - 权限只有“新增”，这点做得对。但泄露后，对方每小时能写 60 条，带标题和链接的提醒会直接推到你的锁屏（可以用来钓鱼）；走 `{text}` 的话，还会消耗你每天 50 次的 AI 额度。
- **补救**：
  - `tools/claude-intake/` 提供一个小脚本，自己从 Windows 凭据管理器读连接码；Claude 只调用脚本、只传内容，命令里永远不出现连接码。
  - 每天上限 200 条。
  - 连接码 180 天过期。
  - 设置页显示“最后使用时间”。
  - 通过连接码写入的条目，location 里的链接一律不显示成可点的链接，或者标上“来自 Claude”。

**中 7　exe 没有自己的 CSP，登录令牌明文存在硬盘上**
- **问题**：
  - exe 打包的是 dist/web，从 `tauri://` 加载，Pages 的 `_headers` 管不到它，CSP 实际为空。exe 里一旦有 XSS，就能调用 Tauri 接口（自启、热键、通知）。
  - supabase-js 把刷新令牌存在 WebView2 的 localStorage 里，也就是硬盘上的明文文件；拷走这个文件，就能长期登录。
- **补救**：
  - `tauri.conf.json` 的 `app.security.csp` 照抄网页版的 CSP，connect-src 写上 `https://example.com wss://example.com`；
  - capabilities 只放行用到的那几个插件命令，不开 shell，不开文件系统；
  - supabase-js 换成自定义存储：exe 里用 Windows 凭据管理器或 Stronghold 保存会话。

**中 8　本机备份是明文，里面有朋友的数据**
- **问题**：`data\backups\` 和 `待办APP-备份\图片\` 里有所有用户的日程、随手记、生日和带定位的照片。给朋友用以后，你就是他们个人信息的保管人，PIPA 要求采取加密等安全措施。如果这些文件夹在网盘同步范围里，风险更大。
- **补救**：
  - D 盘开 BitLocker（最省事）；或者 pull.ps1 下载后用 7-Zip AES 加密，密钥放在凭据管理器；
  - 备份文件夹不放进网盘同步；
  - BACKUP_PULL_TOKEN 能下载所有人的备份，每 90 天换一次。

**中 9　免费版会话永不过期，又没有远程退出功能**
- **问题**：Supabase 默认会话无限期，一个人可以在任意多台设备上同时登录。按时长或不活动自动过期，第三方资料说是 Pro 功能（**未核实**，[Supabase 会话](https://supabase.com/docs/guides/auth/sessions)）。架构里没有设备列表，也没有“退出其他设备”按钮，丢了手机没法远程让它下线。
- **补救**：
  - 设置 › 账号 加“退出其他所有设备”，调 `signOut({scope: 'others'})`；
  - devices 列表显示每台设备的最后在线时间，可以单独删除推送订阅；
  - 隐私记的 vault_token 本来就只有 10 分钟，不受影响。

### 低

1. **Service Worker 不能缓存 `/sb/*`**：sw.js 只预缓存静态文件。所有 `/sb/` 请求（尤其是 vault 返回的明文）一律直连，不进 Cache Storage；写进 A19 的检查和测试。
2. **隐私图片会留在浏览器缓存里**：vault-images 的签名链接返回的图片会进 HTTP 缓存，上锁后仍然留在磁盘上。上传时设 `cacheControl: 'no-store'`，或者用 fetch 拿成 blob 显示、上锁时释放。
3. **note_images 能指向别人的 note_id**：外键检查不走 RLS。改成复合外键 `(note_id, user_id) references notes(id, user_id)`；notes.category_id 同理。
4. **Realtime 的 DELETE 事件会带出别人的 id**：客户端不会硬删，DELETE 只来自 30 天清理和注销。建议只订阅 INSERT 和 UPDATE。Realtime 设置里关闭“公开频道”；publication 只加需要同步的表。
5. **Worker 只转发白名单路径**：只放行 `rest/v1`、`auth/v1`、`storage/v1`、`functions/v1`、`realtime/v1`，其他一律 404，包括 `graphql/v1`。上游地址用 `new URL()` 拼，拼完断言 origin 等于 Supabase 的地址。`/sb/*` 设成不缓存。另外，anon key 里带着项目 ref，别人可以绕过 Worker 直接访问 supabase.co，所以**任何安全限制都不能只放在 Worker 上**。
6. **ai-voice 的上限前后不一致**：第 6 节写的是“audio/wav ≤2.5 MB”，5.11 写的是 600 KB、不再用 WAV。以 5.11 为准：服务器边读边计数，超过 600 KB 就中断，不能只看 Content-Length；Content-Type 只认 `audio/mpeg`、`audio/aac`、`audio/mp4`、`audio/webm`。Gemini 密钥放在请求头 `x-goog-api-key` 里，不放在网址里。出错时只记错误码，不记 Gemini 返回的原文（原文里可能有转写内容）。
7. **签名私钥和发布权限**：
   - TAURI_SIGNING_PRIVATE_KEY 只放在设了审批人的 production 环境里，desktop.yml 也要等你点批准；
   - 第三方 Action 按提交 SHA 固定版本；
   - 私钥离线另存一份（丢了就再也发不了更新，[Tauri 官方](https://v2.tauri.app/plugin/updater/)）；
   - 首次安装包没有代码签名，下载页公布 SHA-256；
   - 安装方式选“仅当前用户”，更新时不弹管理员授权；
   - 开机自启用 autostart 插件（写的是当前用户的启动项），不要管理员权限，这一点是对的。
8. **几个小地方**：
   - VAULT_KEY 按用户派生子密钥（HKDF(VAULT_KEY, user_id)）；
   - applied_ops 的主键改成 (user_id, op_id)；
   - `take_rate` 用单条 upsert 保证原子性；
   - 4.5 说 enqueue_remind 会“清空 defer_until 和 pushed_for”，但它是 after 触发器，改不了 NEW，要另外放进 touch() 处理；
   - 注销时还要清掉 private.vault、vault_credentials、counters 里这个用户的记录；
   - account export 如果包含隐私记，要求 vault_token；
   - invite-signup 再加一个全站每天上限（例如 50 次），邀请码用 32 个以上字符的字母表（8 位约 40 bit）。
9. **账号的大门**：Gmail、Supabase、Cloudflare、GitHub、Resend、Google AI Studio、域名注册商，全部开两步验证或 Passkey。Gmail 收所有验证码，是总钥匙。域名打开注册商锁和 DNSSEC，配好 SPF、DKIM、DMARC。Gemini 密钥在 Google Cloud 里限定只能调 Generative Language API。

### 已确认做得好的地方
- N1 修复到位：看的是 amr 里 otp 那一项的 timestamp，有“刷新令牌后必须失败”的测试。
- 隐私记用 HMAC 加 pepper，常数时间比较，锁定逐级加长；明文只放在内存，不进 IndexedDB（A18 管着）；函数里禁止 console。
- 提示注入防护：用 `<data>` 标签隔开，模型不带工具，输出过白名单，user_id 只取自 JWT 或连接码；ai-classify **按用户分批**，不同用户的内容不会混进同一个提示词。
- `safeHref` 协议白名单、textContent 渲染、CSP `script-src 'self'`、frame-ancestors 'none'。
- 推送内容按 Web Push 标准端到端加密，苹果和微软的推送服务读不到标题，只会显示在锁屏上。
- 录音在我们这边不落盘、不写日志、不进离线队列。

## 3. 合规：给朋友用以后（PIPA）

以下根据公开资料整理，**未经律师核实**。

- **身份变化**：你自用时基本不受约束。为别人处理个人信息，就成了“个人信息处理者”，有以下义务：
  - 公开个人信息处理方针，也就是隐私说明；
  - 收集前取得同意；
  - 告知处理委托和数据转移到国外；
  - 采取加密和访问控制等安全措施；
  - 发生泄露时通知本人，达到一定规模还要报告监管机构；
  - 注销后删除数据。R-60 正好对上这一条。
- **隐私说明至少要写**：
  1. 收集哪些信息：邮箱、日程、随手记、隐私记、录音、照片及其定位、你记下的**他人**生日和姓名；
  2. 交给谁处理：
     - Supabase（数据存放在首尔）；
     - Cloudflare（所有请求都经过它）；
     - Resend（美国，发验证码）；
     - Google Gemini（美国）；
     - 苹果和微软的推送服务；

## 二、补救做法带出的新问题

**中（阻塞）：新增的 `change_pin` 可以绕过“连续输错就锁定”**

- **位置**：5.5 新增了“改密码只能走 change_pin（要旧密码）或 reset”。全文只在这一处提到 change_pin。第 6 节函数表的鉴权规则（“除 setup、unlock、reset 外还要 vault_token”）和逐级锁定规则都没有覆盖它。
- **风险**：如果 change_pin 按“要旧密码”单独实现，又不计入 fail_count、不看 locked_until，拿着已登录手机的人就能用它无限次试旧密码。4 位数字只有 1 万种组合，很快就能试出来。这样，unlock 的逐级锁定就形同虚设。隐私记要防的正是这个人。
- **改法**（一句话，加进 5.5 和第 6 节）：
  - change_pin 必须同时满足两条：
    - 带有效的 vault_token；
    - 旧密码校验和 unlock 共用 fail_count、lock_level、locked_until，输错照样计数、照样锁定。
  - S-B5 的函数测试加一条：“锁定期间调 change_pin 被拒；用 change_pin 连续输错 5 次会触发锁定”。
