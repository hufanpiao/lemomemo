## 结论：有条件通过

下面这些做得对：
- `withGlobalTauri: false`，`freezePrototype: true`。
- 三个窗口各有一份 capability，命令在 Rust 里又按窗口 label 核了一遍（双保险）；capability 里没有 `remote`，所以第三方 iframe（Turnstile、Office 查看器）调不到任何 IPC 命令。
- 页面没有被授予 `core:event:allow-emit`，跨窗口通信只能经 Rust 转发。
- 顶层导航按窗口限制，路径用 `Url` 规整以后再判断。
- 新窗口一律拒绝。
- 权限请求只放行 main 本地页面的通知。
- 会话只存在凭据管理器里，键有白名单。
- 注册页的地址写死在 Rust 里，更新检查以后也只在 Rust 里做。
- 启动时核对环境，对不上就不启动。

要改的有四处：quick-add 页没有注入严格的 meta CSP；main 能导航到 `/app/` 下的任何 HTML；`permissions/autogenerated` 已经落后于 `build.rs`；以及“跳过环境核对”的开关没有在 CI 里禁掉。见第七节。

## 一、和架构原文不同的三处

| 改动 | 结论 | 理由 |
|---|---|---|
| auth、quick-add 改成调 Rust 命令（`auth_done`、`quick_add_submit`），由 Rust 用 `emit_to(main, …)` 转发给 main | **接受，比原文更好** | 另一种做法是给页面 `core:event:allow-emit`，那样哪个窗口都能往任何窗口发任意事件。现在两个小窗口能做的事被收成两个固定动作：`auth:done` 不带载荷，main 收到后自己去凭据管理器重读会话；quick-add 只能交一段 ≤ 2000 字的文字。条件：main 把 `quick-add:submit` 里的 `text` 当不可信的纯文本处理，只交给解析器，不当 HTML 插进页面（建议 X-S6） |
| 注册页由 Rust 用写死的地址打开（`env::ENV.signup_url`） | **接受，比原文更好** | 页面不传地址，auth 窗口也没有 `open_external`，Turnstile 之类的第三方脚本就算在 auth 页里，也没法借这个口子打开任意外链 |
| 暂存脚本放在 `desktop/src-tauri/scripts/` | **接受** | 放在 B6-exe 自己的地盘里，符合 B6-exe 约定 1。从安全角度只有一个要求：正式打包的流水线不准带 `--skip-env-check`，见必改 X-4 |

## 二、WebView2 的权限按来源记

- **事实**：WebView2 按来源（`http://tauri.localhost`）记权限，同一份用户数据目录里，main 允许过通知，auth 页（同一来源）以后也会沿用；`permission()` 里写的“auth 一律拒绝”，在已经记下以后可能根本不会再被调用。
- **结论：接受。** 能沿用这个权限的只有我们自己同源的代码（auth 页和 main 是同一份产物）。第三方 iframe 是别的来源，沿用不到。实际上安全边界是“只有本 App 的来源能发通知”，这一条仍然成立。预览版和正式版的 identifier 不同，用户数据目录也不同，权限不会在两套环境之间串。
- **留一个真机核对点**（X-S3）：main 里的 Office 查看器 iframe（`view.officeapps.live.com`）是跨来源的。Chromium 一般不让跨来源 iframe 申请通知权限；但 Tauri 的回调只传了顶层 webview 和权限种类，**不传是谁申请的**，按现在的写法，main 里任何一层发出的通知申请都会被放行。所以要在真机上看一次：跨来源 iframe 调 `Notification.requestPermission()`，结果必须是 denied。如果放行了，就要按申请来源判断（Tauri 不提供来源信息的话，改用 WebView2 的原生事件）。

## 三、会话分段存进凭据管理器

- **键白名单**：每套环境只认两个键，正式是 `sb-lemomemo-auth-token`、`…-user`，预览是 `sb-preview-…`；白名单以外的键一律拒绝。凭据名的格式是 `lemomemo.session.<键>[~段号]`，键只可能来自白名单，所以不存在拼名字注入。分段、头部最后写、长度和 UTF-8 核对，这几步写得对，单测也覆盖了。
- **两套环境的隔离**：成立，而且是三层隔离：
  - 编译特性：`env.rs` 里正式和预览各是一套常量；
  - 配置文件：`check_identifier` 核对配置里的 identifier 和编进来的环境一致；
  - 页面：`desktop-env.json` 写明这份页面是按哪套环境暂存的，启动时核对。

  两套环境的会话键和凭据名都不同，WebView2 的用户数据目录也不同。
- **读取权限**：只有 main 能读，auth 只能写，quick-add 碰不到会话。
- **剩下的风险，接受**：Windows 的凭据管理器只防别的 Windows 用户和离线拷盘（DPAPI），**同一个用户下的任何进程都能读出这些凭据**，没有按程序区分的权限。这和浏览器把会话存在 localStorage 一样，是这类方案共有的限制，写进 S-B6 的风险接受里。
- **建议 X-S4**：卸载时（NSIS 卸载钩子）删掉 `lemomemo.session.*` 下这套环境的凭据，免得卸载以后刷新令牌还留在本机；退出登录时由页面调 `session_remove`，这一条要在 ③ 时核对。

## 四、open_external 白名单和 target=_blank

- `external_url` 先解析，只放行 http、https、mailto、tel 四种协议；不许带用户名密码；不许本地来源和 `ipc.localhost`；长度 ≤ 2048；交给系统的是规整后的地址，不是页面传来的原文。只有 main 能调。用 `ShellExecuteW("open")` 交给系统默认程序打开。**同意。**
- **target=_blank**：`on_new_window` 一律拒绝开新窗口，main 里的再按 `external_url` 校验，通过了就交给系统浏览器。**同意，但有一个缺口**：这条路径不要求用户点过。main 里的跨来源 iframe（Office 查看器）或任何一段脚本调 `window.open`，都能不经点击就拉起系统浏览器，或者通过 mailto、tel 拉起别的程序。→ 建议 X-S2：新窗口这条路径只放行 http 和 https，并且限速（比如 1 秒最多 1 次，超出的直接丢掉，不记录地址）。
- 打开 localhost、内网地址：这些地址只是交给系统浏览器打开，等于用户在浏览器里点了一个链接，不会让 exe 自己去发请求，接受。

## 五、release 版环境核对失败时没有任何提示

**不算安全问题。** 核对失败时程序不启动，这是 fail-closed，方向是对的。但完全没有提示，会让人以为程序坏了，诱使有人把这项核对关掉，这才是间接的风险。→ 建议 X-S1：失败时弹一个 `MessageBoxW`，写固定文案，比如“安装包和环境不一致，请重新下载安装”，不带任何路径和值；退出码固定；同时在应用数据目录写一行日志。

## 六、permissions/autogenerated/*.toml 要不要提交

**要提交，并且要有一致性检查。**
- 这些文件决定了 `allow-<命令>` 这个标识符的含义，提交进仓库以后，审查的人能在 diff 里看到“授予的到底是什么”。
- **现在已经落后了**：`build.rs` 里登记了 `main_show`、`app_update`，`autogenerated/` 里却没有这两个文件，`main.json` 里也没有授予这两条。没授予就是拒绝，所以这本身不是漏洞，但前端 B 的 `openReminder`、`requestAppUpdate` 调用会失败，同时也说明目录没有跟着重新生成。→ 必改 X-3。

## 八、建议

- **X-S1**：环境核对失败时弹固定文案的提示框，并写一行日志（第五节）。
- **X-S2**：`on_new_window` 这条路径只放行 http、https，并且限速（第四节）。
- **X-S3**：在真机上核对一次，main 里跨来源的 iframe 申请通知权限时被拒绝（第二节）。
- **X-S4**：卸载时删掉这套环境的凭据；③ 时核对退出登录会调 `session_remove`（第三节）。
- **X-S5**：预览版的 `checkBundleEnv` 也要反向查：预览产物里不能出现正式地址 `https://lemomemo.com`（前后按单词边界匹配），也不能出现 `*.supabase.co` 直连地址。现在 `other` 是 null，预览这一侧没有反查。CSP 的 connect-src 是第二道保险，所以不卡。

**新加的 WebView2 网页通知（`src/platform/desktop.ts`、`lib.rs` 的 `permission`）**

- 方向可以接受：Tauri 通知插件在 Windows 上收不到点击，改用网页通知是合理的；通知只用纯文本的 `title`、`body`、`tag`，没有图片、地址、HTML；点通知以后只走 `main_show`，再改 hash，`reminderHash` 由本地参数生成，不从通知里取地址。
- 自动放行：只给 main 窗口、而且顶层是本地来源的页面放行通知，其余权限照旧一律拒。用户装了 exe 就等于同意收提醒，系统的通知设置仍然能关，所以不弹询问框可以接受。
- **限制（已核源码）**：wry 0.57.1 的权限回调只把权限种类交给 Tauri，不交申请方的地址（WebView2 事件里的 `Uri` 没有传出来）。所以 `permission` 判断的是顶层页面的地址，而不是申请方的地址。main 的 `frame-src` 放行了 `view.officeapps.live.com`，这个 iframe 里的页面如果申请通知，从回调这一侧看和本地页面没有区别。Chromium 本身禁止跨来源 iframe 申请通知，所以实际上应该会被拦下，但这一点只能在真机上确认。→ **X-S3 改为发布前必须做**，并且加上这一项：在 main 里嵌入 Office 预览，在 iframe 里调 `Notification.requestPermission()`，结果必须是 `denied`，或者调用直接报错。
