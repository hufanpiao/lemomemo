## 必改项

### M1 AI 失败一律退回额度，可以绕过每人每天 50 次和全项目 global_daily（花费和全站停用风险）

- 位置：supabase/functions/_shared/ai/gate.ts `settleFailure`（第 135～144 行），被 ai-parse、ai-voice、claude-intake 调用。
- 问题：`invalid`、`timeout`、`error` 三种失败都把个人和全项目两边各退回 1 次。但这几种情况下 Gemini 的调用其实已经发生了（invalid 是模型已经回了内容；timeout 是本地中止，谷歌那边多半照样算量、照样计费）。用户可以故意写让模型输出过不了校验的内容（提示注入让它多输出一个键、给 2099 年的日子、超过 10 条等等），每次都被退回，只剩“每分钟 6 次”在拦：一个账号一天能打 6×1440 = 8640 次 Gemini，是 50 次上限的 170 多倍；全项目的 global_daily 也一样被退回，等于失效。结果是费用上去，或者把谷歌额度打满（RESOURCE_EXHAUSTED），`ai_state.exhausted_until` 被写到太平洋午夜，所有用户的 AI 当天都停用。
- 要求（二选一或都做）：
  1. 全项目计数（`ai:global:…`）在 invalid、timeout 时不退回，只在“确定没打到谷歌”的情况（比如连接失败、请求还没发出）才退；
  2. 个人计数的退回加上限：比如每人每天最多退回 N 次（另记一个 `ai-refund:<user_id>:<太平洋日期>` 键），超了就不再退。
- 注：任务单 S12、BE-4 写的是“额度预扣失败退回”，这里不是说实现违反了任务单，而是任务单的这条写法本身留了口子。改法会影响“失败不扣次数”的用户体验，需要负责人确认取哪种。补单测：连续 invalid 超过上限后 `quota_out`；invalid 不退全项目计数。

### M2 claude-intake 的写入上限按“连接码”计，连接码个数又不封顶，一个账号每天能写入的条数没有上限

- 位置：claude-intake/core.ts `HOURLY_LIMIT`、`DAILY_ITEMS`（键 `claude-intake:<token_id>:…`、`claude-intake-items:<token_id>:…`）；token-admin/core.ts 每人每天 10 次、没有“同时有效的连接码最多几个”的限制。
- 问题：每天能新建 10 个连接码，每个 180 天有效，有效的连接码最多能攒到 1800 个；每个连接码每天 200 条，所以一个账号每天能经 service role 写进 events、todos、anniversaries 的条数实际上没有上限（10 个码就是每天 2000 条，攒满就是每天 36 万条）。这条路不经过 RLS 和客户端的同步限流，会撑大数据库，也拖慢这个账号所有设备的同步。只能写本人的数据，但占的是全站共用的数据库。
- 要求：加一个按 user_id 计的每天总条数上限（比如 `claude-intake-items-user:<user_id>:<UTC 日期>`，和按连接码的上限同时查）；token-admin 加“同时有效的连接码最多 N 个”（比如 5 个，查 `api_tokens` 里 revoked_at 为空且 180 天内的行数）。各补一条单测。

## 建议（不阻塞合入）

1. **claude-intake、ai-parse 请求体整段读完才看长度。** claude-intake 的 `readBody` 先 `req.text()` 再比 `text.length`（而且算的是 UTF-16 码元，不是字节），完全不看 Content-Length；ai-parse 只在有 Content-Length 时提前拒绝，分块上传照样整段读进内存。两者都在鉴权之后，风险有限，但 claude-intake 关了网关的 JWT 校验，建议直接复用 ai-voice 的 `readCapped`（边读边计数，按字节）。
2. **F9 ⑥ 只查“有没有出现”。** 调了 `tokenLive(` 但不用它的结果、`tokenHash(` 用在别的值上，静态检查都能过；scopes 含 `create` 也没查。现在靠单测兜底，可以接受。建议 ⑥ 再加一条：源码里要有 `.includes('create')`（或同等写法）；另外 check_backend.py 第 1019 行注释说名单由 `tests/build/check-backend-f9-hashed.test.ts` 钉住，这个文件不存在，实际钉在 check-backend-f9-server.test.ts 里，改一下注释。
3. **add.ps1 存进凭据管理器的码，同一 Windows 账号下的任何进程都能读。** 包括 Claude App 自己能执行的 PowerShell：如果聊天里被提示注入，让它跑一段 CredRead 并打印出来，连接码就会进聊天记录。现在 scopes 只有 create、能随时吊销，损失有限（最多被塞垃圾条目），建议在设置页的说明里写清这一点，并提醒“发现异常就断开连接”。
4. **-Setup 清剪贴板只覆盖了当前内容。** `Set-Clipboard ' '` 清不掉 Win+V 剪贴板历史和云同步。建议在提示语里提醒用户到剪贴板历史里删掉这一条，或者说明连接码只需要粘贴一次。
5. **AI 输出的 title 没去控制字符和双向覆盖字符。** token-admin 的 label 去了，shared/schema/ai.ts 的 title、body、project 没去（claude-intake 的 items 由调用方直接给，等于用户可控）。只影响本人的数据，React 渲染也会转义，但双向覆盖字符会让列表里显示的文字和实际不一致，建议在 itemRaw 里统一拒收或去掉（和 parse-core.ts 的 CTRL 同一份）。
6. **x-app-version 由调用方自报**，claude-intake 和 ai-parse 都拿它算 featureOn：改这个头可以打开按最低版本放出的 beta 类型。只影响本人，记一下即可。

## 逐项核对（通过的部分）

1. **claude-intake 鉴权。** 连接码 256 位随机、`lmc_` 前缀，格式不对不查库；库里只存 SHA-256（码熵够高，不需要 HMAC；按哈希等值查库，没有可利用的时序差）；吊销、180 天过期（按 created_at）、scopes 含 create 三项都查，查不到、吊销、过期一律 401 unauthorized，不区分；接着 isUsable（停用、冷静期 403），再按连接码每小时 60 次，都在读请求体之前。api_tokens 只给 authenticated 授了 `update (revoked_at)`，触发器只准从空改成 now()，用户改不了 user_id、created_at、scopes、token_hash，没法把自己的码改成指向别人或延长有效期；没有 insert 策略，只有 token-admin 用 service role 建。写入时 user_id 一律取连接码那一行，`{...r, user_id}` 放在最后覆盖，行的 id 由服务器生成，capture-map 的输出里没有 user_id、ai_status、deleted_at 这些可被利用的列，只 insert、不改不删，写不到别人的数据。错误信息只回错误码和 invalid_reasons，日志只记错误码，不打印头和请求体。没有 CORS，浏览器跨站带不了 Authorization。
2. **版本门免查。** claude-intake 只免 POST，函数本身其他方法 405；免的只是版本门，不是鉴权，没有扩大攻击面。写入的行由服务器端当前版本的 capture-map 生成，不存在旧客户端写出旧格式数据的问题。转发层新加的 `PATCH /rest/v1/api_tokens` 免查，靠列级授权和 guard_token_revoke 兜住，也没问题。
3. **Gemini。** 密钥只在 `x-goog-api-key` 请求头，不进 URL；失败只回 HTTP 状态码，不打印返回正文、请求体和密钥。模型名按 `^[A-Za-z0-9._-]{1,64}$` 校验，拼不出别的主机。提示注入：用户原话放在 `<data>` 里，去控制字符、转义 `</data>`、`</projects>`，截 2000 字；项目名同样处理；系统提示里写明 `<data>` 是数据不是指令；服务器不按模型输出做任何“动作”，只按 schema 生成条目。返回内容用 zod strictObject 严格校验（多键 not_whitelisted、items ≤ 10、日期格式、范围、kind 必须在这个人能用的类型里、confirm 由服务器重算），不合格整份退回本机规则。额度预扣：take_rate 原子计一次，超了马上退回，退回用乐观锁、不会减到 0 以下，并发下不会多放；31 天窗口跨界那一天先读别的窗口再算剩余，存在极小的竞态窗口（最多多放几次），可以接受。被刷的问题见 M1。
4. **ai-voice。** 先鉴权，再查 Content-Type（去参数、转小写，只认 4 种，不在白名单 415、不读请求体），再查 X-Now、X-TZ、X-Scope，再 `readCapped` 边读边按字节计数，超过 600 KB 立刻中断回 413（Content-Length 声明超了也提前拒）；音频只在内存，不写 Storage；入口的 log 是空函数，整个目录不 console.*，转写正文只在响应里返回，不写日志，校验失败只把 invalid_reasons 写进 logs。
5. **同意、停用、vault。** 三个函数调 AI 都经同一个 aiGate，第一步 aiAllowed，没同意回 consent_required，读不出回 503，都不调 Gemini、不扣次数；claude-intake 的文字路径没同意时退回本机规则，items 路径不调 AI。ai-parse、ai-voice 用 requireActiveUser，claude-intake 用 isUsable，停用一律 403。scope = vault 时 ai-parse、ai-voice 一律回 `{fallback, vault_ai_off}`，不调 Gemini、不扣次数（ai-voice 是读完请求体以后才判断 vault，只多读了一次，不发出去）。
6. **add.ps1。** -Setup 用 `Read-Host -AsSecureString` 读，不进命令行和历史，用 CredWriteW 直接写凭据管理器，不经 cmdkey；平时只用 CredRead 读出来放进请求头，不打印、不落盘，出错只打印中文和状态码。自测开关 `LEMO_INTAKE_TEST_ENDPOINT` 的正则 `^http://127\.0\.0\.1:884[0-9]/[A-Za-z0-9/_-]*$` 主机和端口写死，路径里不准出现 `@`、`.`、`:`，借不到别的主机；命中时改读另一个凭据 `lemomemo.claude.intake.test`，正式的连接码不会发到本机端口。-ItemsStdin 和 -ItemsJson 用原文拼请求体，只影响本人的请求，服务器端会严格校验。
7. **出站白名单。** 只加了 `https://generativelanguage.googleapis.com/v1beta/models/` 这一个前缀，按整串精确匹配（多一个字、写成模板字符串都拒），实际地址是这个前缀加通过校验的模型名再加 `:generateContent`，主机和路径前缀都固定，已经是最小范围。
8. **F9 ⑥。** 名单写死 `{claude-intake: api_tokens}`，单测钉住名单内容、不准从别处改；名单里的函数必须关 verify_jwt，名单外关了又不是 cron 调的一律报错；源码要读 Authorization、从 _shared/intake-token.ts import tokenHash（不准自己定义同名函数）、按 `.eq('token_hash', …)` 查、调 tokenLive 和 isUsable，按明文查直接报错。纯静态检查能被刻意绕过（见建议 2），作为防回退的护栏够用。
9. **本机规则（shared/logic/parse）在服务器上跑用户原话。** 粗看正则没有嵌套量词，项目名拼进正则前都转义了，输入截在 2000 字以内，没看到回溯爆炸的写法。

### 新迁移 20261107100000_core_my_ai_usage.sql

- **授权。** 0001 第 7 行已经收回 postgres 以后新建函数对 PUBLIC 的执行权，Supabase 默认给 anon、authenticated 的执行权只发生在 public 模式下，所以 private 下新建的三个函数默认谁都调不了。`ai_quota_take`、`ai_quota_refund`、`intake_insert` 只 grant 给 service_role，authenticated 虽然有 private 的 usage，也执行不了。`my_ai_usage_impl` 给 authenticated；`public.my_ai_usage` 显式收回了 public、anon、service_role，只给 authenticated。没问题。
- **security definer 和 search_path。** 只有 `my_ai_usage_impl` 是 security definer，配了 `set search_path = ''`，引用一律写全模式名（private.、public.）；门按 0.38 的写法：不是密码会话、账号能用、会话还在；只按 `auth.uid()` 拼本人的键，不收参数，查不到别人的用量。另外三个是 security invoker，以 service_role 的身份执行，也都配了 `search_path = ''`。没问题。
- **额度原子性。** take 和 refund 对同一个键取事务级 advisory 锁（`hashtextextended`），再按这个键所有窗口行合计、判断、写入，原来“先读别的窗口再交给 take_rate”的竞态没有了；只认 `ai:` 开头的键，限额是负数或为空直接报错；refund 只减最新的那一行、并且只减计数大于 0 的，不会减到 0 以下；`lock_timeout` 5 秒，超时整句回滚，调用方按“没扣”回 503。store.ts 已改成调这两个 RPC。
- **intake_insert。** 表名只认三张，标识符一律用 `%I` 拼，值经 `jsonb_populate_record` 按参数传，没有 SQL 注入；行里带 user_id 就报错，user_id 只能由参数给；一次调用就是一个事务，整份成功或整份回滚。**建议（不阻塞）**：现在列的白名单是“这张表里真有的任何列（user_id 除外）”，service role 理论上可以写 ai_status、deleted_at、short_by 这类系统列。眼下行都是 capture-map 生成的，不会出问题，但为了防以后的改动出错，建议按表写死允许的列（和 capture-map 的 EventRow、TodoRow、AnnivRow 对齐），并加一条 pgTAP：带系统列时报 bad_intake_column。
- **其他。** `readJsonCapped` 超长时返回字符串 `'too_large'`，恰好请求体本身就是 JSON 字符串 `"too_large"` 时也会回 413，没有危害。
