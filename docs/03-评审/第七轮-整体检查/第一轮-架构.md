## 一、严重

### S1 同一条记录连续保存会误报冲突，随手记会被拆出"冲突副本"
- **证据**：
  - 架构设计-v4.md:504 队列项在入队时就带上 `base_rev`；
  - :512 "同一条记录连续几个 patch 合并成一个，base_rev 取最早那个"；
  - :530 冲突判定是 `fv[k] > base_rev`；
  - :533 notes 的 title、body 冲突时 `forked`（另存冲突副本）。
  - 全文搜不到"收到确认后更新排队中 patch 的 base_rev"这一步。
- **为什么**：
  1. patch1（base_rev=5）已经发出、还没确认时，用户接着改同一字段，生成 patch2。已发出的 patch1 不能再合并，所以 patch2 的 base_rev 仍然是 5。
  2. patch1 生效后，服务器上 rev=6、fv.title=6。
  3. patch2 到达时 6>5，被判成冲突。
  - 随手记编辑器边写边存，或者在网络慢时连续修改，就会不断出现"已在另一台设备上改过"和冲突副本。自己的改动被当成别人的。
- **建议**：
  - 收到 apply_patch 的 ok 或 conflict 后，把排队中同一 id 的后续 patch 的 base_rev 改成返回的新 rev；
  - 或者改成发送时才取 base_rev（取本机最近一次确认的 rev）；
  - 契约测试加一条"在途期间连续改同一字段，不得出现 conflict 或 forked"。

### S2 iPhone 上"系统降低透明度就自动改实色"做不到（R-77、R-80、纪要 13.12）
- **证据**：
  - 需求 R-80："系统'降低透明度'时回到实色、不模糊"；
  - 架构:226 B6 验收"'降低透明度'时改成实色"；
  - :1003 真机⑫。
- **为什么**：CSS 媒体查询 `prefers-reduced-transparency` 在 Safari 和 iOS Safari 上一直不支持。caniuse 列到 iOS 26.5 都是"不支持"；Chrome 开发者博客写的是从 Chrome 118 起支持、Safari 不支持（2026-10-24 查询）。网页没有别的接口能读到这个系统设置。
  - 来源：[caniuse](https://caniuse.com/wf-prefers-reduced-transparency)、[Chrome 博客](https://developer.chrome.com/blog/css-prefers-reduced-transparency?hl=zh-CN)
- **影响**：Windows 的 Edge 和 WebView2 能做到；iPhone 上这条验收按现在的写法过不了。
- **建议**：按用户规则，先把这一点讲清楚并请用户决定。可选方案：
  - 在 设置 › 外观 加"减少透明"开关（手机默认关）；
  - 或者手机上底部栏直接用实色；
  - 修改 B6 和真机⑫的验收写法。

## 二、中

### M1 已作废的 WAV 方案还留在三处，和 R-68 / N5 矛盾
- **证据**：
  - :582 "录音路：转 WAV → 上传 ai-voice"；
  - :836 "encoding（转 WAV，一般 < 0.5 秒）"；
  - :905 `inlineData {mimeType: "audio/wav"…}`；
  - 与 :818 "不再上传 WAV"、:870 只接受 mpeg / aac / mp4 / webm 冲突。
- **为什么**：开发照着 5.1 的流程图或第 7 节写，会写死 audio/wav 类型，或者传 1.9 MB 的音频。
- **建议**：三处统一改成"直传 AAC/WebM，或压成 MP3"；mimeType 取请求的 Content-Type。

### M2 R-76、R-77、R-79、R-80 在架构里没有落点；依据和修改记录停在 R-78
- **证据**：
  - :7 "依据 R-47 至 R-60"；
  - 0.x 只记到 R-78（:150-154）；
  - 全文搜不到"没赶上""70%""--glass-solid"。
- **为什么**：
  - R-80 要求底部栏 70% 不透明、模糊 6px，并给了"最坏情况对比度"。半透明栏的对比度取决于栏后面的内容，`check_contrast.py`（:949）怎么算最坏情况没有定义。
  - R-79 要求提示条实色，R-76 要求"没赶上"用 F 版的红色描边。这些都要进 skins 的变量和 CI 对比度检查清单。
- **建议**：
  - 加 0.12 节，把 R-76～R-80 映射到 skins 变量、`check_contrast.py` 的检查对象（含"按最坏底色计算"的规则）和验收项；
  - 依据行更新到 R-80。

### M3 exe（Tauri）的页面来源和 lemomemo.com 不同：跨域和 WebAuthn 都会出问题
- **证据**：
  - :956 exe "打包 dist/web"，页面来源是 `http://tauri.localhost`；
  - :1092 "同一个来源…也不需要处理跨域"；
  - :701 和 15.2 中2（:1184）WebAuthn 要校验 origin，RP ID 是 lemomemo.com；
  - 代码审查员 M7 已经指出过来源不同（架构评审-代码审查员.md:274），但架构只回了"单独注册一份凭据"。
- **为什么**：
  1. exe 调 `https://lemomemo.com/sb/...` 是跨域请求。Edge Functions 要自己处理 OPTIONS 预检和 `Access-Control-Allow-Origin`，Worker 也要放行预检，文档没写。
  2. RP ID 必须是页面来源域名的后缀，`tauri.localhost` 的页面用不了 RP ID=lemomemo.com。服务器只认 lemomemo.com 的 origin，exe 的断言会被拒。
  3. Turnstile 也要把 exe 的主机名加进白名单（需核实能不能加 `tauri.localhost`）。
- **建议**：二选一并写明：
  - exe 直接加载远程 `https://lemomemo.com/app/`（会失去离线首屏，需要评估）；
  - 或者保持本地加载：函数统一加 CORS 白名单（只放 `http://tauri.localhost`），vault 校验 origin 时允许 exe 的来源并分开存 RP ID，或者 exe 只用密码。
  - B6 技术验证加这两项。

### M4 R-52 的"电脑 Windows 通知自带按钮"，Tauri 通知插件做不到
- **证据**：
  - 需求 R-52 "电脑 Windows 通知自带按钮"；
  - 架构:654 exe 用"Tauri 本机通知"弹出，没有提按钮。
- **为什么**：Tauri 官方通知插件文档写明 "The Actions API is only available on mobile platforms."（Windows 没有按钮）；"撤回已送达通知"在桌面能不能用，文档没写，需核实。Windows 上另有一条说明："Only works for installed apps"（只对安装版有效）。
  - 来源：[v2.tauri.app/plugin/notification](https://v2.tauri.app/plugin/notification/)（2026-10-24）
- **建议**：
  - 要么在 Rust 侧直接调 WinRT Toast，自己处理按钮点击后的激活（需要 AUMID 和激活回调，工作量另算，需核实）；
  - 要么明确只有 Edge 安装版的 Web Push 通知带按钮，exe 点通知后进整页提醒。
  - 需要用户确认。

### M5 关着 App 时离线新建的提醒不会响（iPhone 没有后台同步，也不能在本机排定时通知）
- **证据**：
  - :1.2 "离线：…联网后自动补传"；
  - :511 只在"上线、切到前台、入队后、每 30 秒"时发送；
  - 提醒全靠服务器推送（5.3）。
- **为什么**：iOS 的 PWA 没有 Background Sync，也没有本地定时通知。离线时记的"下午 3 点提醒"，在用户重新打开 App 之前不会上传，服务器就不会推送。地铁、飞机、大陆网络差的时候很常见。
- **建议**：
  - 提示条和条目上明确标"未同步，提醒可能不响"；
  - 回到前台时先同步提醒类的条目；
  - 写进风险表和真机清单。

### M6 没有请求持久存储，iOS 清理存储时未同步的数据会丢
- **证据**：
  - 全文搜不到 `navigator.storage.persist`；
  - :508 文案写的是"内容还在本机，不会丢"。
- **为什么**：outbox 在 IndexedDB 里。存储紧张时浏览器可能清掉站点数据（iOS 主屏幕版能不能豁免，需核实）。
- **建议**：
  - 启动时调 `navigator.storage.persist()` 并记下结果；
  - "不会丢"改成更谨慎的说法；
  - 真机⑪加"未同步条目在存储压力下是否还在"。

### M7 Turnstile 被 App 自己的 CSP 拦住
- **证据**：
  - :942-944 CSP 是 `script-src 'self'`，没有 `frame-src`；
  - 15.2 中1（:1183）要在 `signInWithOtp` 时带 Turnstile 令牌。
- **为什么**：Turnstile 要从 `challenges.cloudflare.com` 加载脚本，再嵌一个 iframe。照现在的 CSP，登录页的验证组件直接加载失败，而 B1 把它列为 P0。
- **建议**：
  - `/app/` 的 CSP 加 `script-src https://challenges.cloudflare.com`、`frame-src https://challenges.cloudflare.com`；exe 的 CSP 同步改；
  - 大陆能不能打开这个域名，已列入 14.6 实测，保持。

### M8 在大陆收不到 Gmail 验证码
- **证据**：
  - 纪要 13.17 账号都用"现在的 Gmail"；
  - 登录、隐私记重设、注销都要邮箱验证码（5.5、5.6、:880）。
- **为什么**：Gmail 在中国大陆打不开，没有梯子收不到验证码。在大陆换设备登录、重设隐私记密码都会卡住。14.6 的检查表没有这一项。
- **建议**：
  - 14.6 加"在大陆收验证码"；
  - 建议产品负责人另备一个大陆能收信的邮箱，或者确认已有梯子；
  - 隐私说明和安装说明里写明这一点。

### M9 网页登录和"Safari 里不给登录"有冲突（R-74）
- **证据**：
  - :783 "在 Safari 里打开（不是主屏幕版）：只显示'添加到主屏幕'的教程，不给登录"；
  - :167 "网页：任何浏览器打开"；
  - R-74 "网页登录页面也要做"。
- **为什么**：`isStandalone()` 如果对所有平台都生效，电脑的 Chrome、Edge 普通标签页也登不了，网页版等于没有。
- **建议**：写明只在 iOS 和 iPadOS 的 Safari 非主屏幕模式下拦登录，电脑浏览器照常登录；加一条 E2E 测试。

### M10 免费存储 1 GB 和"每人图片 200 MB"、服务器备份互相挤
- **证据**：
  - :1187 每人图片上限 200 MB；
  - :1011 服务器备份放在 `backups/` 桶、保留 7 天；
  - Supabase 免费版存储共 1 GB。
- **为什么**：只要 5 个人用满，存储就到顶了，备份桶也在同一个 1 GB 里。超出后免费版的处理方式（限流还是拒绝写入）需核实，最坏情况是上传图片和每日备份一起失败。
- **建议**：
  - 每人上限按"1 GB × 70% ÷ 预计人数"算，或者先定 50 MB；
  - 备份桶的大小计入用量提醒；
  - 写明到 70% 时怎么办（例如图片迁到 R2）。

已核实的 Supabase 免费版额度（[supabase.com/pricing](https://supabase.com/pricing)，2026-10-24）：数据库 500 MB；存储 1 GB；出站流量 5 GB（另有 5 GB 缓存流量）；Edge Function 每月 50 万次；Realtime 同时 200 个连接、每月 200 万条消息；月活 5 万；最多 2 个活跃项目；不含自动备份；一周不活动就暂停。

### M11 pg_cron 的运行记录会一直涨，占掉 500 MB 数据库
- **证据**：
  - 每分钟一次的 push-dispatch（:627）、每 2 分钟一次的 ai-classify（:611），再加每天的任务；
  - :484-486 的每日清理没有 `cron.job_run_details`。
- **为什么**：pg_cron 默认每次运行都写一行，每天约 2,200 行，不会自动清理，常年下来会持续占用数据库。
- **建议**：
  - 每日清理加 `delete from cron.job_run_details where end_time < now() - interval '7 days'`；
  - 用量提醒同时监控这张表的大小。

### M12 监控告警有缺口
- **证据**：
  - :883 keepalive 用 anon 身份"另外再调一次 push-test 的健康检查"，但 :873 push-test 要求 JWT，这条做不到；
  - :1186 "Cloudflare 定时任务每天查一次数据库和存储用量，超过 70% 就推送提醒"：用什么凭据、调哪个接口都没写；
  - Cron Trigger 只能挂在独立 Worker 上，Pages Functions 不支持定时任务（:1116 又优先写成 Pages Functions）；
  - 全文没有客户端 JS 报错的采集（搜不到 `onerror`）。
- **为什么**：
  - 推送是核心功能。push-dispatch 停了（项目暂停、函数报错、cron 失效）时，没有任何告警，只能靠"提醒没响"自己发现。
  - 用量提醒要读数据库大小，需要 service role 或管理令牌，文档没有说放在哪、怎么保护。
- **建议**：
  - push-dispatch 每轮写一个心跳（例如 app_config 里的 last_dispatch_at）；
  - 独立的 Cloudflare Worker（cron）每 15 分钟检查心跳是否超过 5 分钟没更新，超时就用 Resend 给你发邮件。注意不能靠推送报警，因为坏的可能就是推送；
  - 用量改由一个带 x-cron-secret 的 `usage-report` 函数在服务器内部算；
  - 客户端加 `window.onerror` 和 `unhandledrejection`，按 ADR-010 记成 `act=js_error`，只记错误码。

### M13 Resend 密钥放在哪里，前后矛盾
- **证据**：
  - :981 RESEND_API_KEY 只放在"Auth › SMTP"；
  - 但 :892 注销后用 Resend 发通知、:1185 重设后另发邮件，都是函数自己发信。
- **建议**：
  - 8.4 加一行 `supabase secrets set RESEND_API_KEY`，最好单独建一把只能发信的密钥；
  - 发信量要算进免费额度：每天 100 封、每月 3,000 封（[resend.com/pricing](https://resend.com/pricing)，2026-10-24 已核实，可以把 :737 的"未核实"去掉）。

### M14 删除和修改同时发生时，修改的一方怎么处理没写
- **证据**：:529 行已删除就返回 `gone`，但客户端收到 gone 以后怎么办，全文没有。
- **为什么**：A 设备删了，B 设备离线时改了标题。B 联网后返回 gone，B 的修改是静默丢掉、回滚，还是提示，没有定义。
- **建议**：
  - 收到 gone 时，在"发送失败"区提示"这条已在另一台设备上删除"；
  - 提供"恢复并保留我的修改"（发一个 patch 清掉 deleted_at，再补发修改）。

## 三、轻

1. **离线 24 小时以上才收到确认，会和自己冲突**。applied_ops 只保留 24 小时（:486）。确认丢失、超过 24 小时后重发，同一个 op 会再执行一次，fv 已经被自己加过，于是报冲突。建议保留 7 天，或者按 (user_id, op_id) 只保留最近 N 条。
2. **增量游标的长事务风险**（复审 L14 已提过）。建议再加一条约束："服务器函数不得在数据库事务里等待 Gemini 等外部调用"，防止 synced_at 落在游标往回退的 5 秒之外。
3. **设备时钟偏差**。`deleted_at`、`created_at` 和 ai-voice 的 `X-Now` 都用客户端时钟，没有校时。建议从响应头的 `Date` 算出偏差：显示和清理用校正后的时间，`X-Now` 照旧用设备时间，并写明这样做的理由。
4. **Pages Functions 超额后设成"报错"，影响面比预期大**。Cloudflare 官方：Pages 默认是"放行"（fail open），可以改成"报错"（fail closed），这是整个项目的设置（[文档](https://developers.cloudflare.com/pages/functions/pricing/)，2026-10-24）。所以 `/` 的语言分流也会一起变成 1027 错误页。建议 `/` 的分流挪到独立 Worker，或者接受超额时首页报错，并在 :1115 写明。
5. **节假日数据**。韩国的临时公休日常常只提前几天公布，"每年 11 月发一次修复版"（:680）跟不上，exe 还要等自动更新。建议 holidays 的 JSON 设成不缓存、可以单独更新，不跟版本走。
6. **阴历数据来源**。KASI 公开的数据范围可能只到 2050 年前后（需核实），1900–2100 年的韩国阴历要靠算法生成并和公开数据比对。:670 要写明 2050 年以后的数据怎么来。
7. **R-74 的"邀请制说明"**。16.2 的内容结构（:1300）漏了这一块。
8. **小节顺序**。16.4 排在 16.3 前面（:1311、:1361）。
9. **ADR 和架构约定没跟上**。
   - ADR-002、ADR-005、ADR-007 的状态仍是"已采纳"；第 11 节的取代清单漏了 ADR-002（claude.ai 数据库）；ADR-011～016 还没写。
   - 架构约定.md 还停在 v3（最后更新 2026-10-23，只有 A1–A11，还提到 claude-db）。它自己规定"要改规矩先改本文件"，现在的 A12–A21 只写在架构里。
10. **预览和正式环境可能共用 Gemini 额度**。Gemini 的额度按 Google 项目计算。预览环境如果用同一个 Google 项目的密钥，测试会吃掉正式额度。建议预览用另一个 Google 项目。另外，官方 rate-limits 页面现在不列免费版的具体数字，只让去 AI Studio 看；每天的额度在太平洋时间午夜重置（[文档](https://ai.google.dev/gemini-api/docs/rate-limits)，2026-10-24）。"约 500 次/天"仍是第三方说法，B0 必须在 AI Studio 里截图记下真实数字。
11. **保活的判定标准**。Supabase 官方只说"连续 7 天没有足够的数据库活动"会暂停，没公布细则；"pg_cron 也算活动"只是社区回复（[官方文档](https://supabase.com/docs/guides/platform/free-project-pausing)、[GitHub 讨论](https://github.com/orgs/supabase/discussions/13121)）。建议保活请求做一次真实的写入或查询，不能只建连接；B0 核实的要求保持。
12. **服务器备份函数的 CPU 上限**。backup-daily 在一次调用里导出、压缩所有用户，人多以后可能超过每次 2 秒的 CPU 上限。建议每个用户单独调用一次。
13. **SW 读通知列表需核实**。iOS 上 SW 的 `getNotifications()` 能不能用（:652）需核实，已有真机⑤兜底。
14. **随手记显示方式的设置项**。按设备类型分开记的 `notes.view@mobile` / `@desktop` 在设置页上要写清改的是"本设备类型"，不然用户会以为两边一起改了。

## 四、确认没问题的部分
- **R-75 语言自动识别**：16.4 的规则、cookie、hreflang、Vary 和 no-store、10 条验收都齐全；supabase-js 登录信息的存储键推断正确。
- **R-78 随手记**：默认瀑布流、只在设置里切换（0.11、5.9:794）已经落实。
- **R-74 路由**：首页和 App 拆成 `/` 和 `/app/`，manifest 和 SW 的 scope 都是 `/app/`，放在 B0 做是对的。
- **免费额度**：
  - Edge Function 每月约 6.5 万次（每分钟一次的推送约 4.3 万，加每 2 分钟一次的分类约 2.2 万，加每天的任务），远低于 50 万；
  - Realtime 和 Workers 每天 10 万次请求，按 :1115 的估算够用；
  - Workers 和 Pages 超额时可以设成"报错"，这个设置项存在。
- **中国大陆**：Worker 转发覆盖 REST、Auth、Storage、Functions、Realtime，并有路径白名单；函数用 `x-region` 固定在首尔，Gemini 只从首尔调用；手机不直连 supabase.co 和 Gemini；Realtime 断线后改轮询；大陆实测检查表齐全（还缺 Gmail 和 Turnstile 两项，见 M7、M8）。
- **exe 推送**：exe 不依赖 Web Push 或 WNS，改用程序内每分钟检查加本机通知，所以"不签名的 exe 能不能收 WNS"这个问题不存在。代价是 exe 没在运行时电脑上不提醒，需要写明。Edge 安装版走 WNS，属于浏览器能力，和签名无关。
- **exe 其他**：Tauri 自动更新用的是它自己的签名，不需要代码签名证书；开机自启插件可用；全局热键能不能收到松开事件已列入技术验证，并有"按一下开始、再按一下结束"的备选。
- **数据库权限**：RLS、列级授权、private 白名单、存储策略、图片路径约束、隐私记的锁定和重设（amr 的时间戳）、注销三道保险、迁移步骤（legacy_id、过期提醒的处理、条数核对），这些前几轮评审都已闭环，本轮没发现新问题。
- **时区和阴历**：固定和浮动时刻、current_tz 上报的防抖、腊月跨年、闰月不存在时用平月、节假日固定按本国历法，设计正确。
