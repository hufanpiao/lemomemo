但 0.23 自己新带出 3 个中级问题：

`bypassrls` 加授权白名单的做法**可以接受**，前提是满足下面第四部分 A 里的条件。这一轮没有发现严重问题。

## 二、0.23 带出的新问题

### 严重
无。

### 中

**新中 1：`fn_worker` 只有一个角色，粒度太粗**
- 8 个函数共用一个角色，白名单里有 `private.vault`（含 `pin_hash`）和 `vault_credentials`。
- 这样 file-check、ai-embed 这类函数的 SQL 也能读到 `pin_hash`。
- 每个函数又都能拿到 `VAULT_PIN_PEPPER`（`supabase secrets` 对项目里所有函数都可见）。一处 bug 或注入，就能离线瞬间穷举出 4～12 位密码。
- 同理，account 需要的 delete 权限会让所有函数都有删数据的能力。

**新中 2：ai-parse、ai-voice 怎么核对 `pin_epoch` 没写**
- 0.23 起这两个函数在 `scope=vault` 时要验 vault_token，而验令牌必须比对 `private.vault.pin_epoch`。
- 但它们不在 6.2 的直连清单里，private 又没有对 API 暴露，按现在的写法读不到 `pin_epoch`。vault-image 也一样。
- 要写明走哪条路：列进直连清单，或者用一个只授权给 service_role、只返回 `pin_epoch` 的 security definer 函数。

**新中 3：R-123 草稿密钥是固定的，而且不能吊销**
- 草稿密钥只由用户和 `device_id` 决定，`device_id` 由客户端提供，全文没定义它从哪来、谁核对。
- **能伪造**：拿到过一次 vault_token 的人（例如知道密码，或者绕开 App 直接调 vault 函数），可以替任意 `device_id` 要到原始密钥。
- “不可导出”只管 App 里那份。原始密钥字节是明文出现在响应体里的，直接调接口的人能永久留存。
- 密钥又不随换密码、重设而变，所以：先偷看到密码 → 拿到某台设备的草稿密钥 → 之后偷到这台锁着的设备，就能离线解开它的 `vault_drafts`。用户重设密码也补救不了。
- 补充：只偷到一台锁着的设备（没有密码）时拿不到密钥，这一点没问题；保护强度和隐私记正文一样，都靠解锁的逐级锁定。

### 轻

1. **测试和 R-123 打架**：5.14 第 6 点的函数测试写“隐私记页面离线记下不产生 IndexedDB 写入”，和同一点的 `vault_drafts` 加密写本机冲突。改成“不产生 outbox 条目、不写明文，只写 `vault_drafts` 的密文”。
2. **草稿的 AAD 不含草稿自身信息**：`user_id|device_id|draft` 不含草稿 id 和 `created_at`。几条草稿可以互相调换；`created_at` 是明文可以改，能绕过 24 小时删除。AAD 应加 `id|created_at`。
3. **24 小时删除的时机没写**：应在 App 启动时就删，不必等解锁（只看 `created_at`，不用钥匙）。
4. **密钥轮换**：草稿密钥的推导没带 `enc_key_id`；VAULT_KEY 轮换时要写明草稿作废，可以接受。
5. **下发密钥的通道**：unlock 和 unlock_webauthn 的响应要写明 `Cache-Control: no-store`、函数和 `/sb/*` 转发都不打印响应体。SW 本来就不缓存 `/sb/`，这一条只需写明。
6. **anniversaries 授权可能多给了**：白名单给了 anniversaries 的列，但 8 个函数里看不出谁用到。确认用不到就删掉，D1 照样比对。
7. **`FN_DB_URL` 管不住只给 8 个函数用**：secrets 对所有函数可见，“只给 8 个函数用”只能靠 CI 检查——只有这 8 个函数可以引用 `_shared/db.ts` 或读 `FN_DB_URL`。要把这条写清楚。

## 三、`bypassrls` 加授权白名单是否可接受

**可以接受。** 理由：直连时没有 `auth.uid()`，RLS 策略本来就用不上；按表、按列授权能把“一处 bug 就是整库”缩小到“白名单里的表和列”。

**残余风险**：同一张表里跨用户的行，仍然全靠每条 SQL 写对 `user_id` 条件。而这几个函数手里本来就有 VAULT_KEY，读出所有人的密文列就等于读出明文。

下面第四部分 A 的条件满足了才放行。

## 四、必须满足的条件

### A. `fn_worker`（B0，P0）

1. **拆角色**，至少拆成两个：
   - `fn_vault`：给 vault、vault-file、account 用，只有它能碰 `vault.pin_hash`、`vault_credentials` 以及删数据的权限；
   - `fn_ai`：给 ai-embed、ai-media、note-search、ai-summarize、file-check 用，对 `private.vault` 最多只给 `select (user_id, pin_epoch)` 的列级授权。
   - 如果坚持只用一个角色，`pin_hash` 必须收回列级 select，改由一个 security definer 的校验函数来比对密码。
2. **补写 ai-parse、ai-voice、vault-image 怎么验 `pin_epoch`**（新中 2）。
3. **D1 不只比对表和列的授权**，还要核对：
   - 角色属性：不是 superuser，没有 createrole、createdb、replication，不属于任何别的角色、也没有成员；
   - 对 auth、storage、vault、cron、net、pgsodium、supabase_functions、graphql 这些 schema 没有任何 USAGE；
   - 对 public、private 没有 CREATE；
   - 函数的 EXECUTE：`revoke execute from public` 以后，`fn_worker` 能执行的函数也要和白名单一致，尤其不能执行 private 里的 security definer 函数和 `*_impl`；
   - 如果要用 halfvec 类型，extensions 只给 USAGE，不给别的。
4. **密码不进迁移文件**：迁移里只 `create role … nologin` 或不带密码；正式和预览环境由负责人另外 `alter role … login password`。另外 B0 要核实两件事：
   - Supabase 的 `postgres` 角色能否给 `bypassrls`（PG16 起要求授予者本身带 `bypassrls`）；
   - Supavisor 能否用自建角色连接（用户名格式 `fn_worker.<ref>`）。
   - 这两项并进未核实第 17 项。
5. **建议做（强烈推荐，不作硬条件）**：把 `bypassrls` 换成“会话变量版 RLS”：
   - `_shared/db.ts` 每个事务先执行 `set_config('app.uid', userId, true)`；
   - 给 `fn_worker` 写策略 `user_id = current_setting('app.uid')::uuid`；
   - 这样漏写 `where` 条件时查到的是 0 行，而不是所有人的数据；
   - cron 类函数按用户逐个设置会话变量。

### B. R-123 草稿密钥（B4b-3 前改进架构）

1. **`device_id` 由服务器登记和核对**：
   - 只认 `devices` 表里属于本人的那一行；
   - 推导时加一个只在服务器上的、每台设备一个的随机盐，例如 `HKDF(VAULT_KEY, user_id|device_id|device_salt|enc_key_id, "plus-draft")`；
   - 退出登录、在设置里移除设备、注销时删掉这个盐。这样被盗的设备可以远程作废它的草稿。
2. **重设、改密码时轮换草稿密钥**：换盐，旧草稿作废。
   - 负责人在 R-123 里只要求“App 被关也不丢、本机无明文”，并没有要求换密码后草稿还能解开；“换密码后不变”是架构师自己加的。草稿最多留 24 小时，丢掉的代价很小。
   - 如果仍要保留“换密码后草稿还能解开”，应把这条风险写进 15.7 和风险表，交负责人确认。
3. **草稿 AAD 加 `id|created_at`**；App 启动时不用解锁就删掉超过 24 小时的草稿。
4. **unlock 系列的响应**写明 `no-store`、不打印；修正那条冲突的测试（轻 1）。
