## 结论：有条件通过

- **第四轮的 S1、M1～M5、L1～L8 全部已落实**，S1 和 M1～M4 的做法也站得住。
- 新增内容的大方向成立：

## 二、新增内容的问题

### 中

**N1 "主页面不查隐私记"只写在 5.14，5.13 的查询流程反着写，服务器端没写死**
- **证据**：
  - 5.13 第 6 点的查询流程仍写着"隐私记解锁期间，内存里的隐私记正文、文件名和描述也参与"，"隐私记解锁时带请求头 x-vault-token"；
  - 第 6 节 note-search（2069 行）有 `scope: main / vault`，但鉴权一栏只写了"没有有效 vault_token 时不返回隐私记"。
- **后果**：照 5.13 写代码的人，会在主页面混进隐私记，直接违反 D-16；服务器也没有兜底，主页面只要带了令牌就能查到隐私记。
- **改法**：
  - 改 5.13 第 6 点：主页面本机只查非隐私记；只有在隐私记页面里，才查内存里的隐私记，也才带令牌；
  - note-search 写死规则：`scope=main` 时一律只查非隐私记的向量，带不带令牌都一样；`scope=vault` 时必须有有效令牌，并且只返回隐私记的命中；
  - ai-summarize 用同样的规则：`ids` 里普通记录和隐私记混在一起就拒绝；
  - **在隐私记页面经"＋"记下时**，ai-parse / ai-voice 也要带隐私记的标记，服务器另查 `ai.vault`，关着就只走本机规则。现在 S-B4b-3 只写了查找和总结，没写"记下"；
  - 补函数测试："`scope=main` 带有效令牌，也查不到隐私记"。

**N2 函数直连数据库用的是高权限连接**（6.2 节）
- **证据**：八个函数（ai-embed、ai-media、note-search、vault、vault-file、ai-summarize、file-check、account）都用默认的 `SUPABASE_DB_URL` 直连数据库。这个连接串对应的是 `postgres` 角色，不受 RLS 限制，能读写所有 schema。
- **后果**：按人过滤只靠每条 SQL 自己写对；任何一处拼接出错或逻辑漏洞，影响面就是整个库，包括 auth、隐私记密文和所有用户的数据。
- **改法**：
  - B0 建一个专用的低权限角色（例如 `fn_worker`，带登录密码），只授权这几个函数用到的 private 表，以及 public 表上必要的列；
  - 连接串存成单独的函数密钥，不用默认的那一个；
  - 6.2 写明"禁止用默认的 `SUPABASE_DB_URL`"；
  - D1 或 SQL 检查核对这个角色的授权清单，多一项就失败；
  - 移动事务涉及多张表，也在这个角色的权限范围内完成。
- 这个改法比 6.2 的退路（"临时暴露一个 security definer 函数"）更稳。

**N3 数据清单还不能保证"不漏"**（3.5 节）
- **问题一：一张表里两种行，清单表达不了**。
  - notes、note_files、note_images 里同时有普通行和隐私记行；
  - 清单的 `localCache` 只能按整张表写成"明文 / 只有密文 / 不缓存"三选一。
  - 现在靠数据库的 check 约束兜底，但缓存、导出、备份按清单生成时，表达不出"隐私记行只带密文列"。
  - **改法**：清单加一个按行区分的字段，例如 `vaultRows: {flag: 'is_vault'（或 is_private）, cipherCols: […], plainColsMustBeNull: […]}`；D1 核对这些列和 check 约束一致；按清单生成的测试里，加"隐私记行同步到本机只有密文"。
- **问题二：不按 `user_id` 存的数据，生成不了用例**。
  - `counters`（键名形如 `ai:<user>:…`）、`vault_preview`（对象路径是随机的）、桶里按路径前缀分出来的那一段（例如纪念日头像），按清单生成注销用例时，不知道"这个人的数据"怎么找。
  - **改法**：每张表、每个桶都必须写明"这个人的数据怎么找"（按哪一列、哪种键名格式、哪张登记表），或者明确声明"不存用户数据"；D1 发现两样都没写就失败。
- **问题三：清单范围之外的地方**。
  - 本机 `E:\柠檬记-备份\` 的按人清理、其他设备上残留的 IndexedDB，不在 D1 和生成用例的范围里；
  - 写明这些由 B7 的注销演练覆盖，演练要包含"附件"那个文件夹。

### 轻

1. **告知清单漏了日程和待办的向量**：0.20 起，日程和待办的标题、备注、地点也会交给谷歌算向量（5.14 第 3 点），但 5.13 第 9 点、15.5 告知页的清单、15.7 第 3b 项都没列。补一句"日程和待办的标题、备注、地点（用来按意思查找）"，视觉稿的告知页同步。
2. **15.7 第 7 项补一句**：随手记移进隐私记**之前**的明文版本，还会在服务器备份里留最多 7 天，在本机备份里留最多 30 天；之前预览过的 PPT，微软那边可能有缓存。
3. **隐私记附件的加密粒度**：
   - 文件本体和缩略图用的是同一个 AAD `user_id|file_id`，两个密文可以互相调换，解密照样通过；`name_enc`、`text_enc` 也没写各自的 AAD。
   - AAD 加上用途标记（`|file`、`|thumb`、`|name`、`|text`）。
   - 隐私记那一行的 `sha256`、`bytes`、`kind`、`pages` 是明文，而且会同步到本机。其中 sha256 能用来确认"某个已知文件在不在这里"：改成存在密文里，或者存 HMAC；15.7 第 6 项写明哪些信息是明文。
4. **exe 的 CSP 收紧**：
   - 全局 CSP 为了预览沙箱放开了 `style-src 'unsafe-inline'`，只有 main、auth 两个窗口用 meta CSP 收回；**quick-add 窗口也要加**同样的 meta CSP。
   - B4b-1 第一项再验证一件事：没有来源的预览 iframe 在 exe 里调不到任何 Tauri 命令。预览沙箱的 `connect-src 'none'` 应该能挡住，但 WebView2 的 postMessage 通道要实测。
5. **vault-preview**：
   - 页面隐藏时的 `ms_preview_end` 用 `fetch keepalive` 或 `sendBeacon` 发出，否则切到后台时可能发不出去。
   - 未核实第 16 项的退路（压缩链接时长并告知），本身写得合理，前提是安全审查员签字。补一句：退路启用时，隐私说明要写出实测的分钟数，不能只写"几分钟"。
   - 签名链接会出现在 Cloudflare 的访问日志里。只要 `/sb/*` 的日志里不保留查询串，就可以接受，在 14.2 写明。
6. **note_images 的 `path` 约束**：只检查了第一段是 user_id，没有像 note_files 那样钉死整个拼法。现在服务器一律按 id 拼路径，所以没有越权；为了一致，还是建议照 note_files 钉死，或者改成服务器拼。
7. **ai-summarize**：输出只能当纯文本显示，`cited` 只用来定位条目。现在写的"放进 `<data>`"只是防提示注入；补一句"总结文字不渲染成链接或 HTML"，A26 已经能覆盖这一点。
