## 二、0.16、0.17 带出的新问题

### 中

**M1　exe 跨域：缺"暴露响应头"，预检的请求头白名单也不全**
- **证据**：5.10（:1131-1135）的 CORS 设计里只有 `Allow-Headers`，没有 `Access-Control-Expose-Headers`。
- **为什么**：
  - 跨域请求时，页面 JS 只读得到几个"安全"的响应头，`Date`、`Content-Range` 都不在里面：
    - 4.3 的时钟偏差靠读响应头 `Date`，exe 里会一直拿到空值；
    - PostgREST 的计数和分页靠 `Content-Range`，同样读不到。
  - 预检白名单可能漏了 supabase-js 实际会发的请求头，漏一个，这类请求的预检就会失败。可能漏的有：
    - auth-js 的 `x-supabase-api-version`；
    - 存储上传的 `x-upsert`、`cache-control`；
    - 指定 schema 时的 `accept-profile`、`content-profile`。
    - 具体有哪些按 B0 锁定的版本核实。
- **建议**：
  - 加 `Access-Control-Expose-Headers: Date, Content-Range, Content-Length, X-Total-Count`（后两个视需要）；
  - 预检的请求头白名单按锁定版本的 supabase-js 抓包补齐；
  - 写明 OPTIONS 由 Pages Function 自己直接回 204，不转发给 Supabase；
  - B6 验收加两项：exe 里时钟偏差正常、计数查询正常。

**M2　quick-add 窗口只有 `session_get`，令牌刷新会把会话弄掉**
- **证据**：:1149，quick-add 只给 `session_get`，没有 `session_set`。
- **为什么**：quick-add 窗口如果自己建一个 supabase-js 客户端，它会在 access token 快过期时自动刷新。
  - Supabase 的 refresh token 一次性有效、用后轮换；
  - 新令牌存不回去，主窗口手里的旧 refresh token 就作废了；
  - 主窗口超过重用宽限期再用旧令牌时，可能触发"令牌被重复使用"，整条会话被撤销，结果是 exe 无故掉登录。这一点需按 B0 锁定的 supabase-js 版本核实。
- 另外，quick-add 保存的条目怎么交给主窗口的 outbox 发送，也没写。
- **建议**（二选一，并写进 5.10）：
  - quick-add **不连服务器**：本地规则预览后，经 Tauri 事件或 BroadcastChannel 把条目交给主窗口入队；quick-add 就不需要 `session_get` 了，权限更小；
  - 或者 quick-add 的客户端设 `autoRefreshToken: false`、`persistSession: false`，令牌快过期时请主窗口刷新。

**M3　手机周视图（`buildWeek`）的排布规则在 375 px 宽度下放不下，规则本身也有矛盾**
- **证据**：:1231，"列数超过 3 时后面的块叠放、错开 6 px 露出简称，简称不被遮住"。
- **为什么**：
  - 手机周视图一天一栏，375 px 减去时间轴，每天约 44 px 宽。分成 3 列，每列约 14 px，而两个 9.5 px 的字加边距要 20 px 左右，**放不下 3 列**；
  - 错开 6 px 只能露出 6 px，盖不住和"露出 9.5 px 的简称"互相矛盾；
  - 块的字段 `{…, column}` 里没有正文用到的 `columns`；
  - 全天事项、跨午夜的事项、拉长后超出当天末尾的块，都没定义怎么排。
- **建议**：
  - 最多几列改成按宽度算：`maxColumns = floor(当天栏宽 / 最小标签宽)`，由 `opts` 传入，手机大约是 2；
  - 超出的块不叠放，合并成"+N"或改成只显示颜色，和月历一致；
  - 字段补上 `columns`；
  - 拉长后超过当天末尾的截断到当天；全天事项放到顶部那一行；
  - 和设计确认 R-109 的"宽度"指的是沿时间轴的长度（架构现在是这么理解的），以视觉稿为准。

**M4　Turnstile 的退路没有设计，也没有工期**
- **证据**：:1136，Turnstile 在 `tauri.localhost` 上能不能用"未核实"，不行就"系统浏览器登录、一次性码回到 exe，届时补设计"。B6-exe 只给 3 人日（:431）。
- **为什么**：Turnstile 后台能不能把 `tauri.localhost` 这类本地主机名加进正式 sitekey，我不确定，需核实。如果不能，退路要做的事不少：
  - 自定义协议或深链接回到 exe；
  - 防截获（state、PKCE 一类）；
  - 再走一遍安全审查。
  
  这些加起来至少 2～3 人日。到时候 3 人日的 B6-exe 必然超期，而 B6-exe 又是上线必过项（R-87）。
- **建议**：
  - 把"Turnstile 在 tauri.localhost 上能否通过"从 B6 第一项**提前到 B0 或 B1** 先做个小验证；
  - B6-exe 注明"走退路时 +2～3 人日"，或者现在就把退路的大致流程写出来。

### 轻

- **L1　exe 的 CSP 对所有页面都放行 Turnstile。** 15.6 第 4b 条（:1727）说"exe 里同理"，但 Tauri 的 CSP 是全应用一份，没办法只给登录页放行，所以 5.10 的 CSP 对主 App 也放行了 challenges.cloudflare.com。建议如实写明"exe 里做不到按页面分开，接受这一点"（exe 页面本来就是打包的，风险较低），删掉"同理"。
- **L2　`short` 的数据库检查和 zod 规则不一致。** 附录 A 用 `char_length(short) <= 8` 按码点算（:2014、:2031），zod 按字形簇算 ≤2。两个家庭 emoji（ZWJ 序列）约 14 个码点，zod 放行、数据库拒绝，outbox 就会当成永久失败把整条回滚。建议数据库放宽到 ≤32 码点只防滥用，真正的上限交给 zod。
- **L3　改了标题后 AI 起的简称会过时。** 写明规则，例如：标题改动时，如果 `short` 是 AI 生成的、不是用户手改的，就清空回到 `itemShort`。这需要能区分来源，可以放进 `ai_meta` 或加一个标志。
- **L4　文首和正文的批数没对上。** :15 还写"开发分 8 批"，1.3 是 9 批（B0–B6、B7a、B7b，另有 B6-exe）。
- **L5　"没有待决定事项"的说法不准。** 0.17 末尾说"架构里没有待负责人决定的事项"，但 R-106 的正确率门槛要负责人在 B0 前确认（:428），17.3 的两条缓动令牌也还要 UI 确认。建议改成"架构本身无待决项，有 2 项交给别的环节确认"。
- **L6　ADR 已同步，没有残留。** ADR-011 第 1 条、ADR-014 的背景已经按 R-105 改了（exe 不用 Windows Hello），ADR-017 也没有"方案 A"残留。这一条只是确认。

## 三、确认没问题的部分
- **exe 改为打包页面**：
  - 不开 `remote.urls`；
  - secureStorage 在 Rust 端拼出凭据名，只能读写固定前缀；
  - 更新由 Rust 端做；
  - 外链经 `open_external` 交给系统浏览器，Rust 里再校验一遍协议；
  - WebAuthn 的 origin 只认 lemomemo.com，exe 只输密码，网页版、ADR、15.6 都一致；
  - CORS 只放 exe 一个来源、精确比对、不带 credentials，`/sb/*` 先删掉上游的 CORS 头再重写；
  - Realtime 不受 CORS 影响；签名图片用 fetch 取成 blob。
- **AI 同意由服务器执行**：
  - `record_consent` 公开函数是 security invoker，转调 private 里的实现，授权白名单两处一致（:710、:2246）；
  - `policy_ver` 必须是当前版本；
  - 四个会调 AI 的函数都先查同意，有"调用次数为 0"的函数测试；
  - 客户端改不了同意的两列。
- **照片定位（R-108）**：删掉 lat、lng 两列，比"留列加约束"更稳；B4 有 GPS 的测试。
- **工期拆分**：两条线怎么并行、B7a 和 B7b 的先后、每批六环签字，写得清楚。
