## 二、0.19 新问题

### 严重
无。

### 中

**Z1　附录 A 把隐私记图片写成"跳过识别"，和 D-8、5.13 相反**
- **证据**：
  - 附录 A :2417 的注释写"vault-images 的行插入时由触发器直接写 skip"；
  - 5.13 第 5 点和 R-114 D-8 说隐私记图片**参与**识别：note_images 那行只记 ai_status，描述加密存进 `vault_media_ai`。
- **为什么**：照附录 A 写迁移，ai-media 永远不会处理隐私记图片。负责人定的"隐私记参与"会被悄悄做丢，B4b 验收"搜证件能找出解锁后隐私记里的证件照"必然失败。
- **建议**：删掉这句注释。改成：插入时一律 `pending`；没同意或关了 `ai.vault` 的，由 ai-media 跳过，不写死成 skip。

**Z2　`note_files` 检查通过后，客户端仍能改 path、kind、bytes，绕过类型检查**
- **证据**：:2433 的列级授权让客户端能写 `path, thumb_path, kind, mime, bytes, sha256…`。附录 A 和 3.3 都没说这些列只能在插入时写，也没说改了以后 `check_status` 要回到 pending。
- **为什么**：先上传一个正常的 docx，等 `check_status = ok`，再 PATCH：
  - 改 `path`，指向另一个从没检查过的对象；
  - 或者把 `kind` 从 docm 改成 docx，让带宏的文件进入预览流程。
  
  file-check 不会再跑，于是"两道检查"被绕过。这一点同样适用于 `thumb_path`：它没有路径前缀约束，note_images 的 thumb_path 也一样。
- **建议**：
  - `path, thumb_path, kind, mime, bytes, sha256` 只授权 insert、不授权 update；客户端能 update 的只留 `name` 和 `deleted_at`；
  - 或者加触发器：这些列一变，`check_status` 就回到 pending；
  - `thumb_path` 加和 `path` 同样的前缀加正则约束；
  - 写明 `files` 桶不开放 update 和 upsert（和 images 桶一样），否则检查通过后还能原地覆盖文件内容；
  - RLS 测试加"检查通过后改 path / kind 被拒"。

**Z3　ZIP 炸弹防护只读声明的大小，而且读的位置写错了**
- **证据**：:1432-1440。file-check "用 Range 读对象开头 … ZIP 读中央目录"；炸弹防护按"解压后合计 ≤ 100 MB、压缩比 ≤ 100"判断。
- **为什么**：
  - ZIP 的中央目录在**文件末尾**，不在开头，Range 要从尾部读（结束记录在最后约 64 KB 以内）；
  - 中央目录里的解压后大小是文件**自己声明**的，可以作假，所以服务器这道只能拦"诚实的"炸弹；
  - 真正解压发生在**别的设备预览时**（docx-preview、SheetJS 都会解压），而 5.13 的防护只写在上传端。
- **建议**：
  - file-check 改成从尾部 Range 读；
  - 写明"预览时边解压边计数，实际解压量超过 100 MB 或单个条目超过上限就停"，在 `src/ui/preview/` 统一包一层，所有设备都过这一层；
  - 测试加"中央目录谎报大小的炸弹在预览端被拦"。

**Z4　每人存储上限只在客户端执行**
- **证据**：3.4（:867）和 5.13 第 1 点只写了"超了提示附件空间满了"；附录 A、3.3、file-check 都没有服务器端的合计检查。桶的 `fileSizeLimit` 只管单个文件。
- **为什么**：
  - 现在只有负责人用，风险小；
  - 但 `user_limits` 是为以后的朋友准备的，绕过客户端就能把 1 GB 写满，连负责人一起受影响；
  - 另外，客户端算"已经用了多少"要靠本机缓存，多台设备之间也不准。
- **建议**（任选一种，写进 3.3 和 5.13）：
  - file-check 通过时按 `sum(bytes)`（note_images 加 note_files，不算已删除的）对比上限，超了就按 rejected 处理并删掉对象；
  - 或者在 Storage 的 insert 策略里调用一个 security definer 函数检查合计。
  
  负责人上限为 700 MB 时这只是一行查询，成本很低。

**Z5　算向量（ai-embed）缺"哪些条目需要重算"的队列**
- **证据**：5.13 第 6 点只写"改内容时 sha256 和 `content_hash` 不一样，ai-embed 重算"，ai-embed 每 2 分钟跑一次。
- **为什么**：
  - 只靠 content_hash，就得每 2 分钟把这个人的全部随手记、图片、文档读一遍，逐条算哈希来比；
  - 隐私记还要逐条**解密**才能算哈希，频繁解密和"明文不落地"的原则相悖；
  - 2 万条时，这一轮还可能超出 Edge Function 的 2 秒 CPU；
  - 另外，`ai_status` 是 notes 原有的分类状态，5.13 说"move 时把 ai_status 改回 pending 让 ai-embed 重算"，等于让分类和嵌入共用同一个状态位，两者会互相干扰。
- **建议**：
  - 参照 `remind_queue`，加 `private.embed_queue(kind, source_id)`，由触发器在 title、body、body_enc、category、ai_desc、ai_tags、text_excerpt、name 变化时写入；
  - ai-embed 只处理队列里的条目；`content_hash` 留作去重；
  - 不复用 notes 的 `ai_status`；
  - "移进 / 移出隐私记"用一个 security definer RPC 在同一个事务里完成（Edge Function 用 supabase-js 做不了多条语句的事务）。9.7 已经要求"同一个事务"，但没写怎么做到。

**Z6　B4b 只给 12 人日，偏紧**（判断，不是事实）
- **证据**：:524 B4b = 12，合计 86（66 + 评审返工 17 + 韩文 3）。
- **为什么**：B4b 一批要做的事：

  | 内容 | 我的估计（人日） |
  |---|---|
  | 按内容判断类型（PDF、ZIP、OLE2）、file-check、炸弹防护（含 Z3 的预览端） | 2.5 |
  | 三个预览库、sandbox iframe、DOMPurify | 2 |
  | 微软在线预览和退路，含实测 | 1 |
  | 下载、MOTW、exe 另存（前端 B） | 0.5–1 |
  | ai-media | 1.5 |
  | pgvector、ai-embed（含 Z5 的队列）、note-search、隐私记移动 | 2.5–3 |
  | 两路查找结果合并的界面 | 1 |
  | 语音查找加兜底 | 1 |
  | 上限、备份、pull.ps1、导出 zip、注销 | 1–1.5 |
  | 验证项和测试 | 1.5 |
  | **合计** | **约 14–16** |

  另外，B1 的告知页文案、B7b 隐私说明 15.7 的改写、B7a 备份恢复演练加附件，都会多出少量工作，0.19 没算进去。
- **建议**：
  - B4b 取 15，合计约 89；
  - 或者把 B4b 拆成 B4b-1（附件和预览）和 B4b-2（智能查找和语音），分别签字。这样微软预览、pgvector 的实测结论可以先出，一批的验收也不会过大。

### 轻
- **L1　系统列清单没更新。** :703、:776 的系统列清单还没加 `ai_desc, ai_tags, ai_tries, ai_next_at, check_status`。如果 touch 触发器按这份清单判断"系统改动不加 rev"，ai-media、file-check 写回时会误加 rev，在其他设备上引发冲突提示（H9）。建议同步清单。
- **L2　`note_files.ai_status` 缺取值检查。** note_images 有 `check (ai_status in (…))`，note_files 没有（:2427）。
- **L3　上传顺序没写。** 文件上传完成后要立即调 file-check，但 note_files 那一行还在 outbox 里时，file-check 会找不到这一行，只能等 10 分钟后的 cron 补扫。建议写明"outbox 确认这一行以后再调 file-check"；上传成功但这一行一直没同步上的对象，算进孤儿清理。
- **L4　离线时加附件没写。** 建议写一句：离线时"加附件"按钮不可用，并提示"需要联网"（不把文件内容放进 IndexedDB 排队）；只能预览本机已经取过的内容。
- **L5　请求头没进跨域白名单。** note-search 的 vault_token 放在请求头里（:1606）。如果是自定义请求头（例如 `x-vault-token`），要加进 5.10 的 exe 跨域请求头白名单，否则 exe 解锁后的查找会在预检时失败。
- **L6　图片签名链接有效期前后不一致。** :454 总体图仍写"图片：私有，只发 10 分钟有效的链接"，5.13 定的是 60 秒（交给微软的是 5 分钟）。
- **L7　识图的 70% 让路实际上是一种上限。** ai-media 在全项目用量超过 70% 时让路，这样负责人"不设上限"实际上是"最多用到免费额度的 70%"。这样做合理（保证打字和录音有额度），不违背 D-9，但建议在 5.13 第 8 点写明，免得负责人以为可以用满。
- **L8　Web Speech 在主屏幕模式下的行为。** iPhone 主屏幕模式下 Web Speech 有不可用或行为异常的历史报告（我的了解，**需核实**）。如果真的不能用，R-113 的主路径就变成每次查找扣 1 次 AI 额度。退路已经有了，只是额度消耗会明显上升，建议写进风险 2。

## 四、确认没问题的部分
- 查找的退路完整：离线、没同意、额度用完、超时都退回本机关键词，"查找不能失败"写进了架构约定 9.7。
- note-search 只返回 id 和分数、按 JWT 里的人过滤；没解锁时一条隐私记都不返回。
- 不建 HNSW 索引、按人过滤后精确计算距离：在单人两万条的量级上，这个选择正确。
- 隐私记的图片描述加密存进 `vault_media_ai`，明文列为空，隐私记明文仍然不进 IndexedDB。
- 微软预览：iframe 加了 sandbox、不允许跳转顶层页面、不带来源信息，CSP 只多 `view.officeapps.live.com` 一个域名，exe main 窗口的 meta CSP 同步放行了这一个域名。
- 带宏的格式只存不预览、下载带 Mark-of-the-Web、exe 的 `save_attachment` 只认自己的签名链接：这些把负责人有意接受的宏风险压到了最低。
- 合计 1 GB 的告警线改成 80% 提醒、90% 紧急，理由成立，3.4、6.1、风险 14、ADR-018 四处一致。
- 用量表、每人上限的表、注销清理、备份范围，各章节之间互相一致。
