## 二、改动带来的新问题

### 中

**X1 exe 的 CORS 白名单不完整，exe 会跑不通**（5.10，1133 行）
- **允许的请求头缺了几项**：supabase-js 的登录模块会带 `x-supabase-api-version`；Storage 上传会带 `x-upsert`、`cache-control`；用非 public schema 时还会带 `accept-profile` / `content-profile`。白名单里没有这些，预检会失败，登录可能直接不通。
- **没写允许暴露的响应头（`Access-Control-Expose-Headers`）**：跨域时页面只能读到少数几个"安全"的响应头。
  - **`Date` 不在里面**，所以 4.x 的"用响应头 Date 校正时钟偏差"在 exe 里会失效；
  - PostgREST 计数用的 `Content-Range` 也读不到。
- **建议**：
  - 暴露 `Date, Content-Range, X-Supabase-Api-Version`，以及函数自己用的响应头；
  - 允许的请求头以 B6 抓到的真实请求为准，写成一张表；
  - B6 加一条验收：exe 里的时钟偏差校正生效。
- 补充：Cloudflare 免费额度超了时，默认错误页不带 CORS 头。exe 会收到一个"读不到原因"的网络错误，界面要按"同步失败"处理，不能卡住。

**X2 exe 里 Turnstile 的第三方脚本跑在有本机权限的窗口里**（5.10 的 CSP，1141 行；15.6 第 4b 条）
- **现状**：
  - `tauri.conf.json` 的 CSP 只有一条，作用于安装包里的**所有**页面，而这条 CSP 放行了 `https://challenges.cloudflare.com`。15.6 第 4b 条写的"exe 里同理"实际上做不到。
  - Turnstile 的 `api.js` 跑在顶层页面里，不在它自己的 iframe 里。
  - 登录页在 `main` 窗口里打开，而 `main` 窗口能调 `session_get`、`session_set`、`open_external`、自启和托盘等命令。
- **后果**：Cloudflare 的脚本一旦被篡改，或者 CSP 有漏洞，攻击者就能读走会话令牌，还能调本机命令。
- **改法（二选一）**：
  1. **推荐**：登录做成单独的 Tauri 窗口 `auth`，它的 capability 只给 `session_set`，主页面不加载 Turnstile；同时在 `main` 的 `index.html` 里加一条更严的 `<meta>` CSP。浏览器会同时执行 meta CSP 和 Tauri 注入的 CSP，取两者都允许的部分，这样 `main` 窗口就加载不了 challenges.cloudflare.com 的脚本。
  2. 直接采用 5.10 已经写的退路：exe 登录交给系统浏览器，用一次性码回到 exe。exe 里完全不加载第三方脚本。
- **附带要求**：`withGlobalTauri` 设成 false；B6 加一条验收"主窗口的控制台里，`window.__TAURI__` 不存在"。

**X3 CI 的"构建与部署分开"写得自相矛盾，Rust 依赖和签名缺规定**（8.3）
- **矛盾 1**：deploy-preview 和 deploy-prod 的部署步骤里，在拿到密钥之后**仍然有 `npm run build`**；而供应链第 ⑤ 条写的是"部署任务不跑 npm"。这两条要改成"部署任务只下载构建产物"。wrangler 用锁定的版本，从构建产物里带过去，或者由单独的锁文件安装。
- **矛盾 2**：desktop.yml 里，`tauri build` 会编译几百个 Rust crate，它们的 `build.rs` 能执行任意代码；而 Tauri 签名私钥在"updater 签名（production 环境）"这一步，没写清楚是不是同一个任务。如果是同一个任务，任何一个 crate 投毒都能偷走签名私钥。签名私钥一旦泄露，攻击者就能给所有 exe 推送恶意更新。
- **改法**：
  - 提交 `Cargo.lock`，构建时加 `cargo build --locked`；用 `cargo audit` 或 `cargo deny` 检查依赖漏洞，并把这一步加进 OSV 检查；
  - 编译放在没有密钥的任务里，只上传未签名的安装包；再开一个**不编译、只签名**的任务，放在 production 环境（需要批准）里拿私钥签名。

### 轻

- **X4 预览环境的 CLOUDFLARE_API_TOKEN 能部署正式站**：Pages 的令牌没法限定到单个项目。preview 环境里这把"Pages: Edit"令牌，可以对正式的 Pages 项目执行 `wrangler pages deploy`。现在 exe 不再加载远程页面，影响降低了，但网页版用户（包括 iPhone）仍然受影响。
  - 建议：预览站放到另一个 Cloudflare 账号；或者接受这个风险，在 8.4 写明。
- **X5 同意的几处尾巴**：
  1. **服务器只检查"同意过"，不检查"同意的是哪一版"**。`aiAllowed` 只看 `consent_ai_at` 不为空，不比对 `consent_policy_ver` 是否等于当前版本。隐私说明有实质改动（比如换了 AI 服务商）后，在朋友重新确认之前，服务器照样会把内容送出去。
     - 建议：`aiAllowed` 再加一个条件，`consent_policy_ver >= app_config.notice.min_consent_ver`。
  2. **在设置里打开"AI 整理"时**：如果 `consent_ai_at` 为空，必须先跳到告知页、勾选后再调 `record_consent`。不能只改 `ai.enabled`，否则服务器端不会生效；也不能悄悄调 RPC，那样同意不算数。架构和视觉稿都没写这一步。
  3. **签名不一致**：3.3 D 写的是 `record_consent(policy_ver)`，附录 A 是两个参数 `(policy_ver, revoke)`。要统一。另外写明：点"不同意"时调 `revoke=true`，`consent_policy_ver` 记的是"看过、拒绝了"的那一版。
  4. **负责人自己的账号**：服务器检查同意以后，负责人自己的账号也要有 `consent_ai_at`，否则 AI 会被关掉。15.5 写的"你自己的账号保持现状"要补一句：迁移脚本或 B1 给负责人账号写一条同意记录。
- **X6 Turnstile 加允许主机名 `tauri.localhost`**：所有 Tauri 应用的来源都是这个主机名，所以这一项起不到"确认是我们的 exe"的作用。CORS 白名单同理。这样写没问题，但要在 5.10 写明"这两项都不是身份校验"。
- **X7 备份放 E 盘**：E 盘也是 AI 工具的工作盘（Hunyuan3D 在 `E:\hunyuan3d`）。所以第 10 节要求的"下载后立即加密、删掉解压的明文"必须做到；BitLocker 只防硬盘丢失，防不住在本机运行的工具。建议只用 7-Zip AES 加密，不能二选一时只开 BitLocker。
