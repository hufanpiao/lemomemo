# 柠檬记 4.0.0 安全与隐私独立审查报告

**总体结论：不通过。** 数据库这一层（RLS、列级授权、private 白名单、存储路径约束）设计扎实。不通过的原因有三处：
- 官网对外的隐私文案与实际做法不符；
- 隐私记有明文残留；
- 登录防刷的落地方案有两处按现有写法做不出来。

另有若干处要在开放给朋友之前补上，否则不能对外开放。

（审查范围：架构设计-v4.md 全文、两份安全评审、账号注册清单、需求记录、皮肤视觉稿中相关文案、项目根目录的 .gitignore。只读，未改任何文件。我联网查了 4 份官方文档：Gemini 条款、Cloudflare `_headers`、Cloudflare 速率限制、Supabase CAPTCHA，只读文档，没有做任何探测。）

## 严重

**S1 官网和登录页写着"只有你自己能看到"，与实际做法不符**
- **证据**
  - 皮肤视觉稿.html:881 原文是"你记的东西只有你自己能看到，邀请你的朋友也看不到"。第 539 行写着"这一句需要产品负责人确认"，这句还没定稿。
  - 实际做法：
    - 隐私记由服务器用 VAULT_KEY 解密（架构 5.5，第 702–703 行）；
    - VAULT_KEY 由负责人保管，并且"手抄一份"（第 1077 行）；
    - 服务器备份按用户导出成明文 JSON，拉回负责人电脑（第 1011–1013 行）；
    - 文字、录音、隐私记都发给 Gemini 免费版，可能有人工审阅（第 855 行）。
- **后果**
  - 运营者（拿着 service role 和 VAULT_KEY）能看到所有朋友的全部内容，包括隐私记。
  - 对外写"只有你自己能看到"属于不实告知。PIPA 和中国个人信息保护法都要求如实告知。一旦出事，就是信任问题加合规问题。
- **改法**
  - 文案改成类似："其他用户看不到你的数据；为了提供服务，数据存在服务器上，运营者在技术上可以访问；隐私记在服务器上加密，但不是端到端加密。"
  - 隐私说明里写明：备份存放在运营者本机；录音、文字和隐私记会发给 Gemini。
  - VAULT_KEY 不要纸面手抄，只放进密码管理器，再离线加密存一份。

**S2 Gemini 免费版条款明确不让提交个人信息，并要求 18 岁以上，但朋友账号的隐私记默认送 AI，同意项还是默认勾选**
- **证据**
  - Gemini API 附加条款（ai.google.dev/gemini-api/terms，本次核对）原文："Do not submit sensitive, confidential, or personal information to the Unpaid Services."
  - 同一份条款还写着 "You must be 18 years of age or older to use the APIs"，并且不允许面向或可能被 18 岁以下人群使用的应用接入。
  - 架构第 1240–1243 行：朋友的 AI 同意"默认勾选"，`ai.vault` 默认开。第 1484 行：`ai.vault` 默认 true。
  - 需求记录 R-57 是负责人对**自己**账号的决定。
- **后果**
  - 违反服务商条款，有被停用 API 的风险。
  - 朋友的隐私记以及其中记下的他人信息，会进入谷歌可用于改进产品、可能人工审阅的数据池。
  - 默认勾选的同意，在 PIPA 和 PIPL 下大概率不算有效的"单独同意"（这是推断，需律师核实）。
- **改法**
  - 负责人自己的账号维持 R-57 不变。朋友账号的 `ai.vault` 默认关，AI 同意改成不预先勾选。
  - 或者开放给朋友前改用付费层：付费层不用于训练，也能和条款对上。
  - 条款里写明使用者须满 18 岁。
  - **这一条和负责人"隐私记也走 AI"的决定有冲突。是否改默认值，请负责人拍板，审查员不擅自降级。**

## 中

**M1 登录防刷：两种方案按现有写法都落不了地，验证码可能被刷**
- **证据 1**：第 1183 行写"Turnstile……不行就只在大陆以外开"。Supabase 的 CAPTCHA 是项目级开关，在控制台的 Auth 设置里打开，没法按地区只开一部分。如果只在前端跳过，攻击者直连 supabase.co 也就跳过了。
- **证据 2**：第 1183 行写"每个 IP 每 10 分钟 10 次（用 Cloudflare 免费版的 1 条速率限制规则）"。Cloudflare 官方：免费版的计数周期**只有 10 秒**，封禁时长 10 秒，只能按 IP 计数。所以"10 分钟 10 次"配不出来。
- **证据 3**：第 1198 行自己也承认，别人可以绕过 Worker 直连 supabase.co。直连时 Worker 的限流完全无效。
- **证据 4**：Supabase 文档没有写 CAPTCHA 是否覆盖 `verifyOtp`，**需核实**。如果不覆盖，6 位验证码在 10 分钟有效期内只受 Supabase 自身的 IP 限流保护，攻击者换着 IP 就能试。
- **后果**
  - 给用户邮箱发信轰炸，耗光 Resend 的额度。
  - 分布式猜验证码，接管账号，随后还能重设隐私记密码。
  - 架构里写了"调高发信频率上限"（第 725 行），这会把风险放大。
- **改法**
  - Turnstile 定为全局必开，作为 P0。大陆实测不通的话，就放弃方案 ②，重新选方案（例如自建一层 OTP 中继函数，用 Durable Objects 按真实 IP 和邮箱计数）。
  - 发信频率上限按实际用量设一个保守值，不要只往高调。
  - B1 实测三件事：直连 supabase.co 时 verify 接口的限流；是否有"每个邮箱最多试几次"的上限；`verifyOtp` 是否也要 captcha。

**M2 隐私记有明文残留：raw_text 等列，以及隐私图片**
- **证据**
  - notes 表的 check 约束只要求隐私记的 `body is null and title is null`（第 1455–1456 行），没有约束 `raw_text`、`tags`、`ai_meta`、`converted_to`。
  - 语音记的随手记，`raw_text` 里存着转写原文（第 905 行）。"移到隐私记"只写了"读出明文、加密写回"（第 717 行），没写清空 raw_text。
  - 隐私图片只是"挪到 vault-images 桶"（第 717 行），没有加密；本机每周还会同步全部图片（第 1014 行）。
  - `note_images` 的 lat、lng 是明文（第 1465 行）。
  - notes 的 select 策略不排除隐私记，所以这些列会同步到各设备的 IndexedDB 和每日备份里。
- **改法**
  - check 约束加上：`is_private` 时 `raw_text = '' and tags = '{}' and ai_meta is null and converted_to is null`。
  - vault import 时清空这些列，并补测试。
  - 隐私图片要么加密，要么在隐私说明里写明"图片不加密"。
  - 隐私记的图片不存定位。

**M3 邀请权限前后矛盾，匿名校验接口泄露邀请人**
- **证据**
  - 视觉稿第 793、816、881 行："请已经在用的朋友在'设置 › 邀请朋友'里发一个"。
  - 架构第 727、868 行：invite-admin **只有 private.admins 里的人**能用。
  - 视觉稿第 785 行："NEOX-7K2Q ✓ 有效 · 邀请人：胡"。这意味着有一个匿名的"实时校验邀请码"接口，会把邀请人的姓名返回给未登录的人。
  - 码长写法不一致：第 728 行写 8 位，视觉稿是 8 位，15.3 写的是 12 位、约 60 bit。
- **后果**
  - 开发者照视觉稿实现，就等于给所有用户开了邀请权限。
  - 校验接口能被拿来枚举邀请码，还会泄露邀请人姓名。
- **改法**
  - 请负责人定：谁能发邀请。改了要同步视觉稿和第 6 节。
  - 不单独提供匿名校验接口，只在 invite-signup 提交时校验，并要求 Turnstile。
  - 不返回邀请人姓名。
  - 码长统一为 12 位、32 个字符的字母表。

**M4 预览环境的 SUPABASE_ACCESS_TOKEN 可能能控制正式环境**
- **证据**：第 968 行，deploy-preview 用管理接口恢复暂停的项目；第 979 行，SUPABASE_ACCESS_TOKEN "preview、production 各一套"。
- **问题**：Supabase 的个人访问令牌通常是账号级的，能管这个账号下的所有项目，**需核实**能否限定到单个项目。如果不能，push 到 develop 就会运行的流水线里，拿着一把能改正式库、读 secrets 的令牌。
- **改法**
  - 正式和预览放到两个 Supabase 组织或账号下；或者只在需要审批的 production 环境里放管理令牌。
  - CLOUDFLARE_API_TOKEN 只给对应 Pages 项目的编辑权限。

**M5 本机备份放在项目目录里，开发用的 AI 代理会读到朋友的明文数据**
- **证据**
  - 备份路径是 `D:\claude code\待办APP\data\backups\`（第 192、1013 行），而这里就是开发工作区。
  - 备份加密列为 P2（第 1190 行）。
  - 拉取图片用的 S3 访问密钥放在哪里没写（第 1014 行）。Supabase 的 S3 密钥能访问全部存储桶，**需核实**。
  - BACKUP_PULL_TOKEN 是静态的全量令牌（第 882 行）。
- **后果**：朋友的日程、随手记、带定位的照片，会被 Claude Code 等工具读进上下文发到外部，等于又多了一条外传路径。令牌或密钥一旦泄露，就能拿到所有人的数据。
- **改法**
  - 开放给朋友前，备份挪到项目目录之外，并加密。
  - S3 密钥写进 8.4 的表里，放进凭据管理器，定期更换。
  - backup-manifest 返回的下载链接设成短时有效。

**M6 `.env.local` 实际没有被 git 忽略**
- **证据**：第 983 行写"`.env.local`（已在 .gitignore 里）"。但项目根目录的 `.gitignore` 里没有任何 `.env` 相关的规则。service key 临时就放在这里（第 774、982 行）。
- **改法**：在 `.gitignore` 加上 `.env*`，并加本地 pre-commit 的 gitleaks 检查。CI 里的 gitleaks 要等 push 之后才跑，那时已经晚了。

**M7 重设隐私记密码后，旧的 Face ID / Windows Hello 凭据和 vault_token 仍然有效**
- **证据**
  - 5.5 的重设流程（第 706–712 行）只换哈希、清零计数，没有清空 `vault_credentials`。
  - vault_token 是无状态的 HMAC，有效 10 分钟，"每次调用续期"（第 698 行），没有办法吊销。
- **后果**：用户怀疑被人动过才去重设，但攻击者之前绑上的生物识别凭据还能继续解锁。
- **改法**
  - 重设时清空全部 vault_credentials，并推送通知。
  - vault_token 里加一个 `pin_epoch`，重设或改密码时加 1，旧令牌随即失效。

**M8 Tauri：麦克风权限、外链和 WebAuthn 来源**
- **证据**
  - 第 805 行：在 Rust 端放行 WebView2 的麦克风权限请求，没写只对本 App 的来源放行。
  - location 链接在 exe 里怎么打开没写；capabilities 列表里没有 opener（第 1189 行）。
  - WebAuthn 的 RP ID 是 lemomemo.com，而 exe 的来源是 tauri 本地地址（第 701 行），服务器端可能被迫放宽 origin 校验。
- **后果**：外链如果在 App 的 WebView 内打开，外部网页也可能自动拿到麦克风。为了让 exe 能用，可能把 origin 校验放得太宽。
- **改法**
  - 权限回调只对 App 自己的来源放行。
  - 导航拦截：非本 App 的地址一律交给系统浏览器打开。
  - origin 白名单精确写出 exe 的来源，并补测试。

**M9 法务：开放给朋友之前缺的东西**
- **现状**：隐私说明、使用条款都是占位（第 1271–1272 行，视觉稿第 882 行）。
- **韩国 PIPA**（只列需要什么，未经律师核实）：
  - 公开个人信息处理方针，内容包括：
    - 目的、收集项目、保存期限；
    - 第三方提供（Gemini）和处理委托（Supabase、Cloudflare、Resend、苹果和微软的推送服务）；
    - 国外转移逐项写明：项目、国家、时间和方式、接收方及联系方式、目的、期限、拒绝方法；
    - 销毁程序；
    - 用户的权利和行使方法；
    - 安全措施；
    - 个人信息保护负责人的联系方式。
  - 必填项和选填项分开征得同意，并告知可以拒绝、拒绝的后果；不能预先勾选。
  - 未满 14 岁要法定代理人同意，建议直接限定 18 岁以上，正好和 Gemini 条款一致。
  - 发生泄露时的通知流程。
  - 用户记下的第三方信息（别人的生日、姓名）要在说明里写到。
  - "版本前、发布前的备份永久保存"（第 1021 行）要给出明确期限。
- **中国 PIPL**（对在中国境内的朋友适用；第 1247 行写着"未核实"）：
  - 处理规则要告知的事项（第 17 条）；
  - 向境外提供要单独同意，并告知境外接收方的名称、联系方式和行使权利的方式（第 39 条）；
  - 出境的合规路径（第 38 条；小规模可能有豁免，需核实）；
  - 个人信息保护影响评估（第 55 条）；
  - 照片定位属于"行踪轨迹"类敏感个人信息，需要单独同意，并说明必要性；
  - Gemini 在中国大陆属于不提供服务的地区，经首尔服务器转调是否符合谷歌条款，**需核实**。
- **使用条款至少要有**：服务说明（邀请制、免费、不保证可用）、年龄限制、用户对自己录入的他人信息负责、AI 输出不保证准确、账号停用和注销、免责与责任限制、条款变更、准据法。

**M10 账号接管面：换邮箱、匿名登录、`is_active()` 的判定**
- **需核实**
  - Supabase 是否开着"Secure email change"（新旧两个邮箱都要确认）。没开的话，拿到会话的人就能把账号邮箱改成自己的，永久接管。
  - 匿名登录必须保持关闭。
  - `private.is_active()` 必须写成"profile 存在且 disabled_at 为空"，不能写成"不存在 disabled_at"。否则没有 profile 的身份（例如误开的匿名用户）也算"活跃"。
  - claude-intake、vault 这些用 service role 的函数，也要检查 disabled_at：用户已停用但还没删完的这段时间里，不能再写入。
- **改法**：写进 B1 的验收，并加进 RLS 和函数测试。

## 轻

1. **safeHref 的实现方式**（第 796、998 行）：测试样例里有大小写和首尾空格，但没有 `java\tscript:`、`java\nscript:` 这类。URL 解析时会去掉制表符和换行，正则检查可能被绕过。
   - 改成 `new URL()` 之后检查 `.protocol`，并且用解析后的 href。
   - 补一条 check_arch：禁止 `innerHTML`、`outerHTML`、`insertAdjacentHTML`。现在只在 location 这一处写了不准用。
   - CSP 补上 `base-uri 'none'; form-action 'self'`，可以考虑加 Trusted Types。
   - 随手记正文会不会自动识别链接、会不会渲染 Markdown，文档没写，**需核实**；如果会，也要走 safeHref。
2. **Pages Functions 的响应不套用 `_headers`**（Cloudflare 官方原文）。`/` 的爬虫路径（返回 200，第 1326 行）和 `/sb/*` 的同源响应都拿不到 CSP 和 nosniff，而登录令牌就在同源的 localStorage 里。
   - Function 里自己加响应头。
   - `/sb/*` 统一加 `X-Content-Type-Options: nosniff` 和 `Content-Security-Policy: default-src 'none'; sandbox`。
   - Auth 的 Site URL 和 redirect 白名单只放 `https://lemomemo.com/app/`。
3. **api_tokens 可以"取消吊销"**：`grant update (revoked_at)`（第 415 行）允许把 revoked_at 改回 null。另外 profiles、api_tokens、app_config 三张表的 RLS 策略没有写出来（3.3 A 只列了别的表）。
   - 加触发器：revoked_at 只能从 null 改成 now()。
   - 把这三张表的策略逐条写进附录 A。
4. **邀请注册细节**：
   - invite-signup 在没验证邮箱时就 `createUser(email_confirm: true)`（第 731 行），拿到码的人可以用别人的邮箱占位并消耗邀请；
   - `used_count` 加 1 要用原子的条件更新，防止同一个码被并发用两次（**需核实**）；
   - 视觉稿第 784 行"这个邮箱还没注册"会暴露某个邮箱是否已注册。邀请制下影响小，可以接受，但要知道有这一点。
5. **Claude 代记钥匙**：范围（只能新增）、吊销、180 天过期、每天 200 条、链接不可点，都已到位。
   - 泄露后的影响：每天最多写 200 条垃圾或钓鱼提醒，推到锁屏；走 text 的话还会耗掉当天的 AI 次数。
   - 建议：经连接码写入的条目，推送文案里也标上"来自 Claude"（现在只在 App 里标）；最后使用时间异常时推送提醒。
6. **日志**：
   - 存储签名链接的 token 在查询串里，会进 Cloudflare 和 Supabase 的日志，有效期 10 分钟；
   - Worker 不要用 console 打印请求和请求头；
   - 关掉或确认 Cloudflare Workers Logs 的采集范围。
7. **注销后的残留**：Supabase 的 auth 审计日志、`private.invites.note`、`counters` 里按 IP 计数的键、`deleted_accounts`，以及 Resend、Cloudflare、Gemini 那一侧的数据。在隐私说明里写明保留情况，能清的定期清。
8. **域名和运维账号**：
   - 域名实际注册在阿里云（注册清单第 7–9 行），不是 R-73 建议的 Cloudflare。清单里缺：注册商锁（阿里云的"禁止转移锁"或"安全锁"）、DNSSEC（要在阿里云填 Cloudflare 给的 DS 记录）、阿里云账号的两步验证。另外阿里云有"暂停解析"这类监管风险，是可用性隐患。
   - Gmail 是所有账号的总钥匙，清单里应单独写"Gmail 开 Passkey 或两步验证"。
   - DMARC 建议最终设成 `p=reject`。
9. **会话**：免费版的刷新令牌不过期。"退出其他所有设备"只是 P1（第 1191 行），exe 会话存进凭据管理器是 P2。建议开放给朋友前两项都做完。
10. **推送默认带标题**（R-46）：朋友账号也是默认显示，要在隐私说明里写明，并提示可以关。
11. **claim_endpoint**：知道别人推送地址的人能把对方的订阅挤掉，造成收不到推送。推送地址本身不对外暴露，影响很小。
12. **exe 首个安装包没有代码签名**：SHA-256 公布在同一个站点上，站点被攻破时这层保护就没用了。之后可以考虑代码签名。

## 已确认处理好的部分

- 所有表开 RLS；策略统一写 `(select auth.uid())`；系统列靠列级 GRANT 收回；默认权限也收回；CI 里有 SQL 检查（public 里不能有 security definer，视图必须 security_invoker）。
- private schema 不对外暴露，函数执行权按白名单逐个放行；`*_impl` 和触发器函数固定 `search_path = ''`，只认 `auth.uid()`。
- `apply_patch` 是 security invoker，表名和列名走白名单，用 `%I`；applied_ops 用复合主键。
- 存储：私有桶，策略按路径第一段是不是 uid 来判断，不开 update；note_images 有复合外键和路径约束；桶限制 2 MB、只收 webp。
- Realtime：只订阅 INSERT 和 UPDATE，关闭公开频道，客户端忽略不认识的 id。
- Worker：路径白名单、先删后写 IP 请求头、不缓存 `/sb/`；文档明确说明所有限制不能只放在 Worker 上。
- 隐私记 PIN：HMAC 加 pepper、常数时间比较、逐级锁定；change_pin 必须带 vault_token 并共用失败计数；setup 只能执行一次；WebAuthn 校验项写全；重设看 amr 里 otp 的时间戳，不看 iat；明文不进 IndexedDB，不打日志。按逐级锁定估算，4 位 PIN 在线暴力破解要很多年。
- AI 防提示注入：用 `<data>` 标签隔开、模型不带工具、输出过白名单、user_id 只取自 JWT 或连接码、按用户分批、新分类有数量上限；Gemini 密钥放在请求头里；录音不落盘。
- 管理员身份放在 private.admins，客户端提不了权；管理员不能在 App 里注销；注销按"先停用、再删数据"的顺序，本机清理有三道保险。
- Tauri 更新包签名、私钥只放在需要审批的环境里、第三方 Action 固定 SHA、安装选"仅当前用户"。
- CSP（script-src 'self'、frame-ancestors 'none'）；SW 的 scope 是 `/app/`，不缓存 `/sb/`。
- 代码里没有 service_role（A14 加 gitleaks 检查）；`data/backups/*` 已被 git 忽略。
