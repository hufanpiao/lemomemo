## 高

**高 1：`touch()` 调 `table_meta_of()`，service_role、fn_vault、fn_ai 写表都会报权限错**
- 原文：架构 3895–3897（附A `touch()` 在 declare 里调 `private.table_meta_of(tg_table_name)`）、3962、3980（`usage on schema private` 和 `table_meta_of` 的执行权只给了 authenticated）、3985–3988；D1 规则在 1216 行。
- 依据：
  - `touch()` 不是 security definer，按调用者身份执行。触发器本身触发时不查权限，但函数里面调 `private.table_meta_of` 是普通调用，要求调用者对 private schema 有 USAGE、对这个函数有 EXECUTE。
  - service_role 两样都没有：白名单第一句就收回了 PUBLIC 的执行权，Supabase 的默认授权只覆盖 public schema。
  - fn_vault、fn_ai 有 USAGE，但没有 EXECUTE。
  - 后果：invite-signup 用 service role 建默认 settings、push-dispatch 写回 remind_at、vault 函数写 notes、fn_ai 写 note_images 的 ai_*，都会报 `permission denied`。insert 也一样，因为 declare 在 INSERT 时也会执行。
  - D1 又规定函数角色“不能执行 private 的 security definer 函数”，和“必须能执行 `table_meta_of`”直接矛盾。
- 建议：首选把 `touch()` 改成 `security definer`（它不依赖 current_user）。否则就补授 `usage on schema private to service_role`，以及 `table_meta_of` 对 service_role、fn_vault、fn_ai 的执行权，并在 D1 写明只例外这一个函数。B0 加一条用例：用 service_role 插一行 settings、用 fn_ai 改一行 note_images 的 ai_status。

**高 2：private 的函数授权白名单放不进 0001，“按 schema 收回默认权限”这句不起作用**
- 原文：架构 1403–1420 与 3964–3981（两处一字不差的白名单）、3983（“骨架写在 0001 末尾”）；数据字典第 28 行（2.1 写 0001 含“授权白名单”）。
- 依据：
  1. 白名单里有 `guard_note_file`（0004）、`enqueue_anniv_defaults`（0005）、`enqueue_embed`、`vault_ai_off`（0007）、`file_slot_open` 等后面文件才建的函数。整段放在 0001，`grant execute on function private.vault_ai_off()` 时函数还不存在，0001 直接失败。第 22 条“7 个文件一起部署”让这个问题必然出现。
  2. PostgreSQL 规定：按 schema 写的默认权限只能叠加在全局默认上，不能收回全局默认（函数的全局默认是 PUBLIC 可执行）。所以 `alter default privileges in schema private revoke execute on functions from public…` 是空操作，0002～0007 新建的函数照样对 PUBLIC 可执行，fn_ai、fn_vault 也能调。D1 会因此失败；就算没被 D1 拦住，也是越权。
- 建议：
  - 每个函数的 grant 写在建这个函数的文件里，“两处一字不差”的 CI 改成比对汇总后的结果；或者在最后一个文件末尾统一执行 `revoke execute on all functions in schema private from public…` 再逐个 grant。以后每个新迁移都要重复这一步。
  - 默认权限改成全局写法：`alter default privileges for role postgres revoke execute on functions from public;`。

## 中

1. **存储桶的限制只写在注释里，附录 A 没有对应 SQL**
   - 原文：架构 3956–3957 只对 images、vault-images 执行了 update；files、vault-files、vault-preview、backups 的 `fileSizeLimit` / `allowedMimeTypes` 只出现在 3.3 G 的注释里（1463–1468）。第 28 条（918 行）却写着“改在附录 A”。
   - 另外 update 的前提是桶已经存在；`db reset` 后桶不存在时，这条 update 悄悄更新 0 行。
   - 建议：附录 A 对 6 个桶都写成 `insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types) … on conflict (id) do update`，D1 再核对这些数值。
   - 实现时注意：supabase-js 上传 Uint8Array 时默认 contentType 是 `text/plain`，vault-files 必须显式传 `application/octet-stream`，否则会被桶的类型限制拒掉。backups 单个超过 50 MB 时怎么处理（报警或拆分）没写。

2. **counters 的键格式：用途名带冒号会错，全局计数没有位置**
   - 原文：916 行、3996 行，数据字典 530 行。
   - 依据：
     - 用途名写成 `ai:voice` 时，`split_part(key, ':', 2)` 取到的是 `voice`。结果是注销删不掉这些键，fn_ai 的策略也拒绝写入。而 LIKE `%:<user>:%` 照样能匹配上，于是清单核对和实际删除的结果对不上。
     - 窗口如果写成带时分的格式（如 `T10:00`）也有同样风险。
     - `embed_daily_global` 是“全项目计数”（2465 行），ai-media 还要看“全项目用量超过 70%”（2398 行）。这类全局键的第二段不是 user_id，fn_ai 的策略读不到也写不进。
   - 建议：给 counters 加约束 `check (key ~ '^[a-z0-9_]+:([0-9a-f-]{36}|ip|global):[^:]+$')`，写明用途名和窗口里不许有冒号。另定全局键 `<用途>:global:<窗口>`，并决定谁来写：给 fn_ai 单开一条只针对 `global` 的策略，或者交给 take_rate / service_role。

3. **关掉 ai.vault 以后再打开，没有恢复路径**
   - 原文：`vault_ai_off()` 在 3686–3700 行；2393 行写“以后条件满足再改回 pending”，但没有任何机制。
   - 依据：关掉时把 pending 改成了 skip，队列也删了。再打开以后既不会改回 pending，也不会重新入队，所以隐私记再也不会重新识图、重新算向量。重新同意 AI 也是同样的问题（record_consent_impl 把向量和队列全删了）。
   - 建议：加一个 `ai.vault` 改成 true 或重新同意时触发的入队函数（skip 改回 pending，把这个人的条目 upsert 进 embed_queue），或者明确写“不恢复，有意接受”，并配一条测试。

4. **第 17c 条的 `date_basis` / `confirm` 有三处不确定，测试期望值写不出来**
   - 原文：911、1684–1688、2805 行。
   - 问题：
     - ① AI 没给 `date_basis` 或给了 null 时按 `rel` 处理，等于静默保存过去的日子，违背 R-166 的“不替用户猜”。建议：有日期而 basis 缺失时，交给本机规则判断 basis，或者 `date` 早于今天就按 `md` 去问。
     - ② 待办的日子在 `due`、不在 `date`，“按今年算的日子”指哪个字段没写。
     - ③ AI 已经自己把年份推到明年（例如 `md` + 2027-10-30）时，“按今年算”是忽略 AI 给的年份、只取月日吗？“按今年算”或“按本月算”的那一天本身不存在时怎么办（非闰年的 2 月 29 日；11 月说“31 号”）？“下一年 / 下个月取最后一天”只覆盖了 next 一侧。
   - 建议：写明 `confirm` 只按 (今年, 月, 日) 或 (本年本月, 日) 计算、不看 AI 给的年月；past 那天不存在时只给 next、不弹选项；测试加上这三种情况。

5. **fn 角色在迁移里新建：重复执行会失败，D1 的“无成员”可能必然失败**
   - 原文：3985–3986。
   - 依据：
     - 角色是整个集群共用的，本地多次 `db reset`、或在已有角色的环境里重跑时，`create role` 会报“已存在”。
     - PG16 起，用 CREATEROLE 建角色的人会自动获得这个角色的 ADMIN 成员关系，和 1216 行 D1 的“无成员”冲突。
   - 建议：改成 `do $$ … if not exists (select from pg_roles where rolname = 'fn_vault') …`；D1 的“无成员”排除建角色时自动产生的那一条（B0 实测 Supabase 当前 PG 版本）。

## 二、service_role 缺口：属实；推荐 A，但要满足 5 个条件

**缺口属实，定为高。**
- 3.3 C（1448 行）只给了 authenticated 对 private 的 USAGE。
- service_role 只有 `take_rate` 一个函数的执行权，而且没有 private 的 USAGE，连这个函数其实也调不了。
- private 不在 API 暴露列表里，supabase-js 只能到 public。
- 结果：push-dispatch、invite-signup、ai-parse、各个定时任务、account 读写 private 的表都会失败。B0 跑不通。

**A 暴露 private 以后，anon 和 authenticated 能多做什么：架构师的说法基本成立。**
- anon 对 private 没有 USAGE，什么都做不了。
- authenticated 对 private 的表、视图都没有授权，访问一律 42501。它能多做的只是经 `/rest/v1/rpc` 加 `Content-Profile: private` 直接调白名单里的几个函数：`is_active`、`table_meta_of`、`file_slot_open`、四个 `*_impl`。效果都无害：
  - `*_impl` 和经 public 包装调用的效果完全一样；
  - `table_meta_of` 只泄露列名，不泄露数据；
  - `file_slot_open` 只认本人的路径。
- 一点附带影响：直接调 `*_impl` 会绕过转发层的版本检查，但 732 行已写明版本检查是兼容保护、不是安全措施，可以接受。

- 依据：第 98 条 ①⑤。触发器在"这台设备自己写"时把 session_id 填成写入者的会话。会话存不存在只在 insert 时查，update 不查。devices 的 update 策略是按 user_id 放行，同一个账号的所有会话都能改所有行。
- 后果：丢失的手机 L 在被移除之前，或者被移除后的 10 分钟内，对主人手机 P 那一行做一次 update（比如只改 `last_seen_at`）：
  1. P 那一行的 session_id 变成 L 的会话；
  2. L 的会话被吊销后，每日清理会把 P 那一行连同草稿密钥的盐、布局、推送订阅一起删掉；
  3. P 下次写自己那一行影响 0 行，按第 98 条的处理会"自己退出、丢弃没上传的改动"；
  4. P 的 `is_current_device` 也会判错：P 删不了自己那一行，却能对它调 remove_device，结果吊销的是 L 的会话。
- 等于说，被移除的设备能让主人的设备掉线、丢数据、收不到推送，正好违背这个功能的用意。
- 建议：
  - devices 的 update 策略收紧为"`session_id` 为空，或者等于 JWT 里的会话"，只有自己那一行能改；
  - 触发器在 update 时也查会话还在不在；
  - 设备行被别的会话占过之后，不能再"认领"：只允许 insert 新行，或者 service role 写；
  - vault 的 unlock 下发草稿密钥前，除了核对 device_id 属于本人，还要核对这一行的 session_id 等于当前会话。否则别的会话报出 P 的 device_id，就能拿到按 P 的盐推导的草稿密钥（虽然还要隐私记密码，但不该靠这一层兜底）；
  - 测试：L 改 P 那一行被拒（42501）；L 用 P 的 device_id 解锁，拿不到 P 的草稿密钥。

#### 中

**中 1　第 96 条的地区请求头能伪造**
- 现状：`x-lemo-geo` 由 `/sb/` 转发层写，交给函数用。但别人可以绕过转发层直连 supabase.co 调函数，自己带一个"首尔"之类的假地区。导出通知邮件就会显示假地点，降低本人的警觉。
- 建议：和 `x-client-ip` 同样处理。转发层先删掉、再重写这个头；函数只在 `x-proxy-secret` 对的时候才信它，否则写"未知地区"。测试并进 TC-B0-91。

**中 2　B1 实测失败时的退路大概率走不通**
- 现状：第 98 条的退路是"改成在 account 函数里加一个 action，用管理接口做"。但据我所知，GoTrue 的管理接口没有"按会话 id 删除某个会话"的功能，`admin.signOut` 要拿到那台设备自己的 JWT 才行（未核实，请 B1 一并确认）。另外，postgres 在 Supabase 上对 `auth` 这个 schema 的写权限可能受限，所以主路径（security definer 函数直接删 `auth.sessions`）本身也要实测。
- 建议：预先写好第三条路，用 Supabase Auth 的 **Custom Access Token Hook**：
  - 吊销时把会话 id 写进 `private.revoked_sessions`；
  - 这个钩子在每次签发和刷新令牌时，查到会话在这张表里就拒绝；
  - `requireActiveUser` 也查这张表。
- 这样刷新失败照样能做到，不依赖删 `auth.sessions`。

**中 3　600 秒令牌的副作用**
- **刷新限流**：经 Worker 转发后，所有人在 Supabase 看来是同一个 IP，刷新量大约是原来的 6 倍。按目前的人数离 Auth 默认的刷新上限还远，B1 实测时记下实际的刷新次数和上限。
- **队列遇到过期令牌**：iPhone 主屏幕版从后台回来时，令牌多半已经过期。outbox 必须先刷新再发；令牌过期返回的 401 不能计进 `tries`、不能进"发送失败"区。要加用例。
- **SW 里的通知按钮**：如果点通知上的按钮（"10 分钟后"等）时，SW 直接拿存着的令牌调接口，令牌经常是过期的。要么 SW 先刷新，要么点了以后打开页面再处理。请写明是哪一种。
- **推送和 cron 不受影响**：它们用的是服务器的密钥。离线不受影响：refresh token 不会过期，联网后就能刷新。

**中 4　requireActiveUser 怎么查 `auth.sessions` 没写**
- 现状：`auth` 这个 schema 不经 PostgREST 暴露，函数里的 supabase-js 查不到它。
- 建议：
  - 写明用一个 `private.session_alive(uuid)` 的 security definer 函数，只把执行权给 service_role；
  - 或者用中 2 的 `revoked_sessions` 表；
  - 把它补进 3.3 C 白名单和 D1 的比对。
- 每个函数调用多一次查询，耗时可以接受。

#### 低

1. 每日清理只删"session_id 不为空、但会话已不在"的行。session_id 为空的旧行（service role 建的、或者升级前留下的）永远清不掉，建议设备列表里也标成"已退出"。
2. 第 98 条的 a / b 选项：从安全上我支持 a（被移除的设备退回登录页）。b 等于丢了的手机照样能看全部数据，失去了移除设备的意义。
3. 第 94、95、97 条已确认落实：两个错误码按原因区分，客户端用穷尽的 switch 处理；验收账号不进 admins、永远不放正式数据，清点三项；正式环境的测试账号先核对不在受保护名单和 admins 里，测完正常注销，并在下一次拉取后核对。

### 要加的测试（交 QA）

- 中 1：绕过转发层伪造 `x-lemo-geo`，通知邮件写"未知地区"。

- 函数立即生效：吊销后马上调 vault、account、AI 函数，都返回 `session_revoked`。

### 结论：有条件通过，8.0 / 10

### 一、上一轮意见的落实情况
- **高 1（任何会话都能改别的设备那一行）：已落实**（第 99 条）。

  - 新函数和新表进了 3.3 C、附录 A 和 D1；

- **中 3（600 秒令牌的副作用）：已落实**（第 102 条）：刷新限流要 B1 实测；outbox 发之前先刷新，令牌过期的 401 不计 `tries`；SW 不拿存着的令牌调接口。

### 二、新问题

#### 高

**高 1　重新验证邮箱会换出新会话，这台设备从此改不了自己那一行**
- 依据：隐私记重设，以及选了 b 时的明文导出（第 83 条 b、第 92 条 a），都要求"`amr` 里的验证码在 10 分钟以内"。要满足这一点，只能再走一次 `verifyOtp`，而 GoTrue 的 `verifyOtp` 会**签发一个新会话**，新的 session_id 和这台设备那一行记的不一样。（注销虽然也要重新验证，但注销后设备本来就清空，不受影响。）
- 按第 99 条的写法，接下来会这样：
  - 这台设备 update、delete 自己那一行都被拒，`last_seen_at` 也写不进；
  - vault 下发草稿密钥时回 `device_mismatch`，**刚重设完隐私记，这台设备的草稿功能就坏了**；
  - 旧的那一行还占着推送地址，而旧会话还活着，claim_endpoint 回 `endpoint_in_use`，**这台设备收不到推送**；
  - "不许移除本机"判错：设备列表会把本机的旧行当成"另一台"，用户能对它调 remove_device，吊销的是自己旧的会话。
- 建议：架构写明"同一台设备拿到新会话时怎么交接"，二选一：
  - **a.** 重新验证成功后，客户端先用旧会话调 `signOut({scope: 'local'})` 吊销旧会话，再换一个新的 device_id 插入新行。旧行由每日清理删掉（旧会话已不在），推送地址也就能认领了；
  - **b.** 新增一个 RPC `rebind_device(p_device_id)`：只有当旧行的会话已经不在，或者调用方同时证明它持有旧会话时，才允许把那一行改到新会话名下。
- 无论哪种，都要补测试：重设隐私记后，同一台设备的草稿密钥、推送、设备列表都正常。

#### 中

**中 1　推送地址被"活着的旧行"占住，用户没有出路**
- 情形：断网时退出登录（TC-B4b3-42 ③），旧行留着、旧会话也还活着；重新登录后换了新的 device_id，claim_endpoint 回 `endpoint_in_use`，这台设备一直收不到推送。
- 只回 `endpoint_in_use` 对安全是对的，但用户不知道发生了什么。
- 建议：客户端收到 `endpoint_in_use` 时，提示"推送地址被设备 X（已退出的旧记录）占着"，提供"移除它"（走 remove_device，会吊销那个旧会话）。另外补一条测试：断网退出、再登录、移除旧行之后，推送恢复。

**中 2　第三条路（Custom Access Token Hook）的失败方式要写清**
- **钩子返回的错误客户端认不认**：supabase-js 只把 `session_not_found`、`refresh_token_not_found` 当成"已退出"。钩子返回别的错误时，它可能当作临时故障不停重试，被移除的设备就既不退回登录页、也不清空本机。要写明钩子返回什么错误码、客户端怎么识别（进第 94 条那张穷尽处理的错误码表），并加测试。
- **钩子出错会挡住所有人**：钩子查询慢或报错时，所有人都登录不了、刷新不了。钩子只按主键查 `revoked_sessions`，B1 实测时同时测"钩子报错时的表现"，写进 B1 记录。
- **执行权要收干净**：按 Supabase 文档，钩子函数要显式 `revoke execute … from authenticated, anon, public`，D1 核对除了 `supabase_auth_admin` 没有别人能执行。

**中 3　SW 的 `pending_actions` 仓要进本机清理和清单**
- 现状：这是新加的本机仓，但退出登录、被移除、注销时的清空范围（4.1）、数据清单的本机仓、TC-DEL-idb 都还没有它。换账号时前一个账号按过的键可能被后一个账号的 data 层发出去。服务器会按 RLS 拒绝，不会改到别人的数据，但会留下垃圾请求和错误日志。
- 建议：
  - 把它加进清单（`rebuildable: false`）、4.1 的清空范围和 TC-DEL-idb；
  - 每一项记下 user_id，和当前账号不一致的直接丢弃；
  - 超过 24 小时的直接丢弃，免得几天后才把"10 分钟后提醒"执行掉。

#### 低

1. **设备表会慢慢变长**：每次重新登录都新增一行。正常退出、被移除、"退出其他所有设备"都有清理，问题在于设备被丢弃或本机存储被系统清掉的情形：旧会话永远活着，那一行永远不会被清掉。建议每日清理再加一条：`last_seen_at` 超过 180 天的行，先吊销会话再删，并在设备列表上提示。增长很慢，不影响安全。
2. **草稿密钥不受影响**：换 device_id 不会打乱草稿密钥。退出时本机草稿本来就清空，新 device_id 配新的盐，旧盐跟着旧行删。
3. **电脑布局每次重新登录都会丢**：布局设置键是 `layout.<页>@dev:<device_id>`，换了 device_id 就找不到原来的布局。这是功能上的代价，不是安全问题，请产品经理知悉；如果要保留布局，可以改成按"设备名加平台"迁移。

### 二、你特别问的三处

**rebind_device 能不能被滥用：不能。**
- **只拿到新会话 S2**（能收邮件的人）：没有这一行当前会话的令牌，交接不了任何设备行。
- **只拿到旧会话 S1**（偷了手机）：拿不到 10 分钟内刚验证过的 S2，交接不了。
- **两样都有**（手机被偷，而且手机上的邮件 App 没锁）：只能交接被偷那台自己的行，交接后吊销的是自己的 S1，得不到任何新东西。
- **和主人的移除操作同时发生**：移除时按这一行当前的会话吊销。先交接再移除，吊销的是 S2；先移除再交接，行已经删了，交接失败。两种顺序都安全。

**钩子出错时放行：可以接受，但要补两条（见中 1）。**放行影响的范围：只在走第三条路、而且钩子正好出错时，被吊销的会话能继续刷新，靠 REST 读写的时间超过 10 分钟。真正要守的门是函数里的 `session_alive` 和 devices 触发器，它们必须在出错时拒绝。如果改成钩子出错就拒绝，钩子一出问题，所有人都登录不了。权衡下来放行是对的。

**install_id 的隐私代价：可以接受。**
- 它只是一个随机数，只有运营者（service role）能把同一个浏览器上的两个账号对上。运营者本来就看得到 IP，install_id 没有新增能识别人的信息；客户端按 RLS 只能看到自己的行。
- 建议 15.7 第 1 项"设备信息"补上"安装标识（随机数）"。

### 三、新问题

#### 中

**中 1　放行要有两个配套**（第 106 条）
- **函数和触发器必须在出错时拒绝**：`requireActiveUser` 调 `session_alive` 时，超时或报错要回 `session_revoked` 或 `try_later`，不能放行。devices 触发器同理。
  - 原因：让钩子出错的往往是数据库本身的问题，这时 `session_alive` 也会出错；两道门都放行，就没有门了。
  - 要加测试：让 `session_alive` 抛错，带 JWT 的函数一律拒绝。
- **钩子出错要能被发现**：现在只写了 `raise warning`，没人会看。建议出错时计数（写 counters 或 heartbeat 的 detail），lemo-ops 在 15 分钟内出现任何一次就发邮件告警。否则"放行"可能悄悄持续很多天。

**中 2　没有设备行的会话在设备列表里看不到，remove_device 也管不到**
- 情形：凡是能收到验证码邮件的人，都能新建会话，但不插 devices 行（比如自己写脚本只登录、不注册设备）。rebind 失败后，如果客户端没能用 S2 退出，留下的 S2 也是这样一个没有行的会话。这类会话在设备列表里看不见，remove_device 也无从下手。
- 建议：
  - 设置的设备列表下方，用 `auth.sessions` 和 devices 对比，显示"另有 N 个登录没有设备记录"，旁边放"退出其他所有设备"按钮；
  - 这个对比要新增一个 security definer 函数，只返回本人的会话数和最近时间，执行权给 authenticated，补进 3.3 D 白名单；
  - 或者至少在 15.7 写明"可疑时请用退出其他所有设备"。

#### 低

1. **给放行开关加一道身份核对**（第 104 条）：`devices_session_guard()` 只看 `lemo.rebind` 这个设置等不等于本行 id 就放行改 `session_id`。建议同时要求当前身份是函数主人（`current_user = 'postgres'`，也就是只在 `rebind_device_impl` 这个 security definer 函数里）。这样即使以后哪条路径让客户端能设这个值，也绕不过去。B1 已有"`/rest/v1/rpc/set_config` 被拒"的用例，再加一条：以 authenticated 身份设这个值后改 session_id，被拒。

### 二、你要我判断的两处

**1. 低 1 的改法：对。**
- 我原来的建议确实不起作用。`devices_session_guard()` 是 security definer，触发器里的 `current_user` 永远是函数主人，所以这个条件恒为真。
- 改成核对 `current_setting('role', true) = 'service_role'` 是对的：
  - PostgREST 是用 `set local role` 切换到请求角色的；security definer 只改 `current_user`，不动 `role` 这个设置，所以触发器里读到的仍是请求角色。
  - authenticated 不是 service_role 的成员，没法把 `role` 设成 service_role。
  - 所以即使以后哪条路让客户端能设 `lemo.rebind`，也绕不过这一关。
- 备用方案（改读 JWT 里的 role）同样安全，因为 JWT 是签名过的，客户端伪造不了。
- B1 实测这一步要保留。另外实测时请确认一点：account 函数是经 PostgREST 调 `rebind_device_impl` 的。如果改成直连数据库，`role` 会是 `none`，交接会一律失败。
  - 这属于"拒绝"方向的失败，不会造成安全问题，但要写进 B1 记录，免得开发时误以为是 bug 而放宽条件。

**2. 第 110 条回 503 `try_later`：对。**
- 拦住被移除会话靠的是"拒绝这次请求"，回 503 已经做到了。
- `session_revoked` 还会让客户端清空本机。数据库一抖就让所有人丢掉没上传的数据，代价不对等。
- 唯一要守住的一点：客户端收到 `try_later` 后，只能暂停并退避重试，不能把它归进第 106 条"其他 4xx 重试一次仍失败就清空本机"那一类。503 属于 5xx，按第 110 条写法本就归临时故障。建议加一条测试：连续收到 `try_later`，本机不清空，重试间隔按退避递增。

### 三、低级问题（开发时补上，不影响通过）
1. **15 分钟告警用的却是按小时计的键**（第 1020、4017 行）
   - 问题：键是按小时计的，lemo-ops 判断不出"最近 15 分钟有没有新计数"，同一小时前面的计数会被重复看到。
   - 建议：二选一。要么记下上一轮读到的值，本轮比它大才告警；要么把键改成 15 分钟一档。"同一小时只发一封"要用一个标记记住，写明记在哪里（比如 counters 里再放一个 `hook-alert:<小时>` 键）。
2. **最需要告警的情况，计数本身也会失败**
   - 问题：钩子出错多半是因为数据库有问题，这时 `note_hook_error()` 往 counters 加 1 也会失败，失败又被吞掉，于是不会告警。
   - 建议：在 15.x 运维说明里写明"数据库整体出问题由 lemo-ops 心跳失败告警兜底"，并确认心跳确实会因为查不到数据库而告警。
3. **`note_hook_error()` 没写 `set search_path = ''`**（数据字典第 643 行）
   - 建议：和其他 security definer 函数一致，补上。D1 检查 security definer 函数时也要把它算进去。
4. **`my_sessions()` 刚登录时可能短暂多算一个**（第 111 条）
   - 问题：别的设备刚登录、还没插 devices 行的那几秒，会被算成"没有设备记录的登录"，用户可能被误导。
   - 建议：`orphan_count` 只算创建超过 2 分钟的会话。测试里加一条：刚登录 10 秒内不显示。
