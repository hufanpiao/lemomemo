## 高

**高 1：`touch()` 调 `table_meta_of()`，service_role、fn_vault、fn_ai 写表都会报权限错**
- 原文：架构 3895–3897（附A `touch()` 在 declare 里调 `private.table_meta_of(tg_table_name)`）、3962、3980（`usage on schema private` 和 `table_meta_of` 的执行权只给了 authenticated）、3985–3988；D1 规则在 1216 行。
- 依据：
  - `touch()` 不是 security definer，按调用者身份执行。触发器本身触发时不查权限，但函数里面调 `private.table_meta_of` 是普通调用，要求调用者对 private schema 有 USAGE、对这个函数有 EXECUTE。
  - service_role 两样都没有：白名单第一句就收回了 PUBLIC 的执行权，Supabase 的默认授权只覆盖 public schema。
  - fn_vault、fn_ai 有 USAGE，但没有 EXECUTE。
  - 后果：invite-signup 用 service role 建默认 settings、push-dispatch 写回 remind_at、vault 函数写 notes、fn_ai 写 note_images 的 ai_*，都会报 `permission denied`。insert 也一样，因为 declare 在 INSERT 时也会执行。
  - D1 又规定函数角色“不能执行 private 的 security definer 函数”，和“必须能执行 `table_meta_of`”直接矛盾。
- 建议：首选把 `touch()` 改成 `security definer`（它不依赖 current_user）。否则就补授 `usage on schema private to service_role`，以及 `table_meta_of` 对 service_role、fn_vault、fn_ai 的执行权，并在 D1 写明只例外这一个函数。B0 加一条用例：用 service_role 插一行 settings、用 fn_ai 改一行 note_images 的 ai_status。

**高 2：private 的函数授权白名单放不进 0001，“按 schema 收回默认权限”这句不起作用**
- 原文：架构 1403–1420 与 3964–3981（两处一字不差的白名单）、3983（“骨架写在 0001 末尾”）；数据字典第 28 行（2.1 写 0001 含“授权白名单”）。
- 依据：
  1. 白名单里有 `guard_note_file`（0004）、`enqueue_anniv_defaults`（0005）、`enqueue_embed`、`vault_ai_off`（0007）、`file_slot_open` 等后面文件才建的函数。整段放在 0001，`grant execute on function private.vault_ai_off()` 时函数还不存在，0001 直接失败。第 22 条“7 个文件一起部署”让这个问题必然出现。
  2. PostgreSQL 规定：按 schema 写的默认权限只能叠加在全局默认上，不能收回全局默认（函数的全局默认是 PUBLIC 可执行）。所以 `alter default privileges in schema private revoke execute on functions from public…` 是空操作，0002～0007 新建的函数照样对 PUBLIC 可执行，fn_ai、fn_vault 也能调。D1 会因此失败；就算没被 D1 拦住，也是越权。
- 建议：
  - 每个函数的 grant 写在建这个函数的文件里，“两处一字不差”的 CI 改成比对汇总后的结果；或者在最后一个文件末尾统一执行 `revoke execute on all functions in schema private from public…` 再逐个 grant。以后每个新迁移都要重复这一步。
  - 默认权限改成全局写法：`alter default privileges for role postgres revoke execute on functions from public;`。

## 中

1. **存储桶的限制只写在注释里，附录 A 没有对应 SQL**
   - 原文：架构 3956–3957 只对 images、vault-images 执行了 update；files、vault-files、vault-preview、backups 的 `fileSizeLimit` / `allowedMimeTypes` 只出现在 3.3 G 的注释里（1463–1468）。第 28 条（918 行）却写着“改在附录 A”。
   - 另外 update 的前提是桶已经存在；`db reset` 后桶不存在时，这条 update 悄悄更新 0 行。
   - 建议：附录 A 对 6 个桶都写成 `insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types) … on conflict (id) do update`，D1 再核对这些数值。
   - 实现时注意：supabase-js 上传 Uint8Array 时默认 contentType 是 `text/plain`，vault-files 必须显式传 `application/octet-stream`，否则会被桶的类型限制拒掉。backups 单个超过 50 MB 时怎么处理（报警或拆分）没写。

2. **counters 的键格式：用途名带冒号会错，全局计数没有位置**
   - 原文：916 行、3996 行，数据字典 530 行。
   - 依据：
     - 用途名写成 `ai:voice` 时，`split_part(key, ':', 2)` 取到的是 `voice`。结果是注销删不掉这些键，fn_ai 的策略也拒绝写入。而 LIKE `%:<user>:%` 照样能匹配上，于是清单核对和实际删除的结果对不上。
     - 窗口如果写成带时分的格式（如 `T10:00`）也有同样风险。
     - `embed_daily_global` 是“全项目计数”（2465 行），ai-media 还要看“全项目用量超过 70%”（2398 行）。这类全局键的第二段不是 user_id，fn_ai 的策略读不到也写不进。
   - 建议：给 counters 加约束 `check (key ~ '^[a-z0-9_]+:([0-9a-f-]{36}|ip|global):[^:]+$')`，写明用途名和窗口里不许有冒号。另定全局键 `<用途>:global:<窗口>`，并决定谁来写：给 fn_ai 单开一条只针对 `global` 的策略，或者交给 take_rate / service_role。

3. **关掉 ai.vault 以后再打开，没有恢复路径**
   - 原文：`vault_ai_off()` 在 3686–3700 行；2393 行写“以后条件满足再改回 pending”，但没有任何机制。
   - 依据：关掉时把 pending 改成了 skip，队列也删了。再打开以后既不会改回 pending，也不会重新入队，所以隐私记再也不会重新识图、重新算向量。重新同意 AI 也是同样的问题（record_consent_impl 把向量和队列全删了）。
   - 建议：加一个 `ai.vault` 改成 true 或重新同意时触发的入队函数（skip 改回 pending，把这个人的条目 upsert 进 embed_queue），或者明确写“不恢复，有意接受”，并配一条测试。

4. **第 17c 条的 `date_basis` / `confirm` 有三处不确定，测试期望值写不出来**
   - 原文：911、1684–1688、2805 行。
   - 问题：
     - ① AI 没给 `date_basis` 或给了 null 时按 `rel` 处理，等于静默保存过去的日子，违背 R-166 的“不替用户猜”。建议：有日期而 basis 缺失时，交给本机规则判断 basis，或者 `date` 早于今天就按 `md` 去问。
     - ② 待办的日子在 `due`、不在 `date`，“按今年算的日子”指哪个字段没写。
     - ③ AI 已经自己把年份推到明年（例如 `md` + 2027-10-30）时，“按今年算”是忽略 AI 给的年份、只取月日吗？“按今年算”或“按本月算”的那一天本身不存在时怎么办（非闰年的 2 月 29 日；11 月说“31 号”）？“下一年 / 下个月取最后一天”只覆盖了 next 一侧。
   - 建议：写明 `confirm` 只按 (今年, 月, 日) 或 (本年本月, 日) 计算、不看 AI 给的年月；past 那天不存在时只给 next、不弹选项；测试加上这三种情况。

5. **fn 角色在迁移里新建：重复执行会失败，D1 的“无成员”可能必然失败**
   - 原文：3985–3986。
   - 依据：
     - 角色是整个集群共用的，本地多次 `db reset`、或在已有角色的环境里重跑时，`create role` 会报“已存在”。
     - PG16 起，用 CREATEROLE 建角色的人会自动获得这个角色的 ADMIN 成员关系，和 1216 行 D1 的“无成员”冲突。
   - 建议：改成 `do $$ … if not exists (select from pg_roles where rolname = 'fn_vault') …`；D1 的“无成员”排除建角色时自动产生的那一条（B0 实测 Supabase 当前 PG 版本）。

## 二、service_role 缺口：属实；推荐 A，但要满足 5 个条件

**缺口属实，定为高。**
- 3.3 C（1448 行）只给了 authenticated 对 private 的 USAGE。
- service_role 只有 `take_rate` 一个函数的执行权，而且没有 private 的 USAGE，连这个函数其实也调不了。
- private 不在 API 暴露列表里，supabase-js 只能到 public。
- 结果：push-dispatch、invite-signup、ai-parse、各个定时任务、account 读写 private 的表都会失败。B0 跑不通。

**A 暴露 private 以后，anon 和 authenticated 能多做什么：架构师的说法基本成立。**
- anon 对 private 没有 USAGE，什么都做不了。
- authenticated 对 private 的表、视图都没有授权，访问一律 42501。它能多做的只是经 `/rest/v1/rpc` 加 `Content-Profile: private` 直接调白名单里的几个函数：`is_active`、`table_meta_of`、`file_slot_open`、四个 `*_impl`。效果都无害：
  - `*_impl` 和经 public 包装调用的效果完全一样；
  - `table_meta_of` 只泄露列名，不泄露数据；
  - `file_slot_open` 只认本人的路径。
- 一点附带影响：直接调 `*_impl` 会绕过转发层的版本检查，但 732 行已写明版本检查是兼容保护、不是安全措施，可以接受。
- A 真正增加的风险有两样：
  1. **以后谁误给 private 授了权，就立刻能从公网访问**（现在有“不暴露”这一道垫底）；
  2. **service key 一旦泄露**，能经 HTTP 读到 private 里授给它的表。

**A 的 5 个条件（都写进 3.3 C 和 D1）：**
1. 给 service_role 的逐表授权**不含** vault、vault_credentials、device_secrets、vault_ai、vault_preview、note_vectors、embed_queue。这几张表仍然只经 fn_vault、fn_ai 直连访问；注销时靠级联删除，再由 fn_vault 删第二道（2804 行已经是这么写的）。这样 service key 泄露也碰不到密码哈希和草稿密钥盐。
2. D1 加一条：private 里每张表、每个视图对 anon、authenticated 的实际权限必须为空；对 service_role 的授权和白名单逐项比对，多一项就失败。在控制台暴露 schema 时，不要点系统建议的“授权”。
3. B0 实测 pg_graphql 有没有把 private 反射出去（没用 GraphQL 就关掉它，或者核对它看不到 private）。
4. 确认 PostgREST 的 authenticator 角色不是 fn_vault、fn_ai 的成员，这样带 `role: fn_ai` 的令牌也切换不过去。现有 D1 的“无成员”规则已能保证，写进测试即可。
5. RLS 测试（架构已列）再加两项：经 `/rest/v1/rpc` 调 private 里不在白名单的函数被拒；读四个扫描视图被拒。

**为什么不推荐 B：**
- B 只多挡住一种情况：service key 泄露后读写运维表（remind_queue、counters、invites 等）。可 service key 本来就能绕过 RLS 读写所有用户在 public 里的数据，多这一层收益很小。
- 代价是 B0 +1.5～2 人日，跨用户的定时任务还要按用户拆事务，出错面反而更大。
- 如果负责人想要更严：可以考虑 **C**——private 仍不暴露，另建一个只暴露给 service_role 的窄接口 schema（放 security definer 函数，不放表）。代价大约在 A 和 B 之间。
