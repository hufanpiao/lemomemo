### 交架构师定的一项：exe 自动更新没有测试环境
**定案：加预览更新通道，不留到上线后再测。**

**为什么不能留到上线后**
- 自动更新是上线后远程修 exe 的唯一办法。0.27 里，版本过低时 exe 的横幅也是交给 Rust 端的更新检查去处理。
- 4.0.0 的更新器要是有问题，装好的 exe 全部卡在旧版，只能让用户手动重装。这种错误发出去以后，没法远程补救。

**具体做法（B6-exe，前端 B ＋ 运维）**
1. 预览环境的 Pages 下放 `/desktop/latest.json`。预览版的 exe 编进**预览公钥**和预览的更新地址；正式版只编进正式公钥和正式地址。
2. 预览签名私钥照正式私钥的规矩，由负责人本人运行脚本生成，只写进 GitHub 的 preview 环境。产品负责人待办的 B6-exe 节加一项，约 10 分钟。
3. desktop.yml 加一条检查：编进去的公钥和更新地址必须和当前环境一致。正式包里出现预览公钥，或者预览包里出现正式公钥，就让任务失败。这样不会把一个永远收不到正式更新的 exe 发给用户。S-B6 也加核对这一条。
4. B6-exe 的验收用例：
   - 装 `4.0.0-preview.1`，发布 `preview.2` 后能自动更新（核对 8.5 带 `-preview.N` 后缀的版本按 semver 排序）；
   - 包被改过、验签失败时拒绝安装；
   - `latest.json` 里的版本比本机低时不降级；
   - 断网时安静失败、不打扰用户；
   - 收到 426 后，"更新"按钮走 Rust 端的更新检查。
5. 正式那条线上线前测不了，作为剩余风险记进风险表：上线后发第一个修复版（4.0.1）时，在负责人的电脑和 QA 的机器上验证"4.0.0 → 4.0.1"能自动更新，写进上线与回滚手册的上线后跟进项。
