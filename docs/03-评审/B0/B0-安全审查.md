## 二、意见

### 中

**中 1：TC-B0-35 / S-B0 ⑦ 要求的 CI 静态检查没有做**
- 位置：`build/`、`unit.yml`、`ci.yml`、`deno.json` 里都没有这项检查。`supabase/functions/_shared/db.ts` 头注释写着“谁能 import 本文件……由 CI 管（TC-B0-35）”，但实际上没有任何脚本在管。B0 R2 任务单里也没有把“只有九个函数引用 `_shared/objstore.ts`”分给人。
- 风险：B1 起函数陆续写进来，没有门禁拦以下三种情况：
  - 某个函数直接读 `SUPABASE_DB_URL`，用 postgres 超级权限绕开 fn_vault / fn_ai 的会话变量版 RLS；
  - 规定以外的函数 import `_shared/db.ts`；
  - 规定以外的函数 import `_shared/gen/objstore.ts` 或读 `R2_FN_*`，这把令牌能读写四个桶，含 `vault-*`。

  这正是定向复核 A 和 0.32 S-B0 ⑦ 要防的事。B0 现在还没有函数，所以暂时没有暴露，但 P0 机制缺失。
- 建议（B0 内补，约 0.25～0.5 人日，后端或运维）：
  1. 在 `check_arch.py` 或单独的脚本里，扫 `supabase/functions/**`（不含 `_shared/`），满足三条：
     - 不出现 `SUPABASE_DB_URL`；
     - import `_shared/db.ts` 的函数目录在 6.2 的白名单里，并且用的角色和白名单一致；
     - import `_shared/gen/objstore.ts`，或出现 `R2_FN_ACCESS_KEY_ID` / `R2_FN_SECRET_ACCESS_KEY` 的函数，在“九个函数”的白名单里。
  2. 加三份违规样例，放在 `tests/arch-fixtures/`，证明拦得住。
  3. 接进 `unit.yml`。白名单唯一出处写在架构 6.2，任务单补一行归属。

**中 2：`tools/release/publish.ps1` 第一版和 0.31 第 24 条不一致，冻结前要改的几处**（归 B6-exe，B7a 冻结前复审；本轮不阻塞 B0，列进 S-B7 必查）
- 位置：`publish.ps1` 第 231～259、120～127、344～348、290～299 行；`release-build.yml` 头部注释。
- 风险：
  1. 发布机在同一个窗口、令牌粘贴前跑 `npm ci` 和 `vite build`，项目依赖和 Vite 插件的代码会在这台机器上执行。它们可以留下常驻进程，等令牌粘贴时再读剪贴板或进程内存。0.31 第 24 条选方案 A，理由正是这一点。
  2. 三把令牌写进本进程的环境变量后，**每个子进程都继承全部三把**：wrangler 拿到数据库密码和 Supabase 令牌，`supabase.exe` 拿到 Cloudflare 令牌。不符合最小权限。
  3. 第 6 步用 `Copy-Item shared\*` 复制，而不是 `npm run copy:shared`，不会把 `zod`、`aws4fetch` 改写成 `npm:…@版本`。结果是部署的函数和 CI 测过的不是同一份（推测：会直接部署失败或解析到别的版本）。
  4. 检查只看进程名和剪贴板历史，没有像 `tools/keys/*.ps1` 那样查 transcript、模块日志、脚本块日志策略。
  5. `release-build.yml` 头注释还写“publish.ps1 在本机从同一个 tag 构建”，和已定的方案 A 矛盾。
- 建议：
  - 按 0.31 第 24 条改成“下载 CI 产物，逐个核对 SHA256SUMS”，发布机不跑项目代码。
  - 每个子进程只给它要的变量。可以用 `Start-Process` 带独立环境，或调用前设、调用后立即清。
  - 函数目录改用 CI 产物里已经 `copy:shared` 过的那一份。
  - 检查项和 keys 脚本对齐。
  - 同步改掉 `release-build.yml` 的注释。

### 低

**低 1：`/sb` 的拒绝名单可以用百分号编码绕过**
- 位置：`functions/sb/[[path]].ts` 的 `upstreamPath`。实测下面两条返回的都是非 null，会被转发：
  - `https://x/sb/rest/v1/rpc/files%5Fauthorize`
  - `https://x/sb/auth/v1/%61dmin/users`
- 风险：小。
  - `files_authorize` 只能问到本人的路径，最多烧掉自己的限流计数；
  - admin 接口要 service key；
  - Cloudflare 边缘的 URL 规范化很可能已经把这类非保留字符解码了（推测，没实测）；
  - `wrangler pages dev` 不做这种规范化。
- 建议：
  - 先把路径里百分号编码的非保留字符（字母、数字、`-._~`）解码，再比白名单和拒绝名单；或者除 `%20` 这类确有需要的以外，一律拒绝 `%`。
  - 加两条单测。
  - 预览上用 `curl` 实测一次边缘行为。

**低 2：objstore 允许非回环地址用 `http://`**
- 位置：`shared/objstore.ts` 的 `createObjStore`，正则是 `^https?://`。
- 风险：`R2_ENDPOINT` 配错成 http 时，`UNSIGNED-PAYLOAD` 的请求体会明文传输、可以被篡改。SigV4 本身不泄露 secret。
- 建议：主机不是 127.0.0.1、localhost 或 ::1 时，要求必须是 `https`。

**低 3：`deletePrefix` 不要求前缀形如 `<uuid>/`**
- 位置：`shared/objstore.ts`。
- 风险：以后调用方少写了 `/`，或传了更短的前缀，会删掉超出范围的对象。现在 user_id 都是 36 位，暂时不会撞。
- 建议：断言前缀以 `/` 结尾；R2 桶上再要求它以 `^[0-9a-f-]{36}/` 开头。注销和清理都按这个写。

**低 4：`/files` 有两处细节不一致**
- 位置：`functions/files/[[path]].ts` 的 `onRequest`，以及 `_lib/cors.ts`。
- 问题：
  1. `onRequest` 里 `storeFor()` 抛错的那条分支，回的 500 没有安全头，也没有 CORS。
  2. `/files` 的预检和 `/sb` 共用 `ALLOW_METHODS`，带了 `PATCH`、`DELETE`。
- 风险：很小。
- 建议：异常分支改用 `err()`；`/files` 的预检只给 `GET, PUT, POST, OPTIONS`。

## 五、gitleaks 目录模式：决定

**不放宽 `.gitleaksignore`。门禁只用 git 模式**：pre-commit 用 `gitleaks git --pre-commit --staged`，CI 用 `gitleaks git --log-opts=--all`。

- 现象：`gitleaks dir .` 报 2 处，都是 a14 的同一个假密钥。
  - `tests/arch-fixtures/check_arch/a14-secret/src/core/bad.ts:2`
  - 低 9 那个 worktree 里的副本。

  目录模式的指纹是“文件:规则:行”，不带提交号，所以 `.gitleaksignore` 里那行“提交:文件:规则:行”对它不生效。
- 理由：
  1. 只按“文件 + 行”放行，以后这一行改成真密钥，目录模式也会一起放过。这违背 `.gitleaksignore` 自己写的“只放行这一次提交”。
  2. git 模式已经覆盖暂存区和全部历史，正是要防的“进仓库”这条路。目录模式多扫的只是 `.gitignore` 里的东西和 node_modules，那不是门禁的职责。
- 以后确实要扫工作区（例如发布前扫 `dist/web`）时，只对那个目录用 `gitleaks dir dist/web`；不对仓库根目录用目录模式，也不为它加放行行。
