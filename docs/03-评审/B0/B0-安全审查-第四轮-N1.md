## 一、触发器能不能堵住第三轮描述的路径

触发器是 `before insert or update on auth.users for each row when (coalesce(new.encrypted_password, '') <> '')`，函数体只有 `new.encrypted_password := ''`。它挡在**数据库写入这一层**，和走哪个接口无关：只要某条路径最终要把密码哈希写进 `auth.users.encrypted_password`，就被置空。GoTrue 只有这一列存密码（`auth.identities`、`auth.mfa_factors` 都不存可用于 `grant_type=password` 的口令）。

| 路径 | 结论 | 依据 |
|---|---|---|
| `PUT /auth/v1/user {password}`（第三轮描述的主路径） | **堵住** | GoTrue 改密是对 `auth.users` 的 UPDATE，触发器按 NEW 判断，不管 UPDATE 带了哪些列。后端实测：去掉触发器时设密码 200、库里有哈希、`grant_type=password` 回 **200 拿到令牌**（后门在本地复现）；恢复后设密码仍 200、库里为空、密码登录 **400 `invalid_credentials`、无令牌**。探针 ⑦ a～c 正是这三步 |
| admin 接口：`POST /admin/users {password}` / `{password_hash}`、`PUT /admin/users/{id} {password}` | **堵住（按构造）** | 分别是 INSERT 和 UPDATE，和 pgTAP ②①同一形状。探针没单测 admin 改密（见 L4，提示级）。另外实测发现 **admin 建用户不传密码时 GoTrue 自己生成随机密码**，触发器把它也置空——这证明 0.36 选“置空、不报错”是对的：报错会让 invite-signup 建不出人 |
| 直接 SQL（SQL 编辑器、迁移、`service_role` 经 PostgREST 不可能写 auth schema） | **堵住普通写入** | pgTAP ①② 以 postgres 跑 UPDATE / INSERT 都被置空，并证明过去掉触发器会失败（Failed 2/59）。能绕过的只有 `session_replication_role = replica` 或 `alter table … disable trigger`，需要库的高权限凭据——拿到这个的人已经能做任何事，不在威胁模型内（L4 建议 D1 每次核对触发器在且启用，防的是以后某个迁移误删） |
| INSERT 与 UPDATE | **都覆盖** | `before insert or update`，不写 `update of encrypted_password`——GoTrue 用 ORM 更新时不保证单列，整行 update 也要触发；`when` 条件让平常的 update（登录写 `last_sign_in_at`、改 metadata）几乎零开销。探针 ⑦ d 证明改 metadata 照常 200、不误伤 |
| 置空串 vs null | **空串正确** | GoTrue 的用户模型把 `encrypted_password` 当可空字符串，“有没有密码”按非空判断；它自己给无密码用户写的就是空串，旧版模型读 null 会出错。空哈希比对必然失败，实测回 400 `invalid_credentials`（和“密码错”同一错误，不泄露“此账号没有密码”）。原本是 null 的行 `when` 不成立、不动，也正确 |
| recovery（`POST /recover` → 邮件链接 / 码） | **不是写密码的入口；后续写入被堵** | recovery 本身就是一次邮箱验证（等价于验证码登录，同受发信限频），拿到的会话 `amr` 是 recovery / otp，不是 password；之后若 `PUT /user {password}` 就落回第一行。它不构成绕过验证码 |
| reauthenticate（`GET /reauthenticate`） | **不写密码** | 只发一个改密用的 nonce；`secure_password_change = false` 时根本不用。即使将来打开，最后写密码仍是 UPDATE，被堵 |
| signUp（`POST /signup {email, password}`） | **两道都挡** | `[auth] enable_signup = false`（`GOTRUE_DISABLE_SIGNUP`）使 `/signup` 在写库前就回 422；万一配置被误开，新用户是 INSERT、已存在的未确认用户重注册是 UPDATE，触发器都置空 |
| 其他：`/admin/generate_link type=signup {password}`、`/invite`、手机密码登录、第三方 / SSO / Web3 | **覆盖或不适用** | generate_link 建人是 INSERT；手机登录关着（且同一列）；config 里没有任何 `[auth.external.*]`；匿名登录关 |
| **触发器之前已经存在的密码** | **不覆盖（见 L1）** | 触发器只在写入时生效。本地每次 `db reset` 从零开始、没问题；托管预览项目若在 `db push` 前已经有人在控制台用密码建过用户，那一行的哈希会留着，直到下一次被写（而第一次密码登录本身就会成功） |

**小结**：第三轮 N1 描述的路径（拿到 access token → 设密码 → 随时 `grant_type=password` 建新会话）在本地真库上被证明“去掉触发器能打通、加上触发器打不通”，判据是库里的值和密码登录的结果，而不是接口回码——做法正确。

## 二、security definer / invoker、search_path、执行权

| 要确认的 | 结论 | 依据 |
|---|---|---|
| definer 还是 invoker | **invoker，正确** | 函数只改 `NEW`，不读不写任何表，不需要提权。用 definer 反而多一个 Security Advisor 关注点。GoTrue（`supabase_auth_admin`）触发它时以 invoker 身份执行，没有可借的权限 |
| `search_path` | **合规** | 带 `set search_path = ''`，函数体不按名字找任何对象（连 `pg_catalog` 函数都没调），没有被同名对象劫持的面；Security Advisor 的 `function_search_path_mutable` 不会报。D1“每个 security definer 必须带 search_path”那条对 invoker 不要求，带了也无害 |
| 执行权 | **合规** | 0001 第一句 `alter default privileges for role postgres revoke execute on functions from public`，迁移以 postgres 建这个函数，所以 PUBLIC、anon、authenticated 都没有执行权（D1 `FUNCTION_EXEC` 白名单不用动，正好要求“谁都没有”）。触发器触发时 PostgreSQL 不检查执行者对触发器函数的 EXECUTE 权（只在 `create trigger` 时查建者），也不查 `private` 的 USAGE（按 OID 调用）——**实测佐证**：探针 ⑦ b 里 GoTrue 以 `supabase_auth_admin` 做 UPDATE 回 200 且库里被置空，若缺权限会是 500。即使将来有人误授执行权，触发器函数被直接调用也只会报“只能作为触发器调用”。没写 `revoke … from public` 所以 3.3 C、附录 A、M4 不涉及，和 0.36 原文一致 |
| 函数能否被篡改 | **不能** | 属主 postgres，在 `private`；客户端角色在 `private` 没有 CREATE / USAGE |
| 失败模式 | **可接受** | 函数体是一句赋值，不会抛错；`auth.users` 上的 before 触发器若抛错会让所有 Auth 写入失败（fail closed），这里不存在这种风险 |
| 离线桩加 `encrypted_password varchar(255)` | **无安全影响** | 和真库列类型一致，只为让 0001 在 PGlite 上建得出触发器 |

## 三、托管版不让挂触发器时的退路

**已写清，不回头卡 B0。** 架构 0.36 第 1 条写明：以第一次预览 `db push` 为准、查 `pg_trigger`；不让建就把同样的判断放进已设计好的 `private.access_token_hook`（`authentication_method = 'password'` 或 `amr` 含 password → 403 `password_login_disabled`），负责人开 Auth Hooks，N1 改在 B1 关，“不回头卡 B0”；实测清单 P13 和 TC-B1-112 ⑤ 都对上了这条退路。判断：Supabase 官方“管理用户数据”文档的 `handle_new_user` 就是在 `auth.users` 上挂触发器、函数放在自己的 schema，托管版不让建的可能性很低。

两处可以补一句（L2、L3 的一部分），都不影响 B0 签字：

- **push 失败时 0001 整体回滚**：`supabase db push` 每个迁移文件在一个事务里，`create trigger` 被拒会让整个 0001 不生效，预览项目一张表都没有。P13 目前只写“记下原文告诉架构师”。建议补：架构师拍板后，后端把这两句（函数和触发器）从 0001 挪出（0001 没推成功，可以直接改），先把其余 B0 推上去，钩子留 B1。否则“不卡 B0 签字”成立，但“预览部署”会被卡住。
- **退路比主路径弱一点**，记在这里给 B1：钩子只拦签发，密码仍存在库里；而 0.29 续第 106 条定的是钩子内部出错时**放行**（fail open）。对“拒密码会话”这一判断，出错放行就等于放过密码登录。若真走退路，B1 那时请把 password 判断放在 `exception` 块之外（或对它单独 fail closed），并靠 ② 的 `amr` 纵深兜底。
