**中 3：对象存储的请求没有超时**
- 位置：`shared/objstore.ts` 第 205～231 行（`send`）；调用方 `functions/files/[[path]].ts` 第 91、139 行
- 问题：`files_authorize` 有 2 秒超时（`files-authorize.ts` 第 149～159 行），版本门有 1.5 秒，但 `ObjStore` 的每个请求（put、get、head、list、deleteMany）都没有 `AbortSignal`，`ObjStoreConfig` 也没有超时参数。R2 或替身卡住时，`/files` 的 GET、PUT 会一直挂着，客户端只能等自己的 60 / 120 秒超时；以后 storage-sweep、account-purge 经 `deletePrefix` 翻页列、批量删，一次卡住就整步卡住，不会走“报错重试”。
- 为什么：关注点里的“错误处理和超时”；注销是 P0 流程（3.4、第 6 节 account-purge 要“不为 0 就整步报错重试”），卡住比报错更难发现。
- 建议：`ObjStoreConfig` 加 `timeoutMs`（默认例如 list / delete / head 10 秒、put / get 拿到响应头 30 秒），`send` 里用 `AbortController`，超时抛 `ObjStoreError('network')`（或新码 `timeout`）；GET 只给“拿到响应头”计时，流式响应体不计；单测用一个永不返回的假 fetch 覆盖。

### 低

1. **非 200 的响应体没读也没取消**（推测会影响 Deno 测试和连接复用）。`shared/objstore.ts` 第 233～236、313～314、321～322、329～330 行：`fail(res)` 和 `get`、`head` 回 404 时直接返回或抛错，不读 `res.body` 也不 `cancel()`。Deno 的测试有资源泄漏检查，打真替身时可能报 leak；undici 下连接也回不到池里。建议在 `fail` 和 404 分支先 `await res.body?.cancel?.()`（或读掉 `text()`）。
2. **`deletePrefix` 不强制前缀以 `/` 结尾**。`shared/objstore.ts` 第 338～346 行只拦空前缀。现在的 user_id 都是定长 uuid，传 `<uid>` 不带斜杠也不会删到别人，但这是靠调用方自觉；account-purge、storage-sweep 都会用它。建议 `checkPrefix(pfx, false)` 之外再要求 `pfx.endsWith('/')`，测试里加反例。
3. **附件缩略图的查找用不上主键索引**。`supabase/migrations/0004_attachments.sql` 第 171～173 行 `f.note_id::text = … and f.id::text = …`（头像那段第 154～155 行同样）：把 uuid 列转成文本再比，主键索引用不上，只能靠 `(user_id, synced_at)` 索引把这个人的 note_files 一行行过滤；一次 sign 最多 100 项，每项各扫一遍。行数上限是每表 2 万行，量不大时影响有限（没跑 EXPLAIN，量级是推测）。建议改成按整条路径查：缩略图的原文件路径是 `left(p, -7)` 加 `.` 加 kind，kind 未知时可以用 `f.path like left(p, -7) || '.%'`（path 有唯一索引，前缀 like 在 `text_pattern_ops` 下能用索引），或者把文本转 uuid（正则已保证 36 位，再包一层异常处理）。
4. **同一个“桶不对”在 PUT 里有两种回法**。`functions/files/[[path]].ts` 第 56 行本地判断是 `403 forbidden` 带 `reason: bad_bucket`，第 80～82 行 RPC 回 `bad_bucket` 时是 `400 bad_path`；sign 里两种都是单项 `reason: bad_bucket`。客户端都归成 `denied`，不影响行为，但架构 14.2 第 11 点的错误码表要只有一种写法。建议统一成一种，并在注释里写明。
5. **`onRequest` 建 store 出错的那条 500 没带安全头和 CORS**。`functions/files/[[path]].ts` 第 218～223 行，和第 212～215 行、`files-http.ts` 第 2 行注释“每个响应都带 /files 的安全头和 CORS”不一致。建议复用第 212～215 行的写法。
6. **客户端的超时只管到响应头**。`src/platform/files.ts` 第 199～209 行在 `doFetch` 返回后就 `clearTimeout`，`fetchBlob` 第 297 行读 10 MB 的 `res.blob()`、`upload` 读 JSON 都不在超时里。慢网下读体卡住不会变成 `retry`。建议把计时器留到读完响应体再清，或者给读体单独计时。
7. **`/sb` 的拒绝名单可以用百分号编码绕过**（推测，未实测）。`functions/sb/[[path]].ts` 第 97～98、116 行：`PATH_CHARS_RE` 放行 `%`，`SUSPICIOUS_PATH_RE` 只拦 `%2e %2f %5c %00`，所以 `/sb/rest/v1/rpc/%66iles_authorize`、`/sb/auth/v1/%61dmin/users` 过得了 `DENIED_PREFIXES`；PostgREST、GoTrue 收到后会把路径解码。影响按架构 0.32 第 11 条是“无害”（files_authorize 只能问到自己的，admin 要 service key），而且 Cloudflare 入口的 URL 规范化很可能先把 `%66` 解成 `f`；但 S-B0 ⑧ 是 P0 验收项，代码本身不该依赖区域设置。建议：拒绝名单前先把路径按段 `decodeURIComponent` 再比（解码失败就拒），或者 `/rest/v1/`、`/auth/v1/` 下一律不许出现 `%`；`sb-proxy.test.ts` 加这两条反例。
8. **`note_images` 的 insert 不查随手记是不是隐私记**（推测，交架构定，可能属于 B4 / B5）。`0004` 的 `guard_note_file()` 拦“挂到隐私记上”，`0003` 第 104～105 行的 `note_images` insert 策略只要求 `bucket = 'images'`。客户端可以把 `bucket = 'images'` 的图挂到 `is_private` 的随手记上，`files_authorize` 会照常放行上传，之后 ai-media 会把它当普通图处理、描述写明文列。只影响本人自己的数据，但和附件那边的规矩不对称。建议架构师确认后补一个和 `guard_note_file()` 同口径的触发器。
9. **附件 file-check 已经把状态改成 ok 以后再重传，会回 403 not_pending**（推测，取决于 B4b-1 的调用顺序）。`src/platform/files.ts` 第 224～228 行只把 `409 exists` 当成功。如果上传成功但响应丢了，而 file-check 在客户端重试之前已经把 `check_status` 改成 `ok`，重试会拿到 `forbidden / not_pending` 并被归为 `denied`（不再重试），界面会以为失败。B4b-1 接页面时要么约定“file-check 由客户端在上传成功后才调”，要么把 `not_pending` 在附件上传场景下也当成“已存在”。
10. **注释和代码不一致**：`functions/index.ts` 第 1 行仍写“_routes.json 只让 `/` 和 `/sb/*` 进 Functions”（已加 `/files/*`）；`shared/objstore.ts` 第 4 行、`tests/shared/objstore.test.ts` 第 246 行仍写替身是 MinIO（运维 O-1 选了 LocalStack，`docker-compose.objstore.yml` 第 8 行写了原因）；`ci.yml` 第 87 行见中 2。
11. **架构规则样例只核对规则名，不核对是哪一条**。`tests/arch/eslint.test.ts` 第 50～54 行只看 `ruleId`（例如 `no-restricted-imports`）。同一个规则 id 下挂了 A1、A12、A19、R2 等很多条模式，样例可能被“别的一条”拦住也算过。建议样例头加一个可选的 `message=` 片段（比如 `A19`），测试里同时比对 `message`。
12. **重复的小工具**：原始 URL 取路径的写法在 `functions/files/[[path]].ts` 第 26～46 行和 `functions/sb/[[path]].ts` 第 104～118 行各一份；“读满 N 字节拼成 Uint8Array”在 `files-upload.ts` 第 28～36 行、`files-sign-route.ts` 第 21～49 行各一份。建议挪进 `functions/_lib/` 一处共用，免得以后只改了一边。

### 各人之间的接口（files.ts ↔ /files ↔ files_authorize ↔ objstore）

逐项对过，**一致**：
- 入参：`/files` 发 `{p_op, p_items: [{bucket, path}]}`，`0004` 第 97 行同名参数；put 1 项、get ≤ 100 项，两边一致（sign 本地也限 100）。
- 返回：`{uid, items: [{i, ok, reason?}]}`、整批 `{uid, error, items: []}`；`files-authorize.ts` 第 119～135 行要求 items 个数等于请求数、i 不重复，和 SQL 第 137～189 行逐项按 ordinality 输出对得上。
- 错误码：`account_disabled` → 403 `forbidden` 带 reason、`session_revoked` → 401 `unauthorized` 带 reason、`rate_limited` → 429、22023 → 400；`src/platform/files.ts` 第 129～140 行按 reason 把前两种归成 `account`，和架构 14.2 第 11 点、任务单 FA-2 一致。
- 路径正则：清单 → `functions/_generated/files-rules.ts` → `files_authorize_impl`，由 `check:files-rules` 和 D1（含违规样例 21）双向核对，都在跑。
- 签名链接：服务端 `signedUrl` 的形状和客户端 `checkSignedUrl` 第 96～120 行对得上；`d` 用 `encodeURIComponent` 编码、GET 解码，来回一致；文件名清理后再签，签名串里不会混进换行。

## 做得好的地方

- **`files_authorize_impl` 写得扎实**：security definer、`search_path = ''`、没有动态 SQL；先查停用和会话、再限流、再逐项判断，单项不过不连累整批；“先写行再传”比原来的 `img_ins` 更严；路径正则和清单逐字核对。pgTAP 51 条覆盖了跨用户、头像 avatar_id、vault 桶、pending / ok / rejected、30 天“最近删除”、百分号和 `..`、大写十六进制、结尾换行、101 项、限流按人按操作分开，**而且在离线 PGlite 上真的跑通了**。
- **`/files` 函数的安全细节到位**：路径用原始字符串判断；便宜的检查（类型、长度、webp 头）放在调数据库之前；写 R2 前再比一次 `uid`；HMAC 用 `crypto.subtle.verify` 常数时间比较、签名长度先卡 43 位；“签名对但有效期超 600 秒”也拒；GET 带 `sandbox` CSP、`nosniff`、`no-store`；日志只有错误码和耗时，有专门测试。
- **测试是真的在测**：TC-B0-111 把桶、路径、e、d、s 各改一处，最后再用原链接取一次证明 200（排除“什么都 403”的恒真）；SigV4 用 AWS 官方样例向量核对，不依赖不验签的 LocalStack；D1 每个违规样例都断言了具体的报错文字；注销 runner 还检查“造的数据有没有覆盖每一段路径”，防止“删完为 0”是因为本来就是 0。
