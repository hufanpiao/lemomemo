## 结论：不通过，1 条必改

## 一、下载失败时，浏览器推送订阅还在不在

- **认领记录不受影响**：`forgetPushClaim()` 在下载之前同步执行、不抛错（FA2-1 照旧满足），测试第 23 行钉住了。
- **下载失败时会留下两样东西**：
  - 浏览器的推送订阅（没退订）；
  - 通知中心里已经显示的旧通知（没关掉）。
  失败会记一条 `push_disconnect_fail`（code 是 load），只有错误类型，不带账号信息。
- **实际多容易失败**：
  - SW 预缓存收了全部带哈希的 JS 分块（`inject_sw_manifest.mjs` 只排除 holidays、fonts、map 等），所以只要 SW 装好了，push.ts 的分块离线也能从缓存取到。新版本部署以后，旧页面在新 SW 接管之前用的也是旧缓存。
  - 会真的失败的情形：SW 还没装好的第一次访问、浏览器禁用了 SW（比如 Firefox 隐私窗口）、开发模式、缓存损坏。这些都比较少见，但不是零。
- **和改动前比**：原来静态引入，不存在“下载失败”这一种情况；现在多了这一种，而它的后果正是 FE-2 要防的两件事。见建议 S1。

## 二、服务器上的 devices 行会不会让下一个账号收到上一个账号的推送

**不会。**
- 退出流程第 ① 步按会话删 devices 行，和推送断开无关，下载失败也照样删。所以在线时，即使订阅还在，服务器也不会再给这个 endpoint 推上一个账号的提醒。
- 离线退出，而且 ① 删行和下载都失败时，旧账号的推送还会到达这台设备，有两层兜着：
  - SW 显示前核对 owner（FE-1）：本机库已清，owner 对不上，只显示 App 名，不显示标题和正文；
  - 下一个账号登录后认领同一个 endpoint 时会换绑（claim_endpoint，FA2-2），旧账号的推送从此到不了这台设备。
- 所以下一个账号**看不到**上一个账号的提醒内容。最多是在换绑之前，收到几条只写 App 名的空通知。

## 三、退出流程是否在任何分支都能完成

- 下载抛错、断开抛错、日志通道自己抛错：都被接住，`disconnectPushLazy` 正常返回（测试第 23、39 行）。调用处的 `wipeThisDevice`、`account.ts` 的 `disconnectPush` 外面还各包了一层 try。
- **下载一直不回（没成功也没报错）时，不能完成**。`disconnectPushLazy` 用的是 `await load()`，没有任何上限；原来那个 2 秒上限在 `disconnectBrowserPush` 里面，模块还没下载到时根本走不到。草稿目录里的探测：用永不返回的 load，5 秒后仍然没有结束。
- 调用处 `wipeThisDevice` 和 `account.ts` 都是直接 `await`，外层也没有总超时（`useSessionExit.ts`、`useAccountGate.ts`、`useSessionGate.ts` 都没有）。于是：
  - **退出**：卡在第 ② 步，第 ④ 步 `signOut`、第 ⑤ 步删库都不会执行，本机会话还留着。在共用设备上，这意味着用户点了退出、账号却还登着；
  - **换账号**：`ensureAccount` 卡住，新账号进不来。
- 什么时候会“一直不回”：没有 SW 时，网络卡住（比如需要登录的公共 Wi-Fi、请求被挂起）。和第一节一样少见，但这是改动前没有的倒退：原来整个断开都有上限。

### 一、必改 1：已解决

`disconnectPushLazy` 现在的流程：

1. 先同步执行 `forgetPushClaim()`，不等下载。
2. 下载 push.ts 最多等 `LOAD_PUSH_MS`（1 秒）。
3. 下载到了，就调 `disconnectBrowserPush({}, left())`，外面再用 `within(…, left())` 包一层。
4. 下载失败或超时，就走兜底，兜底同样受 `left()` 限制。

所以整体不超过 `DISCONNECT_PUSH_MS`（2 秒），只多几个微任务。`within` 对成功、失败、超时都只 resolve，不会 reject。下载晚到时，结果直接丢掉，不会在超时以后再去断开。函数不会抛错。调用处（`sign-out.ts`、`account.ts`）外面原来的 try 也还在。

测试结果：

### 二、S1：已解决，跳过退订的条件可以接受

兜底 `fallbackDisconnect` 只依赖 env、native-bridge、push-claim-key，不依赖 push.ts：

- **网页**：等 `navigator.serviceWorker.ready`，关掉已显示的通知，再 `getSubscription` 后 `unsubscribe`。
- **exe**：调 `closeAllLocalReminders`。

兜底失败或超时记 `fallback`。

**“权限是 default 或 denied 时不退订”这一条在安全上可以接受**，理由：

- 和正常路径（push.ts）是同一个判断，兜底没有比正常路径多留任何东西。
- 权限不是 granted 时，SW 显示不出通知。另外，主流浏览器在用户收回或重置权限时会自己作废订阅，服务器再推会收到 410。
- 服务器那边：在线退出时，第 ① 步已经按会话删了 devices 行，和退不退订无关。
- 离线退出、旧订阅又没作废时，仍有第二节说的两层兜底：
  - SW 显示前核对 owner（FE-1），对不上就只显示 App 名，不显示标题和正文；
  - 下一个账号认领同一个 endpoint 时会换绑（FA2-2）。
- 最坏的情况是：用户以后在没登录的状态下重新给了权限，在换绑之前收到几条只写 App 名的通知。看不到内容，和第二节的结论一致。
- 反过来，如果为了退订去调 `getSubscription`，会踩 WebKit 卡死主线程的已知问题（PUSH-getsub-hang），代价更大。

和原建议不同的一处：用的是 `serviceWorker.ready`，不是 `getRegistration()`。在支持 SW 但还没有注册的页面里（第一次访问、开发模式），`ready` 会一直不回，等满剩余时间后记一条 `fallback`。这只是日志噪声，不影响安全，也不会卡住流程。见建议 S4。

### 结论：通过，S4、S5 已解决，没有新问题

- **S4（scope 写法对不对、会不会漏退订）**：
  - **网页**：SW 由 `sw-register.ts` 注册，`SW_URL = '/app/sw.js'`、`SW_SCOPE = '/app/'`。兜底调的是 `getRegistration('/app/')`，参数按当前页面 origin 解析成 `<origin>/app/`，正好落在这个注册的 scope 里。正式站和预览站都是这样。
  - **和其他地方是否一致**：`push.ts` 和 `notifications.ts` 取注册也是同一个写法，订阅就挂在这个注册上。所以兜底拿到的注册，和正常路径退订的是同一个，不会漏退订。
  - **没注册时**：`getRegistration` 立刻返回 undefined，兜底直接结束，不记 fallback。这种情况本来就没有订阅可退，也不会漏退订。
  - **exe（tauri.localhost）**：在 `isTauri` 那一步就转去调 `closeAllLocalReminders`，根本走不到 `getRegistration`。exe 也不注册 SW（stage-web 跳过 `sw.js`）。所以 scope 写法和 exe 无关。
- **S5（同步抛错）**：新增单测覆盖了两种情况：`load` 同步抛错记 load，取注册同步抛错记 fallback，函数都不抛错。`within` 的注释也写明了这段只为防御。
