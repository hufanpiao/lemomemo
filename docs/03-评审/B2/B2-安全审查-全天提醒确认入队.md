## 一、权限、security definer、search_path

- 触发器执行的是已有的 `private.enqueue_remind()`。真库查到：`prosecdef = t`、`proconfig = {search_path=""}`、属主 `postgres`、ACL `{postgres=X, authenticated=X}`。`authenticated` 的 EXECUTE 是 0001 就有的，这次没动；探针 P4 证实直接 `select private.enqueue_remind()` 报 `0A000`（触发器函数不能直接调），所以这条授权没有可利用面。收不收窄属于 0001 的旧债，不算本次问题。
- `authenticated` 对 `private.remind_queue` 没有 insert、select 权限（真库核对）；入队只能经 definer 函数走。变异 M6（换成同样函数体但 security invoker 的新函数）让第 ①②⑧ 条都失败，说明“必须复用 definer 入口”这一点被测试钉住。

## 三、重复推、漏推

主路径核对（07:00 推过 → default_time 改 07:20 → R-336 压住 remind_at = 07:00 → 客户端按知道了写 07:20）：

1. 触发器：全天、没删、notified_for 变了且 ≠ remind_at(07:00) → 入队。
2. 第 0 步：新算 07:20 ≠ 07:00，但 `row.notified_for === patch.remind_at`，跳过 R-336，写回 remind_at = 07:20。`writeRemind` 只写 remind_at，`touch()` 的清列名单不含 remind_at，所以 pushed_for 留着 07:00。
3. resolve：`remind_pushed` 里 `nf = ra` 和 `d(07:20) <> pf(07:00)` 两条都成立 → 发 resolve。
4. 第 1 步：`notified_for === remind_at` → 不算到点，07:20 不再推。edge 测试第 1 条把 1 次 remind、1 次 resolve 钉住。

其他情况：

- 照常的“知道了”（写 07:00）：WHEN 不成立、不入队，resolve 本来就成立（36 号 ③、edge 第 2 条）。
- 写了同一天的别的时刻（07:10）：入队，第 0 步照旧按 R-336 压住、不写回、不推（edge 第 3 条）。只多一次空算。
- 挪日期合并补丁：`events_occ_reset`（before）先清空 notified_for，after 触发器看到的是 null，不入队；`events_remind` 入一次，总共 1 项（36 号 ⑨）。两个 after 触发器都调 `enqueue_remind`，按名字排序先后执行，靠 on conflict 去重，不会重复。
- 正被租着的项：用户这时按知道了，清租约 → 这一轮 `finish` 按租约删不到它 → 下一轮按新值重算（36 号 ⑧）。不会丢。
- 有时刻的日程、待办、纪念日：不加，它们的 remind_at 不会被 R-336 压住（36 号 ⑥）。

## 六、建议（都不阻塞）

- **A1（低）**：WHEN 加 `new.remind_days is not null`。P2 实测不提醒的全天日程按知道了（或客户端整行写回带了 notified_for）也会入队，第 0 步算出 null、与原值相同、不写，只是多一次空算。加上以后 36 号再补一条“不提醒的不入队”。
- **A2（既有，记录）**：用户写 notified_for 和写 snooze_at 一样，会把自己已在队列里的项清租约、attempts 清零，所以一条一算就崩的“有毒行”可以被它的主人反复拉回按批出队，绕过 5 次丢弃。这是 20261104130000 ④ 起就有的语义（经 `events_remind`），这次没有扩大；如果以后要防“自己的有毒行连坐整批”，应该在入队函数统一处理（例如 attempts 不清零、只清租约），不在本触发器单独改。
- **A3（低，写进方案）**：S1 只在客户端现算的时刻和服务器新算的完全相等时成立。客户端时区和 `current_tz` 不同、或另一台设备又改了 default_time 还没同步过来时，notified_for ≠ 新算值，仍按 R-336 压住、收不回（edge 第 3 条钉的就是这个行为）。另外 resolve 只回看 60 分钟（`BEHIND_MS`），推过超过一小时才按知道了也收不回。这两点都是既有口径，建议在方案第 7 节写明，免得验收时当成回归。
- **A4（低）**：第 0 步写回的乐观条件只比 remind_at，不比 notified_for。读完行以后用户在另一台设备把 notified_for 又改成别的值时，会写回 07:20 而 notified_for ≠ 07:20，07:20 可能再推一次。用户改 notified_for 会清租约、触发下一轮重算，影响只是多一次本人的推送，概率很低；要堵可以在 `writeRemind` 加 `notified_for` 等于读到的值的条件。
