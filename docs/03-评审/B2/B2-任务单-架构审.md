## 二、架构侧决定

### D1　R4 推送端点校验

**架构定**：

1. **规则**（两处同一套）：
   - 只认 `https:`；不许带用户名密码；**不许写端口**（只能是默认的 443）；主机名转小写、去掉末尾的点以后比对；**IP 地址一律拒**；路径不能为空；整条地址 ≤ 2048 字符。
   - 主机白名单，写成固定常量，只有两种写法，**不支持别的通配**：

     | 推送服务 | 写法 | 含义 |
     |---|---|---|
     | Apple（iPhone 主屏幕版、Safari） | `*.push.apple.com` | 只匹配**一级**子域，即主机名符合 `^[a-z0-9-]+\.push\.apple\.com$`；现在用的是 `web.push.apple.com`。苹果的文档建议服务器放行 `*.push.apple.com`，它以后换子域也不用改 |
     | Microsoft（Edge 安装版，WNS） | `*.notify.windows.com` | 同上，一级子域：`^[a-z0-9-]+\.notify\.windows\.com$`（例如 `wns2-xxx.notify.windows.com`） |
     | Google（Chrome，FCM） | `fcm.googleapis.com` | 完全相等。旧的 `android.googleapis.com`（GCM）不收 |
     | Mozilla（Firefox） | `updates.push.services.mozilla.com` | 完全相等 |

     “一级子域”的意思：`a.b.push.apple.com`、`push.apple.com` 本身、`evilpush.apple.com.example.com` 都不匹配。
   - `p256dh` 必须是 base64url、解码后 65 字节且首字节 `0x04`；`auth` 解码后 16 字节。SQL 一侧按长度和字符集查（86～88 字符、22～24 字符，`[A-Za-z0-9_=-]`），push-dispatch 一侧解码后按字节查。
2. **两处都查**：
   - **`claim_endpoint_impl` 写入时**：放在会话检查之后、删任何行之前；不合格的整次拒绝，一行都不动。规则写成一个不授权的 immutable 函数 `private.push_endpoint_ok(text)`，只给 `claim_endpoint_impl` 内部调（进 3.3 C 的说明，不进授权白名单）。另加一个新迁移给 `public.devices` 补 check 约束：`push_endpoint` ≤ 2048、`p256dh`、`auth` 长度和字符集如上（现在 0001 里这三列没有任何长度约束）。
   - **push-dispatch 发送时**：每个订阅发之前再查一次（库里可能有约束加上之前写进去的旧行，也防有人绕过 RPC 用 service role 写）。不合格的：**不发**，把这一行的 `push_endpoint`、`p256dh`、`auth` 置空，写一条 logs（`act = push_bad_endpoint`，code 只写 `host_not_allowed` 这类原因，**不写地址**）。
   - 发送用 `fetch(..., { redirect: 'manual' })`，**3xx 一律算失败、不跟随**（否则白名单主机一个重定向就绕出去了）；每个请求 5 秒超时。
3. **拒绝时的错误码**：`endpoint_not_allowed`，HTTP 400——照 B1 迁移的写法 `raise exception 'endpoint_not_allowed' using errcode = '22023'`（和 `bad_tz`、`bad_platform` 同一类）；p256dh、auth 不合格回 `bad_push_keys`（同样 22023）。前端：显示“这个浏览器的推送服务暂不支持”，不自动重试、不进 outbox。两个码登记进 3.3 D 的 claim_endpoint 一段。
4. **不要缓存**：白名单是代码里的常量，比对只是字符串操作，没有要缓存的东西；**也不做 DNS 解析、不缓存解析结果**（主机名白名单已经把范围收死了）。SQL 和 TS 各写一份常量，**用同一组测试向量**在 pgTAP 和 Deno 单测里各跑一遍（放 `tests/fixtures/push-endpoints.json`，合法、不合法各 15 条以上，含上面三种不匹配写法、带端口、带用户名、IP、http、超长），两边结果必须一致，CI 拦。唯一要缓存的是 VAPID 的 JWT：同一轮里按推送服务的源（audience）各签一次、复用，有效期 ≤ 12 小时，**只放内存、不落库**。
5. **iPhone 不发 `resolve`**：按端点主机判断——主机属于 `*.push.apple.com` 的一律不发 resolve 推送（5.3），**不按 devices.platform 判断**（那一列是客户端写的）。
6. **本机测试**：SQL 白名单不留任何测试例外（认领时不会去连这个地址，测试直接用 `https://fcm.googleapis.com/fcm/send/<假 token>` 这种形式即可）。push-dispatch 加一个只在本机认的环境变量 `PUSH_SERVICE_OVERRIDE_URL`：设了就把所有发送改投到这个替身，**只认 `http://127.0.0.1:<端口>`、`http://localhost:<端口>`**；预览、正式设了它函数回 500 `misconfigured`（照 0.38 第 22 条 TURNSTILE_SITEVERIFY_URL 的规矩）。替身由测试开发在 `tests/` 下写，能按需回 201、404、410、429、3xx、超时。
7. **安全审查签哪一条**：15.4 S-B2 **新增一项**：“推送端点白名单在 claim_endpoint 和 push-dispatch 两处生效、发送不跟随重定向、本机替身变量在线上环境拒绝启动”，**P1**（不是 P0：请求体是加密的推送负载，响应不回给用户，能造成的是“让服务器向任意地址发 POST”，危害有限，但必须堵）。QA 新增用例 TC-B2-80 对应它。
8. **理由**：推送地址是用户给的，不校验就等于服务器替任何人往任意地址发请求（SSRF）；只在写入时查挡不住绕过 RPC 的写入和约束之前的旧行，只在发送时查又会让脏数据一直留在表里，所以两处都查。固定主机名比“按前缀、按正则配置”好审，和 0.38 第 22 条“出站地址按完整地址登记”同一个思路。
9. **要改架构哪一节**：5.3（加“推送端点校验”一段，含以上 1～6 点）；3.3 D 的 claim_endpoint（签名、返回值、两个错误码、校验位置）；3.3 C 说明里加 `push_endpoint_ok`；0.38 第 22 条“由 push-dispatch 自己校验”后面加“规则见 5.3”；15.4 S-B2 加上面那一项；附录 A devices 的约束；第 6 节 push-dispatch 行。

### D2　USAGE-REPORT-gateway-401

**架构定：做法 ②（usage-report 关网关 JWT 校验、只靠 `x-ops-secret`），① 作为附带的告警改进一起做**。不同意任务单“建议 ①”。

- **理由**：
  1. ① 只是让告警说清原因，旧格式 anon key 一停用，usage-report 照样调不通。而 keepalive 的“真实查询”就是调 usage-report（第 6 节 keepalive 行）——调不通就没有保活，项目可能被免费版暂停，监控也同时失明。② 去掉了对 anon key 格式的依赖，是根治。
  2. **这条口子以后反正要开**：claude-intake 用 `Bearer 连接码`（B3）、backup-manifest 用 `Bearer BACKUP_PULL_TOKEN`，都不是 JWT，网关校验一开就到不了函数。现在就把“服务器对服务器、自带密钥校验”这一类写成规则，比到 B3 再临时放宽好。
  3. 代价和 account-purge 已接受的一样（安全审查 11-03）：未鉴权的请求能进函数、算一次调用，函数常量时间比对后很快回 401。
- **做法**：
  - `config.toml` 加 `[functions.usage-report] verify_jwt = false`；函数里 `x-ops-secret` 常量时间比对（现在已经是）。
  - check_backend F9 ③ 改成**按名单放行**：新增常量 `SERVER_SECRET_FUNCTIONS = { 'usage-report': 'x-ops-secret' }`（以后 B3 加 `claude-intake`、backup 那一批加 `backup-manifest`，每加一个都要代码审查和安全审查）；名单里的函数必须关 verify_jwt，且函数源码里必须对名单写的那个头做常量时间比对；**名单外、又不是 cron 调的函数关了 verify_jwt 照旧报错**。违规样例两个（名单里的没比对、名单外的关了）。
  - ①：lemo-ops 把“网关回的 401（返回体是 `UNAUTHORIZED_*`）”和“函数自己回的 401（`{"error":"unauthorized"}`）”分开报，前者写“网关拒绝，查 verify_jwt 或 key”；lemo-ops 调 usage-report 不再带 anon Bearer。
- **人日**：后端 0.25（config、F9 和样例）、运维 0.25（lemo-ops），都在任务单已列的 BE-5 0.5 和 O-3 0.25～0.5 里，不另加。
- **安全审查员要签**：F9 ③ 名单的口径和 usage-report 关校验这两件，写进 `B2-安全审查-S-B2签字.md`。
- **要改架构哪一节**：第 6 节 usage-report 行“鉴权”一栏加“网关不校验 JWT（0.4x）”；第 6 节 keepalive 行；2.3 F9 的说明；8.4 不变。

### D3　R6：push-dispatch 和 pg_net 5 秒超时

**架构定**：

1. **不把 5 秒照搬过来**。0.38 第 46 条的 `timeout_milliseconds := 5000` 是给 account-purge 的模板；**push-dispatch 的 cron 写 `timeout_milliseconds := 25000`**。pg_net 的超时只决定 pg_net 等不等回包，和函数跑不跑完没关系；B1-left-pgnet-timeout（“pg_net 超时后函数照样跑完”）**至今没测到**，push-dispatch 不能押在这个未核实的行为上。
2. **函数自己给自己定预算，保证在 pg_net 等待之内跑完**：一轮最长 **20 秒**墙钟；到 20 秒就**不再认领新条目**，已认领的发完、写日志和心跳后返回 200（detail 里写 `budget_hit: true` 和剩余条数）。剩下的到点条目还在 `due_at > now − 60 分钟` 的窗口里，下一分钟接着发。一轮发送并发上限 10；再加一个发送条数上限（初值 200 次发送/轮，BE-1 第 1 天在替身上量出免费版每次 2 秒 CPU 下的实际值再定，写进函数常量和 5.3）。这样一轮总在 25 秒、也总在下一次 cron（60 秒）之前结束，正常情况下两轮不会重叠。
3. **不会重复发——靠架构已有的“先认领再发”**（5.3 第 3 步、4.4 第 8 点）：每条先条件更新 `pushed_for = due_at`（`where pushed_for is distinct from due_at`），更新到 1 行才发，0 行就跳过；认领、发送、写回各是一条独立语句，不在事务里等外部调用。万一两轮重叠，同一条只有一轮能认领到，所以**不加全局锁**。pg_net 本身不重试，不会因为超时被再调一次。
4. **漏发怎么兜**：选“**最多一次**”，不选“至少一次”。认领后、发出前函数崩了，这一条这一轮就不再推——接受，理由：重复响比漏一次更打扰；漏的那条在 App 里的“错过的提醒”（5.9，按 `notified_for` 判断）照样会出现；心跳 detail 记 `claimed`、`sent`、`failed` 三个数，两者差值大于 0 时 lemo-ops 照“失败过半”同一条规则看（6.1）。**不另加“发送中”状态列**。
5. **第 0 步队列也要防丢**：`remind_queue` 只有主键 `(table_name, id)`，“先读、算完再删”会把处理期间新入队的同一行一起删掉（入队是 on conflict 不插新行）。改成**出队即删**：`delete … returning` 取一批（每轮上限 500），重算写回失败的再插回去。PostgREST 做不了带上限的 delete 时，加一个只授 service_role 的 `private.remind_queue_pop(int)`（security definer，`set search_path = ''`，进 3.3 C 白名单和附录 A 末尾，两处一字不差，D1 核对）。
6. **测试**：替身把每个请求拖到 3 秒，造 300 条到点提醒，验证 ① 一轮在 25 秒内返回、`budget_hit` 正确、剩下的下一轮发完；② 两轮人为重叠时每条只发一次；③ 认领后让函数抛错，这一条不再推、“错过的提醒”里有它。顺带让一轮故意超过 5 秒（例如替身拖慢），看 `net._http_response` 和心跳——这条结果**可以**作为 B1-left-pgnet-timeout 的旁证，但那一行本身仍按原判据在 account-purge 上测，不替它关单。
7. **理由**：两种失败（重复、漏）里，“认领在前”已经把重复挡掉；剩下只要保证函数一定跑完、不依赖 pg_net 等回包，所以用“加长超时 + 自定预算 + 剩余顺延”，而不是赌“超时后函数照样跑完”。
8. **要改架构哪一节**：5.3（第 1 步加“时间预算和顺延”、第 3 步写明条件、第 0 步改出队即删）；第 6 节 pg_cron 写法后面加一句“push-dispatch 的超时 25000 ms，理由见 5.3”；6.1 心跳 detail 字段；必要时 3.3 C、附录 A 加 `remind_queue_pop`。
