## 必改

### M1 主页标签页一放锁，gate 就永久停掉，整页再也不出卡

- 位置：`src/app/sync-notice-gate.ts:102-105`（`check()` 里的 `sync.getState().stopped`）、`:127`（`sync.subscribe` 触发 `check`）。
- 链路（读代码确认过）：
  1. `platform/tab-leader.ts:3-4`：页面隐藏时，主页主动放手。
  2. `sync-wiring.ts` 的 `lead()` 返回的 stop 先 `await sync.drain()`；`engine.ts:292-299` 的 drain 最后调 `halt()`，把 `hub.setState({ stopped: true })`。
  3. facade 的 `attach` 把状态变化转给外面的订阅者。这时 `current` 还是这个引擎（`current = null` 在 drain 之后才设），所以 `facade.getState().stopped === true`。
  4. gate 的 `check()` 因此调 `stop()`：卸宿主、移除容器、全部退订。
- 后果：
  - iPhone 上切到别的 app、锁屏、切标签页都会触发，这是最常见的用法。
  - 回到前台后，tab-leader 会重新抢锁、建新引擎，但 gate 已经死了。
  - 这一页之后的冲突卡、gone 卡、“已彻底删除”轻提示都不出，直到重新载入。
  - gone 项留在 outbox 里挡住这条记录后面的同步（方案 4.3 跟随组那段），用户却看不到卡。
  - 限次触发时的 `yieldLeader()` 也会走 drain，结果一样。
- 测试问题：`src/app/__tests__/sync-notice-gate.test.tsx:131-137`“同步停了：同样卸掉”拿假 facade 把 stopped 置真，钉住的正是这个错误行为。
- 改法（建议）：
  - gate 只在“这一页不会再同步”时停：`boot.switching`、`wireSync` 的 close（exiting）、被移除或停用（`outbox.onEvent` 的 removed / disabled，这时页面也随即离开）。
  - 引擎 `stopped` 只表示“当前引擎放手了”，不能当停止信号。
  - 测试换成真 facade 的语义：放锁（stopped → 新引擎 attach）之后再发 conflict，仍要出卡；gone 照样能读出。

### M2 `handled` 按记录记，会把还在的 gone 永久藏掉

- 位置：`src/app/sync-notice-store.ts:204-206`（`r.ok` 时一律 `handled.add(key)`）、`:166`（只有某次读不到这条记录的 gone 组才清）、`:178`（`handled.has(key)` 时跳过）。
- 情形一：`resolveGone` 返回 `done: 'nothing'`。
  - `outbox-gone.ts:127-140`：连续两次 `GoneChanged` 时，gone 项原样留在 outbox，也不 `notify` / `refresh`。
  - 方案 4.2 写的是“界面按 outbox 现状重新出卡”。实际上 `handled` 里已有这一条，之后每次读都跳过，永远读不到“不在”，卡就永远不再出。
- 情形二：restore 成功后，在途项又回 gone。
  - 方案 4.3：“已发出的、在途的不动，回来照样走 gone 流程，最多再出一张卡”。
  - 如果新 gone 落库早于（或等于）恢复后第一次读队列，这一次读就看到同一 key 的 gone 组。于是 `handled` 不清、卡不出，之后也一直不出。
- 后果：gone 项卡在 outbox 里，不出卡、不能处理。它排在这条记录最前时，会挡住这条记录之后的所有同步。
- 改法（建议）：
  - `handled` 记“办掉的那一组 op_id”，读的时候只在这一组的 op_id 是已办集合的子集时才跳过；出现新 op_id 就照常出卡。
  - `done: 'nothing'` 不记 `handled`，并主动 `readGone()` 一次。
- 测试缺口：`sync-notice-store.test.ts:147-157` 只测了“旧项还读得到时不再出卡”。要补两条：
  - `nothing` 之后 gone 还在 → 重新出卡；
  - restored 之后同一记录出现新 op_id 的 gone → 出卡。

### M3 自动收起的悬停、焦点状态在卡卸掉后不复位，之后的冲突卡不再自动收起

- 位置：`src/features/sync-notice/hooks/useSyncNotices.ts:36-37`（`hover`、`focus` 存在宿主这一层的 hook 里）、`:57-63`；挂载在 `ui/SyncNoticeHost.tsx:126`、`:138`。
- 情形：
  - 鼠标点“知道了”：卡卸掉，浏览器不会对已移除的节点发 mouseleave，`hover` 停在 true。
  - iPhone 轻点卡上按钮：会合成 mouseenter，同样停在 true；iPhone 是用户的主力设备。
  - 键盘按“知道了”：按钮被移除，浏览器一般不发 blur / focusout，`focus` 也可能停在 true。
- 后果：
  - 之后再来的冲突卡，计时 effect 因为 `hover || focus` 直接返回，永远不自动收起。
  - 后面排着的 gone 卡也一直等着，要用户手动点。
  - 违背方案 3.1“冲突卡 8 秒后自动收起”。
- 另一处相关：卡片 `div` 和按钮没有 `key`，换卡时 React 复用同一批节点，`hover`、`focus` 从上一张卡带到下一张。
- 改法（建议）：
  - 卡片按 `current.key` 加 `key`。
  - `key` 变化或卡卸掉时把 `hover`、`focus` 复位。
  - 悬停只认 `pointerType === 'mouse'` 的 pointerenter / pointerleave，触摸不算悬停。
- 测试缺口：`SyncNoticeHost.test.tsx:134-152` 只测了“指针在卡上时不走”。要补：mouseEnter 之后点“知道了”，下一张冲突卡 8 秒后照样收起。

## 建议

### S1 冲突列全是 hidden 列时，出一张说不清的卡，对话框是空的

- 位置：`sync-notice-store.ts:215-230`（只对“刚恢复”的项过滤列）、`data/fields.ts:127-150`（hidden 列不出行）、`ui/SyncNoticeHost.tsx:148-151`。
- 服务器的 `no_conflict` 只排除 `notified_for`、`snooze_at`、`updated_at`、`sort`（见 `0002_calendar_todos.sql:29,74`、`0003_notes.sql:12,47`、`0005_anniv.sql:25`）。`deleted_at`、`undone`、`short`、`short_by`、`done_at`、`category_seen`、`category_source`、`converted_to`、`batch_id` 等 hidden 列都可能单独冲突。
- 典型场景：两台设备都删了同一条。后到的删除带 `deleted_at`，服务器判 conflict，不判 gone。
  - 卡上写“‘X’已在另一台设备上改过……现在保存的是这台设备的修改”，可这一条已经删了；
  - “看另一台设备的版本”打开是空列表。
- 页面刷新后，`restored` 内存表丢失，恢复项回来的 `deleted_at` 冲突也会走到这里（见 L1）。
- 建议：
  - 冲突列去掉 hidden 列后为空，就不出卡。判断放在 hooks 层或宿主层（store 在 app 下，不能引 data，A27）；或者由 index.ts 导出一份 hidden 列字面量，配一致性测试。
  - 至少在 `conflictLines` 为空时不给“看另一台设备的版本”按钮。

### S2 live region 在容器被样式藏起来时写入，读屏不播报，之后也不补报

- 位置：`ui/SyncNoticeHost.tsx:97-103`（`said` 只看路由），`SyncNoticeHost.module.css:208-214`（`visibility: hidden` 作用在整个 `.region`，常驻 live region 也在里面）。
- 主 App 弹层开着、或者在告知页时来了卡：文字写进了被隐藏的 live region，读屏不播报。弹层关上以后 `said` 没变，不会再写，读屏用户就漏了这张卡。
- 建议二选一：
  - live region 挪到 `.region` 外面（gate 预建时放成兄弟节点）；
  - `said` 把“被样式藏起来”也算进去，恢复显示后再写一次。
- 另外，同一段文字重复写入不一定会再播报。

### S3 点完按钮，卡收起，焦点掉回 body

- 位置：`ui/SyncNoticeHost.tsx:153`、`:160`、`:164`。

## S1 补审（2026-11-05）

- 审的对象：前端 A 副本里的改动，还没进主仓库。

### 做法

- **过滤的条件：** 宿主算当前卡之前，先滤掉 `status === 'conflict'` 且 `conflictLines` 为空的冲突卡（副本 `SyncNoticeHost.tsx:75-83`）。
  - 滤掉的卡由副作用替用户 dismiss，不会一直占着队列。
  - “还有 n 条”只数显示得出来的卡。
  - forked 卡不滤。
- **为什么放在宿主：** store 在 app 下，只能引 index.ts；A27 不许 index.ts 导出这一类值，所以放在宿主滤是对的。
  - 代价是这种卡会让宿主分包先下载一次。冲突本来就少见，可以接受。
- **按钮：** 原来只藏“看另一台设备的版本”按钮的写法已经去掉，现在冲突卡的这个按钮照常显示。只有隐藏列的卡在前面就被滤掉了，不会走到这里。

### 检查

- 副本里 `src/features/sync-notice/__tests__` 4 个文件 28 条全过（`--maxWorkers=4`）。
- 副本里宿主文件的 eslint 0 错误。
- 新增 3 条用例，有效性如下：
  - 第一条和第二条把 dismiss 换成只记调用、不删卡，所以卡被藏起来只能是宿主自己滤的。这样才能抓住“去掉过滤”的变异，不是测了假实现。
  - 第二条还断言 live region 不写字，读屏不会念出一张没显示的卡。
  - 第三条钉住 forked 不滤。

### 低（不挡合入）

- **S1-L1 竞态（窗口极窄）：**
  - 经过：store 先 emit 一张只有隐藏列的卡；宿主的 dismiss 副作用还没跑，同一条记录又来了真冲突，在 store 里合并（还是同一个 key）。
