## 建议

- S1 预先已中止的 signal 会留下一条 pending 假记录，入口遇 `signal.aborted` 直接抛错不记录（`push-service.ts:110-114`）

- S3 原生 Linux docker 走网桥，连不到只听 127.0.0.1 的替身，CI 上 TC-B2-81～83 可能不通；由运维实测，改监听前先回安全审查（转运维）
- S4 补推送服务真有的行为：正文 > 4096 回 413；检查 idlen = 65、rs、单条记录；`Content-Type: application/octet-stream`、JWT `typ`、签名正好 64 字节；sub 正则 `https:` 改 `https://`
- S5 加 `Response.error()` 回复种类和能记录读取字节数的流式大响应体，用来测 D1-4
- S6 先验签再计 `times`，被拒的请求不消耗次数（`push-service.ts:284-286`）
- S7 `close()` 和发送方超时都记成 `clientClosedAt`，加原因字段（`:170`、`:273`）
- S8 注释说拖延用真定时器，实际用全局 `setTimeout`（`push-service-types.ts:75`）
- S9 D1-7 的 p256dh 正则 `^B[A-Za-z0-9_-]{86}=?$` 会放过首字节 0x05～0x07（如 `BQ…`），SQL 收、Deno `importKey` 失败；建议 `^B[A-P][A-Za-z0-9_-]{85}=?$`，fixture 加 `BQ…` 不合格样例（转安全审查）
