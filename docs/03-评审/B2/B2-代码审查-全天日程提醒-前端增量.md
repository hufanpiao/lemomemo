## 协调者点名的四个问题

**1. `occurrenceKey` 会不会把不同的两次提醒当成同一次**
- key 是 `event:<id>:allday:<date>:<remind_days>`。
- 前一天提醒和当天提醒：`remind_days` 不同，key 也不同，不会混。
- 日程日期改了：`date` 不同，key 也不同，不会混。
- 跨午夜：key 里只有日程日期，没有提醒时刻，和午夜无关。前一天 20:00 被免打扰推到当天，key 不变，tag 仍用推迟前的时刻，没问题。
- `current_tz` 变了：key 不变，所以会当成同一次（见 L3）。这和 R-336“同一条当天推过”的意思大致相符，但和下面的 `allDayAcked` 口径不一致。
- **真正会误判的是 `allDayAcked`（reminder-model.ts 第 103 行），见 M1。** 它只比“`notified_for` 和这次 `remindAt` 是不是同一天”，没有带上 `date`、`remind_days`。所以 key 分得开的两次提醒，在“算不算处理过”这一步又被合到了一起。

**2. 撤回旧通知时 tag 对不对**
- exe 本机通知：`shown` 改成 `Map<shownKey, 弹出时的 tag>`，`staleShown` 返回的是当时弹出的 tag，`closeLocalReminder` 撤的就是那条通知。卸载时遍历 `values()`，也对。
- 按了“稍后”以后，key 从 allday 变成稍后那个 tag，旧 key 变成过期项，撤回的是原来那条通知。这是对的。
- 网页、手机推送这边的 `shouldCloseShown`（local-notify.ts 第 97 行）没跟着改，仍然是“tag 对不上就撤”。改了默认时刻以后，手机上已经推出来的那条会被撤掉，而 exe 是保留的。两边不一致，见 L1。

**3. 有时刻的日程、待办、按过“稍后”的，行为有没有被改坏：没有。**
- `occurrenceKey` 对这三类返回 `r.tag`。`ringing` 里 `rang.get(tag)` 要么没有，要么等于 tag 本身，过滤结果和原来一样。
- `allDayAcked` 前面有 `!snoozed`、`time === null` 两个条件，碰不到这三类。
- `handled` 对这三类仍然是 `notified === remindAt`。

**4. 补班尾巴在韩国节假日数据上会不会误删：不会。**
- 只有 `kind === 'work'` 才去尾巴。`holidays.ts` 第 96 行规定只有中国的文件能有 `work`，韩国两份文件里也没有 `work`。
- 韩国的“대체공휴일(…)”属于 `off`，走的是 `narrowHolName`，不受影响。
- 问题在反方向：中国补班的韩文名去不掉尾巴，见 M2。

**1. 靠“带 time 又带 `notified_for: null`”判断“全天改成有时刻”，这个推断稳不稳**

**2. 只在本机了结以后，换设备、重开 App 时会不会又响；有没有别的副作用**
- **本机、这次打开：不会再响。** `markSessionAcked` 把 `handled` 置为 true，横幅（`ringing`）、“错过的提醒”（`missed`）、本机通知（`localDue` / `staleShown`）、网页通知（`shouldCloseShown`）都按已处理来算。outbox 同步完以后，服务器算出来的 `remind_at` 和本机一样，tag 不变，仍然算已处理。
- **重开 App：会再响，或者进“错过的提醒”**，属于 REMIND-shown-persist 已知的限制。
- **除了“重开会再响”之外，还有一个副作用，而且是长期的（L10）：这次“知道了”永远不会写进库。**
  - outbox 同步完以后，服务器知道了新的提醒时刻，`notified_for` 被触发器清空，又没人补写。
  - 如果还在 60 分钟窗口内，手机会再收到一次推送。
  - 7 天之内，所有设备的“错过的提醒”里都会出现这一条，哪怕本机这次打开时看不到。
  - 这比“重开会再响”的范围大，而且不是 REMIND-shown-persist 那条限制能覆盖的。
- 换账号：`sessionAcked` 记的是 tag，tag 里有行的 uuid，不同账号不会撞上。它在引擎卸载时清空，和第二轮的 L8 一样，要看 RemindHost 以后的接线。

**3. 那一处 eslint-disable 合不合理，能不能不用豁免**
- **用法不合理，可以去掉。** 现在 `ackVer` 在 useMemo 里根本没用到，只是为了让它重新计算才放进依赖数组。真正用到的 `sessionAcked` 是模块级的可变 Set，React 看不到它的变化。这正是 exhaustive-deps 要防的写法：一旦有人删掉 `ackVer`，就会读到过期的数据。
- 不用豁免的写法：
  - 让外部存储的快照本身就是一个只读集合，每次变化时整个换成新对象（`snapshot = new Set(sessionAcked)`）；
  - `const acked = useSyncExternalStore(subscribeSessionAcked, () => snapshot)`；
  - 在 useMemo 里用 `markSessionAcked(list, acked)`，依赖数组里放 `acked`。
  - 这样不用豁免，数据流也看得见。或者把 `markSessionAcked` 移到 useMemo 外面，在 `list` 算完以后再标一遍；成本很低，每分钟最多算几次。

**4. 已经发出、但服务器还没确认的项也一并拦下，这个取舍对不对**
- **不对，拦多了（L9）。** 看 `outbox.ts` 第 99～100 行：只有 `last.state === 'pending' && !last.sent && last.op === 'patch'`，并且是这一行**最后一项**时，才会被合并。
  - 已经发出的项（`sent: true`，包括正在发送、发送失败退回 pending 的），新写入会另外开一个 op_id，按 seq 排在后面，服务器先改日期、再写 `notified_for`，不会出现 R4-L1 那种合并。拦下它们，只会白白丢掉一次能写进库的“知道了”，还把 L10 的副作用带进来。
  - 永久失败的项（`state === 'failed'`）也会被拦。只要它一直留在 outbox 里，这一行的每一次“知道了”都只在本机了结。
  - insert 项（刚新建、还没同步的日程，`data` 里带 `date`）也会被拦。但 patch 不会合并进 insert，所以没有必要拦。
  - 如果“换一次提醒”的那一项后面还有一个待发的普通 patch（比如改了标题），“知道了”会合并进那个普通 patch，它排在后面发，本来也是安全的。
- 准确的判断条件应该是：这一行在 outbox 里的**最后一项**是 `op === 'patch'`、`state === 'pending'`、`!sent`，并且它的 `data` 里有“换一次提醒”的改动。`OutboxLikeItem` 要多带 `op`、`state`、`sent` 这几个字段。`outbox.list()` 已经按 seq 排好序，直接取这一行的最后一项就行。

### 结论：L13、L14 都已解决，可以提交。第四轮仍然是 8.5 / 10，通过

**1. `dirty` 再跑一次会不会死循环：不会。**
- `dirty` 只在 `busy` 期间收到 outbox 通知时才设为 true。`finally` 里先把它复位，再 `void flush()`，每次再跑都需要一个新的外部通知来触发。
- 唯一会自己引出通知的是补写本身：`ackReminder` 进 outbox，outbox 发通知。但被写的那一项在写之前就已经从 `laterAcks` 删掉了，所以自己引出的再跑次数不会超过当时 `laterAcks` 里的条数。
- 没有可写的项时，再跑只读一次 `outbox.list()`，不写，也就不会再引出通知。
- `laterAcks` 空了以后，`flush` 一进来就在 `laterAcks.size === 0` 那里返回。
- 所以再跑的次数有上限，不存在不停自己触发自己的情况。

**2. 卸载以后会不会还在 `finally` 里再跑：不会。**
- 清理函数先把 `alive` 设为 false，再取消订阅。
- `finally` 的再跑条件是 `dirty && alive`，卸载以后不成立。
- try 里两处 `await`（`outboxItems()`、`ackReminder()`）之后都会检查 `alive`，提前 return 时 `finally` 照样执行，但不会再跑。
- 卸载以后新来的 outbox 通知已经收不到了。
- 遍历用的是复制出来的 `[...laterAcks]`，不受卸载时清空的影响，有了 `alive` 检查就不会接着往下写。

**3. 测试能不能真的抓到问题：两条主要场景都能抓到，有一个小缺口。**
- **L13 那条**：两条“知道了”都只在本机了结。卡住第一次 `savePatch`，在它卡住时卸载，再放开，断言总共只写了一次。
  - 如果去掉 `ackReminder` 之后那次 `alive` 检查，循环会接着拿复制出来的那份写 E2，变成两次，测试会失败。
  - E2 的条件全满足（时刻没变、`notified_for` 为 null），所以这次失败只会是因为少了那道检查，不会是别的原因。
- **L14 那条**：E1 能写、E2 还在排队。卡住 E1 的写入，这时把 E2 也设成已发出并发一次通知，放开后断言 E1、E2 都写了。
  - 如果没有 `dirty`，那次通知在 `busy` 时被丢掉；测试里的 `savePatch` 替身不会引出新的通知，E2 就永远不会写，测试会失败。
  - 所以这条测的确实就是“跑完再跑一次”。
- **小缺口（不影响提交）**：
