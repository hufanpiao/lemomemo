## 协调者点名的四个问题

**1. `occurrenceKey` 会不会把不同的两次提醒当成同一次**
- key 是 `event:<id>:allday:<date>:<remind_days>`。
- 前一天提醒和当天提醒：`remind_days` 不同，key 也不同，不会混。
- 日程日期改了：`date` 不同，key 也不同，不会混。
- 跨午夜：key 里只有日程日期，没有提醒时刻，和午夜无关。前一天 20:00 被免打扰推到当天，key 不变，tag 仍用推迟前的时刻，没问题。
- `current_tz` 变了：key 不变，所以会当成同一次（见 L3）。这和 R-336“同一条当天推过”的意思大致相符，但和下面的 `allDayAcked` 口径不一致。
- **真正会误判的是 `allDayAcked`（reminder-model.ts 第 103 行），见 M1。** 它只比“`notified_for` 和这次 `remindAt` 是不是同一天”，没有带上 `date`、`remind_days`。所以 key 分得开的两次提醒，在“算不算处理过”这一步又被合到了一起。

**2. 撤回旧通知时 tag 对不对**
- exe 本机通知：`shown` 改成 `Map<shownKey, 弹出时的 tag>`，`staleShown` 返回的是当时弹出的 tag，`closeLocalReminder` 撤的就是那条通知。卸载时遍历 `values()`，也对。
- 按了“稍后”以后，key 从 allday 变成稍后那个 tag，旧 key 变成过期项，撤回的是原来那条通知。这是对的。
- 网页、手机推送这边的 `shouldCloseShown`（local-notify.ts 第 97 行）没跟着改，仍然是“tag 对不上就撤”。改了默认时刻以后，手机上已经推出来的那条会被撤掉，而 exe 是保留的。两边不一致，见 L1。

**3. 有时刻的日程、待办、按过“稍后”的，行为有没有被改坏：没有。**
- `occurrenceKey` 对这三类返回 `r.tag`。`ringing` 里 `rang.get(tag)` 要么没有，要么等于 tag 本身，过滤结果和原来一样。
- `allDayAcked` 前面有 `!snoozed`、`time === null` 两个条件，碰不到这三类。
- `handled` 对这三类仍然是 `notified === remindAt`。

**4. 补班尾巴在韩国节假日数据上会不会误删：不会。**
- 只有 `kind === 'work'` 才去尾巴。`holidays.ts` 第 96 行规定只有中国的文件能有 `work`，韩国两份文件里也没有 `work`。
- 韩国的“대체공휴일(…)”属于 `off`，走的是 `narrowHolName`，不受影响。
- 问题在反方向：中国补班的韩文名去不掉尾巴，见 M2。
