## 一、本机护栏

### 必改

**M1（红线，已实测）`guard.mjs` 的入口判断失败放行。**
`guard.mjs` 末尾用 `resolve(process.argv[1]) === fileURLToPath(import.meta.url)` 判断是不是被直接运行。Node 启动入口时会取真实路径，`import.meta.url` 是真实路径，`argv[1]` 却是调用时写的路径。两者对不上，就什么都不查，退出码 0。实测：

| 调用方式 | 退出码 |
|---|---|
| 仓库根目录 `node supabase/tests/store-it/guard.mjs` | 2 |
| 盘符小写、反斜杠 | 2 |
| 经目录联接 `node <联接>\supabase\tests\store-it\guard.mjs` | **0** |
| cwd 在联接里，`node supabase/tests/store-it/guard.mjs`（也就是 `npm run test:db` 的写法） | **0** |

这样一来，在联接（或 subst 盘、符号链接）路径下跑 `npm run test:db`，第一步会放行，第二步 `supabase test db supabase/tests/rls` 会读仓库 config（project_id 是 lemomemo），打进本机 lemomemo。`run.mjs` 是按模块引 guard 的，那一步还会再拦一次，但 pgTAP 和 `deno task d1` 已经跑完了。仓库里早就有同一类问题的先例：`real-backend.mjs` 的 `entryKind`（真实路径、不分大小写比较，还有 `mismatch` 分支），以及 `tests/build/copy-shared.test.ts` 的“经目录联接调用，入口比真实路径”。
改法：一律失败即拒绝。最简单的写法是新建一个只做检查的 CLI 文件，不加入口判断，无条件检查并设退出码，`test:db` 改调它；或者复用 `entryKind`，`mismatch` 时退出码 2。另外补一条经目录联接调用的单测，退出码必须是 2。

**M2（环境变量注入）CI 这条路没有挡 `SUPABASE_*` 环境变量和 `.env*` 文件。**
`real-backend.mjs` 文件头自己写明了：CLI 2.120 认 `SUPABASE_PROJECT_ID`、`SUPABASE_API_PORT`、`SUPABASE_WORKDIR` 等变量，还会读 cwd 里的 `.env`、`.env.local`、`.env.<SUPABASE_ENV>`，这些都能绕过 config。e2e 那条路在 spawn 时把它们全去掉了。`guard.mjs` 只看 `config.toml`，`test:db` 里的 `supabase test db` 和 `run.mjs` 的 `readStatus()` 都原样继承 `process.env`，在仓库根目录跑。只要 `CI=true`（act、手动 export）、config 是 lemo-ci，再加一个 `SUPABASE_PROJECT_ID=lemomemo`（或一个 `.env`、一个 `SUPABASE_WORKDIR`），就会打到别的库，而护栏照样放行。ci.yml 的 db 任务没有设任何 `SUPABASE_` 变量，所以加上这条拒绝不影响 CI。
改法：`repoSupabaseProblem` 再收一个参数，传入仓库根目录和 `supabase/` 下的文件清单。出现任何 `/^supabase_/i` 环境变量，或者有 `.env*` 文件，就拒绝。单测各补一条。

**M3（多行 / 注释写法）project_id 的解析是“数符合格式的行”，不是“认出顶层那一行”。**
用 node 调 `repoSupabaseProblem({CI:'true'}, …)` 实测，下面几种写法都**放行**，但 CLI 实际用的是顶层的 lemomemo：
- `project_id = "lemomemo" # main` 加上 `[remotes.ci]` 里的 `project_id = "lemo-ci"`（supabase 的 remotes 小节本来就有 project_id 这个键，是合法 config）；
- 顶层缩进写 `  project_id = "lemomemo"`，或单引号 `project_id = 'lemomemo'`，或带引号的键 `"project_id" = "lemomemo"`，同样再加一个小节里的 lemo-ci；
- 只有 `[api]` 下面一行 `project_id = "lemo-ci"`，顶层没有。

改法：照 `checkGuard` 的白名单思路来。① 只认第一个 `[` 小节头之前的那一行。② 文件里任何一行，只要去掉空白后包含 `project_id`（含引号键、注释里的），就必须正好是 `project_id = "lemo-ci"`，否则拒绝。ci.yml 的 sed 和 grep 同样只认 `^project_id = `，最好一并收紧。单测补上面几种写法。

### 建议

- S1：`supabase test db` 被直接手敲时，guard 管不到，这是固有的口子。可以在 `rls/_helpers.psql` 开头加一个前置断言，比如检查本测试库里有没有 CI 才会写的标记，作为第二道防线；做不到的话，至少在 `supabase/tests/rls/` 的说明里写明“本机必须带 `--db-url` 指 55322”。
- S2：`store-it-guard.test.ts` 的“仓库 config 是 lemomemo”那条，依赖仓库现状。建议再补一条：用 `CI=true`、指向一份临时 lemo-ci config 跑一遍 `run.mjs`，确认它会走到读 status 那一步，而不是在护栏处被误拒（这条只需 mock 掉 supabase，可以留到以后做）。

### 已核实没问题的

- 报错信息不带口令：`guard` 只回显 project_id 的值；`pickDbUrl` 只回显 `hostname` 或 `host`（URL 的 host 不含用户名和口令），单测也断言了 `postgres:postgres` 不在消息里；`readStatus` 的异常被吞掉了，`withStatus` 只说“不是 JSON（原文不显示）”。
- `--e2e-sb` 这条路：四项都经 `withStatus` → `guardOrExit`（lemo-e2e 白名单）→ `checkEnv`（去掉 `SUPABASE_*`），API 必须是 55321，DB 必须是本机 55322；`run.mjs` 还会再查一次是不是本机地址。没发现能绕过的地方。
- `CI` 必须严格等于 `'true'`（`'1'`、`'TRUE'` 都拒）。Windows 的 `process.env` 键名不分大小写，这里没有影响。
- 其他 npm 脚本：只有 `test:db` 会调 `supabase test db` 和 `store-it/run.mjs`；`test:db:offline` 用的是 PGlite，不连库。

## 二、清列纯函数

### 已核实没问题的

- 和 SQL 逐条对过：`events_occ_reset` 的 when 条件（date、remind_days 变了，或 time 在空和非空之间变了）；notified_for 合并后的值等于原值，或等于原 `remind_at`（原值非空），就清空；snooze_at 合并后的值等于原值就清空；pushed_for 一律清空。`touch()` 的顺序是先处理待办 due 为空、清 due_time 和 remind_before_min，再按 20 列判断，清 pushed_for、defer_until；触发器先后（occ_reset 在 touch 之前）也和纯函数一致。INSERT 时 `touch()` 先返回，和 `old === null` 只合并一致。
- L6：一律按合并后的值和原值比，不看补丁里有没有这个键，有“显式写了原值”的向量（第 2、10、16、19、23 条）。
- L7：签名上 `applied` 只放实际落库的列，SQL 和 TS 各有一条 forked 的用例。接线（`ackImpl` 传 `appliedColumns(sent, ack)`）归前端 A，本次没有可审的代码。
- L8：向量只写在 `rls/38` 里，`server-reset-vectors.ts` 逐行解析。格式对不上就抛错，条数必须等于 `plan(26)`，所以少读、悄悄跳过都会失败。纯函数（Node，加上 Deno 的 `deno task test tests/shared`，`--allow-read=.` 够用）和替身 `edit()` 读的是同一份。BASE 和 `tests.r38_base` 一致，`fmtReset` 和 `tests.r38` 的格式也一致。
- 不改入参：`old`、`applied` 都先拷进 Map，最后 `Object.fromEntries` 出新对象，单测断言了两个入参都没变。数组值是浅拷贝（和 old 共用同一个引用），函数自己不改它们，可以接受。
- null 和数组：`undefined` 当 null；数组、对象按 `JSON.stringify` 比。相关列（`remind_offsets smallint[]`）只有数组，没有 jsonb 对象，所以键顺序的问题不会出现；`null` 和 `[]` 判为不同，和 SQL 的 `is distinct from` 一致。`time`、`due_time`、`remind_time` 都是 text，没有 `09:00` 和 `09:00:00` 格式不同的问题。

### 必改

**M4（漏列）touch() 的 20 列里有 10 列，既没有向量，也没有静态核对。**
有向量（值确实改了）的列：date、remind_days、time（空和非空）、tz、deleted_at、due、done、month、remind_offsets、calendar（和 lunar_variant 一起改）。没有的列：**due_time、remind_before_min、remind_min（只有“值不变”那条）、remind_time、day、lunar_variant（单独改）、is_leap、year、after_due、kind**。把这些列中任何一个从 `TOUCH_REMIND_COLS` 或替身的 `remindCols` 里删掉，三份测试都不会失败。也就是说，L8 要的“三方一致”对这一半列没有证明力，`touch()` 以后加列时也不会有测试提醒。
改法（两条都做最好，至少做第 ① 条）：① 加一条静态单测，从 `0001_core.sql` 的 `touch()` 里解析出那串 `e.key in (...)`，断言它和 `TOUCH_REMIND_COLS`、替身的 `remindCols` 三者集合相等（替身的列表可以导出来，或直接改成 import shared 的常量）；② 在 `rls/38` 里给上面每一列补一条“只改这一列就清”的向量，每张表各补一条“null 改成值、值改成 null”，比如 `remind_offsets` 从 null 改成 `[0]`，`remind_time` 从值改成 null。

### 建议

- S3：SQL 那边插入时，没写的列取表的默认值，TS 那边没写的列是“没有”（按 null 算）。如果以后有向量把某一列写成它的默认值（比如待办 `done:false`），SQL 判为没变，TS 判为变了，三方就会对不上。建议把 `r38_base`、`BASE` 补成提醒相关列的完整默认值，或者在文件头注明“补丁里不许写成表的默认值，除非原行里写明了这一列”。
- S4：`mergeWithServerResets` 依赖 `old` 是完整的一行，有缺列的话，补丁写 null 会被当作“没变”。请前端 A 接线时确认 `ackImpl` 拿到的 server 副本是整行（拉取时用的是 `select *`），并在函数注释里写明这个前提。
- S5：替身里 `[...remindCols, 'snooze_at'].some(changed)` 决定入队，用的是清列之后的 row 和 old 比（和真库 after 触发器看到的新行一致），没有问题。新加的 `events_allday_ack_enqueue` 分支不在本次范围，rls/36 另外审。

## 结论

不通过。必改 4 条：M1（入口判断失败放行，已实测，红线）、M2（CI 这条路要挡 `SUPABASE_*` 变量和 `.env*` 文件）、M3（project_id 只认顶层那一行，出现其他写法就拒绝）、M4（touch 的列清单要有静态核对或补齐向量）。改完以后送回同一位审查员，复审时逐条复查。
