## 1. 结论

1. **两层判定**：“本机弹过”（每台设备自己记，管 exe 本机通知弹不弹）和“这一次响过”（按 occurrenceKey 认，管 R-336 要不要压住）。
   “这一次响过” = **本机持久记录**，再加上**服务器 `pushed_for` 对得上**。两者有一个成立就算响过。只在“同一次提醒、tag 变了”（全天日程改了 `remind.default_time`、换了时区）时起作用，**tag 没变时各设备的行为照旧**（R-52 两边都响不变）。
2. **本机存**：每个账号一份本机库，记在 meta 仓的一个新键 `remind_seen` 下：`occurrenceKey → { tag, dueAt, local }`。只留 7 天（和“错过的提醒”同一窗口），最多 500 条。不用 localStorage。退出登录、换账号时随整个库一起清掉，不用另写清理代码。
3. **和服务器对齐**：判断“`pushed_for` 落在同一天”的规则抽成 shared 里的一个纯函数，push-dispatch 第 0 步和前端都调它（只是搬家，服务器行为不变）。另外有一处口径不一致需要后端补，见第 7 节 S1。
4. **撤回**：本机通知和 SW 通知的 data 都带上 `occurrence_key`。“打开 App 时撤回”改成直接比 occurrenceKey，只有没带 key 的旧通知才退回现在的推断写法；SW 收到 resolve 时，tag 和 occurrenceKey 有一个对上就撤回（架构 5.3 已写明的兜底约定）。
5. **首屏 0 字节**〔修订 1，P2，主持人定〕：合并视图（持久记录 + 服务器推导）只在 `RemindHost` 分包里算，算好的快照放进 kit 状态，`MissedReminders` 只读快照、不 import 推导代码、不读 outbox。**`MissedReminders` 在引擎 armed（读完 `remind_seen`、算出第一份快照）之前不显示**，之后用今天页现有的 `GrowIn` 展开（实现时改，审查“错过提醒推迟挂载”建议；GrowIn 管高度过渡、手指按着时不动）：不先显示一个数再跳、不占首屏字节。这改掉了 J1“首屏一打开就显示错过 N 条”的行为（主持人 11-05 定）。

## 3. 统一判定

对一条提醒 `r`（`key = occurrenceKey(r)`）：

```
本机记录  seen = remind_seen[key]                         // 持久的，见第 4 节
服务器那边 pushedSameOcc(r) =
    row.pushed_for 是数字
    且 key !== r.tag                                                       // 〔修订 1，L4〕只对全天日程（没按稍后）做，理由见下
    且 这一行在 outbox 里没有换了“哪一次”的改动（见下面第 ③ 条）
    且 sameRemindDay(row.pushed_for, r.remindAt, tz)                       // 和第 0 步同一个函数
这一次响过 rangOcc(r) = seen ?? (pushedSameOcc(r) ? { tag: reminderTag(kind, id, row.pushed_for), dueAt: row.pushed_for, local: false } : undefined)
```

| 用到它的地方 | 规则（tag 没变的情况照旧） |
|---|---|
| 横幅 `ringing` | `rangOcc(r)` 存在、而且它的 tag ≠ `r.tag`：不进横幅（R-336）。合并视图在 RemindHost 分包里算（每分钟、list 变了时各算一次），结果写进 kit 状态（或 `rangStore`），`rangSnapshot` 读它，签名不变〔修订 1，P2〕 |
| 错过的提醒 `missed` | 同上：按 `rangOcc.dueAt` 显示当时实际响的时刻（R-336 ②）。这条在服务器推过、本机没响过的情况下也成立：手机 07:00 推过，电脑重开后显示“07:00”。`MissedReminders` 只读引擎算好的快照，armed 之前不显示〔修订 1，P2〕 |
| exe 本机通知 `localDue` | 本机弹过（`seen.local === true`）的不再弹；`rangOcc(r)` 存在、而且 tag ≠ `r.tag` 的也不弹。tag 相同、只是服务器推过的，照旧弹（R-52） |
| 已处理 `handled` | 不变：仍然只看 `notified_for`（`allDayAcked`），持久记录不参与 |

③ **离线改动的防护**：本机换了“哪一次”以后，本机行里的 `pushed_for` 还是旧那一次的，服务器那边已经清空或即将清空。照用的话，新的那一次就会被误压。分两段时间防：
   - **还在 outbox 里**：这一行在 outbox 里有任何一项（pending、inflight、failed 都算，发没发出去都算）改了 date、remind_days 或 time 的空与非空，就不采信 `pushed_for`。`timingPending` 只看最后一项、只认 pending 而且没发出去的，口径不够，要新写一个 `occurrencePending(r, items)`。
   - **〔修订 1，P1〕已确认、还没拉回**：`ackImpl` 确认以后，项离开 outbox，本机 server 副本里的 `pushed_for` 却还是旧值，要等下一次拉取或实时推送才会变。评审举了三种会在这段时间里误压的组合：有时刻改成全天且同一天；D 挪到 D+1 且 remind_days 0→1；D 挪到 D−1 且 remind_days 1→0。做法：`core/outbox-send.ts` 的 `ackImpl` 合 server 副本时，照服务器触发器的规则先清本机副本：
     - 日程换了“哪一次”（date 变、remind_days 变、time 的空与非空变；和 `events_occ_reset` 同一条件）：`pushed_for` 一律清空；`notified_for`、`snooze_at` 这次补丁没改就清空，改成了 `old.remind_at` 也清空（迁移 20261104110000）。
     - 提醒相关列变了（`touch()` 那一组）：`pushed_for`、`defer_until` 清空。
     - 规则写成 shared 里的纯函数（core 不准 import features，A1），本机替身 `tests/edge/push-dispatch-mem.ts` 的 `edit()` 和它对照测试，免得两边各写一份走样。这样也顺带修好了 `allDayAcked` 在同一段时间里的同类问题。
     - **已做（11-05 后端，待审）**：`shared/logic/server-reset.ts` 的 `mergeWithServerResets(table, old, applied)`——`old` 是合并之前的 server 副本（新建时传 null，只合并），`applied` 是实际落库的列（forked 时传 `appliedColumns(sent, ack)`，L7），返回新副本、不改入参；一律按合并后的值和原值比（L6）。照 `events_occ_reset` 和 `touch()`（含纪念日那组提醒列、待办清空 due 时连带清 due_time、remind_before_min）。三方一致（L8）：向量只写在 `supabase/tests/rls/38_server_reset_parity.test.sql`（真库、离线库都跑），`tests/shared/server-reset.test.ts` 读同一份向量跑纯函数（Node、Deno），`tests/edge/push-dispatch-mem-reset.test.ts` 跑替身 `edit()`（替身顺带补齐了纪念日的列、数组按值比、清截止时刻）。接线：`ackImpl` 里把三处 `{ ...server, ...X }` 换成 `mergeWithServerResets(sent.table, server, X)`，归前端 A。L9（remindDown 时 MissedReminders 用空快照照旧显示）是前端的事。
       11-05 审查补：rls/38 的向量 48 条（touch() 的 20 列每列都有，可空的列另有“空改成值”“值改成空”），另有静态测试从 0001 的 touch() 解析列清单、和 shared、替身三方比对（M4）。S3：SQL 插入时没写的列取表的默认值，TS 那边按 null 算，所以向量的补丁里不许把一列写成表的默认值，除非原行里写明了这一列（rls/38 文件头写明）。S4：`old` 必须是整行（`select *` 拉来的 server 副本），接线时由前端 A 确认。
   - L4〔修订 1〕：服务器推导和 `occurrencePending` 只对全天日程（key ≠ tag）做。有时刻的提醒 key 就是 tag，推导出来的 tag 等于 `r.tag`，三处规则都不起作用，套上只会多花字节、多读一次 outbox。

## 4. 本机存什么

- **位置**：本机库的 meta 仓，键 `remind_seen`，`MetaMap` 里加 `remind_seen: RemindSeen`。只是加一个键，**库结构不变，不升 `DB_VERSION`，`cache-schema.lock` 不变**。
  - 选 meta 的理由：这个库按账号分（有 owner 仓），退出、换账号、被移除时 `clearAll` 或按库名删库会一起清掉，不用另写清理代码。
  - 不选 localStorage 的理由：localStorage 不分账号，同步读写会占主线程，两个标签页也没有事务。
  - meta 仓迁移失败时会被重建（`rebuildable: true`）。重建以后退回到“只靠服务器 `pushed_for`”，最坏多响一次，和现在一样，可以接受。
- **格式**：

```ts
interface RemindSeen {
  v: 1;
  /** occurrenceKey → 那一次 */
  items: Record<string, { tag: string; dueAt: number; local: boolean }>;
  /** 只在本机了结、还没补写的“知道了”（REMIND-offline-ack-merge 第三轮 L10 的 laterAcks，可选并入，见第 8 节） */
  laterAcks?: Record<string, { kind: 'event' | 'todo'; id: string; remindAt: number | null }>;
}
```

  - `tag`、`dueAt`：第一次响的那一次，同一个 key 只记第一次，和 `recordRang` 一致。`local`：本机弹过系统通知（exe）。横幅响过但没弹系统通知的记 `false`。
  - **不存标题、正文、日期文字**。key 里只有 uuid、日期、0 或 1，tag 里只有 kind、uuid、毫秒数，和 outbox、同步仓里已有的数据同一级，不新增敏感内容。
- **读**：引擎（`useRemindEngine`）挂上时读一次，读完灌进 `rangStore` 和 `shown`，**然后才调 `setRemindArmed(since)`**。读失败当成空的，照常挂上。
- **写**：`recordRang`、`shown.set` 有新项时标记“脏了”，每分钟那次 tick 里最多写一次。**〔修订 1，L2〕`local: true` 的项（本机弹过系统通知）一记下就立刻写**（次数很少）；另外在 `pagehide`、`visibilitychange` 变成 hidden 时补写一次（React 关页面时不会卸载，光靠“卸载时补写”不够）。都在同一个 readwrite 事务里先 get 再按 key 合并：已有的 key 保留原值，然后 put。两个标签页各自写时不会互相覆盖。写失败不重试，下一次再试。
- **清理**：写的时候顺便剪掉 `dueAt ≤ now − 7 天` 的项。超过 500 条时按 `dueAt` 从旧往新删。

## 5. 和 `notified_for` 的关系

- “知道了”照旧只写 `notified_for = r.remindAt`。持久记录**不替代**“知道了”，只回答“响过没有”，不回答“处理了没有”。
- **口径差异**：服务器的 R-336 对 `remind_days = 1` 也按天比，本机的 `allDayAcked` 对 `remind_days = 1` 要求正好相等（前端增量审查 M1）。平时前一天提醒固定 20:00，两边一样；**换了时区（R-341）以后**就会不同：服务器认为当天已经处理、不推，本机算出新的 20:00、和 `notified_for` 不相等，于是本机又响。
  - 建议：本机改用和服务器同一个“按天比”的函数。M1 担心的是把“当天提醒”的“知道了”套到“前一天提醒”上，这种情况已经被换次清空覆盖了：改 `remind_days` 时服务器和本机都会清空 `notified_for`。
  - **11-05 主持人定：统一按服务器“同一天”口径比**，前端 B 调 shared 的 `sameRemindDay`。〔修订 1，L5〕效果收窄为：**前一天提醒换时区不多响**；当天提醒往西跨日换时区（如首尔换到洛杉矶），旧 `pushed_for` 在新时区落在前一天，**服务器和本机会一致地再响一次**（R-341 已接受）。

## 6. 撤回判定（REMIND-close-occkey 前端一半）

**带上 key**
- 服务器负载已经带了可选的 `occurrenceKey`。SW 的 `NotificationData` 加一个 `occurrence_key?: string`：`parsePushPayload` 和 `dataOf` 调 `shared/logic/remind-route.ts` 的 `validOccurrenceKey`（11-05 后端已加；和服务器 payload.ts 那份照抄的由 `tests/shared/push/occkey-parity.test.ts` 钉住逐条一致），不合格就不带，**只用来比较、不显示**。
- exe 的 `showLocalReminder` 的 `LocalReminder` 加 `occurrenceKey`，desktop.ts 放进 WebView2 通知的 data。

**“同一次”的定义（三处都用这一条）**：两条通知 tag 相同，或者两边都带了 key 而且 key 相同（字符串全等），就算同一次。

| 场景 | 规则 |
|---|---|
| SW 收到 resolve | 同一个 owner 的通知里，凡是和 resolve 指的那一次是“同一次”的，都关掉，然后照旧显示同 tag 的“已在另一台设备上处理”。只关通知，不做别的（安全审查复核四条：全等比较、核对 owner、只关通知） |
| 打开 App、回到前台（`closeHandledNotifications` → `shouldCloseShown`） | 遍历时把 `dataOf(n)?.occurrence_key` 也传进去：找不到这一行，就按 `rowKnown` 处理（照旧）；已经处理了就关；**〔修订 1，L1〕带了 key 时先按 key 判**：等于 `occurrenceKey(r)` 就留着（R-336 ①），不等就关，不看 tag。原因是默认时刻设成 20:00 时，“D 当天 20:00”和“D+1 前一天 20:00”是同一个时刻，tag 相同、key 不同，先比 tag 会把旧通知留下；**没带 key**（旧通知、iPhone 拿不到 data）：tag 相同就留着，不同就退回现在的按天推断。SW 收到 resolve 时照旧“tag 或 key 任一对上就撤回”，不用改 |
| exe 撤回（`staleShown`） | 现在就是按 key 记的，不用改。〔代码审查一 L13 更正〕`closeLocalReminder` 只能关本页内存里留着的通知对象，所以重开 App 以后**撤不回**上一次打开时弹出的通知：持久记录灌进 `shown`，只是为了不重复弹。重开后那条旧通知会不会留在系统通知中心、留多久，记进真机验收清单核对 |

L7 漏洞的那个例子：旧通知的 key 是 `…:allday:D:1`，新的那一次是 `…:allday:D−1:0`，两个 key 不等，旧通知会被撤回。

## 7. 需要后端做的（S 项，我这边认领）

- **S1 resolve 漏掉了“全天日程改了默认时刻以后按的知道了”**（11-05 主持人定修，已做；安全审查 9/10 通过，见 `B2-安全审查-全天提醒确认入队.md`，采纳 A1、A3、A4，A2 不动）。
  - 现象：R-336 压住以后，服务器的 `remind_at` 还是旧值，本机“知道了”写进去的是本机现算的新时刻，所以 `notified_for ≠ remind_at`；`due_at` 也还等于 `pushed_for`。`remind_pushed` 和 `round-util` 的 resolve 条件都不成立，安卓、Edge 上那条旧推送就收不回来（iPhone 本来就不发 resolve）。而且这次写入只改了 `notified_for`，不在 `events_remind` 的触发列里，这一行不会再进 remind_queue。
  - **实际改法和初稿不同**：初稿想在 SQL 里按 current_tz 比“同一天”。动手时发现 current_tz 坏了的话，`at time zone` 会报错，整个 `remind_pushed` 失败，全站的 resolve 都停掉（20261103140000 ④ 不在 SQL 里认时区名，也是这个理由）。所以改成两半：
    - ① 迁移 `20261105120000_core_allday_ack_enqueue.sql` 加触发器 `events_allday_ack_enqueue`：全天日程（time 为空、没删、remind_days 不为空——A1）的 notified_for 改成了不等于 remind_at 的值，就复用 `private.enqueue_remind` 入队。只多一次入队，不改列、不授权限。
    - ② 第 0 步的 R-336：如果 notified_for 正好等于新算出的 remind_at，就不压住、照写回。写回后 notified_for = remind_at，第 1 步不会在新时刻再推，resolve 在同一轮成立。写回时除了 remind_at 还是读到的值，另要求 notified_for 也还是读到的值（A4：读完以后另一台设备又改了 notified_for，就不按旧的“知道了”写回新时刻；没写成就放回队列，按新值重算）。
  - 用例：`supabase/tests/rls/36_allday_ack_enqueue.test.sql`（12 条，含 A1“不提醒的不入队”）、`tests/edge/push-dispatch-allday-ack.test.ts`（4 条，含 A4 夹在读写之间改 notified_for，变异验证会红）、`tests/functions/push-dispatch-store.test.ts`（A4 的查询链）。
  - **收不回的两种情况（A3，既有口径，验收时不算回归）**：
    - S1 只在客户端现算的时刻和服务器新算的**完全相等**时成立。客户端时区和 `current_tz` 不同，或者另一台设备又改了 default_time 还没同步过来，notified_for 就不等于新算值，仍按 R-336 压住，旧推送收不回（edge 用例“notified_for 落在同一天、但不等于新算出的时刻”钉的就是这个行为）。

## 11. 实现记录（前端 B，11-05）

- 本机记录：`src/features/reminders/data/remind-seen.ts`。meta 键是 `remind_seen`，内容为 `{v:1, items}`，只留 7 天、最多 500 条；写的时候在同一个 `cache.tx([meta])` 里先读、按 key 合并再写（`mergeSeen`：已有的 key 保留原来那一次，local 只会从 false 变成 true）。读失败当空的，写失败返回 false、不抛错（引擎会把这批放回 dirty，下次再写）。
