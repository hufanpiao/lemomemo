## 分项

### 1 · occurrenceKey 白名单两份
- `shared/logic/remind-route.ts` 的 `validOccurrenceKey` 和 `payload.ts` 的 `occKey`、两份 `isRealDay` 逐字一致。
- `tests/shared/push/occkey-parity.test.ts`：固定向量（非字符串、包装对象、大小写、首尾空格、闰年、非法月日、全角和阿拉伯数字、超长尾巴）× 三种 kind × remind/resolve，另有 2000 条确定性随机变形；经 `buildPayload` 比对结果，比的是实际发出去的负载。变异验证证明能测出差异。Deno 的 `deno task test` 也覆盖 tests/shared。
- 低 L1：remind-route.ts 注释写“SW 读负载和通知 data 时调这一份”，但 `src/sw/` 目前还没有调用者（前端那一半没接）。建议改成“将由 SW 调”，免得以为已经接好。

### 3 · 系统列同步
- 对照 `private.touch()`（0001_core.sql）：rev、fv、synced_at、updated_at 加上 table_meta 的 system_cols 都跳过，最后统一写 `synced_at = now()`。37 号先把 synced_at 往回拨一小时，再断言等于 now()（事务内 now() 不变），能区分“刷新了”和“插入时的旧值”。系统列如果从 system_cols 里漏掉，rev 会加 1，测试会红。
- 本机一半：同 rev 照收、rev 更旧照跳、本机有待确认改动时 view 叠加，4 条都会因为合并条件写错（比如写成 `<=`）而红。
- 低 L2：37 号第 ② 段写 remind_at、defer_until 以后马上又往回拨，这一次 synced_at 有没有刷新没有单独断言，最后的断言只证明了最后一次（清 pushed_for）。建议在第二次往回拨之前补一条 `synced_at = now()`。

### 5 · 首屏块里不能有农历数据
- 按块的键、src、name 认 `_lunar-…`、`shared/logic/anniv/lunar…`；内容按 LUNAR_CN 前三项数字串认。测试直接从 lunar-data.ts 现取前三项核对，数据换了会红；LUNAR_KR 有了数据会强制要求登记。只经动态 import 引入的农历块不报，对照用例有。
- 在现有产物里核实过特征串确实存在。通过。

### 4 · store-it 的 `--e2e-sb`
- 红线核对：带这个选项时，不在仓库根目录跑 `supabase status`（仓库 config 的 project_id 是 **lemomemo**），只经 `statusEnv()`：先过 workdirProblems、checkGuard（project_id 严格等于 lemo-e2e，所有端口 55320～55329/8084），在 `.e2e-sb` 里用去掉 SUPABASE_* 的环境跑 status，并要求 API 在 55321；DB 端口固定 55322，不是 543xx/583xx。**连不到 lemomemo、lemo-purgeit**。出错时返回 null，退出码 1。不带选项时 `readStatus` 一字未改。
- 中 M1：DB_URL 的端口取的是 `PORT_TARGETS` 里的“改写目标值”，不是 `.e2e-sb/supabase/config.toml` 实际写的值，也不是 status 给的 DB_URL。checkGuard 只保证 db 端口在 553xx 范围内，不保证正好是 55322。注释“护栏钉死的 [db] port”不准确。现在不会突破红线（553xx 里没有别的项目），但 API 是按 status 核过的，DB 却只是拼出来的，两边口径不一致。建议：`pickEnv` 一并取 status 的 `DB_URL`，并要求端口 === 55322（或者 run.mjs 读副本 config 核对 `[db] port = 55322`），不一致就拒绝。
- **范围外，高（需主持人定）**：不带选项的老路径会在仓库根目录跑 `supabase status`，而仓库 config 的 project_id 是 `lemomemo`。本机直接跑 `node supabase/tests/store-it/run.mjs` 或 `npm run test:db`，会把集成测试写进 lemomemo 的本地库。CI 里没有问题，但本机是在红线边上。这一条和“不传时行为不变”的要求冲突，所以不算本次必改。建议主持人决定是否改成：非 CI（`CI !== 'true'`）时，status 返回的 API 端口是 54321，或者仓库 project_id 是 lemomemo，就拒绝，并提示加 `--e2e-sb`。

### A4 · writeRemind 加 prevNotifiedFor
- 误放行：只有 `notified_for === 新算出的 remind_at`（毫秒绝对时刻、严格相等）才走例外。换了“哪一次提醒”（挪日期、改 remind_days、time 在空和非空之间变）都会被 events_occ_reset 清掉 notified_for，旧的“知道了”不会恰好等于新时刻。写回以后 notified_for 等于 remind_at，等于用户已经确认过这个时刻，不推是对的。没发现误放行的路径。
- 误挡：读完以后 notified_for 被别的设备改了，`.eq('notified_for')` 就更新不到行，这一项放回队列；下一轮按新值重算，要么照 R-336 压住，要么再走例外，不会死循环。不走例外时不传这个参数，链上没有这一项（store 测试按整条调用链精确比对），旧行为不变。
- 测试：MemDb 替身和真 store 的调用链都钉住了；allday-ack 有竞态用例（读写之间 notified_for 改成 07:10，确认不写回、之后也不再推）。去掉 store.ts 里的 `.eq` 会让 push-dispatch-store 那条红。
- 低 L3：push-dispatch-store 那条用例标题说“不传时链上没有这一项”，用例体只测了传的情况；不传的情况是靠上一条用例的整链比对兜住的。建议在本条里补一个 `writeRemind('events', …, 5)` 的对照。
