## 结论：不通过，3 条必改

- 两个新函数的权限面是对的：security definer、`search_path = ''`、lock_timeout 5s、只授 service_role，anon 和 authenticated 调用都回 42501。

## 三、必改

| # | 级别 | 问题 | 改法 |
|---|---|---|---|
| **1** | 中（跨用户；重算会被丢掉，可能漏提醒） | **有毒项是按整批累计次数的。** `attempts` 每次出队都加 1，只有被 finish 放回时才减 1，被删就清零。租约过期时，整批 ≤ 500 项（其中最多 50 项是同一个人的）会被一起重取，每项都再加 1。所以一批里只要有一项一算就把进程弄死，或者 finish 连续失败（见必改 2），连续 5 次以后，**同一批里所有用户的项都会被当成有毒项删掉**，他们的 remind_at 不会再重算，要等他们自己再编辑才会重新入队。这正是第 4 问“故意让别人的提醒重算被丢掉”的答案，而方案“一个有毒项最多拖垮 5 轮”的前提不成立。另外，用户在处理窗口内编辑了自己的项、清掉了租约，这一项就逃过了 finish 的“放回减 1”，次数也会一直往上涨 | 让次数只记在真正出问题的那一项上。可选做法：① 已经被取过的项（attempts ≥ 1）重取时单独成批、或者每轮最多取 1～几项，取完马上单独 finish，这样无辜的项一被隔离就不会再涨；② 或者 step0 每处理完一项就 finish 这一项（逐项收尾），崩溃时只有排在崩溃点之后的项会被重取，再配合 ①。选定后补 pgTAP：一批里一项一直“崩”，同批其他用户的项连续 5 轮以后仍然还在 |
| **2** | 中（可被普通用户触发，要真库确认） | **finish 会被用户的写入锁住，超时就整批失败。** finish 的 update、delete 碰到被用户事务锁住的队列行时，要等那个事务结束；超过函数的 lock_timeout 5s 就报错，`queue_finish_failed`，这一批的租约都不清、项都不删，3 分钟后整批重取、每项 attempts + 1。一个用户用 PostgREST 发一条批量 PATCH（例如把自己 2 万条日程的 `snooze_at` 或 `deleted_at` 都改一遍，authenticated 的 statement_timeout 默认 8 秒），只要掐在第 0 步的处理窗口里，就能让 finish 超时；连续 5 轮，就落到必改 1：同批其他用户的项被丢掉 | finish 里的放回和删除都改成先 `select ... for update skip locked`，只处理锁得到的行。被用户锁住的行，要么正在被重新入队、租约会被清掉，要么用户事务回滚、留着等过期重取，而且只影响用户自己的项。补真库并发测试：一个连接锁着某一项不提交，另一个连接调 finish，应该不等锁、其余项照常删掉 |
| **3** | 中（可用性，没人知道） | **回滚以后第 0 步一直跳过，没有告警。** 手册第四节第 2 层写清楚了后果，但 `queue_pop_failed`、`queue_finish_failed`、`queue_poison` 都只记在 push-dispatch 的日志里，lemo-ops 和 usage-report 都不读。心跳只有 claimed、sent、failed、budget_hit，第 1～8 步照常跑，心跳也照常新鲜。所以回滚以后、或者 pop 因为别的原因持续失败时，编辑过的提醒一直不重算，**没人会知道**；有毒项把别人的项丢掉也一样没人知道 | push-dispatch 心跳加两个非负整数，比如 `queue_ok`（这一轮第 0 步成功是 1、失败是 0）和 `queue_poison`（这一轮丢弃的个数）。同步进 usage-report 的 `DETAIL_FIELDS_BY_NAME['push-dispatch']`，只是个数，符合 D2-S2 口径。lemo-ops 加两条：第 0 步连续 N 轮（例如 10 轮）失败就告警；`queue_poison > 0` 当天提示。或者 usage-report 报“队列里租约过期最久的那一项距今多少秒”和“项数”，lemo-ops 超过阈值告警 |

## 四、第 4 问：有毒项丢弃会不会被人利用

- **只靠编辑自己的行**：4 个入口都只按本人的行或本人的 user_id 入队（RLS 只允许改自己的行；anniv、allday 两个入口按 `new.user_id`；floating 按本人 uid），所以没法直接把别人的项写进队列，也没法改别人的 attempts。
- **借整批连坐**：可以，见必改 1、2。要么有一个“一算就崩”的输入（方案本身就假设可能存在），要么用一条持锁超过 5 秒的批量修改让 finish 超时；连续 5 轮，同一批里别人的项就会被丢掉。
- **放大效应**：以前出队即删，一个有毒项每次编辑只能让一轮崩。现在每次编辑可以换来最多 5 轮崩溃（每轮间隔一个租约，180 秒）。不过攻击者本来就能每分钟编辑一次，单论崩溃次数不算新的放大；真正新增的风险是上面的整批连坐。
- **用户自己的项**：频繁编辑也可能把自己的项推到 5 次被丢掉，只影响本人。修好必改 1 以后会一起缓解。

## 五、第 3、5 问：回滚和迁移本身

**回滚（第 3 问）**：
- 手册说“回滚 push-dispatch 到租约版之前，第 0 步会一直跳过；队列不丢，到点推送照常；回滚期间尽量短；不要手工把旧函数建回来”，这些都对。
- 有一句不准：“下一轮把积下的项一并算完”。出队每轮最多 500 项、每人最多 50 项，积压要分好几轮才能消化完，积得多的人要等更久。建议改成“之后每轮最多 500 项（每人 50 项）逐轮消化”。
- 没有告警，见必改 3。
- 迁移本身不能回滚（旧签名已删）。手册写了“迁移不跟着回滚”，这一点对。
- 发布顺序“先后都行，中间第 0 步跳过、队列不丢”：两种顺序都只是 pop 调不到签名、走 catch 分支，第 1～8 步照常，结论成立。

**迁移本身（第 5 问）**：
- **重复执行**：`add column`、`drop function`、`create function` 都没有写 if exists 或 or replace，所以不能重复执行。迁移由 Supabase 的迁移记录保证只跑一次，每个迁移在一个事务里，中途失败会整体回滚，可以接受。
- **新列会不会锁大表**：`claim`、`claimed_at` 可空，没有默认值；`attempts smallint not null default 0` 是常量默认值，PG 11 以后只改元数据，不重写表，三列都不会重写表。但 `alter table` 要拿 ACCESS EXCLUSIVE 锁。迁移没有设 lock_timeout，如果有长事务正持有 `remind_queue` 的锁，alter 会一直排队；排队期间，所有走入队触发器的用户写入也会排在它后面，看起来就像整站写入卡住。仓库里已有 3 个迁移在开头写了 `set lock_timeout`，建议照做（建议 S1）。
- 删旧签名：仓库里没有别的 SQL 引用 `remind_queue_pop(int)`。离线全量测试通过，03 号白名单也同步了。

1. **“在持锁方提交前结束”这一条并不是决定性的**（文件头的注释是这么说的）。
   - 持锁方的提交时刻 `holderCommitAt`，是在 `commit` 之后另一条语句里取的，比真正放锁晚一个往返。
   - 如果另一边确实在等锁，放锁后它几毫秒就能结束，而持锁方下一条语句也要几毫秒。谁先谁后是竞态，`endAt < holderCommitAt` 有可能成立。

2. **另一边起得太慢，语句在持锁方提交之后才开始时，根本没测到锁**。
