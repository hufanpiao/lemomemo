## 逐项核对

**1. 安全**

- `private.enqueue_allday_defaults()`：plpgsql，`security definer`，`set search_path = ''`，表名都写全（`public.events`、`private.remind_queue`）。
- 只按 `new.user_id` 选行。`settings` 的 `upd` 策略带 `with check (user_id = auth.uid())`，`authenticated` 只能改 `value, deleted_at, undone` 三列（0001 第 279～280 行），改不了 `user_id` 和 `key`。客户端没有办法借这个触发器把别人的行放进队列；写进队列的也只是 id，不改业务行。
- 执行权：0001 第 7 行收回了 PUBLIC 默认的函数执行权，这个迁移也没有 grant；rls/32 第 21～24 行检查了 anon、authenticated、PUBLIC 三者都没有。Postgres 只在 `create trigger` 时检查建触发器的人有没有执行权，触发时不检查，所以不给执行权照样能触发；rls/32 第 37 行用 `authenticated` 身份写入，验证了这一点。D1 白名单 `FUNCTION_EXEC` 不用改，和注释说的一致。
- 触发列 `value, deleted_at, undone` 正好是客户端能改的三列。`settings` 不给 `authenticated` delete 权限，所以没有“硬删以后不入队”的漏洞。
- 放大写入：每改一次设置，会把这个人所有没删的全天日程放进队列。数量受这个人自己的行数配额限制，和 0005 的 `enqueue_anniv_defaults` 一样，可以接受（另见 L3）。
- store：`settings` 查询加了 `.eq('undone', false)`；service_role 本来就绕开 RLS，按 `user_id` 分组，不会串到别人。

**2. 正确性**

- 提醒时刻：`round-step0.ts:80` 把 `settings.get(user)['remind.default_time']` 作为第 6 个参数传给 shared 的 `allDayRemindAt`。`remind_days = 0` 取当天的 `default_time`，没设或认不出时按 09:00；`= 1` 取前一天固定的 20:00；tz 用 `current_tz`。待办分支不传第 6 个参数。`store.ts:20` 读取的列里本来就有 `remind_days`。有测试（allday 第 50、64、117、133 行）。
- 文案：`round-dispatch.ts:204` 传 `allDay: { date, at: x.due }`，其中 `x.due` = greatest(remind_at, snooze_at, defer_until)，已经算进了免打扰推迟。第 192 行的 tz 是第 2 步定下的 current_tz（current_tz 无效时，全天日程在第 2 步就跳过了，到不了这里）。有时刻的日程不传 `allDay`。这和前端约定的三点一致。免打扰把前一天 20:00 推到当天 08:00 时写“今天”，有测试（allday 第 103 行）。
- “开始时刻”：`eventStartAt` 对全天日程改用 `startAtOf(当天, current_tz, default_time)`，和 shared 的 `remind-actions` 口径一致。全天分支里 notify-text 不用 `timeMs`，所以不会影响文案。
- 已过时不回落：shared 原样返回算出的时刻，不回落。但不补推这一点有出入，见 M1。
- store 读 settings 排除撤销的：已经做了，测试真的按条件筛了行（store 测试第 200 行起），不只是检查“调用里有这一项”。
- current_tz 无效：第 0 步对全天日程先判断，原因码记 `profiles`（step0 第 74～77 行）；待办、纪念日也统一记 `profiles`；日程自己的 tz 无效仍记 `events`。第 2 步原来就记 `profiles`。有测试（allday 第 145、156 行，step0 第 116、132 行），而且断言了日志里不会出现时区串和标题。

**3. 上线顺序（已定：先部署函数，再单独推迁移）**

- **函数先上、迁移还没上：不会出事。**
  - 新函数读的 `settings.undone` 列 0001 就有了，`SETTING_KEYS` 多读一个键也不需要新表结构。
  - 已有的全天日程这时 `remind_at` 仍是空的（旧服务器一律算出 null，`remind_at` 又是系统列、客户端写不了），所以不推。这和上线前一样，不比原来差。
  - 新建或编辑的全天日程会经 `events_remind` 入队，由新函数算出来。
  - 改 `default_time` 在迁移上之前还不会入队，只是晚生效。
- **迁移先跑、函数还是旧的：会出事。** 上线手册第三节已经写明了这个顺序和预览要分两次推，但真实后果和手册写的略有不同：
  - 正式库里全天日程的 `remind_at` 本来就是空的。旧函数算出 null 以后，判断“和原来一样”就不写回，所以并不是“写成空”。
  - 真正的后果是：出队即删已经把补算的队列消耗掉了。之后新函数上线，也没有行可以重算，这些日程要等用户编辑或者改 `default_time` 才会恢复。只有预览库里已经被新函数算过的行，才会真的被写成空。
  - 结论没变：必须先上函数。见 L4。
- 回滚：函数回滚到旧版、迁移还留着时，用户每改一次 `default_time`，旧函数就会把这个人的全天日程 `remind_at` 写成空。手册第四节的回滚部分没有提到这一点，见 L4。

**4. 测试覆盖**

- 已覆盖：两种 `remind_days`；有没有设 `default_time`；改 `default_time` 以后重算；前一天的提醒不受 `default_time` 影响；R-333 中文、韩文；R-334 两种；免打扰推到当天写“今天”；current_tz 无效时第 0 步和第 2 步记 `profiles`、不泄露时区串和标题；纪念日也记 `profiles`；settings 撤销、软删的过滤；rls/32 的函数属性、执行权、新建、改值、重复入队、软删、恢复加撤销、别的键不入队，计划 11 条，数目对得上。
- 缺：
  - “已过时不补推”在服务器一侧没有测试（M1）；
  - 推过以后再改 `default_time`（M2）；
  - 免打扰推到日程过后只写名称、按“稍后”以后的文案，服务器一侧没有测（shared 已经测了）；
  - `index.ts` 里真正的 LOGIC 没有被任何测试执行（L1）；
  - 补算那一句、只改 `undone` 的情况（L5）。

### 协调者点名的三点

**1. 触发器的执行顺序，以及和 `touch()` 的交互：顺序对，后端说的属实。**

- events 表上的 BEFORE UPDATE 触发器只有 `events_occ_reset` 和 `events_touch`（`events_quota` 只在新建时触发）。Postgres 对同一时机的触发器按名字顺序执行，`events_occ_reset` 排在 `events_touch` 前面，所以先清空、再交给 touch。
- `touch()` 第 54 行先把 `new.fv`、`new.rev` 换回旧值，再逐列比较新旧值。`notified_for` 不在 events 的 `system_cols` 里（系统列只有 `pushed_for`、`defer_until`、`ai_status`、`remind_at`），所以“置空”会被记进 fv、`rev` 加 1，同步时能把“已清空”带回各端。`pushed_for` 是系统列，不进 fv，这也是对的。如果顺序反过来，touch 已经比较完了，“置空”就同步不出去。
- 触发列 `update of date, time, remind_days` 加上 `when` 判断，只有值真的变了才触发。客户端的补丁只带变了的列（`patchOf`），`apply_patch` 也按补丁里的列写，不会误触发。
- 函数只改 `NEW`，不读写任何表；security definer、`search_path` 置空、不授执行权，rls/32 都断言了。
- 测试有一处没证到，见 R3-L1。

**2. “显式写了 `notified_for` 就保留”会不会被旧客户端误用：不会造成安全问题，正确性上只剩一个很窄的情况。**

- 判断的写法是 `new.notified_for is not distinct from old.notified_for` 才置空，看的是“值有没有变”，不是“补丁里有没有这一列”。所以旧客户端把整行原样写回（`notified_for` 还是旧值）时，照样会被清空。
- B2 之前的客户端改日期时根本不带 `notified_for`，会被清空，这正是需要的效果。
- 客户端只能改自己的行（RLS 加上列级授权），写了奇怪的值也只影响自己这一条，没有越权。
- 唯一会误判的情况：离线时先改了日期（补丁里 `notified_for: null`），又在系统通知栏对**旧那一次**的通知按了“知道了”（写 `notified_for` = 旧的提醒时刻），outbox 把两次合成一个补丁：`{date, notified_for: 旧值}`。服务器照客户端的值保留，如果新那一次落在同一天，就会被压住。顺序反过来（先“知道了”、再改日期）时，后写的 null 覆盖前面的值，没有问题。见 R3-L4。

**3. 前端 B 本机编辑同时清 `notified_for`、`snooze_at`，和服务器会不会打架：不会，两边写的值相同。**

- 本机补丁是 `{date…, notified_for: null, snooze_at: null}`。服务器触发器看到 `notified_for` 是 null：原值不是 null 时，算“显式写了新值”，照 null 保留；原值本来就是 null 时，置空，结果还是 null。两边一样，`touch` 只记一次 fv，不会来回改。
- 两个触发条件逐项一致：`date` 变了、`remind_days` 变了、`time` 在空和非空之间切换（`event-edit.ts:147` 和迁移第 91～93 行）。
- 不一致的只有一处：服务器**不清 `snooze_at`**。前端 B 之外的写入路径（B2 之前的客户端、以后服务器一侧的 AI 编辑）改了日期以后，旧的“稍后”还在。见 R3-L2。
