### hit-target 把编辑页拆成单独用例：正当写法，还是掩盖夹具缺陷

**判断：拆开本身是正当写法，但这里的动机是绕开 `csp-fixture.ts` 的一个真缺陷。这个缺陷还在，而且不只会多报违规，还会漏判违规。拆开可以先这样合，但必须把夹具缺陷登记成遗留。**

**夹具缺陷是什么**（`tests/e2e/csp-fixture.ts`）：
- 两路判断的口径不一致：
  - 控制台那一路：`consoleErrors` 在 Node 一侧收集，整条用例累计；
  - 能抵掉 WebKit 误报的额度 `__cspSelects`（建过几个 `<select>`）、以及违规事件列表 `__csp`，都存在页面的 `window` 上，每载入一次文档就清零。收尾时只能读到最后一个文档的值。
- 这会造成两种后果：
  1. **多报**：前面几个文档里建 `<select>` 引起的控制台报错留在累计里，抵扣额度却只剩最后一个文档的，于是被当成真违规。B 这次遇到的就是这一种。
  2. **漏判**（更要紧）：前面几个文档里真正的内联样式违规事件，随着 `window` 一起丢掉了，事件那一路根本看不到。只剩控制台那一路的通用文字可能兜住，而那一路本来又按 select 个数在扣。所以凡是一条用例里载入多个文档的 e2e，前面文档的 CSP 违规都可能漏掉。

**拆开以后还有一个疑点**：
- `measure()` 每页都是先 `goto` 再 `reload`，`seed()` 也先载入过一次 `/app/#/todos`。`goto` 到编辑页的那一下只改了 hash，还是同一个文档，编辑页会先在这个文档里画一次、建一次 select；`reload` 以后新文档再建一次，额度却从 0 重数。
- 照这个口径，单页用例在 webkit 上也应该是“报错 2 份、额度 1 份”。B 的说明只讲了“两个编辑页放在一条用例里”的情况，没解释为什么拆开以后能过。

1. 贴出 hit-target 在 webkit 项目（iPhone 15）上跑通的记录，证明编辑页那两条真过了，不是被跳过、也不是碰巧。

### 1. 真违规会不会漏判

先说两路的关系：控制台那一路始终是整条用例累计、在 Node 一侧收的，`CSP_TEXT` 会收下所有 CSP 报错。WebKit 的 select 误报和真正的内联样式违规，控制台文字一模一样，扣除只按“建过几个 select”一条抵一条。所以页面里的计数只要算少了，后果只能是控制台多剩几条，判失败（多报）；不会因为算少而放过真违规。逐种情况：

| 情况 | 会怎样 | 判断 |
| --- | --- | --- |
| 跨源导航（sessionStorage 按源分开） | 另一个源那几个文档的计数和事件带不回来，事件那一路看不到它们 | 计数只会少算：控制台那一路照样收着另一个源的报错，抵扣额度更少，只会多报。另一个源的真违规事件丢了，但控制台文字还在，抵不掉就判失败。**不漏判**；目前 e2e 也都在同一个源里 |
| 页面自己清 sessionStorage | 查过 `src`：没有 `sessionStorage.clear`；应用里的两个 `pagehide` 处理（`useReminders.ts:137`、`Form.tsx:79`）也不碰这个键。注入脚本在页面脚本之前跑，一载入就先读走、删掉，页面清不到。就算以后清掉了，后果也是计数少算 | 不漏判，最多多报 |
| 多个标签页 | sessionStorage 每个标签页一份，这个键只在“离开文档”到“下一个文档载入”之间存在，新开的标签页几乎不可能复制到它。另外，夹具本来就只盯 `page` 这一个标签页，新开的标签页从来不在检查范围里，这是原有限制，不是这次引入的 | 不影响 |
| 后退缓存恢复（pageshow persisted） | 读回的是离开时带出去的累计数，覆盖掉恢复的那个文档自己的旧值。数是对的：带出去的那份已经包含了它自己 | 正确，但没有测试覆盖（见建议 2） |
| 同源 iframe | 注入脚本在 iframe 里也会跑，可能先把主文档要用的那份读走。查过 `src`：没有 iframe | 目前不影响，记一笔（建议 3） |
| 离开前还没派发的违规事件 | select 计数是同步加的，对应的事件如果在离开前还没派发，计数会多出一条，没有事件配它 | 多出的额度只能抵“来源是注入脚本本身”的 style-src-attr，真违规的来源是应用脚本，抵不上，不会因此放过 |
