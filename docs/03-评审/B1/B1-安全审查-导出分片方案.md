## 结论：改了再开工

方案 A 的方向我同意：扣次数的那次调用不做重活，每片的工作量有上限，不发下载链接，服务器不留文件。但有两处照现在的写法**做不出来，或者做出来和设计说的不一样**（M1），一处放大上界太宽（M2），一处跨设备借用任务的口子（M3），加上预览实测工作流的护栏还没写（M4）。**M1～M4 改进架构以后再开工**；S1～S6 是建议，可以开工后在代码审查里一并核。

## 一、必改

### M1：任务键照现在的写法过不了 counters 的约束，`take_rate` 的固定窗口也表达不了“开始后 1 小时”

1. **键的格式过不了约束**：`export-job:<user_id>:<export_id>:<模式>` 是四段。counters 的 check 约束（0001 第 172～173 行）要求“一律三段，第三段不准有冒号”，所以第一次 insert 就会报错，start 永远回 `try_later`。
2. **`take_rate` 的窗口按 UTC 整点对齐，不是从开始时刻起算**：迁移 20261029130000 第 4～5 行写明，窗口是把 `now()` 按 `p_window_s` 往下取整，3600 秒就是 UTC 整点。照 0.47 续 ① 的写法（`take_rate`，窗口 3600，上限 `EXPORT_MAX_PARTS + 1`）会出两个问题：
   - **“1 小时内可以继续”实际是 0～60 分钟不等**：11:59 开始的导出，窗口开始是 11:00。part 要是按“窗口没过 1 小时”判断，12:00 就过期了。
   - **分片上限每到整点就清零**：part 每取一片调一次 `take_rate`，12:00 以后算的是新窗口里的新一行，`count` 从 1 重新数起，200 片的上限在整点前后可以用两次。part 要是按“键在当前窗口里存在”判断过期，又会在整点直接把正在导的任务判成 `export_expired`。两种读法都不对。
3. **文件头的 `exported_at` 和 start 的回应对不上**：0.47 续 ① 写文件头的 `exported_at` 取任务键的窗口开始时刻，那是整点；start 回给客户端的 `exported_at` 是真实时刻。两个时间不一致，“最近的导出”和文件里的时间会差到将近 1 小时。

**改法**（架构定写法，后端照做）：
- 任务不用 `take_rate`，改成一个专门的 RPC，比如 `private.export_job_take(p_user, p_export_id, p_session, p_mode, p_max)`，只给 service_role 执行。它在一个原子语句里做三件事：
  - 查这个任务存在，而且**真实开始时刻**在 3600 秒以内；
  - 分片数 +1；
  - 返回“是否放行”和开始时刻。
- start 时用 `window_start = now()`（真实时刻）建这一行。
- 键仍守三段：`export-job:<user_id>:<export_id>`。模式和会话（M3）放进第三段时不能用冒号，比如 `<export_id>.<模式>.<session_id>`；或者另存列，但 counters 没有可用的列，所以**倾向三段键加专用 RPC**。
- 文件头和 start 回应的 `exported_at` 都用这个开始时刻。
- 附录 A 的 counters 键表、3.3 C 和附录 A 的授权行要同步加，过 M4 的一致性检查。
- 单测覆盖：跨 UTC 整点继续不过期、整点前后分片数不清零、开始满 3600 秒那一刻回 `export_expired`。

### M2：分片上限 200 太宽，按出网流量算，放大上界太高

0.47 第 6 条写的滥用上界是“每天 3 个任务 × 200 片”。按方案自己的数算：
- 每片原文最多约 39 MB（24 MB 预算加一页 15 MB），gzip 按 3.6 倍约 10 MB。一个任务 200 片，最多能让服务器往外送约 2 GB；每天 3 个任务约 6 GB。
- 游标是客户端带回来的，同一个任务里可以把游标一次次设回 `null`，**反复下载整个账号**。满载账号约 9～10 片，200 片等于一个任务能下 20 多份全量。
- 预览、正式都是免费版，出网流量是按月计的小额度。**一个账号（或者一个出了 bug、不停重试的客户端）一天就可能把整个项目当月的出网额度用掉**，所有用户一起受影响。这比“绕过每天 3 次”更实际。

**改法**：
- `EXPORT_MAX_PARTS` 按需要定，不按“永远够用”定：满载约 10 片，加上重试和继续，**30～40** 足够。数要后端按 R1 实测的片数给，架构写死。
- 加一个**按人按天的分片总数**，比如 `export-part:<user_id>:<UTC 日期>` 每天 100 次。**所有 part 调用都算，包括游标校验失败、410、413 的**，在任何数据库读取之前先扣。这样坏游标、过期任务也不能被拿来空转。
- 0.47 第 6 条的滥用上界按新数重写，写成“每天最多 N 片、约 X GB”，并交负责人知道。

“part 不扣当天次数、1 小时内免费继续”本身我同意（④ 第 3 点推荐 a）。它不会绕过每天 3 次：新任务只能经 start 建，start 照样扣次数、发通知。

### M3：任务要绑定发起它的会话，part 只认同一个会话

现在 part 只认“本人的 user_id 加 export_id”。export_id 是 `crypto.randomUUID()`，别人猜不到；任务键里带本人的 user_id，别人借了 export_id 也读不到自己以外的数据，**跨用户越权是挡住的**。缺口在同一个用户的不同会话之间：
- export_id 写在 logs 的 `code` 里，本人的任何设备都能在“最近的导出”里读到。
- 一台被偷、还没移除的设备，可以拿本人刚在另一台发起的 export_id 直接取片，自己不用 start。于是不扣次数，也不触发新的通知邮件；“最近的导出”里记的发起设备和实际取走数据的设备也对不上。

**改法**：
- start 时把 JWT 的 `session_id` 写进任务（M1 的第三段，或者专用 RPC 的参数）。
- part 用自己 JWT 的 `session_id` 拼键或比对，不同就回 `410 export_expired`（不另给码，不泄露“任务存在”）。
- 换设备、重新登录以后要重新 start，这和 ④ 第 3 点的“继续”只在同一台设备上用是一致的。
- 单测要覆盖：同一用户的另一个会话、别的用户、模式不一致，都回 410；被移除设备的会话回 `session_revoked`（`requireActiveUser` 已有）。

### M4：预览 5,000 行档的 CI 工作流和硬删账号，要先把护栏写进架构

0.47 续 ④ 第 5 点和 ⑤ 只写了“只连预览、只用已有的 `E2E_PREVIEW_SERVICE_KEY`、只建 `.test` 账号、跑完硬删”。**仓库 10-30 起已经公开，Actions 日志是公开的**，service key 又能做任何事，所以工作流本身要按下面这些写清楚，安全审查员审了 YAML 再合并：

1. **触发和权限**：
   - 只有 `workflow_dispatch`，没有 push、pull_request、schedule；
   - `if: github.ref == 'refs/heads/main'`；
   - `permissions: contents: read`，不要 id-token；
   - checkout 用 `persist-credentials: false`；
   - `concurrency` 一组，不排队、不并行，并和别的预览 E2E 互斥。
2. **密钥**：
   - 只用 `E2E_PREVIEW_SERVICE_KEY`，只放在跑脚本那一步的 env 里；
   - 脚本只认预览 ref（照 `preview-login.ts` 的 `PREVIEW_REF` 写死），别的 ref 一律不建客户端；
   - 验证码、令牌拿到先 `::add-mask::`；
   - 不上传 trace、截图、报告产物（里面会有会话）；
   - **日志只打印条数、字节数、毫秒数和错误码，不打印任何行内容和响应体**，因为日志公开。
3. **库大小前置检查**：开跑前读预览库大小，超过 250 MB 就失败退出、不造数（要有只读的 RPC 或 usage-report 的接口能读到，没有就先补）；跑完再记一次。
4. **建号**：
   - 邮箱每次唯一，比如 `e2e-export-<run_id>@lemomemo.test`；
   - **建之前查这个邮箱不存在，存在就失败退出、不删**，免得删掉一个不是这次建的账号；
   - 建出来的 user id 记在内存里；
   - 只造合成数据（第 95 条、R-95），**不造任何 R2 对象**（硬删不经 account-purge，R2 里的东西删不到）。
5. **硬删的护栏**（不走 7 天冷静期）：
   - 只删**这次运行建出来的那个 user id**（按 id 删，不按邮箱模式删）；
   - 删之前再核一次：邮箱等于这次的邮箱、以 `@lemomemo.test` 结尾、不在 `private.admins`、不在 `PREVIEW_OWNER_EMAILS`、建号时间在这次运行开始以后；任何一条不符合就失败退出、不删，交人处理；
   - 删完核对：`auth.users` 里没有这个 id；按数据清单生成的各表计数为 0（复用注销用例生成器的探针）；counters 里 `%:<id>:%` 的键也删掉（`account:`、`export-job:`、`export-part:`），否则留在库里 30 天；
   - 清理步骤放在 `if: always()` 的单独一步里：中途失败也要删；删不成就让工作流失败，并在摘要里写出 user id，交主持人手工处理。
6. 备选方案“负责人本人在自己电脑上跑一条命令”：上面第 2～5 条照样适用，只是不涉及公开日志。我**倾向备选**：负责人点一次 CI 和在本机跑一条命令的工作量差不多，后者不用把 service key 的使用面扩到一个新工作流。两种都可以，由负责人定（④ 第 5 点）。

## 三、建议（开工后在代码审查里一并核）

- **S1 游标的 `after` 按主键类型校验**：现在只要求“不超过 64 字的字符串或安全整数”。建议按每张表的主键类型收窄：uuid 主键只接受 uuid 格式，整数主键只接受安全整数，文本主键只接受一个窄字符集（比如 settings 的键名只能是小写字母、数字、点、下划线、横线）。值是经 supabase-js 的 `.gt()` 进查询的，不拼 SQL；但 PostgREST 的过滤串对逗号、括号有自己的语法，收窄以后不用再去证“特殊字符无害”。
- **S2 头和编码写准**：
  - 正文第 6 节 account 一行、0.47 续 ① 里“account 函数和 `/sb/*` 转发层的 CORS”改成“`functions/_lib/cors.ts` 的 `EXPOSE_HEADERS` 加 `x-lemo-export-next`”；
  - 写明响应 `Content-Type: application/gzip`、**不带 `Content-Encoding`**；
  - 游标头的长度设上限（比如 512 字节），超了回 `bad_request`。
- **S3 审计多记两个数**：`export_done` 那一行另记分片数和总字节数（不记内容）；start 那一行记发起的 device_id（已有就保持）。
- **S4 start 的回应丢了的情况**：start 已扣次数、客户端没收到 export_id 时，用户再点一次会再扣一次。这不是安全问题，提示文案里写清“每天 3 次”就行；不要为了这个让 start 支持“按客户端给的 id 幂等”，那会多一个可以伪造的输入。
- **S5 546 当 `try_later`**：同意。但 start 要是 546（理论上不会），次数已扣、logs 可能没写，这种“扣了次数没留记录”的情况在 B1 QA 里专门测一次：把 start 里建键或写 logs 那一步人为弄慢或弄失败，看有没有走到 `export_log_failed` 的退回。
- **S6 单测清单补几条**：别的用户的 export_id 回 410（和“任务不存在”同一个回应，不泄露存在与否）；同一用户别的会话回 410（M3）；模式不一致回 410；跨 UTC 整点继续（M1）；游标设回 `null` 重下也计入上限（M2）；按人按天的分片总数在坏游标、410、413 时也扣（M2）。

## 四、要负责人知道或定的

- M2 的新上限（每片约 10 MB gzip，一个任务 N 片，每人每天最多 M 片）会写进架构。数由后端实测后给，属于防滥用的参数，不改产品范围；按 R-103 由主持人告知即可。
- M4 的预览实测，在“新 CI 工作流”和“负责人本机跑一条命令”之间由负责人选（0.47 续 ④ 第 5 点）。安全审查倾向本机跑；选 CI 的话，YAML 合并前要过安全审查员。
- 0.47 续 ④ 的其余几点（一个文件、logs 导 90 天、1 小时内免费继续、文案）从安全角度都没有意见，按架构推荐即可。

### 一、必改

**Q1 预检本身没有限流，可以拿来反复压数据库**
- 照现在的顺序，预检在扣当天次数之前。下面两种请求都会先完整跑一次预检，而且都不扣任何次数：
  - **超大账号**：每次都回 413、不扣次数，可以无限次重来；
  - **普通账号当天 3 次已用完**：照样先预检（最多扫约 480 MB），扫完再被扣数那一步回 429。
- 每次预检最多扫约 480 MB 的行做 JSON 序列化，库的 CPU 可能吃十几秒。一个会话（或者一个出 bug 的客户端）循环点 start，或者并发点，就能把免费版的小数据库长时间占满，所有用户的同步、登录一起变慢。第 6 条和 M2 防的是出网，这里是**库的 CPU**，两个上限都管不到。
- **改法**（架构定写法）：
  1. 预检前先过一个**专门的限流**：`take_rate('export-size:<user_id>:<UTC 日期>', EXPORT_SIZE_CHECK_DAILY_LIMIT, 86400)`，建议每天 6 次（3 次正常导出加 3 次重试）。超了回 `429 rate_limited`，不预检。附录 A 的 counters 键表登记这个键；account-purge 按第二段删，自然覆盖。
  2. 预检前再**只读查一次**当天的 `account` 计数，已经到 3 就直接回 429，不预检。这一步不扣数，扣数仍在预检之后。
  3. 预检加一个**全局并发闸门**，比如 `pg_try_advisory_xact_lock`，同一时刻全库只跑一个预检，拿不到锁回 `try_later`。也可以退一步，用 `export-size:global:<UTC 小时>` 每小时 N 次。朋友小范围使用，一次只跑一个足够。
  4. 单测补三条：超大账号连点 start 第 7 次回 429、不再预检；当天 3 次用完以后的 start 不预检；两个 start 并发时只有一个在预检。

**Q2 函数上写 `set statement_timeout = '20s'` 不起作用**
- **本机实测**（lemo-e2e 的 `supabase_db_lemomemo`，事务内建临时函数，跑完回滚）：函数声明 `set statement_timeout = '1s'`、函数体 `pg_sleep(3)`，调用照样跑满 3.0 秒，没有被打断。Postgres 的语句超时在**外层语句开始时**就按当时的设置定好了，函数的 `SET` 子句改了这个参数，但不会重新计时。
- 所以预检真正受的是调用时角色的超时。本机 `service_role` 是 `statement_timeout=4min`，`authenticator` 是 8 秒；经 PostgREST 调用时以哪个为准，要实测。两种情况都不对：
  - 按 4 分钟算，“最多 20 秒”的护栏不存在，Q1 的放大更严重；
  - 按 8 秒算，正常的大账号预检超过 8 秒就永远回 `try_later`，永远导不出。
- **改法**：
  1. 超时改由函数自己判断：循环里每累加一段（比如每 1,000 行）比一次 `clock_timestamp()`，超过 `p_budget_ms`（建议 15 秒，必须小于实测的有效超时）就提前返回一个“超时”标记（比如 `-1`），函数回 `try_later`；
  2. 去掉函数上 `set statement_timeout` 这句，免得让人以为有效；
  3. pgTAP 用小预算断言会提前返回；
  4. R5 记下经 PostgREST 调用时实际生效的超时，以及满载、超大两档的预检耗时，写进 TC-B1-73。

### 二、主持人点名的另外几点

- **`text[]` 能不能注入表名**：
  - **SQL 注入挡住了**：动态 SQL 用 `format('public.%I')`，`%I` 一律加引号转义，表名里塞引号、分号都不会被当成 SQL。
  - 只给 service_role 执行，调用方只有 account 函数；service_role 本来就能读所有表，所以就算传了白名单以外的表，也不会多出越权。
  - 但架构里写的“只认在 `p_tables` 白名单里的表”，白名单就是调用方传进来的参数本身，不算白名单。见 Q3。
- **超时和 `search_path`**：超时见 Q2。`search_path = ''` 没问题：函数体里所有对象都要写全名（`public.<表>`、`private.…`）；`row_to_json`、`octet_length`、`clock_timestamp` 在 `pg_catalog` 里，`pg_catalog` 总会被隐式查找，不用另写。
- **拒绝时会不会泄露别的信息**：
  - 预检的 user_id 来自 JWT，413 只告诉本人“你自己的数据太大”，不涉及别人；

### 一、内存探针和 `Content-Length`

- **K1 探针要防误开，开了也只记数字**：架构写的是“`EXPORT_MEM_PROBE=1`，正式、预览不设”，单靠“不设”防误开。建议代码里要两个条件同时满足才开：环境变量是 `1`，**而且** `_shared/env-kind.ts` 判定为本机。线上就算有人误设了这个变量，也只记一次 `mem_probe_ignored`，不开探针。
  - 泄露面本来就小：探针只调 `Deno.memoryUsage()`，读的是这个 isolate 的堆大小，不碰数据。日志行写成固定格式，比如 `export_mem_peak mb=<整数>`，**不带 user_id、export_id、表名、行数**；要对得上是哪一片，用片序号就够了。
  - 探针每页调一次，开销可以忽略。就算误开，也只是多几行日志，没有安全后果。
- **K2 `Content-Length` 只在整片写完以后算，并且和要发出的是同一个数组**：
  - 写法是先 `close()` 拿到全部压缩块，再在同一个数组上按 `byteLength` 求和写头，最后 `ReadableStream.from(同一个数组)`。求和以后不再往数组里放东西，也不再改任何一块。单测断言头的值等于各块之和，也等于响应体实际字节数。
  - 头和实际字节对不上时，Deno 或网关要么断连，要么截断。截断的结果是这一片的 gzip 成员不完整，拼起来的文件解压时 CRC 会报错，不会悄悄少数据。但用户要等存完、打开文件才发现，所以要加 K3。
  - 也可以干脆不写 `Content-Length`，让运行时自己决定，进度条按已收到的字节显示。安全上两种都可以，由后端选；选了自己写，就照上面做。
  - `/sb` 转发层会原样转发这个头，B6 抓包的时候顺带核一次网页版和 exe 两条路。
- **K3 客户端逐片校验**：
  - 每片收完，核对收到的字节数等于 `Content-Length`（写了这个头的话）；
  - 核对开头两个字节是 gzip 魔数 `1f 8b`、长度至少 18 字节；
  - 不对就当这一片失败，用同一个游标重试。重试照常计入两个上限。
  
  这样被截断的片不会进文件。
- 口径方面（按每个 worker 算 256 MB；单次峰值 ≤ 150 MB；连取 12 片不逐片上涨；超了降到 8 MB 一片，上限改成 72、144，出网上界按字节不变）：安全上没有意见。降片大小的时候任务上限和每天上限一起翻倍，出网上界不变，第二次复核算的数字照样成立。

### 一、D1：`.test` 收件人不真发信（线上函数行为变了）

- **判断方式**：`/@lemomemo\.test$/i.test(to.trim())`。JS 的 `$` 在没有 `m` 标志时只认字符串末尾，不认换行前；`/i` 管住了大小写；`trim` 去掉首尾空白。单测正反例都有：`A@LEMOMEMO.TEST`、前后带空格的都会跳过；`x@lemomemo.test.com`、`x@a.lemomemo.test.evil`、`lemomemo.test@gmail.com`、`x@test` 都照常发。
- **会不会误跳过真实用户**：不会。只有以 `@lemomemo.test` 结尾的地址才跳过，`.test` 是 RFC 2606 保留的顶级域，世上不存在能收信的真实邮箱。`x@lemomemo.test.evil.com` 这类地址不会被误跳过（照常发，本来就该发）。

### 一、逐项分析

- **能不能靠超时多退次数、绕过每天 3 次**：
  - 退回只发生在“扣次数确认成功之后”的超时上，而且每人每天最多退 3 次（`export-refund:`）；退回本身用比较并交换，不会减到 0 以下。
  - 风险点在“扣次数那一步本身超时”：`take_rate` 的 HTTP 请求被中止了，但语句可能已经提交。这时如果按“扣了以后超时”去退回，就等于没扣成也退了一次。见 T1。
  - 就算真退多了，也受每天 3 次退回上限封顶，而且要数据库真的卡住才会出现，攻击者控制不了。最坏一天多 3 次导出，导出的都是本人的数据。
- **“HTTP 中止但语句稍后仍提交”**：start 扣了次数以后，建任务、写 logs 超时，走退回并删任务行；如果建任务的那条插入在删除**之后**才提交，就会留下一行有效的任务；写 logs 的那条插入如果也稍后提交，`export_id` 就会出现在“最近的导出”里。同一个会话的人于是能拿这个 `export_id` 取片：次数已经退了，也没发通知邮件（失败路径不发信）。条件是数据库卡住，加上两条写入都晚到，概率很低，导出的也只是本人的数据；但它是“导出了却没扣次数、没发通知”。见 T2，一条小改就能堵上。
- **part**：超时回 `try_later`，已占的分片数不退。这是保守的做法，最坏只是让本人更早碰到上限，可以接受。
- **delete 超时、不退次数**：注销申请可能稍后提交，用户看到的是 `try_later`。
  - 再点一次时，`requireActiveUser` 会回 `account_pending_deletion`，客户端会进恢复页，状态以数据库为准，不会分叉。
  - 这种情况下申请当时的注销通知邮件不会发出（超时走的不是成功路径）。但 account-purge 有“到期前 48 小时、`notice_sent = false` 的先发提醒”这一道（`account-purge/core.ts` 第一段），本人最晚在到期前 48 小时会收到信，还能恢复。被盗会话发起注销时，本人失去的是前 5 天的提早知情，不会失去恢复的机会。可以接受，见 T4。
- **restore 超时、不退次数**：恢复可能稍后提交，用户再查一次状态就能看到 active。恢复每天 5 次，偶尔多耗一次可以接受。如果恢复没提交，账号仍在冷静期，下次照样能恢复，不会出现“看上去恢复了、其实没恢复”。
- **`requireActiveUser` 的 2 秒**：原来就是超时回 `try_later`，不放行，口径不变。
- **墙钟**：start 最坏约 80 秒，在 150 秒以内，退回走得到。客户端自己的超时如果比服务器先到，会显示失败，服务器照样退回，次数不会白扣。

### 二、写代码时必须守的口径

- **T1 扣次数那一步本身超时，按“没扣”处理，不退**：`takeRate('account:…')` 抛 `StoreTimeout`（或任何错误）时直接回 `try_later`，**不走退回**；只有拿到 `true` 以后的步骤超时，才算“扣了以后超时”。同理，`export-refund:` 的 `takeRate` 超时就当“不退”，只记日志；`export-size:` 在 `-2` 时的退回超时，只记日志。单测要有一条：桩的 `takeRate(account)` 永不返回 → 回 `try_later`，`refundRate` 没被调用。
- **T2 取片前确认 logs 里有这次的 `export` 记录**：part 在 `export_job_take` 回 `ok` 之后、读数据之前，查一次 logs 里有没有 `user_id = 本人、src = 'account'、act = 'export'、code = export_id` 的行，没有就回 `410 export_expired`（和别的 410 是同一个回应）。只有第一片（游标为 `null`）查也可以，但每片都查更简单，一条按索引的查询，代价很小。

## 审查：INVITE-late-commit 与 INVITE-auth-timeout（占码、退码改成库函数；Auth 管理接口加超时）

文件：
- 迁移 20261031150000；
- invite-signup 的 core.ts、index.ts、store-timeout.ts、types.ts、wire.ts；
- D1 的 whitelist、fn-lock-timeout；pgTAP 26。

结论：**必改一条（N1）**；其余通过；建议三条。

**N1（必改）：认领来的用户，补 profile 失败时也会被删掉，可能误删已经在用的真实账号**
- 现在 verify 在 insertProfile 失败时，对 `created` 一律 `deleteUser`，不管这个用户是这一次请求刚建的，还是 `createOrAdopt` 按派生 id 认领来的。
- 认领来的不一定是半成品。举例：
  1. 第一次 verify 全部成功：建号、建 profile、发 magiclink，用户已经登录、开始用 App；
  2. 只是删 pending 失败了（记了 `pending_delete_failed`），pending 行还在，验证码 10 分钟内仍有效，试的次数没满；
  3. 客户端因为回应丢了重试，或者用户又点了一次 verify，用的还是同一版验证码；
  4. 这一次 `invite_claim` 沿用（ok），`createUser` 回“已存在”，按 id 查得到，于是认领；
  5. `insertProfile` 的 upsert 此时碰上库一抖或超时，就会 `deleteUser`，把这个真实账号连同 auth 记录删掉，接着还退了码。
- 两次 verify 并发时也一样：后到的那次认领了先到那次建出的用户，后到那次补 profile 失败，就会删掉先到那次正在发登录链接的用户。
- 改法：`createOrAdopt` 返回时带上“是不是这一次刚建的”。只有刚建的才允许在 profile 失败时删除、退码；认领来的，profile 失败只回 try_later，不删、不退码。重试时会再认领、再补 profile。
- 补一条单测：认领路径加 profile 失败时，`deleteUser` 没被调用、`releaseInvite` 没被调用。

**通过**
- **同码重试不会重复占**：invite_claim 用 `for update` 锁住这个邮箱、这一版验证码的 pending 行；`claimed_code` 已经是这个码就直接回 ok。两次并发 verify 在这一行上排队：后到的那次重新读到已提交的 `claimed_code`，回 ok，不会再加一次。
- **换码先退旧码**：新码占上了，才在同一个事务里把旧码减一并改记新码；新码占不上就回 invalid，旧码照旧占着。
- **退码只退本条占的那一次**：`update … where claimed_code = 这个码` 和减一在同一个事务里。重复调用或晚到提交时，第二次 where 已经不成立，回 false，不会多退。
- **锁的顺序**：两个函数都是先锁 pending、再锁 invites。只有两个邮箱同时反向换码（A→B 和 B→A）才可能死锁；Postgres 会让其中一个报 40P01，落到 try_later，可以接受。
- **函数属性和授权**：
  - 都是 invoker、`search_path=''`、lock_timeout 5s，pgTAP 26 核对了 proconfig 和 service_role 能执行；
  - 0001 已有 `alter default privileges … revoke execute on functions from public`，D1 的 FUNCTION_EXEC 名单也加上了这两个；
  - `claimed_code` 有 64 位十六进制的 check，满足 TC-B1-147。
- **回包仍然统一，不泄露**：
  - 验证码核对之前，所有失败都和以前一样。
  - 占码回 no_pending 时按 code_wrong 处理，只有验证码已经对了的人才会遇到。
  - createUser 超时、按 id 查不到、查出错三种都回 try_later，看不出邮箱在不在。
  - `email_exists` 仍然只有验证码正确以后才回，等于只告诉邮箱的主人。
- **派生 id**：
  - 由密钥对这一版验证码的哈希做 HMAC 派生，没有密钥算不出来，重新发码就换一个 id；
  - UUID v4 的版本位、变体位设置正确；
  - 别人早就注册的同一邮箱，id 对不上，照旧 email_exists。
  - 除了 N1，“先查再删”不会删到别人：只有 id 正好等于这一版派生值的用户才会被认领。
- **已知取舍（过期 pending 不退码）可以接受**：后果只是码要由负责人重发，和以前函数被平台杀掉时一样。在清理时退码反而会让已注册成功的码多出一次，宁可少退。

**建议**
1. 有一个和 N1 同源的问题：注册成功但删 pending 失败、残留了 `claimed_code`。这时同一邮箱用另一个有效码 B 重新发码并验证，invite_claim 会走换码分支，把旧码 A 退回一次（A 其实已经用于一次成功注册）；随后 createUser 回 exists，再退 B。结果 A 白多出一次可用。
   - 要同时满足“删 pending 失败”和“手上有另一个有效码”，危害只是多出一个名额，所以不算必改。
   - 建议成功路径在删 pending 失败时，至少再尽力把 `claimed_code` 清空（失败只记日志），或者在迁移文件头的已知取舍里写明这一条。
2. 第 276 行注释“只对这一步刚建出来的用户签发 magiclink（5.6）”和现在的认领路径不一致：认领来的用户也会拿到 magiclink。能认领的前提是持有这一版正确的验证码，等于已经证明自己是邮箱主人，安全上可以接受。但请同步改注释和架构 5.6 的说法：“刚建或认领本次验证码派生 id 的用户”。
3. `withAuthTimeouts` 中止不了底下的请求（auth.admin 不收 signal），deleteUser 超时也可能晚到删成。N1 修好以后，只有刚建的用户会走到删除，晚到删成也只是删掉自己这次建的半成品。到时候在注释里写一句即可。
