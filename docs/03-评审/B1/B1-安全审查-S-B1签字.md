## 二、TC-B1-112 要不要复跑：不复跑整套（10-31 只读 SQL 已补齐）

**决定：不复跑 `login-token-tests.ps1 -Only TC-B1-112`。** 主持人 10-31 在预览 SQL Editor 做了两句只读查询：触发器在且是 `O`；带密码的账号是 0 个。结果已写进验收清单 P4。

理由：

1. 10-29 23:35 之后提交的迁移里，没有一个碰 `auth.users` 或 `guard_no_password`。全仓库提到 `auth.users` 的迁移只有 0001～0007 和 `20261029191000_auth_password_session.sql`；之后新带的 20261030110000、120000、130000、140000 都不涉及。主持人 10-31 只读核对：预览库已执行 24 个迁移，最新是 20261030140000，和仓库里的 24 个一致；验收清单 M1 记的 23 个是 10-30 数的，当时还没有 140000。触发器只能经迁移或 SQL 改动，部署代码不影响它。
2. 现在预览开着 CAPTCHA。按脚本第 28～30 行的说明，现在复跑的话，“密码登录回 invalid_credentials”那一半会被人机验证挡在前面、记成跳过，**拿到的证据比 10-29 那次还少**；而且要负责人本人收码。
3. 10-29 的记录缺的正好是两样只读就能查的：① 触发器在预览上存在且启用；④ 10-30 用 invite-signup 新建的账号没有密码。10-31 的两句查询都盖住了。
4. 什么时候必须复跑：以后有迁移动了 `auth.users` 上的触发器、`private.guard_no_password()` 或 `is_active`，或者以后再查出带密码的行不为 0、触发器不是 `O`。

## 三、正式项目没对上的三项：安全意见

**意见：可以按 15.6“正式项目在 B7a 上线前设”留到 B7a，不必 B1 就设。但必须守一条硬线：正式项目建第一个账号之前（包括负责人自己的管理员账号；按 B7a 上线前和第一个账号哪个更早算），三项都要先设好，由 TC-B7a-25 核对。**

| 项 | 现在 | 应为 | 现在不设的风险 | 为什么可以等 |
|---|---|---|---|---|
| JWT 有效期 | 3600 | 600 | 没有会话就没有令牌。只有账号存在、会话被吊销以后，残留窗口才会从 10 分钟变成 60 分钟（架构 0.29 续第 98 条③） | 正式项目现在一个账号都没有、公开注册关着（明早清单第 10 条），没有任何会话 |
| Site URL 和跳转白名单 | `http://localhost:3000`，白名单空 | Site URL 和白名单都只有 `https://lemomemo.com/app/` | 登录、邀请邮件里的跳转会去 localhost。App 只用验证码（detectSessionInUrl: false），没有账号就没有邮件可发 | 同上；要先有账号才会发信 |
| CAPTCHA | 关 | 开（Turnstile，正式组件密钥） | 发码接口不受人机验证保护。现在给不存在的邮箱发码回“Signups not allowed”、不发信，所以到不了发信额度这一层；按 IP 限流（10 次 / 5 分钟）照样有效 | 没有账号就没有可以穷举的验证码，也没有可以骚扰的邮箱 |

另外三点：

1. **这三项是“设置时点”的问题，不是核对缺失**：S-B1 要求的“两个项目逐项核对、截图存档”已经做到（第 5 项）。15.6 同一段里“B1 两个项目逐项核对”和“正式项目在 B7a 上线前设”两句，建议架构师补一句写明：B1 核对时，正式项目“没设的项记差异，B7a 前设”。改架构不在本文件范围内，交主持人安排。
2. **TC-B7a-25 的期望目前写了跳转白名单、JWT 600、CAPTCHA 用 Turnstile，没有写 Site URL**。建议补上“Site URL 是 `https://lemomemo.com/app/`”。改测试用例不在本文件范围内，交主持人安排。
3. 改正式项目的配置要负责人同意、由负责人本人点保存（主持人不动）。什么时候设由负责人定，只要在上面那条硬线之前就行（第五节 O4）。

### C2 ③ 的只读 SQL（主持人在预览 SQL Editor 跑）

只数条数、看最早的 `created_at`，**不读内容**。查的是 public、private 两个 schema 里带 `user_id` 列的表：

```sql
select c.table_schema, c.table_name, u.email,
  (xpath('/row/n/text()', query_to_xml(format('select count(*) as n from %I.%I where user_id = %L', c.table_schema, c.table_name, u.id), false, true, '')))[1]::text::bigint as rows,
  case when exists (select 1 from information_schema.columns d
                    where d.table_schema = c.table_schema and d.table_name = c.table_name and d.column_name = 'created_at')
    then (xpath('/row/m/text()', query_to_xml(format('select min(created_at)::text as m from %I.%I where user_id = %L', c.table_schema, c.table_name, u.id), false, true, '')))[1]::text
  end as earliest
from information_schema.columns c
join information_schema.tables t
  on t.table_schema = c.table_schema and t.table_name = c.table_name and t.table_type = 'BASE TABLE'
cross join auth.users u
where c.table_schema in ('public', 'private') and c.column_name = 'user_id'
order by c.table_schema, c.table_name, u.email;
```

判断标准：

- 每张表、每个账号的 `earliest` 都**不早于这个账号自己的建号时间**（`hufanp+lemotest` 是 10-28，`hufanp@gmail.com` 是 10-30）。从正式环境或 v3 导出搬来的数据，一般会带着更早的原始时间，这一条能把它们筛出来。
- 条数在手工测试的量级（几十条以内）。
- 有任何一条不符合，就交负责人看那几行是不是本人手工输入的测试内容。审查员和主持人都不读内容。

为什么要做：第 95 条 ③ 明文要求抽查；`hufanp@gmail.com` 是负责人的主邮箱，最可能被当成日常账号用。抽查只看条数和时间，代价很小。

**10-31 结果（主持人在预览 SQL Editor 跑；只多套了一层“只显示 rows > 0 的行”，其余照原样）：符合，C2 ③ 满足。** 共 10 行：
