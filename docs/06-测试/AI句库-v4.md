## 1. 测试集 ① 测什么

### 1.1 测的对象

“＋”记事的识别结果：用户打一句话或说一句话，系统给出的结构化条目对不对。按调用的路分三路，**同一份句库三路都跑，分开统计**：

| 路 | 输入 | 被测的东西 | 说明 |
|---|---|---|---|
| A 路：AI 解析 | 文字：打字，或键盘听写 / Web Speech 转出的文字（标“语”的句子） | 后端提供的纯函数 `parseWithAI({text, now, tz, locale, projects, features}, provider)`：`parse.v*.md` 提示词 + Flash-Lite + `shared/schema/ai.ts` 校验。正式的 ai-parse 也调这个函数 | **门槛针对这一路**。这个入口不经过 AI 同意检查、额度计数和“本机有把握就不调 AI”，所以每句都送 AI（见 5.2） |
| B 路：本机规则 | 同上 | `shared/logic/parse/parse-split.ts` + `confidence.ts` | 单独统计，不设整体门槛；只设一条“有把握却错了”的上限（4.1 表），因为本机有把握就不调 AI，错了没人纠正 |
| C 路：ai-voice | 录音文件 | `voice.v*.md` + Flash-Lite（转写和拆分一次完成） | **ai-voice 不调 ai-parse**，所以 Gemini 的转写正确率只能靠 C 路的真录音来测，本句库的文字句测不到它。录音样本从哪来见 Q7 |

标“语”的句子定位为：**键盘听写或 Web Speech 退路转出来的文字，再交给 A 路解析**。它们模拟口语转成文字后的样子（带“嗯、那个”、自己改口、没有标点、数字读法、不分写、同音错字），以及 Web Speech 只认一种语言、把另一种语言听成音近的字。

### 1.2 固定的基准时间

所有句子都按同一个“现在”来写期望结果，跑测试时把它作为 `now`、`tz`、`locale` 传进去：

- **现在 = 2026-11-02（周一 / 월요일）10:00，时区 Asia/Seoul**
- **locale 固定**：中文组 `zh`，韩文组 `ko`；混说组和负责人组固定 `zh`（负责人的界面语言）。jsonl 每行带 `locale` 字段
- 项目列表 `projects[]` 固定为：`SignPlex`、`NEOX`、`官网改版`、`이사 준비`
- `app_config.features` 四种类型（event、todo、note、anniv）全部打开
- 一周从周一开始（沿用 v3：“下周三”= 下一个周一开始的那一周的周三）

### 1.3 期望输出的字段

以架构第 7 节的 parse 输出结构为准（`{"items":[{kind, title, date, time, duration_min, due, important, project, body, short, anniv}]}`；B4b-3 起外面再包一层 `intent`）。

### 1.4 每个字段怎样算对

| 字段 | 算对的条件 | 不评的情况 |
|---|---|---|
| 条数（拆分） | `items` 的条数和期望**完全一致** | — |
| kind | 和期望一致。期望写“E/T”的，日程和待办都算对（待 Q3 定）；**判成日程就查 `date`，判成待办就查 `due`**，日期都按表里的那一天 | — |
| 日期 | 日程看 `date`，待办看 `due`，按 1.2 的基准日推算，**必须完全一致**（YYYY-MM-DD）。期望是“—”的，必须为 null（不许编日子）。纪念日的日子只看 `anniv` 里的月日；**纪念日带没带 `date`、`due` 暂不算进整句对错**（anniversaries 表只存 month、day、year，`date`、`due` 存库时本来就丢掉），只在报告里单独统计“纪念日带了 date / due”的句数，等架构第 7 节写明（Q13） | 随手记不评日期，但**不许**把句子里顺带提到的日子当成日程（这类句子的考点就是这个，见各句“考点”） |
| 时间 | 日程的 `time` 必须和期望**相差 0 分钟**。期望是“—”的，必须为 null（**不许编时间**，例如“明天晚上”不能变成 19:00）。**待办的 `time` 一律必须为 null**（todos 表没有时间列，架构 3.2、附录 A） | 期望写“—（标题须含 17:00）”的截止句（Z13、K13、M07）：`time` 必须为 null，**标题必须含这个时刻**，写法“17:00”“5点”“五点”“5시”任一种都算；**匹配到的数字前面不能紧挨着别的数字**（“5点”不能算匹配到“15点”）（Q4 定之前按这条） |
| 时长 | 句子说了起止时间的，`duration_min` 必须一致（Z09、K09 = 120） | 句子没说时长的不评 |
| 标题 | ① 包含“标题须含”列出的每个词（比较前去掉空格、统一全角半角、英文不分大小写；人名“박 대리”和“박대리”算同一个）；② **不包含“标题不许含”列出的任何词**（已经取走的日期、时间说法，口头语和改口前的说法；每句逐条列在表里和 jsonl 的 `title_forbid`）；③ 中韩混说**照原样保留**，不许翻译成一种语言 | 随手记的标题可以为空，这时看 `body`，“须含”的词在标题或正文里出现即可。**规则 ② 的两种豁免**：模糊时段句在 Q3 定之前不评时段词（“晚上”“저녁”“점심”等在标题里有没有都行）；截止句（Z13、K13、M07）的那个时刻必须在标题里，不算违反 ② |
| 项目 | 和期望一致（必须是 `projects[]` 里的原名）。期望是“—”的，必须为 null（**不许编项目**） | 随手记不评项目（notes 表没有 project 列，分类由 ai-classify 另管） |
| 重要 | 期望“重要”的必须是 true；其他句子必须是 false | — |
| 纪念日 | `anniv.type`（birthday / anniversary / countdown）、`calendar`（solar / lunar）、`month`、`day`、`is_leap`、`year`（句子说了出生年或倒数日年份才有，否则 null）全部一致；标题含人名或事由 | 农历的中韩版本（`lunar_variant`）现在输出结构里没有，不评，见 Q9 |
| short | 日程、待办：只查格式，1–2 个字形簇或 null（schema 会拒不合格的）。**随手记和纪念日的 `short` 必须为 null**（架构第 7 节：event、todo 才有） | 不评内容 |
| intent | B4b-3 以后：测试集 ① 的每一句都必须是 `record`。判成 search / summarize 的，这句算错，并且**单独记入测试集 ③ 的“本该记下却被判成查找”**（D-15 要求 0 条） | B3 时还没有 intent，不评 |

**整句算对**：条数对，并且每一条（按句中出现的顺序一一对应）上面所有要评的字段都对。一句里有一个字段错，整句就算错。

**schema 拒收**：AI 的输出被 `shared/schema/ai.ts` 拒收（整份不合格、返回 null）的，**这句整句算错**；报告里另外统计拒收的句数和每次的原因。测试程序**同时存两份**：AI 的原始输出和校验后的结果，判分用校验后的结果。

**校验范围的两点前提（请架构第 7 节确认，见 Q13）**：① “日期在今天前 1 年到后 5 年之间”的“今天”按请求传入的 `now` 和 `tz` 算，不按服务器当天，否则基准日固定在 2026-11-02 的句库过一段时间会被误拒；② `anniv.year` 的允许范围按数据库约束 1900–2100，不套用“前 1 年到后 5 年”（否则 Z32 的 1992 年会被拒）。

**观察项**：标“观察”的句子（重复说法、取消、改期）**现在不计分**，只记录系统怎么处理，写进报告。等第 8 节 Q1、Q2 定下来以后，评测员补上期望结果，再改成计分句。

句库转成 `tests/ai/set1/zh.jsonl`、`ko.jsonl`、`mix.jsonl`、`owner.jsonl`，一行一句，例如：

```json
{"id":"M17","set_version":"set1-v1.2","group":"mix","source":"typed","scored":true,
 "text":"수요일까지 NEOX 报价单 보내고, 周四上午九点 치과",
 "now":"2026-11-02T10:00:00+09:00","tz":"Asia/Seoul","locale":"zh",
 "expect":[
  {"kind":"todo","due":"2026-11-04","time":null,"title_has":["报价单"],"title_forbid":["수요일까지"],
   "project":"NEOX","important":false},
  {"kind":"event","date":"2026-11-05","time":"09:00","duration_min":null,"title_has":["치과"],
   "title_forbid":["周四","上午九点"],"project":null,"important":false}],
 "accept":{}, "note":"2 条，一待办一日程"}
```

字段说明：
- `duration_min`：说了起止时间的写数字（Z09、K09 为 `120`），没说的写 `null` 并且不评；
- `title_forbid`：照“标题不许含”一列逐句抄；模糊时段句不放时段词；
- 截止句（Z13、K13、M07）：`"time":null`，并写 `"title_time":"17:00"`，表示标题必须含这个时刻（“17:00”“5点”“五点”“5시”任一写法；匹配到的数字前面不能紧挨着数字，防止“5点”匹配到“15点”）；
- 随手记、纪念日：`"short":null`（必须为 null，第 7 节明文）；纪念日另写 `anniv` 的全部字段，`date`、`due` 不写期望、不评，只统计带了没有（Q13）；
- `accept` 放“两种都算对”的情况，例如 `{"kind":["event","todo"]}`（判成日程查 `date`，判成待办查 `due`）；`title_ignore_person:true` 表示人名不评（M31、M32）。

本文件是句子和期望结果的出处，两处不一致时改 jsonl，并升 `set_version`。

## 4. 门槛建议（负责人确认前只是建议）

### 4.1 建议数字（A 路，门槛按第一遍的结果判）

**生成参数**：测试调用的模型参数（temperature 等）必须和正式 `gemini.ts` 完全一致，不许为了测试单独调低或调高。建议正式就用 temperature 0，**具体值待架构第 7 节定（并入 Q13）**；报告里写明这次用的参数。

| 项目 | 建议门槛 | 负责人确认 |
|---|---|---|
| 中文组 | 40 句至少对 **36** 句（90%） | ☐ |
| 韩文组 | 40 句至少对 **36** 句（90%） | ☐ |
| 中韩混说组 | 40 句至少对 **34** 句（85%） | ☐ |
| 整体（三组 120 句计分） | 至少对 **108** 句（90%），同时三组各自过线 | ☐ |
| 负责人真实说法（20～30 句） | 至少对 **90%**（向上取整：20 句对 18、25 句对 23、30 句对 27） | ☐ |
| 关键字段：日期（日程 date、待办 due、纪念日月日和阴阳历） | 所有要评日期的条目里正确率 **≥ 97%**，并且“期望为空却编了日子”**0 条** | ☐ |

| 拆分条数 | 13 句多件事的句子里条数全对至少 **12** 句；单件事的句子被拆成多条 **最多 2 句** | ☐ |
| 不比上一次差 | **按句子比**：上一次基线里对、这次“稳定错”（第一遍错，补跑 3 次也都错）的句子，全库**达到 3 句或以上**就算变差，即使还在门槛以上，也算不通过，要说明原因。只在句库版本相同的两次之间比 | ☐ |
| B 路 本机规则 | 只统计、不设通过线；但“本机判为有把握、结果却错了”的句子 **最多 2 句**（全库） | ☐ |
| B4b-3 起：intent | 测试集 ① 里被判成查找或总结的 **0 句**（同 D-15） | ☐（D-15 已固定为 0，这里只是在 ① 里也查） |

### 4.2 理由

- **为什么中文、韩文 90%，混说 85%**：一组 40 句，90% 就是最多错 4 句。v3 的本地规则在单一语言、规则内的说法上已经很稳，AI 至少不能比它差太多；混说组故意放了更多难句（单语识别听错、不分写、三种语言混在一句），略放宽一档。负责人平时多半是混说，如果你认为混说也应该 90%，直接改数字即可，句库不用变。
- **为什么日期、时间单独要 97%**：记错日子或时刻会让提醒在错的时间响，是最伤人的错误；标题少一个字用户一眼就能改。全库要评日期的条目约 120 条，97% 就是最多错 3～4 条。
- **为什么“编时间”“编日子”单列**：“明天晚上吃饭”被编成 19:00，看起来像对的，用户不会去改，到点提醒却是 AI 编的。这类错误比留空更糟。
- **为什么整体 90% 还要三组各自过线**：防止中文、韩文很高把混说拉过线。
- **为什么要“不比上一次差”，而且按句子比**：只比总数，一边修好 3 句、一边弄坏 3 句会看不出来；偶尔错一次可能只是模型的随机波动。所以只数“上次对、这次补跑 3 次都错”的句子，这种基本是真的被改坏了，达到 3 句要查清再合并。
- **本机规则为什么只管“有把握却错”**：本机没把握时会去问 AI，错了也有 AI 兜底；只有“有把握”的会直接保存，错了就是静默错误。
- **跑一遍定输赢**：AI 每次结果可能略有不同。门槛只用第一遍的结果判，不挑最好的一次；第一遍错的句子再补跑 3 次，3 次都错标“稳定错”，否则标“偶尔错”，用于“不比上一次差”和后端定位。

### 4.3 生效方式

产品负责人在 4.1 表里逐项确认（或改数字）以后，评测员把确认后的数字写进本文件状态行和测试用例 v4，才算生效。确认前，B3 验收**不能**引用这里的数字。

## 5. 怎么跑

### 5.1 什么时候跑

- 后端**每次改**提示词（`_shared/ai/prompts/parse.*`、`voice.*`）、输出结构（`shared/schema/ai.ts`）、本机规则（`shared/logic/parse/`），或**换模型**（`app_config.ai.model`）、换服务商，都由评测员**全量跑一遍**测试集 ①（人员名单：AI 识别回归，评测员独立跑，他不改提示词）。
- B3 验收时跑一遍，作为 B3 “正确率达到门槛”的依据。
- 负责人的真实说法补进来、负责人确认后，跑一遍定出第一个基线。

### 5.2 怎么跑

- **测试程序**：`tests/ai/run.ts`（Deno），读 `tests/ai/set1/*.jsonl`，逐句调后端提供的纯函数 `parseWithAI({text, now, tz, locale, projects, features}, provider)`。`now`、`tz`、`locale`、`projects[]`、`features` 按 1.2 固定。这个函数**不经过 AI 同意检查、额度计数和“本机有把握就不调 AI”**，正式的 ai-parse 也调它，所以测的就是线上的那段解析（Q8 据此回答）。
- **在哪里跑**：GitHub Actions 的一个工作流，**只能手动触发**（不随每次推送自动跑），用 GitHub Environment **preview** 里单独的一把 Gemini 密钥 secret（R-90 的预览谷歌项目）。**密钥不经过 AI、不放在本机**；评测员只触发工作流、看报告。是否为测试再单独开第三个谷歌项目，见 Q14。
- **密钥的使用范围**：评测工作流用的是 preview 环境的 Gemini 密钥，preview 环境要**限定可用的分支**（例如只允许 develop），别的分支上的工作流拿不到这把密钥。这一条交**安全审查员在 S-B0b 核对**（参照架构 8.4 对 preview 环境令牌的做法），见 Q15。
- 模型名和提示词版本与要合并的那一版一致；生成参数和正式 `gemini.ts` 一致（4.1）。
- **速度**：按 B0 存档的 AI Studio 额度截图（`docs/06-测试/Gemini额度-<日期>.png`）上每分钟、每天上限的 **80%** 放慢。一次全量约 120 句计分 + 15 句观察 + 20～30 句负责人说法 ≈ 160 次调用，第一遍错的句子再各补跑 3 次。
- **产物**：报告和每句的原始输出、校验后结果作为工作流产物（artifact）下载，评测员存档到 5.3 的位置。
- B 路本机规则同一份句库在 Vitest 里跑，不花额度。

### 5.3 报告

- 放在 `docs/06-测试/AI回归/`，文件名 `set1-<日期>-<提示词版本>-<模型名>.md`，例如 `set1-2026-11-20-parse.v1-gemini-flash-lite.md`；每句的原始输出和校验后结果存 `tests/ai/reports/<同名>.json`（只有测试句，负责人的句子已换化名）。
- 报告写：
  1. 这次改了什么（提示词版本、模型名、生成参数、对应的合并），以及**句库版本**（`set_version`）。句库改过版本的，旧基线不能直接比，要用新句库重跑一次旧版本定新基线；
  2. 4.1 表每一项的结果和过没过；和上一次基线按句子对比（新对的、新错的、其中稳定错的）；schema 拒收的句数和原因；纪念日带了 `date` / `due` 的句数（暂不计分，Q13）；
  3. 错的句子逐句列出：句子、期望、实际、错在哪个字段、稳定错还是偶尔错；
  4. 本机规则的统计和“有把握却错”的句子；
  5. 观察项每句系统实际怎么处理的；
  6. 结论：通过 / 不通过。评测员签名。

### 5.4 不达门槛怎么办

- 建议：**门槛生效后，不达门槛的改动不能合并**；换模型（改 `app_config.ai.model`）不经过合并，所以要求**先跑通过再改配置**。
- 这一条人员名单和架构里**没有写明“不能合并”**（只写了“重跑、出报告”和“改提示词前后对比准确率”），需要主持人和架构师确认，见 Q6。
