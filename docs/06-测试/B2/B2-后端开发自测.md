### 5.2 真库 D3 进 CI

- 接法：CI 的 db 任务原来就跑 `npm run test:db`，它的最后一段是 `node supabase/tests/store-it/run.mjs`（打 lemo-ci）。在 `run.mjs` 里加第三个 deno 进程跑 `push-dispatch-d3.it.ts`（和 purge-remind 一样单独一个进程，因为 harness 收尾会关库连接），退出码并进 `run.mjs` 的退出码。所以**功能上的改动在 `run.mjs`（已改工作区）**，ci.yml 不用改命令。
- ci.yml 只改 store-it 那一步（约第 247 行）的名字和注释：步骤名加上 push-dispatch；注释写明另起 deno 进程跑 `push-dispatch-d3.it.ts`、约 35 秒、3 分钟超时、只发进程内替身、cron 任务按原状态停和恢复、失败时这一步失败。命令行不变。补丁已交协调方（主仓库 ci.yml 没动），`git apply --check` 和 YAML 校验都通过。没加“tee 日志再核对四行结果”的写法，因为 `tests/build/store-it-guard.test.ts` 认 `run: npm run test:db` 这一行。
- `run-d3.mjs` 已删：本机改用 `node supabase/tests/store-it/run.mjs --e2e-sb`（会把 account、invite-admin、purge-remind 一起跑，多约 20 秒）。
- 为 CI 加的稳妥处理：开跑时先记下 push-dispatch 的 cron 任务原状态（写进 `supabase/.temp/d3-cron-state-<库端口>.json`）再停掉，收尾按原状态恢复并删掉这个文件；上次被 kill 留下这个文件时，下次开跑先按它恢复。文件名带库端口，同一个检出目录并发打不同的库时不会串；收尾先恢复 cron（单独一层 try/finally，排在删数据前面），删数据抛错也能恢复。已知遗留：harness 原有的 `supabase/.temp/store-it-ids.json`（残留用户清单）文件名不带端口，并发打两个库时会串，这次不动。cron 调用本来就回 401（lemo-e2e 是函数和 vault 的 CRON_SECRET 不一致，lemo-ci 是函数没设），这里不靠这一点。实跑后查过 cron 任务为开、状态文件已删。推送只发进程内替身，CI 上也不联网。`run.mjs` 给这个进程 `timeout: 180_000`。
