## 4. 一句话解析用例表（机器可读）

### 4.1 表格约定（转单元测试用）
- 每行一条用例，列顺序固定：`编号 | 输入 | 今天 | kind | title | date | time | project | important | 提醒 | 优先级 | 备注`。
- `今天` 一律 `2026-10-23`（周五）；项目名单 `SignPlex, NEOX, SOIL STUDIO`。
- 空字符串写 `""`；`kind` 为 `event`（日程）或 `todo`（待办）；待办的截止日写在 `date` 列（对应 `due` 字段）。
- `提醒` 列写**保存后**的提醒设置：`min=15`、`min=30`、`min=1440`、`min=null`（日程）；`days=0`、`days=1`、`days=null`（待办 / 全天日程）；`-`（无截止日的待办，没有提醒）。值后带 `*` 表示是默认值（解析器没识别到提醒说法）；不带 `*` 表示解析器从原话里识别出来的，解析结果应带上这个字段。
- 输入里的空格就是原文空格，没有首尾空格；表格里不出现 `|`。
- `备注` 列含【待确认】的行，预期值是 QA 的建议，确认前单元测试可先标 `todo`（不计失败）。
- 解析器输出建议增加字段 `remind`（`{remindMin}` 或 `{remindDays}`，未识别时不带），与现有 `{title, date, time, important, project, kind}` 一起比对。

### 7.3 回滚步骤（出现 P0 缺陷且无法在 1 小时内修复时）
1. **先停推送**：如果已经创建 Claude 定时推送任务，先暂停或删除，避免回滚后继续按 v3 字段推送。
2. **重新发布冻结文件**：把 `archive/releases/v2/planner.html` 原样发布到同一个 artifact 地址（保持链接不变；不传 `capabilities` 以保留仅本人的访问规则，或显式带上同样的规则）。线上版本号会变成 Version 4，内容等于 v2；在发布记录里写明“Version 4 = 回滚到 v2”。
3. **核对数据**：v2 页面不认识 `deletedAt`，软删除过的条目会重新显示出来。处理方式二选一，由用户决定：
   - 接受它们暂时重新出现（不丢数据，推荐）；或
   - 让 Claude 把这些条目真删（不可恢复，必须用户明确同意，且先确认已有备份）。
   v3 新加的提醒字段对 v2 无害，保留在数据库里，修复后的 v3 会继续使用。
4. **数据损坏时**：用 7.1 的备份 JSON，由 Claude 按 id 把受影响的文档写回（先列出差异给用户确认，再写入）。
5. **验证**：按 7.2 的前 3 项检查回滚后的线上版本。
6. **记录**：在测试记录里写缺陷、影响范围、回滚时间；修复后的版本重新走第 7.1 节全部检查。

## 8. 通过标准
同时满足以下各条才能发布：
1. **P0 用例 100% 通过**（含第 4 节表格中的 P0 行，和视口矩阵里涉及 P0 的检查项）。
2. **P1 用例通过率 ≥ 95%**（按条数计算，第 4 节表格的 P1 行计入）；未通过的 P1 要逐条记录原因、影响和计划修复版本，并经主持人同意。
3. **没有未解决的高严重度缺陷**：凡是会导致数据丢失或被改错、页面崩溃或白屏、错过提醒或重复轰炸、隐私泄露（推送带标题、他人可读写、脚本执行）的缺陷，不管来自哪条用例，都必须修复并复测。
4. 架构检查 0 错误，构建成功，全部单元测试通过。
5. 【待确认】项中被标为影响 P0 的，已有用户结论。
P2 用例不阻塞发布，结果记录在测试记录里。
