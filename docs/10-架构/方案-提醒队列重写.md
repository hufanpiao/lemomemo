## 0. 给负责人的摘要

1. 提醒推送这条线，“把要重算的提醒排进队”现在有 9 个在用的入口（另有 1 句跑过一次的补算），同一条规则最多抄了 10 份（数据库 6、服务器程序 1、测试替身 2、前端 1）。
2. 11-04、11-05 两天里，这块的数据库程序被整份复制重写了 8 次：7 次是抄整份、实际只改 2～11 行，1 次是真改了设计；下次再改很容易漏掉一份。
3. 读代码看到的现状问题（评审用测试替身跑过前两条，真库都没跑；动手前先各补一条用例钉住）：① 新建待办时提前量已经过了（比如明天 10 点截止、提前 1 天、今天下午才建），规格说在截止时刻提醒，服务器不响；② 推过以后一小时内把待办勾完成又取消、删了又恢复，会再响一次；③ 一个人一下子要重算很多条时（改默认提醒时刻、换时区），排在后面的新条目等到算出来时已过提醒时刻 60 分钟以上的，就不响；④ 提醒没响时，重算这一段没有记录可查。
4. 改法：排队只留一个入口，而且只从真正写进库的行排队（不给“别人往你的队列里塞东西”留口子）；“哪些字段算提醒”记进现有的表信息，不新建表；用户自己改的在全站范围先算；补上重算记录。
5. 以后改提醒算法：算法文件改一处、版本号加 1、加一句一行的迁移；只重算还没到点的，已经响过的不会再响；发布不用再讲究先后。
6. 退回：服务器程序可以退回上一版；数据库照现有手册“只往前修”，所以先在预览跑稳，正式随首发一起上。
7. 工作量约 7 人日（分项见 6.1）。代码行数大致持平，好处是同一条规则的份数变少，不是行数变少。
8. 要你定 5 件事（6.3），每件都给了推荐；其余技术取舍由主持人定（6.4）。

### 3.3 新对象的要点

**① 谁能往队列里放东西（安全）**

规则：队列项一律来自已经通过 RLS 写进库的行，入队函数不接受客户端给的 user_id。

- 行入队只在 **after** 触发器里做：`INSERT … ON CONFLICT (id) DO NOTHING`（客户端新建就是这一种，src/platform/supabase/sync-transport.ts:223）撞了主键时 after 触发器不触发，别人的行不会被塞进队列；普通 INSERT 撞主键整句回滚；`ON CONFLICT DO UPDATE` 落到别人的行上会被 UPDATE 的 RLS 拦下。user_id 取 after 触发器里的 `new.user_id`：新建时是默认的 auth.uid()（0002:6，客户端不能写 user_id，0002:47-48），更新时 touch() 已把它钉回 `old.user_id`（0001:54）。
- 批量入队（设置、时区、规则版本）从三张表里按 user_id 选行，user_id 就是行上的主人；设置和时区那几路的 user_id 来自设置行、profiles 行或 auth.uid()，都是本人。
- 冲突时 `user_id = excluded.user_id`：行被硬删后别人重用了同一个 id，队列项跟着换成真主人。
- 第 0 步读行后照旧核对 `row.user_id = q.user_id`（round-step0.ts:98），对不上丢弃，新加记一个原因码 `recalc_owner_mismatch`。
- 所有新函数要么不授任何角色，要么只授 service_role（3.2 的表）；rls/03 加“anon、authenticated 直接调这几个函数都被拒”。
- 结果：没有任何客户端能给别人的行塞队列项，也碰不到别人在途的租约。第一版“入队放进 before insert 触发器”这一条撤掉。

**② 唯一入队 `remind_enqueue(p_scope, p_user, p_tn, p_id, p_fresh, p_min_ver)`**

一句 `insert into private.remind_queue as q (table_name, id, user_id, prio, fresh, min_ver) select … on conflict (table_name, id) do update set user_id = excluded.user_id, claim = null, claimed_at = null, attempts = 0, prio = least(q.prio, excluded.prio), fresh = q.fresh or excluded.fresh, min_ver = greatest(q.min_ver, excluded.min_ver) where <有任何一项要改>`（清租约照 R-348：正在处理时又有改动，finish 删不到它）。select 部分按 scope 分支（不在本 scope 的分支靠只看参数的 One-Time Filter 跳过，T19 用 explain 钉住）：

| scope | 谁调 | 选哪些行 | prio |
|---|---|---|---|
| `row` | enqueue_remind() | 就是这一行（p_tn、p_id、p_user 来自 after 触发器的 NEW） | 0 |
| `floating` | enqueue_floating（时区采纳、切固定时区） | 这个人的全天日程、待办、纪念日，没删、待办没完成，并且 **remind_at > 现在，或 remind_at 为空且设了提醒**（条件逐字照 20261104130000:180-194，纪念日补上“为空且设了提醒”，修 P3） | 见下 |
| `allday` | remind_on_settings（remind.default_time） | 这个人设了提醒的全天日程，**日期没过两天以上，或“稍后”、免打扰顺延还在 1 小时以内**（修 P16；11-13 整块评审必改 1 改：原写“只收未到点或未算的”，会把当天推过按了“稍后”、被免打扰顺延还没响的挡在外面，改了 P12 现状、顺延那条不跟新默认时刻走） | 见下 |
| `anniv` | remind_on_settings（anniv.default_*） | 这个人用默认值的纪念日（remind_offsets 或 remind_time 为空，照 0005:56），**不看时间**（每年都会再来，照原 enqueue_anniv_defaults；评审建议 2） | 见下 |
| `all` | 规则版本迁移（④） | 全站设了提醒的日程（有时刻的也收：算法改了也可能影响它）、没完成的待办，口径同 allday（看 date、due）；纪念日不看时间。现在没有调用方，第一次用之前要核有时刻的日程、待办当天推过又被挪到将来的会不会再推（它们没有 R-336） | 见下 |

批量项的 prio：remind_at 为空或在 24 小时内的记 1，其余记 2——快到点的先算。用户自己改的永远是 0。

“设了提醒”的粗判（例如待办 `due is not null and (remind_days is not null or remind_before_min is not null)`）是 shared todoRemindAt 分支的影子，以后加提醒字段要一起改；它只用来少入队，宁多勿少，T09 按 shared 的分支逐个列举钉住。批量范围是原来各入口的子集，只去掉重算了也推不出去的（第 1 步只回看 1 小时，日期过了两天的推不出去）；当天推过的照原来一样重算，全天日程由第 0 步 R-336 压住不重推。

**③ 行改了怎么处理：touch() 里的 `remind_reset` + after 触发器 `enqueue_remind()`**

“哪些列算提醒输入”只有一个源头：清单 `shared/manifests/calendar.ts`、`todos.ts`、`anniv.ts` 各加 `remindCols`（和 systemCols、noConflict 并排，shared/schema/manifest.ts:53-56），迁移把它写进 table_meta.remind_cols，D1 第 8 节（build/d1/checks.ts:236-249）照比对 system_cols 的写法多比一列。初始值逐列照 0001:67-71、0002:37、82、0005:31-32：

| 表 | remind_cols（变了要重算，并清 pushed_for、defer_until） |
|---|---|
| events | date、time、tz、remind_min、remind_days、deleted_at |
| todos | due、due_time、remind_before_min、remind_days、remind_time、done、deleted_at |
| anniversaries | remind_offsets、remind_time、month、day、calendar、lunar_variant、is_leap、year、after_due、kind、deleted_at |

snooze_at（三张表都是“变了只重算、不清”）不进 table_meta，直接写在 enqueue_remind() 里，省掉第一版的 act 字段。

- `remind_reset(p_tn, o, n)`，touch() 在“截止日期清空连带清截止时刻”（0001:55-57）之后、比较 fv 之前调它，所以它看到的是规整过的新值，清掉的 notified_for、snooze_at 照常记进 fv。内容：读 table_meta.remind_cols；为空就原样返回（非提醒表只多一次按主键的查找）；日程“换了哪一次”（date、remind_days 变了，time 在空和非空之间变）照 20261104110000:15-18 清 notified_for、snooze_at、pushed_for，判定和清列都在这里；remind_cols 有一列变了就清 pushed_for、defer_until。以后改“换了哪一次”的判定或清哪几列，只替换这个约 20 行的小函数。
- 不再有单独的 before 提醒触发器，“events_occ_reset 必须排在 events_touch 前面”这个名字顺序的依赖没了（真正解决 P7）。
- `enqueue_remind()`，挂三张表的 `after insert or update`：insert 一律入队；update 时 remind_cols 或 snooze_at 有一列变了入队；全天日程的“知道了”写成了不等于 remind_at 的值也入队（条件逐字照 20261105120000:21-22）。待办新建、或 due、due_time、remind_before_min 变了时 `p_fresh = true`（给 P13 用，见 6.3 Q2）。push-dispatch 写 remind_at、next_date、pushed_for、defer_until 时这几列都不在名单里：不入队、不清。
- after 触发器不带列清单，每次 update 都会调一次函数（对新旧值各取几列比一下），和 touch() 现在每次都做的比较同一量级。

**④ 规则版本号（只重算还没到点的，旧实例不会把它吃掉）**

- `shared/logic/remind.ts` 加常量 `REMIND_RULES_VER`（第一版 = 1），和算法放在同一个文件。
- 队列项带 `min_ver`（默认 0）；出队多一个参数 `p_ver`（默认 0），只交出 `min_ver <= p_ver` 的项。push-dispatch 传自己的 REMIND_RULES_VER。
- 改算法时：版本号加 N，同一个 PR 加一个一行的迁移 `select private.remind_enqueue('all', null, null, null, false, N);`（迁移以 postgres 在发布时跑，不受 PostgREST 语句超时和一轮 20 秒的限制）。

- 忘了怎么办：CI 加一条检查（tests/build/remind-rules-ver.test.ts）：一张固定输入（约 50 组：全天、有时刻、待办两种、跨夏令时、换时区）的算法结果快照，快照里记着版本号。算法结果变了而快照没更新就红；快照的版本号不等于 REMIND_RULES_VER 就红；迁移目录里找不到调 `remind_enqueue('all', …, REMIND_RULES_VER)` 的迁移就红（版本 1 除外）。
- 这次重写本身不改算法，所以**不做全量重算**（第一版 PR2 上线就 0 → 1 全量重算的那一步没有了）。
- 规模：一句语句把全站未到点的提醒入队（每人每表最多 2 万行，0001_core.sql:213-214）。每轮出队 500、每人 50，用户自己改的 prio 0 跨用户排在最前，所以只是批量项慢慢算；迁移开头写 `set local statement_timeout = '4min'`（db push 会话的默认值没核实）。

**⑤ 出队 `remind_queue_pop(p_limit, p_lease_s, p_retry, p_per_user default 50, p_poison default 5, p_ver default 0)`**

### 4.2 M1 迁移的步骤（同一个事务）

0. 开头 `set local lock_timeout = '5s'; set local statement_timeout = '4min';`，然后**按用户写入的顺序一次拿齐锁**：`lock table public.settings, public.events, public.todos, public.anniversaries in access exclusive mode; lock table private.remind_queue in access exclusive mode;`。用户写入都是“先锁业务表、后写队列”（apply_patch 20261029200000:83、109 → after 触发器 → 写队列），设置、时区那几路是“设置或 profiles → 读三张表 → 写队列”；M1 先拿业务表、最后拿队列，不会出现“M1 握着队列等业务表、用户握着业务表等队列”的互等。
   - **拿锁的写法（第二阶段在 lemo-e2e 上实测后定）**：两句 `lock table` 放进 `do $$ … $$` 块里，不写在顶层。supabase CLI 推迁移是把整份文件的语句一次管道发出，不是显式的 begin … commit 事务块，顶层的 `lock table` 会报 25P01（只能在事务块里用）；函数体里的 `lock table` 没有这个要求，拿到的锁一直持有到这份迁移结束。两句 `set local` 写在 do 块前面，这种推法下照样管到最后。
   - **do 块开头先核对超时设置（兜底）**：`current_setting('lock_timeout')` 不是 `5s` 或 `current_setting('statement_timeout')` 不是 `4min`，就 `raise exception` 停下，整个迁移回滚。这是防将来 CLI 改了推法、`set local` 没生效时，迁移在没有等锁上限的情况下一直挡着四张业务表；正常推法下这句永远不触发。
1. 队列表加 user_id（先可空）、prio、min_ver、fresh、enqueued_at；按三张表回填 user_id；回填不到的是孤儿（现在的出队函数下一轮本来也要删），删掉；user_id 设 not null；建 `remind_queue (user_id)` 索引。claim、claimed_at、attempts 不动，在途的租约照常由不动的 finish 收尾。
2. table_meta 加 remind_cols 列，三张表各一句 update。
3. 建 remind_enqueue、remind_reset、remind_on_settings、remind_queue_stats；enqueue_remind 换函数体；enqueue_floating 改成转发。
4. 换触发器（同一事务里先删后建，没有空窗）：删 8 个，建 4 个（3.2）。
5. touch() 整份替换一次：删 0001:66-73，加一行调 remind_reset。
6. drop + create remind_queue_pop（新签名），grant 给 service_role。
7. 删 enqueue_anniv_defaults、enqueue_allday_defaults、events_occ_reset。
8. 收回 service_role 对 remind_queue 的表权限。
9. 最后加外键 user_id → auth.users on delete cascade（要拿 auth.users 的 ShareRowExclusive，放最后，持锁时间最短）。
10. 不写任何一次性补算。

锁的代价照实写：第 0 步起四张业务表连读都被挡，直到事务提交（回填和加外键的量都是队列的大小，预计在秒级以内）；lock_timeout 是每次等锁各算一次，最坏五次各等满 5 秒约 25 秒，期间已拿到的表被挡。对策：推之前用 `private.long_transactions()`（0001_core.sql:532）看有没有长事务，挑没人用的时候推；等不到锁整个迁移回滚，重推即可。剩下的死锁可能只来自“一个用户事务按别的顺序碰两张业务表”，数据库约 1 秒判定后杀掉一方：用户那边客户端把 40P01 当临时故障重试（数据字典-v4.md:941），迁移这边重推。tests/build/migration-lock-timeout.test.ts 的 HOT_TABLES 加上这四张表。

### 4.3 不丢、不重的保证

- **排队中的不丢**：队列表只加列、只删孤儿；在途租约不动。
- **入队不断档**：触发器在同一事务里换，提交前旧的生效，提交后新的生效。迁移提交瞬间还在跑旧入队函数的语句，会因 user_id 非空报错回滚，客户端重发，不会静默丢。
- **不重复推**：pushed_for、notified_for、snooze_at、defer_until 迁移里一个都不改；清 pushed_for 的规则由 rls/38 的 48 条向量钉住，期望一字不改；认领代码不动。
- **读行时间点不变**：第 0 步照旧出队提交后再读行（3.3 ⑤），第一版那个“快照早于加锁、吞掉用户改动”的洞不会出现；两连接工具 tools/db/remind-queue-2conn.mjs 加一个场景“出队语句开始后、加锁前提交的改动”，期望拿到改后的值或本轮不取这一项。
- **批量不重推**：批量范围是原来各入口的子集，只去掉重算了也推不出去的（11-13 整块评审改：allday、all 按日期没过两天以上或稍后／顺延还在 1 小时以内，纪念日不看时间，floating 照原样，见 3.3 ② 的表）；当天推过的全天日程照旧重算，由第 0 步 R-336 压住不重推；all 第一次真用之前要核有时刻的日程、待办。
- **用户改动先算**：prio 0 跨用户排在最前（3.3 ⑤），批量再多也只排在用户改动后面。
- **旧实例不吃新规则的项**：出队按 min_ver 放行（3.3 ④）。
- **推送不断**：M1 后 PostgREST 刷新函数信息的那一会儿里，个别 RPC 可能失败，按现有逻辑这一轮跳过那一步（queue_pop_failed、due_query_failed、resolve_query_failed），条目还在 60 分钟窗口里，下一分钟补上。
- **限定**：上面只说重写不引入新的丢和重。P2（排队太久）因 prio 和批量范围收窄而大大缓解，但单个人一次改出几千条 prio 0（比如导入）仍要排队；P13、P14、P12 是现状，修不修看 6.3 Q2、Q3；认领超时看 Q4。

## 7. 未核实

- 正式库状态：在正式项目的 SQL 编辑器只读执行 `select max(version) from supabase_migrations.schema_migrations;`（看是不是 ≥ 20261105140000）和 `select count(*) from auth.users;`（看有没有用户）。我没有正式库权限。
- drop + create 出队函数（加带默认值的参数、多返回一列）以后，PostgREST 是否自动刷新函数信息、旧版按三个名字传参能否调到新函数：预览上 PR1 时看第一分钟有没有 queue_pop_failed、due_query_failed、resolve_query_failed，T18 在真库钉住。
- 锁的实际行为（drop trigger 拿 AccessExclusive、死锁判定）是按 PostgreSQL 通常行为和评审员在 PGlite 单会话里测的锁级别写的，两连接的死锁没有复现；Supabase CLI 遇到“远端有、本地没有的迁移版本”会停住，是通常行为，本仓库锁定的 2.120.0 没实测。
- db push 会话的默认语句超时（3.3 ④ 的全量入队要用）。
- P2、P12、P13、P14 的实际行为：P13、P14 评审用内存替身跑过，真库都没跑；T00 先钉住。
- remind_enqueue 里 row 一支靠 One-Time Filter 跳过其余几支，要在真库 explain 确认（T19）。
- 后端整改分支合入前可能再改；3.6 是按 d4bc408b 写的。
- 手机收到推送、通知被收回这几项，电脑和替身证明不了，只能负责人用 iPhone 看。
