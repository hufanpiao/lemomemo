## 0. 给负责人的摘要

1. 提醒推送这条线，“把要重新算时间的提醒排进队”现在有 10 个入口、6 段几乎一样的写法；同一条规则在数据库、服务器程序、测试里最多抄了 6 份。
2. 11-04、11-05 两天里，这块的数据库程序被整份复制重写了 8 次，每次其实只改一两行；下次再改，很容易漏掉其中一份。
3. 没查到“必然丢提醒、必然重复推”的硬伤。会出错的有三处：一个人一下子要重算很多条时，他刚改的那条要排队（每多 50 条多等 1 分钟）；纪念日“恢复默认提醒”不重算（纪念日推送上线后才显出来）；提醒没响时没有记录可查。
4. 改法：每类事只留一个入口。排队只有一个入口，“到没到点”只在一处判断，“哪些字段算提醒”只记在一张表里；服务器程序不再把数据库判过的再判一遍，同时补上记录。
5. 以后改提醒规则：算法只改一个文件、版本号加 1，服务器自动把所有提醒按新规则重算，不用再写补算，也不用讲究先后顺序。
6. 切换时排队中的提醒原样保留、推过的记录不动，不会重复推；先上预览跑稳，正式跟首发一起上；每一步都能单独退回。
7. 估计 5 个工作日左右（含评审返工），分三次提交；代码估计净减 200～300 行。
8. 需要你拍板 4 件事（第 6.3 节），每件都给了推荐。

## 3. 目标设计

### 3.1 一类事只有一个出口

| 一类事 | 现在 | 目标唯一出口 |
|---|---|---|
| 往队列里放 | 4 个函数里 6 句 insert，加 1 句迁移里的补算 | `private.remind_enqueue(...)`：全仓唯一一句 `insert into private.remind_queue` |
| 一行改了：要不要重算、要不要清推送记录 | touch() 的提醒段、3 个 *_remind 触发器、events_occ_reset、events_allday_ack_enqueue | `private.remind_row()`：一个 before 触发器函数，挂三张表 |
| 设置改了 | 2 个函数、3 个触发器、两套写法 | `private.remind_on_settings()`：一个函数、一个触发器 |
| 时区变了、设置变了要批量重算哪些行 | enqueue_floating 三句、两个 defaults 函数各一句 | `private.remind_enqueue_user(user, scope)` |
| “哪些列算提醒输入” | 6 份 | `private.remind_cols` 配置表（由数据清单生成、D1 比对） |
| 三张表的“提醒形状”（活着没有、是不是浮动时刻、due_at、推送要用的列） | 散在 6 个函数的三支 union 和 store.ts 的 colsOf | `private.remind_items` 视图 |
| 到点、收回、账号能不能用、每人上限、有没有设备 | SQL 一份 + TS 一份 + 替身一份 | 只在 `remind_due` / `remind_pushed`（读视图）；push-dispatch 信它 |
| remind_at 怎么算 | shared/logic/remind.ts（已唯一）+ 第 0 步里内联的 R-336 / S1 | shared/logic/remind.ts，R-336 / S1 挪进同一处的新纯函数 `recalcRemind` |

### 3.3 新对象的要点

**队列表**

```
private.remind_queue
  table_name, id                        主键不变
  user_id uuid not null → auth.users on delete cascade   新：出队不再三表左连接；注销时级联删，不再要等下一轮当孤儿删
  prio smallint not null default 0      新：0 = 这一行自己改了；1 = 批量（设置、时区、规则版本）
  enqueued_at timestamptz default now() 新：同一人、同一级先来先算
  claim, claimed_at, attempts           不变（R-348 租约）
```

有了 user_id，数据清单 `shared/manifests/core.ts:58-59` 的 remind_queue 改成按 user_id 找主人、注销级联；全仓只有它在用的 rowRef 机制（shared/schema/manifest.ts:17、build/d1/checks.ts:311-335、d1-fixtures 16、17）可以删掉。

**唯一入队 `remind_enqueue(p_tn text[], p_id uuid[], p_user uuid[], p_prio smallint)`**

一句 `insert … select from unnest(…) on conflict (table_name, id) do update set claim = null, claimed_at = null, attempts = 0, prio = least(q.prio, excluded.prio) where q.claim is not null or q.attempts > 0 or excluded.prio < q.prio`。不授任何角色执行权，只由属主是 postgres 的 security definer 触发器函数调用（和现在 enqueue_floating 一样）。

**配置表 `remind_cols(tbl, col, act)`**

act 两种：`reset`（变了要重算，并清 pushed_for、defer_until）、`enqueue`（变了只重算，例如 snooze_at）。初始行和现在 touch()、三个触发器的列逐个对上：

| 表 | reset | enqueue |
|---|---|---|
| events | date、time、tz、remind_min、remind_days、deleted_at | snooze_at |
| todos | due、due_time、remind_before_min、remind_days、remind_time、done、deleted_at | snooze_at |
| anniversaries | remind_offsets、remind_time、month、day、calendar、lunar_variant、is_leap、year、after_due、kind、deleted_at | snooze_at |

源头只有一处：数据清单 `shared/manifests/calendar.ts`、`todos.ts`、`anniv.ts` 各加 `remind: { reset: […], enqueue: […] }`。脚本按清单生成增量 SQL（insert / delete 几行）贴进新迁移；D1 比对库里的表和清单，写法照现有的 `ai.vectors` 比对（build/d1/checks.ts:276-286）。客户端 server-reset.ts 和测试替身直接 import 清单，不再自己写一份。

**行触发器 `remind_row()`**

挂在三张表上：`before insert or update`，不带列清单，名字是 `<表>_remind`，按字母排在 `<表>_quota` 后、`<表>_touch` 前。

- insert：入队，prio 0。
- update：用 to_jsonb 比新旧（同 touch 现在的写法），算出 reset 列、enqueue 列各有没有变。
  - 日程换了“哪一次”（date、remind_days 变了，time 在空和非空之间变）：`new := private.remind_occ_reset(old, new)`；
  - reset 列变了：清 new.pushed_for、new.defer_until（原 touch() 0001:66-73）；
  - reset 列变了、enqueue 列变了，或者全天日程的“知道了”写成了不等于 remind_at 的值（原 20261105120000:21-22）：入队，prio 0。
- push-dispatch 写 remind_at、pushed_for、defer_until 时，这几列不在配置表里：不入队、不清。

入队放在 before 触发器里是安全的：同一语句后面撞了约束，整个语句回滚，队列项一起没了。

**设置触发器 `remind_on_settings()`**

`after insert or update of value, deleted_at, undone on public.settings`，`when (new.key in ('remind.default_time', 'anniv.default_offsets', 'anniv.default_time'))`。函数里：update 时三列都没变就返回（照 20261104100000:37-38）；`remind.default_time` 调 `remind_enqueue_user(uid, 'allday')`，`anniv.*` 调 `remind_enqueue_user(uid, 'anniv_defaults')`。两种设置从此一套写法，纪念日默认的删掉、撤销也重算（修 P3），原样再写不重算（修 P11）。

**视图 `remind_items`**

三张表 union all 成一种形状：`tn, id, user_id, remind_at, snooze_at, defer_until, pushed_for, notified_for, due_at, live, floating, has_cfg, row`。

- `live`：没删、没撤销，待办还没完成。待办一支写成 `t.done = false`，和部分索引 0002:77 的谓词一字一样，规划器才认得出。
- `floating`：全天日程、待办、纪念日为真。
- `has_cfg`：设了提醒（粗判，只用来少入队，宁多勿少）。
- `row`：推送和重算要用的列（jsonb），取代 store.ts:15-23 的 colsOf；不含 note、raw_text、location 这些正文列。

remind_due、remind_pushed、remind_enqueue_user、出队、规则版本号都读它。以后加第四张提醒表，只在视图里加一支、在配置表里加几行。

**出队 `remind_queue_pop`**（参数不变）

- 删孤儿那句一个字不动（20261105110000:32-42，统计信息那次的教训）；
- 候选不再三表左连接（:49-56），直接用 q.user_id；
- 同一人内编号从 `order by tn, qid`（:60）改成 `order by prio, enqueued_at, tn, qid`，修 P2；
- 每人 50、有毒 5 次两个常量写在函数开头的 declare 里，全仓只此一处；

**到点、收回 `remind_due` / `remind_pushed`**（参数不变）

条件逐条照 20261103140000:56-59、72-74、79-80、96、107，只是从三支 union 改成读视图一处；多返回 `row`。旧版 push-dispatch 只读前几列，照常能用。

**规则版本号**

- `shared/logic/remind.ts` 加常量 `REMIND_RULES_VER`（第一版 = 1），和算法放在同一个文件，改算法的人一眼看得到。

- 迁移里从此不写一次性补算。

### 3.5 和 push-dispatch 的分工

| 事 | 谁做 |
|---|---|

### 3.6 和“加超时”那边的衔接

- push-dispatch/store.ts 现在每个调用都没有超时。等 `_shared/store-timeout.ts` 那边落地后，store.ts 的每个调用套上它，`until` = 这一轮开始 + ROUND_BUDGET_MS（20 秒）。PR2 等那边合进去再开，在它上面改，不各改一份。
- 超时 = “可能做了，也可能没做”（store-timeout.ts:5）。逐个调用这样收尾：
  - 出队超时：这一轮跳过第 0 步，租约 180 秒后重取（attempts + 1，在有毒上限内）；
  - 收尾超时：同上；
  - 写回 remind_at 超时：放回，下一轮重算；结果相同就不写；
  - **认领超时：当作已经认领，不再发**（最多一次，App 的“错过的提醒”兜底），记 `store_timeout:claim`；
  - 收回超时：pushed_for 可能已清，下一轮不再回它，只是少一次收回；
  - 规则版本号超时：下一个实例再调。
- 改完以后每轮请求数变少（不再逐人查账号、不再按 id 回读行），超时的地方也跟着少。

### 3.7 记录和监控（按 11-11 最高规则）

- 第 0 步每一项写一行函数日志：`recalc:<结果>:<表>:<id 前 8 位>`，结果是 written / same / r336 / ack / tz_invalid / no_profile / failed / released 之一。只记原因，不记标题和时刻。
- logs 表（App 诊断区看得到）加 `act = 'recalc'`，只记 written、r336、failed。same 不记，免得批量重算刷屏。
- 心跳 detail 加 `recalc_written`、`recalc_r336`、`queue_depth`、`queue_oldest_s`。usage-report 的白名单（usage-report/core.ts:122）跟着加；lemo-ops 在 queue_oldest_s 超过 900（15 分钟）时提示。

### 4.3 不丢、不重的保证

- **排队中的不丢**：队列表只加列、不删正常行；在途租约不动。
- **入队不断档**：触发器在同一事务里换。提交前旧的生效，提交后新的生效。
- **不重复推**：pushed_for、notified_for、snooze_at、defer_until 迁移里一个都不改；清 pushed_for 的规则由 rls/38 的 48 条向量钉住，期望一字不改；认领代码不动。
- **推送不断**：迁移后 PostgREST 刷新函数信息的那一两分钟里，个别 RPC 可能失败。按现有逻辑这一轮跳过那一步（queue_pop_failed / due_query_failed），条目还在 60 分钟窗口里，下一分钟补上。
- **第一次规则版本号**（PR2 上线，0 → 1）会把所有提醒以 prio 1 排一遍，相当于一次全量回归：算出来和原来相同的不写回。用户自己的改动 prio 0，照样先算。

### 6.4 我直接定的技术取舍（不用拍板，评审会复核）

1. 同一人内“自己改的先算、批量的后算、同一级先来先算”（P2）。
2. 纪念日默认设置删掉、撤销也重算，原样再写不重算（P3、P11），和全天日程一套写法。
3. “哪些字段算提醒”用配置表加清单生成、D1 比对。不用触发器参数：改列要删建触发器；也不继续写在触发器定义里：那是三处。
4. 到点、收回、账号能不能用只在数据库判，push-dispatch 不复核（安全审查员复核签字）。
5. 队列存 user_id、注销级联删，删掉只有它在用的 rowRef 机制。
6. 认领仍用 PostgREST 条件更新，不挪进 SQL：挪进去三张表要各写一支；“查出到点到认领之间用户刚按了知道了”的几十毫秒窗口和现在一样，接受。
7. 收回 service_role 对 remind_queue 的表权限（P9）。
8. 改过的文件头注释压到 5 行内，来龙去脉挪进本文件和 CHANGELOG（P10）。
9. 租约、重试、有毒项、最多一次、各项上限一律不动（3.8）。
