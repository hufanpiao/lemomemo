## 1. 结论（一句话）

**推荐建独立子表 `public.todo_items`**（每个子任务一行，带全套公共列，复合外键挂到 todos），走现有的 outbox、`apply_patch`、墓碑和按清单生成的导出、注销、清理；**不在 todos 行里放 jsonb 数组**。主待办的“自动完成”和“撤销”都由客户端发普通 patch，服务器不加联动触发器。

## 2. 数据：两种做法的比较

### 2.1 做法 A：独立子表 `todo_items`（推荐）

每个子任务一行：`id, user_id, todo_id, title, done, sort, created_at, updated_at` 加公共列（rev、fv、deleted_at、undone、synced_at）。

### 2.2 做法 B：todos 加一列 `items jsonb`

`items = [{id, title, done, sort}, …]`，整列作为 todos 的一个字段。

### 2.3 逐项比较

| 方面 | A 独立子表 | B todos.items jsonb |
|---|---|---|
| **冲突合并：两台设备同时勾不同项** | 不同项是不同的行，各自 rev、fv，**互不冲突，两个勾都留下**。同一项两边同时改 `done`：字段级后写胜出（4.4 第 5 步），见 2.5 的 no_conflict | 两个 patch 都改同一个字段 `items`：`fv.items > base_rev`，第二个报 `conflict`，**整列后写胜出，先到的那个勾被冲掉**。要不丢，只能在 `apply_patch` 里给 `items` 写专门的按元素合并（类似 notes 的 forked 特例），违背“冲突规则只在一处、按字段通用”（4.4 第 7 条），pgTAP 和 K8 的 rebase 都得另写一套 |
| 离线叠加（rebase，4.3） | 现成：每行 `server`/`view`，outbox 的 patch 叠上去 | 本机 patch 带的是整个数组；服务器推来新数组时，本机未发的整列 patch 会把别的设备新增、勾掉的项盖回去，要另写数组级 rebase |
| **墓碑** | 子任务只软删（写 deleted_at）；硬删只发生在 30 天清理、永久删除、主待办被硬删时的外键级联——三种都由通用 `write_tombstone()` 留墓碑（行级 after delete 触发器对级联删除同样触发）。要做：`tombstones.tbl` 的 check 加 `'todo_items'` | 不需要墓碑（数组里删一项只是改列）；但“一边删一边改”同一项时丢改动、不提示 |
| **RLS** | 照 3.3 A 普通用户表三条策略；**复合外键 `(todo_id, user_id) → todos(id, user_id)`**（`todos_id_user_key` 已有，0.29 P-06 就是为这个建的），加上 ins 策略强制 `user_id = auth.uid()`，挂不到别人的待办上（外键检查不走 RLS，复合键保证对得上） | 不用新策略，跟着 todos 走 |
| **导出、备份** | 清单 `export: 'json'`、`backup: 'json'`，按清单自动进账号导出和 backup-daily（多一个 `todo_items.json`） | 跟着 todos 走，零改动 |
| **注销清除** | `user_id` 外键 `on delete cascade` 到 auth.users，`onAccountDelete: 'cascade'`；`tests/data-manifest/` 按清单自动生成“注销后删干净”的用例 | 跟着 todos 走 |
| 30 天清理、永久删除 | 清单 `softDelete: true`，清理任务按清单生成；主待办被清理或永久删除时子任务级联删掉、各留墓碑。`purge_deleted` 的“全部清空”要多清一段已软删的子任务（2.6） | 跟着 todos 走 |
| 行数上限 | 通用 `row_quota()`：每人每表 2 万行，够用；每条待办的项数另加触发器（2.5） | 64 KB patch 上限内；项数上限要在 check 里数数组长度 |
| 旧版客户端 | 旧版的清单里没有这张表：不建本机仓、不同步，看到的是没有子任务的待办，照常能改、能完成 | 宽容读取把不认识的列留在 server 副本里（lenient.ts），也不出事 |
| 工作量 | 后端多一张表的标准套件（迁移、授权、白名单、D1、pgTAP） | 后端少，但 `apply_patch` 特例 + 前端数组 rebase 的风险和测试量更大 |

**推荐 A。** 决定性的是第一行：负责人截图就是一张卡片多个勾，手机和电脑同时开着、各勾一项是常见场景，B 会悄悄丢勾，要补救就得在冲突核心里开特例。A 的额外成本都是现成套路（照 note_images 挂 notes 的样子）。

### 2.4 表结构（新迁移的设计，**只写设计，不建文件**）

文件名：`supabase/migrations/20261113170000_todos_items_create.sql`（功能名 todos，3.5 第 3 条的命名法；11-13 开工定，晚于 R-411 的 20261113160000）。下面是定稿时的设计，实际迁移和它的差别见本节末尾“开工后的改动”。内容：

```sql
-- ===== todo_items（R-350）=====
create table public.todo_items (
  id uuid primary key,
  user_id uuid not null default auth.uid() references auth.users on delete cascade,
  rev int not null default 1, fv jsonb not null default '{}', deleted_at bigint,
  undone boolean not null default false, synced_at timestamptz not null default now(),
  todo_id uuid not null,
  title text not null check (char_length(title) <= 100 and char_length(btrim(title)) >= 1),   -- 开工后改：去掉首尾空格后至少 1 个字
  done boolean not null default false,
  sort double precision not null,               -- 排序键，见 6.4
  created_at bigint not null, updated_at bigint not null,
  foreign key (todo_id, user_id) references public.todos (id, user_id) on delete cascade);
insert into private.table_meta (tbl, system_cols, no_conflict)
  values ('todo_items', '{}', '{done,sort,updated_at}');          -- 见 2.5
create index on public.todo_items (user_id, synced_at);           -- 3.1 每张表都建
create index on public.todo_items (todo_id);                       -- 开工后改：完整索引（原为 where deleted_at is null 的部分索引），级联删、计数都用得上

create trigger todo_items_touch     before insert or update on public.todo_items for each row execute function private.touch();
create trigger todo_items_quota     before insert on public.todo_items for each row execute function private.row_quota();
create trigger todo_items_cap       before insert or update of deleted_at, undone on public.todo_items for each row execute function private.todo_items_cap();
create trigger todo_items_tombstone after delete on public.todo_items for each row execute function private.write_tombstone();

alter table public.todo_items enable row level security;
create policy sel on public.todo_items for select to authenticated using (user_id = (select auth.uid()) and private.is_active());
create policy ins on public.todo_items for insert to authenticated with check (user_id = (select auth.uid()) and private.is_active());
create policy upd on public.todo_items for update to authenticated
  using (user_id = (select auth.uid()) and private.is_active()) with check (user_id = (select auth.uid()));
revoke all on public.todo_items from anon, authenticated;
revoke delete on public.todo_items from anon, authenticated;     -- 和 TC-B2-04 同口径：没有 REST 硬删
grant select on public.todo_items to authenticated;
grant insert (id, todo_id, title, done, sort, created_at, updated_at) on public.todo_items to authenticated;
grant update (title, done, sort, deleted_at, undone, updated_at) on public.todo_items to authenticated;

alter publication supabase_realtime add table public.todo_items;

-- tombstones 的 tbl 白名单加一项（0001 的 check 约束，drop 后重建）
alter table public.tombstones drop constraint tombstones_tbl_check;
alter table public.tombstones add constraint tombstones_tbl_check check (tbl in
  ('settings','devices','events','todos','categories','notes','note_images','note_files','anniversaries','todo_items')) not valid;
alter table public.tombstones validate constraint tombstones_tbl_check;   -- 开工后改：先 not valid 再单独 validate
```

另外同一个迁移里要改的：

- **`apply_patch` 白名单加 `todo_items`**（4.4.1 的 `case p_table`；可改列 = 上面 `grant update` 的六列）。`apply_patch` 要 `create or replace` 重建，照 0.38 第 59 条的授权行重新 revoke/grant；3.3 C 文字不变。
- **`private.todo_items_cap()`**（`language plpgsql`、`security invoker`、`set search_path = ''`，只在触发器里调，`revoke execute … from public`）：插入、或从删除状态恢复（`deleted_at` 由非空变空、`undone` 由 true 变 false）时，数同一个 `todo_id` 下 `deleted_at is null` 且 `undone` 为假的行，**≥ 30 就 `raise exception 'items_quota'`**。客户端上限 20（第 7 节），服务器留 10 项余量给“两台设备离线各加几项”的情况。**数之前先锁主待办行**（`perform 1 from public.todos where id = new.todo_id and user_id = new.user_id for no key update`，锁不到就 `raise exception 'not_found'`）：同一条待办下的插入、恢复排队进行，30 项上限守得住。原写“不为这件事锁主待办行”，**R-350 主持人 11-13 代定改成要锁**：不锁的话 N 个并发请求能把上限顶到 29+N；锁只挡同一条待办内的写入，代价很小。账号不可用（停用等）时 todos 的 upd 策略本来就锁不到，这时不报 not_found、交给 RLS 拒成 42501（不让客户端把停用期间的写入丢掉）。`items_quota` 进 outbox 的永久错误码（丢掉这一项、提示“子任务最多 20 项”）。
- **`purge_deleted_impl` 的“全部清空”**（`p_items is null`）多一段固定 SQL：删本人 `todo_items` 里 `deleted_at is not null` 的行。逐条永久删除（`p_items` 非空）不接受 `tbl = 'todo_items'`（子任务不进“最近删除”，见 6.3），`bad_table` 名单不变。
- **主待办已经不在**：子任务 insert 时主待办已经不在了（离线期间主待办被另一台设备永久删除），`todo_items_cap()` 锁不到主待办，报 `not_found`（原写外键报 `23503`、outbox 按表限定丢掉；**R-350 主持人 11-13 代定改成服务器报 not_found**）。`not_found` 本来就在 K8 的 `DROP_CODES` 里，outbox 不用为子任务单独写判断。本机那一行由前端按 5.6 第 1 条删掉。
- **开工后的改动（R-350 评审，11-13）**：上面“锁主待办”“not_found”两条；标题 btrim 检查；`(todo_id)` 改完整索引；tombstones 约束先 not valid 再 validate；另补了方案没写到的两处手写表名单：`cleanup_batch` 的 30 天清理（实际是手写名单，不是“按清单生成”）、`export_size_over` 的表清单。三处手写名单（tombstones check、apply_patch 的 case、cleanup_batch）由 D1 第 7 节和清单比对（`build/d1/sync-lists.ts`）。

不改的：`fn_ai` 不授权（子任务不算向量，第 9 节 Q8）；`remind_queue`、`enqueue_remind` 不挂（子任务没有提醒）；`todos` 表结构不动（不加计数列，已勾/总数由客户端现算）。

### 2.5 冲突口径（`table_meta.no_conflict`）

- `done`、`sort`、`updated_at` 进 `no_conflict`：同一项两边同时勾/取消勾、同时拖动排序，后写胜出、**不弹“已在另一台设备上改过”**——一个勾选框没有值得对比的“对方版本”。
- `title` 照常报冲突（两边同时改同一个子任务的字，少见，提示合理），客户端沿用待办的冲突提示。
- `system_cols` 为空（没有服务器写的系统列）。

## 3. 本机库：IndexedDB 仓与版本迁移

- 同步仓按清单生成（`syncStores()`），清单加了表，就多一个 `todo_items` 仓（主键 id，行存 `{id, server, view, ro?}`），不手写。
- **`DB_VERSION` 加 1**（现在是 2，到时以主干为准），重新生成 `core/cache-schema.lock`（CI 核对）；`cacheMigrations` 末尾加 `{ to: N, up: () => undefined }`——结构核对会自动补建缺的仓，这一步不改数据。
- 新仓没有游标，主页启动后照“没有游标就整表拉”拉一次 `todo_items`（开工时核对 boot 对新表确实走整表拉，写一条单元测试）。

## 4. 同步：怎么走现有 outbox 和 K8 冲突规则

1. **新建子任务** = 一个 `insert` 项，`data` 是整行可写列；`deps` 写 `[{table: 'todos', id: todo_id}]`（调用方忘写时 core 入队兜底按 `data.todo_id` 自动补上，`src/core/outbox-new-item.ts` 的 `PARENT_OF`，R-350 评审第 3 条）。`sendOrder()` 已经支持“依赖的记录还有没发的项时先发依赖”，所以主待办（新建页里刚建的）一定先上服务器，不会撞外键。
2. **勾选、改标题、排序、删除、撤销** = `patch` 项，走 `apply_patch('todo_items', …)`，base_rev、own_revs、合并、`sent` 标记全部照 4.2；删除写 `deleted_at`，撤销写 `deleted_at = null`（照现有 `saveDeleted`）。
3. **带提醒的条目优先**（4.2）：主待办有 `remind_at` 时它整条提前，子任务不带提醒、不提前；patch 之间没有外键顺序问题。insert 依赖主待办，主待办提前不影响。
4. **自动完成主待办**：最后一项勾上时，客户端在同一次点击里依次入队两项——`todo_items` 的 patch（`done: true`）和 `todos` 的 patch（`done: true, done_at: now, updated_at: now`，remind 标记照现有 `remindAfterDone` 算）。两项各自发送、各自幂等。**不加服务器联动触发器**，理由：
   - 触发器替用户改 todos 会让 todos 的 rev 前进，本机随后发的 todos patch 的 base_rev 落后，正常操作被误报冲突；
   - 本机离线时界面必须马上显示“已完成”，客户端本来就得自己算，服务器再算一次是两套规则；
   - 撤销也只是两个普通 patch，不用和触发器打架。
5. **已知局限（接受）**：两台设备**同时**各勾“剩下的最后两项”中的一项，每台看到的都还剩一项没勾，谁也不会触发自动完成，结果是 4/4 而主待办未完成。很少见；卡片显示满格进度，用户自己点一下主待办即可。**收到同步时不补做自动完成**（那会让每台设备都去写，一台离线的设备回来还会把用户手动取消的完成又写回去）。
6. **墓碑和 30 天**：主待办软删时子任务不动（随主待办一起藏起来；恢复主待办时子任务原样回来）；主待办被清理或永久删除时，服务器外键级联删掉子任务、每行一条墓碑，别的设备按 tombstones 删本机行（4.3）；本机的“第二道”规则（启动时删 deleted_at 早于 30 天的行）对 `todo_items` 同样生效，另加一条：**主待办在本机已不存在的子任务一并删掉**。
7. **`gone` / `not_found`**：子任务的 patch 回 `gone`（子任务本身被别的设备删了）：**不弹“恢复并保留我的修改”**，直接丢掉本机修改——为一个勾选框弹对话框不值得。回 `not_found` 照通用规则丢掉。主待办回 `gone` 时照旧弹现有提示。
8. **只读行**：宽容读取把 `todo_items` 也当普通表处理（不认识的值 → 只读）；主待办只读时，它的子任务一律只读（勾选、加删改都拦下，出“这条要新版本才能修改 · 更新”）。

## 5. 界面

### 5.1 待办列表页卡片

- 有子任务的待办：标题下面一行 `2/4`（和截止标签同一行，排在最前，例如 `2/4 · 今天 17:00 截止`），卡片底部一条**分段进度条**（每项一段，勾上的段填柠檬色；20 项时每段约 14 px 宽，手机够看）。
- 摊开时，标题下列出子任务：圆形勾选框（和主待办同一个 `CheckCircle`，小一号）+ 标题，按 `sort` 排；已勾的标题变淡、不加删除线（和主待办“已完成”的样式一致）。卡片右下“收起 / 展开”。
- **列表页只能勾选，不能加删改排序**；点子任务标题区和点主标题一样进编辑页。
- 没有子任务的待办外观完全不变。
- 动效（17.1、17.2）：勾子任务时圆圈原地填满（`--dur-ui`）、对应的进度段同时填满；**最后一项**勾上后，先停 `--dur-ui` 让人看到满格，再按现有“勾选完成”的动效整张卡片挪到“已完成”组（复用 `useHoldView`）；收起、展开用高度过渡；`prefers-reduced-motion` 时都换成直接切换。

### 5.2 今天页

- 推荐：今天页的待办行**只显示 `2/4` 和一条细进度条，不摊开**（今天页一屏要放日程和待办，摊开会把“下一件”挤下去）；点进编辑页勾选。见第 9 节 Q5。
- 今天页的打勾（主待办）照旧。

### 5.3 编辑页（`#/todo/<id>`、`#/todo/new`、电脑右侧编辑栏）

- 标题下面一个“子任务”区：每项一行“勾选框 + 可直接编辑的标题 + 删除 ×”，最底下一行“添加子任务”输入框；回车加一项、焦点留在输入框，方便连着加；**粘贴多行文字**按行拆成多项（去掉空行，超过上限的部分不加并提示）。
- 改标题失焦即存（和编辑页其余字段一样）；清空标题失焦 = 不保存，恢复原来的字（不当删除，免得误删）。
- 删除：软删，页内出“已删除子任务 · 撤销”（和编辑页现有的删除撤销同一个样子）。
- **排序**：手机长按拖动、电脑拖动左侧把手；另给键盘和读屏一条路：聚焦把手后 `Alt+↑/↓` 移动，读屏的“操作”菜单有“上移 / 下移”。
- **新建页**：标题还没保存（主待办还没 insert）时，“子任务”区灰掉，提示“写上标题才能加子任务”——和现在“写上标题才会保存”同一口径，避免子任务挂到不存在的待办上。
- 编辑页不收起（一直摊开）。

### 5.4 收起状态

- 推荐：**每台设备各记各的，不同步**（手机和电脑屏幕大小不同，想看的不一样；同步还会让每次收起都产生一次写入）。存法见第 3 节。
- 默认：**未完成的待办默认展开**（同负责人截图）；**“已完成”组里的默认收起**。见第 9 节 Q4。

### 5.5 自动完成、撤销、再取消勾

| 情况 | 建议 | 需负责人确认 |
|---|---|---|
| 勾上最后一项 | 主待办自动完成（`done = true`、`done_at = now`），页底出撤销条“全部完成，已完成这条待办 · 撤销”，8 秒，和删除撤销条同一组件（`UndoToast`）、同一个位置、同时只出一条 | 已定 |
| 点撤销条的“撤销” | **两件一起撤回**：主待办回到未完成，**刚勾的那一项也取消勾**（回到点之前的样子）。只撤主待办会留下 4/4 却未完成的卡片，看着像出了错 | **Q1** |
| 主待办已完成，再取消勾某一项 | **主待办自动改回未完成**（卡片从“已完成”组挪回原来的组），不出撤销条（再勾回去就又完成了） | **Q2** |
| 子任务没勾完，直接勾主待办 | 允许；子任务不动（卡片在“已完成”组里显示 2/4、变淡）；不弹“要不要把剩下的也勾上” | **Q3** |
| 自动完成后手动取消主待办 | 子任务不动（仍是 4/4），主待办回未完成 | 随 Q2 |
| 已完成的待办新加一项（未勾） | 主待办不变 | 随 Q2 |
| 删掉唯一没勾的那项、其余都已勾 | **不自动完成**：自动完成只由“勾上”这个动作触发 | 随 Q2 |

规则一句话：**主待办只在“勾上最后一项”和“取消勾某一项”这两个动作时被自动改，其余情况都不动。**

- 现有规则“打勾没有撤销条（只有删除有）”（TodosPage 文件头）对自动完成**开一个例外**：主待办是被顺带改掉的，用户没直接点它，所以给撤销。撤销条的 `onUndo` 发两个 patch（子任务 `done: false`、主待办 `done: false, done_at: 0`）。
- 撤销条出现期间又做了别的操作（再勾一项、删一条）：现有 `useReadonlyGuard` 同时只显示一条，新的替换旧的，旧的撤销作废——照现状。

### 5.6 前端接手要做的（后端评审转来，11-13）

1. **本机清掉孤儿子任务**：主待办在本机已经不存在（被墓碑删掉、或 TC-R350-12 那种服务器回 not_found 丢掉了 insert）时，它的子任务在本机一并删掉（4 节第 6 条那条“第二道”规则）；服务器丢掉的那一项不会再有墓碑来删它，只能本机删。
2. **`NOTICE_TABLES` 加 `todo_items`**（`src/features/sync-notice/data/notice-tables.ts`）：现在名单外的表回 `gone` 会静默丢、回 `conflict` 不出提示卡，和 2.5“title 照常报冲突”对不上；`gone` 静默丢本来就是 4 节第 7 条要的，conflict 要出提示。
3. 本机库 `DB_VERSION` 已在后端这次提交里升到 3（加了 `todo_items` 本机库表；锁文件校验要求结构变了就升版本，拿不出来），前端不用再升；发版后网页不能回滚到 v2（上线与回滚手册第四节第 1 层已写）。

### 5.7 前端落地（11-14）

5.1～5.6 和第 6 节都已做，落在哪、代定了什么见架构 0.66。和上文不一样的地方：
- 5.6 第 1 条的“本机删掉”：服务器回 not_found 丢掉 insert 时，outbox 当场按 rewriteRow 删本机行（服务器没有、队列也没有剩下的项）；启动时按 `PARENT_OF` 再清一遍父行已不在、且服务器上从来没有过的子任务，作兜底；同步过的子任务不按“本机没有主待办”删（拉取一张表一张表来，可能先于主待办到本机），由服务器级联删和墓碑删。

## 6. 上限、无障碍、中韩文案

### 6.1 上限

| 项 | 客户端 | 服务器 |
|---|---|---|
| 每条待办的子任务数（未删除的） | **20**：到 20 项“添加子任务”输入框禁用，提示“最多 20 项” | `todo_items_cap()`：≥ 30 报 `items_quota`（留离线并发余量） |
| 子任务标题 | **1～100 字**（去掉首尾空白后；输入框 `maxLength` 100） | check `char_length(title) between 1 and 100` |
| 每人每表行数 | — | 通用 `row_quota()` 2 万行 |

数字见第 9 节 Q6。

### 6.2 无障碍

- 进度：卡片上的 `2/4` 和进度条合成一个 `role="progressbar"`，`aria-valuemin=0`、`aria-valuemax=总数`、`aria-valuenow=已勾`、`aria-valuetext="子任务已完成 2 项，共 4 项"`；分段本身 `aria-hidden`。
- 收起/展开按钮：`aria-expanded`、`aria-controls` 指子任务列表；读屏名带上待办标题（“收起「买菜」的子任务”），一屏多张卡片时分得清。
- 子任务勾选框：读屏名 = 子任务标题 + 状态；触摸区不小于 44 × 44 px（视觉圆圈可以小，点击区补足）。
- 自动完成：撤销条本来是 `role="status"`，读屏会念“全部完成，已完成这条待办”。
- 排序有键盘和读屏的替代操作（5.3）；拖动中按 Esc 放回原位。
- 对比度：进度条未填的段和卡片底色至少 3:1（非文字元素），按 8.1 的皮肤对比度清单四套皮肤各验一次。
- 减少动效：见 5.1。

### 6.3 “最近删除”

子任务**不进“最近删除”**：只能在编辑页删完当场撤销；之后 30 天由服务器清理（“全部清空”时一起清，2.4）。主待办进“最近删除”时，恢复它子任务原样回来。见第 9 节 Q7。

### 6.4 排序键

`sort` 用浮点：新加的项 = 当前最大值 + 1；拖到两项之间 = 两项的中点；两项之差小于 `1e-9` 时，把这条待办的所有子任务按顺序重编为 1、2、3……（一批 patch，少见）。不同设备同时拖不同项不冲突；同时拖同一项后写胜出（no_conflict）。
