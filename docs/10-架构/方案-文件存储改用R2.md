## 0. 结论摘要（负责人看这一页就够）

**推荐：② 只把照片和附件搬到 R2**（四个桶：`images`（含纪念日头像）、`vault-images`、`files`、`vault-files`）；**服务器备份 `backups` 和隐私记 PPT 的临时桶 `vault-preview` 留在 Supabase**；数据库、登录、同步、Realtime 全部不动。

| 项目 | 结论 |
|---|---|
| **能不能做** | 能。R2 不对外开放，App 上传、下载一律经我们自己在 `lemomemo.com/files/` 下的一个 Pages Function，身份由 Supabase 数据库判断，和现在的存储策略同一个口径 |
| **省下什么** | 文件存储从“1 GB 里大家抢”变成 **10 GB 免费、流出不收费**。按估算，负责人一人用约 **12 年**、十个人约 **3 年**才会超 10 GB；超了每 GB 每月 0.015 美元（十个人第五年约每月 0.1 美元）。Supabase 的 1 GB 只剩备份用（一人约 50 MB、十人约 200 MB）。照片流量也不再占 Supabase 免费版每月 5 GB 的流出额度 |
| **每月花多少** | **0 美元**（在免费额度内）。对比：不改、到线升 Pro 是 **每月 25 美元起** |
| **工作量** | 开发 **8～12 人日**，加评审返工 25%，合计 **约 10～15 人日**；运维另 1.5～2 人日（按 R-204 单列）。**主持人粗估的 4～7 人日偏少**：漏了转发函数本身、清单和 D1、生成的注销清理用例、六个服务器函数改读 R2 |
| **日历时间** | 约 **+3～5 个工作日**。B0 只改清单、迁移、D1 和生成器（+1～2 天）；新的文件函数放到 **B4 第一项**做（B4 才第一次用到文件），和前端 A 并行 |
| **现在做还是以后做** | 现在做最便宜：B0 的代码刚写、还没有任何真实文件。上线后再搬要多写搬数据的脚本、重做已验收的 B4、B4b-1、B5，约 **16～24 人日** |
| **安全：变好的** | ① 读文件也查“账号停用、会话被吊销”（现在 `img_sel` 策略不查）；② 上传时核对 webp 文件头，不只看声明的类型；③ 本机备份拉取用的 R2 密钥**确定能设成只读**（Supabase 的 S3 密钥能不能只读一直没核实）；④ 网页和文件同源，R2 不开 CORS、不开公开访问 |
| **安全：变弱的** | ① 文件的权限检查从 Supabase 自带的存储策略，改成**我们自己写的函数**来执行（判断仍在数据库里做，函数照结果办）；② 多三类密钥要管（R2 访问令牌、下载链接的签名密钥）；③ **数据所在地**：Supabase 在首尔；R2 只能指定“亚太”，**不保证在韩国**，隐私说明要改，按韩国 PIPA 属于向境外转移 |
| **隐私记** | 隐私记的附件本来就是密文，放哪里都一样；**隐私记的图片 4.0.0 不加密（R-104）**，搬到 R2 后由 Cloudflare 保存明文，要么如实写进隐私说明，要么顺带加密（B5 约 +1 人日），由负责人选 |
| **退路** | R2 用的是 S3 通用接口，对象路径和现在一样，搬回 Supabase 约 3～5 人日；R2 出问题时只有图片和附件打不开，文字照常能记（Cloudflare 本来就是 `/sb/*` 的必经之路，没有新增“单点”） |

## 4. 推荐方案（②）的设计

### 4.1 总体图

```
App（网页 / iPhone 主屏幕 / exe）
  ├─ 数据、登录、同步、Realtime：lemomemo.com/sb/*  ──→ Supabase（首尔），不变
  └─ 照片和附件：lemomemo.com/files/v1/*  ──→ Pages Function（新）──→ R2（亚太，私有）
                                               │
                                               └─ 先拿用户的 JWT 调 Supabase 的 RPC，由数据库判断“能不能”
服务器函数（file-check、ai-media、vault、vault-file、vault-image、storage-sweep、account-purge、usage-report）
  └─ 用 R2 的 S3 接口读写（只授四个桶的读写令牌）
本机 pull.ps1（每周日拉照片和附件）
  └─ 用 R2 的 S3 接口，令牌是**只读**的
留在 Supabase 的桶：backups、vault-preview（流程不变）
```

**为什么让 App 经我们的函数、而不是直接用 R2 的预签名链接**：
- 预签名链接只能用 R2 自己的域名（`<账号>.r2.cloudflarestorage.com`），**不能用自定义域名**（官方写明），这样就和 14.2“全部走自有域名、同源”冲突：网页要开 CORS，exe 的 `save_attachment` 只认 `lemomemo.com` 的规则要改，大陆能不能连上那个域名也要另测；
- 预签名链接不支持 POST 表单上传，也不能限制上传大小；
- 经自己的函数：同源、不用开 R2 的 CORS、可以边收边计数、可以核对文件头、可以查账号状态。

### 4.2 上传和下载链接：谁签、怎么验身份、多长时间

**上传**（`PUT /files/v1/o/<桶>/<路径>`，带 `Authorization: Bearer <用户的 JWT>`、`X-App-Version`）：
1. 路径白名单：桶只认四个；路径按清单 `pathPattern` 的正则（和现在 3.3 G 一字不差）判断，原始 URL 先过 `functions/sb/[[path]].ts` 现成的 `SUSPICIOUS_PATH_RE` 检查；
2. 版本检查：上传是写操作，按 `version-gate.ts` 查 `min_client_version`；
3. **身份和权限由数据库判断**：函数带着用户自己的 JWT 调新 RPC `public.files_authorize(op, bucket, path)`（security invoker，内部调 `private.files_authorize_impl`，security definer）。PostgREST 会先验 JWT 的签名和有效期，RPC 里再判断：
   - `is_active()`（账号存在、没停用）、JWT 的 `session_id` 没被吊销（和服务器函数的 `requireActiveUser` 同一口径）；
   - 路径第一段等于 `auth.uid()`；
   - **上传**：照现在的 `file_slot_open()`——`files` 桶要求 note_files 里已有这一行、本人的、`is_vault = false`、`check_status = 'pending'`、没删；**`images` 桶收紧成同样的“先写行、再传文件”**（现在 `img_ins` 只看路径，不要求有行；收紧后孤儿少，B4 本来就是先写行）；纪念日头像要求 anniversaries 那一行的 `avatar_id` 等于路径里的 id；`vault-images`、`vault-files` 一律拒绝（只能经服务器函数写）；
   - 按 `counters` 计数限流（每人每分钟上传 30 次，和 file-check 同级）；
   - 返回允许的最大字节数和 Content-Type（来自清单 `limits`）。
4. 函数检查 `Content-Length` 不超过上限，边收边计数，超了中断；**前 12 个字节必须是 webp 的 `RIFF….WEBP`**（`images`、`files` 里的缩略图）；文档的内容检查照旧交给 file-check；
5. 写 R2 用**条件写**（对象已存在就失败），对应现在“不给 update、upsert”的规则；条件写在 R2 上怎么表达（S3 的 `If-None-Match: *`），**B0 实测**；
6. 不提供客户端删除：图片、附件一律只写 `deleted_at`，对象由 storage-sweep 删（现在 `img_del` 允许客户端删自己的图，改后取消，少一个口子）。

**下载**（和现在 Supabase 签名链接的用法一样，前端改动最小）：
1. `POST /files/v1/sign {items: [{bucket, path}]}`（一次最多 100 个，瀑布流的缩略图一次签完），带 JWT；函数调 `files_authorize('read', …)` 批量判断（本人、行存在、`is_active`、会话未吊销；`vault-images`、`vault-files` 一律拒绝）；
2. 返回 `https://lemomemo.com/files/v1/o/<桶>/<路径>?e=<到期时间>&s=<签名>`，签名是 `HMAC-SHA256(FILES_URL_SECRET, "GET|桶|路径|到期时间")`；
3. `GET` 这个链接不要 JWT（`<img>`、微软查看器、exe 的 `save_attachment` 都能直接用），函数常量时间比较签名、看没过期，从 R2 取对象流式返回；`?download=<清理过的文件名>` 照 5.13 第 4 点加 `Content-Disposition`；
4. **有效期**：本机预览、下载、看图 **60 秒**（同 5.13 第 4 点、15.3 第 2 条）；给微软预览普通 PPT 的，按 B0 实测的“最短能稳定打开”（先定 5 分钟）；
5. 响应头：`Cache-Control: private, no-store`（和现在签名链接不缓存一致）、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: sandbox`，复用 `functions/_lib/security-headers.ts`；
6. **函数和 Cloudflare 都不记查询串**（14.2 第 8 点扩到 `/files/*`）。

**隐私记的图片和附件**：
- `vault-images`：`vault-image` 函数**改成直接返回图片字节**（`Cache-Control: no-store`），不再发 60 秒签名链接——少一个能被转发的链接，比现在更严；
- `vault-files`：照 5.13 第 11 点，`vault-file {get}` 本来就是函数解密后直接回内容，只是读密文的地方从 Supabase 桶换成 R2；
- 隐私记 PPT 给微软：`vault-file {ms_preview}` 从 R2 读密文、在内存里解密，**明文照旧写进 Supabase 的 `vault-preview` 临时桶**，签名链接、删除和 sweep 流程一概不变（已经过两轮安全复核，不动）。

**JWT 在 Pages Functions 里怎么验**：
- 推荐做法（上面写的）：**不在函数里自己验**，把用户的 JWT 原样带去调 RPC，由 PostgREST 验签、由 SQL 判断权限。好处：不用在 Pages 里放任何 JWT 密钥；吊销、停用、限流和数据库一个口径；直连 supabase.co 也绕不过（R2 根本没有对外入口）。代价：每次上传、每批签名多一次到首尔的往返（韩国约几十毫秒）。
- 可选优化：Supabase 的新式非对称签名密钥（ES256）可以在函数里用 JWKS（`/auth/v1/.well-known/jwks.json`）先本地验一遍，挡掉明显无效的请求、不打到数据库。**前提是项目已换成非对称密钥**，B0 核对两个项目用的是哪种；如果还是旧的 HS256 共享密钥，**不要**把它放进 Pages（那等于把能伪造任何人身份的钥匙多放一处），只用上面的 RPC 做法。

### 4.3 对象命名和用户隔离

- **路径完全不变**：`<user_id>/<note_id>/<id>.webp`、`<…>/<id>.t.webp`、`<user_id>/anniv/<anniversary_id>/<avatar_id>.webp`、`<user_id>/<note_id>/<id>.<kind>`。表上的 check 约束、清单的 `pathPattern`、服务器“按 user_id、note_id、id、kind 自己拼路径”的规矩都照旧。
- R2 建 **4 个桶**，名字和现在一样（`images`、`vault-images`、`files`、`vault-files`），正式、预览各一套，预览的加 `preview-` 前缀；位置提示 `apac`；**不开公开访问、不绑自定义域名、不开 r2.dev、不配 CORS**。
- `note_images.bucket` 列的取值不变（`images` / `vault-images`），它表示“哪个逻辑桶”，和存在哪家无关。
- 用户隔离靠三层：路径第一段 = user_id（RPC 核对）；行属于本人（RPC 核对）；R2 本身对外不可达。

### 4.4 大小和类型限制放在哪一层

| 层 | 现在（Supabase） | 改后（R2） |
|---|---|---|
| 桶设置 | `file_size_limit`、`allowed_mime_types`（只看声明的类型） | R2 没有这两项；**由 `/files` 函数按清单 `limits` 执行**（同样的数字），并加 webp 文件头核对 |
| 数据库行 | `bytes ≤ 10 MB` 的 check、路径 check、`guard_note_file` 不可变列 | 不变 |
| 服务器复查 | file-check：大小、sha256、类型、每人合计、etag | 不变，只是从 R2 读对象 |
| 客户端 | 预览沙箱里判断内容、ZIP 炸弹 | 不变 |

### 4.5 用户上限和配额怎么计

**不变**。口径本来就是数据库里的 `sum(bytes)`（note_images 加 note_files，图片、文档、纪念日头像合计），由 file-check 执行、`my_ai_usage()` 给设置页显示，和对象存在哪家无关。负责人上限 700 MB、朋友 50 MB 照旧；**R2 有 10 GB 以后，负责人可以把自己的上限调高**（例如 5 GB），这是负责人的决定（第 10 节第 6 条），不影响代码。

运维告警（3.4 的 80% / 90%）分成两条：Supabase 文件存储（只剩备份和临时桶）照旧；R2 另算“四个桶合计占 10 GB 免费额度的百分比”，到 80% 提醒（只是说“要开始付几毛钱了”，不是“要满了”）。

### 4.6 数据库记录和对象两边怎么保持一致

**顺序不变：先写行、再传对象、最后由服务器核对**（5.13 第 2 点 ⑥，第四轮架构 L3）。

| 情况 | 怎么处理 |
|---|---|
| 行写了、对象没传上（断网、App 被杀） | 行停在 `check_status = pending`；file-check 的 cron 补扫找不到对象，超过 24 小时标 rejected（图片照现在的“没有对象就显示占位”）；客户端下次打开重传，`files_authorize` 认 pending 的行 |
| 对象传上了、file-check 没跑 | cron 每 10 分钟补扫，照旧 |
| file-check 不通过 | 删 R2 对象（S3 DeleteObject）、行标 rejected，照旧 |
| 移进移出隐私记（三步：准备新对象 → 一个事务提交 → 删旧对象） | 不变；对象在 R2 的两个桶之间，用 S3 接口读写 |
| 中途崩溃留下的对象（孤儿） | storage-sweep 每天按清单 `orphanSweep`：用 S3 `ListObjectsV2` 按 `<user_id>/` 前缀列出、超过 24 小时、表里没有对应行的，批量删（`DeleteObjects` 一次最多 1000 个） |
| 30 天清理 | 02:30 storage-sweep 先删对象、03:00 SQL 再删行，照旧；只是删对象从 Supabase Storage API 换成 R2 的 S3 接口 |

“删不删得掉”的风险反而小了：3.4 写过 Supabase 上“SQL 直接删 `storage.objects` 只删了元数据、文件还在”；R2 上只有一种删法。

### 4.7 注销、清理、备份、恢复、D1 和生成用例

- **注销**（account-purge 第 2 步）：四个 R2 桶按 `<user_id>/` 前缀列出、批量删；删完再列一次确认为 0，写进 heartbeat 明细。`backups`、`vault-preview` 在 Supabase，照旧。
- **服务器备份**：不变（备份本来就不含文件本体，只含行）。
- **本机拉取**（第 10 节第 2 步）：每周日从 R2 增量拉四个桶，用 **R2 的只读令牌**（Object Read only，限定四个桶），存法、位置、不加密（R-210）都不变。可以用 `rclone` 或 AWS CLI 兼容命令，由运维在 B7 定。
- **恢复**：数据库按第 10 节的 JSON 导入；文件从本机 `图片\`、`附件\` 文件夹用写令牌传回 R2（恢复脚本加一段，B7 演练覆盖）。
- **用量报告**（usage-report）：R2 的用量用 S3 列表累加或 Cloudflare 的用量接口（B7 定），Supabase 只报 `backups`、`vault-preview` 两个桶。
- **清单**：`bucketSchema` 加一个字段 `store: 'supabase' | 'r2'`。
- **D1**：`store = 'supabase'` 的桶照旧和 `storage.buckets` 比；`store = 'r2'` 的桶**必须不在** `storage.buckets` 里（防止两边都建），并核对 `/files` 函数里的路径正则、大小、类型表是由清单生成的（静态比对生成文件）；预览环境的 E2E 另核对 R2 上这四个桶存在、不公开。
- **生成用例**（`tests/data-manifest/generate.ts`）：现在探针是 `select … from storage.objects`；R2 桶改用“对象存储探针”（按 `userLookup` 列前缀、数个数），本地和 CI 用一个 S3 兼容的替身（MinIO 容器）代替 R2，正式代码和测试走同一套 S3 调用。
- **3.5 第 4 点“清单管不到的地方”**：不变（本机备份和其他设备的 IndexedDB 由 B7 注销演练覆盖）。

### 4.8 隐私记的图片和附件

| | 现在 | 改后 |
|---|---|---|
| 隐私记附件（`vault-files`） | 密文，在 Supabase | 密文，在 R2。Cloudflare 拿到的是密文，钥匙在 Supabase 的 secrets 里，**不影响安全性** |
| 隐私记图片（`vault-images`） | **明文**（R-104 不加密），在 Supabase，靠权限隔离 | **明文**，在 R2。多了一家（Cloudflare）在服务器上保存明文。注意 Cloudflare 本来就终结 `/sb/*` 的 TLS，传输中已经能看到这些图片，改后多的是“存放” |
| 隐私记 PPT 预览的临时明文 | Supabase `vault-preview` | 不变 |

可选：顺带把隐私记图片也加密（和隐私记附件同一套：数据密钥 + VAULT_KEY + AAD），架构 5.5 原估 B5 约 +1 人日。由负责人选（第 10 节第 2 条）。

### 4.9 Realtime、离线、Service Worker

- **Realtime、同步、离线队列**：不受影响。它们只同步数据库行；文件本来就不进 IndexedDB 排队（5.13 第 1 点“离线时加附件变灰”）。
- **Service Worker**：`src/sw/routes.ts` 现在把 `/sb/*` 一律直连；**`/files/*` 照同样规则直连、不缓存**（15.3 第 1 条扩一行，A19 检查和 E2E 加一条）。
- **大陆**：路线和 `/sb/*` 一样走 Cloudflare，不新增域名；看图不再绕到首尔的 Supabase，可能略快，14.6 实测时顺带看。

### 4.10 exe（`http://tauri.localhost`）的 CORS

- `/files/*` 函数直接复用 `functions/_lib/cors.ts`：只给 `http://tauri.localhost`、预检本地回 204、不是白名单来源不带任何 CORS 头。`ALLOW_HEADERS` 已有 `authorization`、`content-type`、`x-app-version`，不用加；`EXPOSE_HEADERS` 加 `ETag`（上传后客户端要拿）。
- **R2 桶本身不配 CORS**：浏览器和 exe 从不直接访问 R2。
- exe 的 `save_attachment`（5.13 第 4 点，B4b-1，前端 B）：URL 前缀从 `/sb/storage/v1/object/sign/files/` 改成 `/files/v1/o/files/`，其余检查不变。
- 网页版和 `/files/*` 同源，不涉及 CORS。

## 5. 安全影响

### 5.1 新增的攻击面

| 攻击面 | 风险 | 措施 |
|---|---|---|
| `/files/v1/*` 函数 | 权限判断写错，能读写别人的文件 | 判断放在数据库 RPC 里（和现在的存储策略同一套 SQL）；函数只照结果办；把现在 RLS 测试里 H7 那几条（B 读、写、删 A 的图片失败）原样搬成函数测试；路径先过白名单正则和可疑字符检查；拼出的 R2 键再断言第一段等于 RPC 返回的 user_id |
| 下载链接（我们自己签的） | 链接被转发或泄露，有效期内谁拿到都能下 | 和现在 Supabase 签名链接**同等**：60 秒；不打印、不记查询串；**改进**：换掉 `FILES_URL_SECRET` 就能让所有未过期链接立刻作废（Supabase 的签名链接作废不了） |
| R2 访问令牌 | 泄露后能读写四个桶 | 按用途分三把，各自只授需要的桶和权限（见 5.5）；放 Pages 加密变量、`supabase secrets`、Windows 凭据管理器；不进仓库、不进 CI；每 90 天或怀疑泄露时轮换 |
| Cloudflare 账号 | 账号被盗，文件和网站一起丢 | 15.3 第 9 条已要求 Cloudflare 开两步验证或 Passkey；R2 之后这条更要紧 |
| 账单 | R2 没有消费上限，被刷读写会产生费用 | 上传必须先过 RPC 和每人上限；读要有效链接；读类操作 1000 万次/月免费，超出 0.36 美元/百万，影响很小；负责人设账单提醒（例如 1 美元） |
| Functions 每天 10 万次额度 | 看图占用额度 | **不新增**：现在看图本来就走 `/sb/storage/…` 同一份额度；改后签名一次可以签 100 个，反而更省 |

### 5.2 和现在 Supabase 存储策略比：哪些变弱、怎么补

| 现在的保护 | 改后 | 怎么补 |
|---|---|---|
| 存储策略由 Supabase 执行，**直连 supabase.co 也绕不过** | 由我们的函数执行 | R2 没有任何对外入口，绕不过函数；判断仍在数据库 RPC 里；函数测试覆盖 |
| 桶级 `file_size_limit`、`allowed_mime_types` | R2 没有 | 函数按清单执行，并多核对 webp 文件头 |
| `file_slot_open()` 里“对象还不存在”由数据库原子判断 | 改由 R2 条件写判断 | B0 实测条件写；实测不行就“先查再写”，剩下的竞争窗口由 file-check 的 sha256 和 etag 兜底（检查过的文件被换掉会退回 pending） |
| Supabase 的安全顾问（Security Advisor）会检查存储策略 | 对 R2 不检查 | D1 核对 R2 桶不在 `storage.buckets`；预览 E2E 核对 R2 桶不公开、没有 r2.dev |
| — | **变强**：读文件也查停用和会话吊销（现在 `img_sel`、`file_sel` 不查 `is_active`） | — |
| — | **变强**：本机拉取的密钥确定是只读的 | — |
| — | **变强**：隐私记图片不再发签名链接，函数直接回字节 | — |

总体：**持平略好**，前提是 `/files` 函数和 RPC 过一轮安全评审（算在评审返工里）。

### 5.3 数据所在地

- Supabase：项目建在**首尔**（14.2 第 5 点，函数固定 `ap-northeast-2`）。
- R2：只能给位置提示 `apac`，官方写明“尽力而为、不保证”；没有韩国或日本这一级的辖区选项。所以**照片和附件可能存放在韩国以外的亚太地区**，具体在哪里我们无法保证、也无法事后核实到国家。
- 对用户的影响：按韩国 PIPA，属于把个人信息存放到境外（国外移转），隐私说明要写明接收方、国家或地区、项目、方式、保存期限（**未经律师核实**）；大陆用户本来就属于跨境（PIPL），不新增类别。
- 如果负责人要求“数据只能在韩国”，R2 做不到，只能选 ④（第 10 节第 3 条）。

### 5.4 隐私说明要怎么改（B7b 写隐私说明时一起改）

- 15.7 第 3 项“交给谁处理（委托）”：“Supabase（数据库和文件，首尔）”改成“**Supabase（数据库、登录、备份，首尔）；Cloudflare（网络转发，全球；照片和附件的存放，亚太地区，不保证在韩国）**”；
- 加一条“个人信息存放到境外”：项目（照片、附件、纪念日头像）、接收方（Cloudflare, Inc.）、地区（亚太）、保存期限（同现在：删除后 30 天、注销后 7 天冷静期满即删）；
- 隐私记图片如果不加密：“隐私记的图片不加密，存放在 Cloudflare”；
- 告知页和官网隐私句：现在的句子“数据存在服务器上，运营者在技术上能访问”仍成立，不用改。

### 5.5 负责人要新管的密钥

每个环境（正式、预览各一套，值都不一样）：

| 名字 | 是什么 | 放哪里 | 权限 |
|---|---|---|---|
| `R2_FILES_ACCESS_KEY_ID` / `R2_FILES_SECRET_ACCESS_KEY` | `/files` 函数用 | Pages 项目的**加密变量** | Object Read & Write，限四个桶 |
| `R2_FN_ACCESS_KEY_ID` / `R2_FN_SECRET_ACCESS_KEY` | 服务器函数用 | `supabase secrets set`；和 `FN_*_DB_URL` 一样由 CI 限定只有规定的函数能读（file-check、ai-media、vault、vault-file、vault-image、storage-sweep、account、account-purge、usage-report） | Object Read & Write，限四个桶 |
| `FILES_URL_SECRET` | 下载链接的签名密钥（32 字节随机） | Pages 加密变量 | — |
| `R2_PULL_ACCESS_KEY_ID` / `R2_PULL_SECRET_ACCESS_KEY` | 本机 pull.ps1（只正式环境） | Windows 凭据管理器，**取代**原来的 Supabase S3 密钥 | **Object Read only**，限四个桶 |

- 生成方式：R2 令牌只能在 Cloudflare 后台建、只显示一次。照 8.4“三把钥匙”的做法：**负责人本人在后台建，用运维写的脚本以 `Read-Host -AsSecureString` 读入、直接写进 Pages 和 `supabase secrets`**，不经过 AI、不进命令行参数；`FILES_URL_SECRET` 由脚本在内存里生成。
- 不新增的：不需要在 Pages 里放 Supabase 的 JWT 密钥或 service key（4.2）。
- 减少的：Supabase 的 S3 访问密钥不再需要（只有 pull.ps1 用它）。

## 8. 风险和退路

| 风险 | 影响 | 应对 |
|---|---|---|
| R2 或 Cloudflare 故障 | 图片、附件打不开、加不上；文字照常能记（本机优先） | Cloudflare 本来就是 `/sb/*` 和网站的必经之路，同一个故障域，没有新增单点；界面照现在的“离线时打不开”处理 |
| `/files` 函数出 bug，权限放宽 | 能读到别人的文件 | 判断在数据库 RPC；函数测试照搬 RLS 的 H7；新函数单独过一轮安全评审 |
| R2 条件写不支持我们要的写法 | 同一路径可能被覆盖 | B0 实测；退路是“先查再写”+ file-check 的 sha256、etag 兜底 |
| 数据所在地不在韩国 | 隐私说明多一项境外存放 | 如实写；负责人不接受就选 ④ |
| R2 收费方式变化、免费额度取消 | 要付钱 | 用量很小，按现价十人五年约每月 0.1 美元；真变贵就搬回 |
| Cloudflare 账号被封或被盗 | 文件和网站一起受影响 | 两步验证（15.3 第 9 条）；本机每周有一份完整的图片和附件备份（第 10 节） |
| Supabase 和 Cloudflare 两边对不上（行有、对象没有） | 个别图片显示占位 | 先写行后传对象、file-check 补扫、孤儿清理，和现在一样 |

**以后能不能迁回去**：能，成本不高。R2 用的是 S3 通用接口，Supabase Storage 也有 S3 兼容接口；对象路径两边一样、数据库一行不用改。迁回要做的是：建回四个桶和存储策略、用 `rclone` 把对象复制回去并核对、`/files` 函数换成转发到 Supabase、清单的 `store` 改回去，约 **3～5 人日**。

## 9. 推荐和理由

**推荐 ② 只搬照片和附件，B0 先改清单和迁移，`/files` 函数放到 B4 第一项做。**

理由：
1. **钱**：负责人一人用十年左右都在免费额度里；对比 ④，到线后每年约 300 美元。
2. **时间点**：现在没有任何真实文件，B4 以后的代码都还没写，是最便宜的时候；拖到上线后要多花一半以上的工作量，还要停机搬数据。
3. **范围最小**：最占地方、最占流量的是照片和附件；备份很小（几十到两百 MB），搬过去收益小，反而让 Cloudflare 多保管一份全量明文数据；`vault-preview` 的流程刚过两轮安全复核，不值得动。
4. **安全持平略好**：权限判断仍在数据库里，多了停用和吊销检查、文件头检查、只读的拉取密钥；代价是多三类密钥、多一个自己写的函数要评审。
5. **不排斥以后升 Pro**：如果以后为了数据库升 Pro，R2 也不用搬回去。

不推荐 ③（解决不了问题）。① 比 ② 多 2～3 人日、隐私上更差。④ 可以接受，适合“宁可花钱也不想多一家服务商、多管几把钥匙、或要求数据只在韩国”的情况；如果暂时拿不定，选 ④′ 先留接口。

## 10. 要负责人决定的

1. **文件存储改不改、改哪些？**
   - **② 只把照片和附件搬到 R2，备份和隐私记 PPT 临时桶留在 Supabase（推荐）**；
   - ① 全部文件都搬 R2；
   - ③ 只搬备份；
   - ④ 不改，到线时升 Supabase Pro（每月 25 美元起）；
   - ④′ 不改，但现在多花 1～1.5 人日留一层接口，以后再搬更便宜。
2. **隐私记的图片搬到 R2 以后要不要加密？**
   - **不加密，隐私说明如实写“隐私记的图片不加密，存放在 Cloudflare”（推荐，维持 R-104，不加工期）**；
   - 顺带加密（和隐私记附件同一套，B5 约 +1 人日）；
   - 隐私记图片留在 Supabase，只搬普通照片和附件（多维护一个桶在 Supabase，约 +0.5 人日）。
3. **能不能接受照片和附件存放在“亚太地区”、不保证在韩国？**
   - **接受，隐私说明写明境外存放（推荐）**；
   - 不接受，数据必须在韩国 → 只能选第 1 条的 ④。
4. **什么时候做？**
   - **B0 收尾时改清单、迁移、D1 和生成器，`/files` 函数和 R2 开通放到 B4 第一项（推荐）**；
   - 全部在 B0 做完（B0 日历多 3～5 天）；
   - 上线后再做（约 16～24 人日，要停机搬数据）。
5. **R2 的开通和账单谁来做？**
   - **负责人本人在 Cloudflare 后台开通 R2（可能要绑卡）、设 1 美元的账单提醒、建三把令牌并运行写入脚本（推荐；约 20 分钟，运维写步骤）**；
   - 交给运维代做（运维要拿到 Cloudflare 账号的账单权限，不推荐）。
6. **搬到 R2 以后，负责人自己的存储上限调不调？**
   - **先不调，保持 700 MB，等用到 80% 再说（推荐；不影响代码）**；
   - 调到 5 GB；
   - 不设上限（只受 R2 免费 10 GB 的运维告警约束）。
