### 1.2 几句话说明白
- **软件本身**和**数据**分开放：软件放在 Cloudflare，数据放在 Supabase。软件更新时数据不动。
- **钥匙分两种**。一种是你登录后手机里拿到的“登录令牌”，只能开你自己的数据。另一种是 AI 密钥、推送密钥、隐私记密钥，只放在服务器上，拆开软件也找不到。
- **AI 用 Gemini 的免费额度**。额度用完的当天自动改用本地规则（就是现在 v3 的一句话识别），第二天恢复。全程 0 元。
- **推送**：服务器每分钟检查一次。到点就通过苹果或微软的推送服务发到你的设备，App 关着也能收到。推送里直接写标题。
- **离线**：没网时也能看、能记。记下的内容先存在设备里，联网后自动补传。

## 3. 数据库

### 3.1 公共约定
- 业务字段沿用数据字典，只把驼峰改成下划线，由适配器自动互转。业务时间仍用 **bigint 毫秒**（`created_at`、`remind_at` 等），logic 层不用改。
- 每张用户表都有这些列：
  - `id uuid primary key`（客户端生成，插入天然幂等）
  - `user_id uuid not null default auth.uid() references auth.users on delete cascade`
  - `rev int not null default 1`
  - `changed text[]`（最近一次更新改了哪些字段）
  - `deleted_at bigint`
  - `synced_at timestamptz not null default now()`（服务器时间，增量同步的游标）
  - `legacy_id text`（claude.ai 的旧 id，搬数据用）
- 触发器 `trg_touch`，在每次插入和更新前执行：设 `synced_at = now()`；更新时 `rev = old.rev + 1`；`user_id` 不能改（`new.user_id := old.user_id`）。
- 索引：每张表都建 `(user_id, synced_at)`。

### 3.3 RLS（伪 SQL）

所有表都执行 `enable row level security`。辅助函数 `is_active()` 判断 `profiles.disabled_at is null`，`security definer`。

**A. 普通用户表**（events、todos、anniversaries、categories、note_images、settings、devices、logs）：
```sql
create policy sel on T for select to authenticated using (user_id = auth.uid() and is_active());
create policy ins on T for insert to authenticated with check (user_id = auth.uid() and is_active());
create policy upd on T for update to authenticated using (user_id = auth.uid() and is_active())
                                                  with check (user_id = auth.uid());
create policy del on T for delete to authenticated using (user_id = auth.uid() and is_active());
-- logs：没有 upd 策略（只能新增）；settings：没有 del 策略
```

**B. notes**（隐私记只能经服务器函数写）：
```sql
select：using (user_id = auth.uid() and is_active())
insert：with check (user_id = auth.uid() and is_private = false and body_enc is null)
update：using (user_id = auth.uid() and is_private = false)
        with check (user_id = auth.uid() and is_private = false and body_enc is null)
delete：using (user_id = auth.uid() and is_private = false)
-- 列权限：revoke select (body_enc) on notes from authenticated;
-- 客户端读不到隐私记的密文；只能看到“有一条隐私记”和它的 id、分类、时间
```

**C. 只给服务器函数用的表**（invites、vault、vault_credentials、ai_usage、ai_provider_state、ai_config、rate_limits）：开 RLS，**不建任何策略**，authenticated 和 anon 都无权访问，只有 service role 能读写。

**D. api_tokens**：select 和 update 只能操作自己的行，update 只允许改 `revoked_at`；不建 insert 策略，由 `token-admin` 函数生成；`token_hash` 列 revoke select。

**E. profiles**：select 和 update 只能操作自己的行，只允许改 display_name、tz_mode、current_tz；insert 由 `invite-signup` 函数做。

**F. app_config**：`select to anon, authenticated using (true)`。

**G. 存储桶**：
- `images` 私有桶：
  ```sql
  select / insert / delete：using ((storage.foldername(name))[1] = auth.uid()::text)
  ```
  路径是 `<user_id>/<note_id>/<image_id>.webp`。
- `vault-images`、`backups` 不建任何策略，只能经服务器函数访问。

### 3.4 软删除和 30 天清理
- 删除照旧写 `deleted_at`（ADR-006）。随手记转成待办后，原来那条也是写 `deleted_at`，所以会出现在“最近删除”里。
- 记录流程里的“撤销”：刚新建的条目直接硬删除（客户端有 del 策略）。
- `pg_cron` 每天 03:00（首尔时间）执行：
  ```sql
  delete from T where deleted_at < (extract(epoch from now()) * 1000 - 30 * 86400000);
  ```
  同时删掉对应的图片对象，并清理 90 天以前的 logs。
- 硬删除以后，增量同步就看不到这些行了。所以离线超过 25 天的设备，重新上线时直接整表重拉（见 4.3）。

## 4. 同步和离线

### 4.1 本机缓存
- IndexedDB 库 `planner-v4`。每张表一个 store（键是 id）；另外有 `meta` store（各表的 `cursor` 即最后一次的 synced_at、`last_full_sync`、当前 user_id）和 `outbox` store。
- 启动时先读 IndexedDB 马上渲染，再连网同步。退出登录或切换账号时，清空整个库。
- 隐私记的明文**不进** IndexedDB，只在 `data/vault.js` 的内存里；上锁或切到后台时清空。

### 4.2 离线写入队列（outbox）
- 每条队列项：
  ```
  {op_id, table, id, op: insert|update|delete, patch, base_rev, client_ts, tries, next_at}
  ```
- 写入时先改本机缓存（乐观更新）→ 入队 → 马上尝试发送。触发发送的时机：上线、切到前台、每 30 秒。
- 同一条记录，队列里连续的几个 update 合并成一个（patch 合并，base_rev 取最早那个）。insert 后面跟着 delete，两条一起抵消。
- 发送顺序：全局按先进先出。失败后按 2、4、8 秒……退避，最长 5 分钟。返回 4xx 错误（权限、校验）时不再重试，移进“发送失败”区，界面上提示。
- 幂等：insert 用 `upsert(onConflict: id, ignoreDuplicates)`；update 走 RPC `apply_patch`（见 4.4），用 op_id 去重（服务器记录 24 小时内用过的 op_id）。

### 4.3 多设备实时更新
- App 在前台时用 **Supabase Realtime**（`postgres_changes`，按 RLS 过滤）。收到改动后合并进缓存，再发 `change` 事件。
- iOS 切到后台时会断开 WebSocket，所以**每次回到前台、每次重连**都做一次增量拉取：`select * where synced_at > cursor order by synced_at`。游标往回退 5 秒，防止时钟抖动漏掉记录。
- Realtime 连不上时，退回每 60 秒轮询一次。
- 距离上次整表同步超过 25 天，就整表重拉。
- Realtime 免费版的连接数和消息数上限没有核实，个人和几十个朋友预计够用（**未核实**）。

### 4.4 冲突
RPC `apply_patch(table, id, patch, base_rev, op_id)`，`security invoker`，所以照样受 RLS 约束：
1. 当前 `rev == base_rev`：直接应用，rev 加 1，`changed = patch 里的键`。
2. `rev > base_rev`，并且 patch 的键和服务器自 base_rev 以来改过的字段**不重叠**：合并应用，返回 `merged`。（服务器只记得最近一次改了什么；`rev − base_rev > 1` 时无法判断，按第 3 条处理。）
3. 字段有重叠：**后保存的胜出**（应用 patch），返回 `conflict`，同时带回旧值。界面提示“已在另一台设备上改过”，提供“看对方的版本”。
4. notes 的 `title` 或 `body` 冲突时，不覆盖，另存一份“（冲突副本）”。
5. 记录已被删除（deleted_at 有值）：返回 `gone`，客户端丢掉这次修改并提示。

合并规则写在 `logic/conflict.js` 里，服务器的 SQL 函数照着实现，两边用同一组单元测试用例。

### 4.5 Service Worker 缓存
- **预缓存**（按构建号分版本）：index.html、app.\[hash].js、app.\[hash].css、字体、图标、manifest。
- **不缓存** Supabase 的接口和 Realtime：数据已经在 IndexedDB 里了。
- **图片**：签名链接会过期，所以按“对象路径”做键存进 Cache Storage，先读缓存；最多 300 张或 60 MB，超出时淘汰最久没用的。
- **更新**：新的 SW 装好后，等页面发来“点击刷新”再 `skipWaiting`。
- **推送**：处理 `push` 和 `notificationclick`，点击后打开 `/#/item/<kind>/<id>`。iOS 网页推送是否支持通知上的操作按钮（例如“稍后”）**未核实**，所以“稍后”放在 App 里的提醒卡片上。

 │             │                   │      │                           │──────────────────►│

 │             │                   │      │◄── {items[], source} ─────│

- 语言：设置里选“中文 / 한국어”，浮层上也能一键切换。Web Speech 一次只能识别一种语言。
- iPhone 主屏幕模式下 Web Speech 是否稳定：**待真机实测**。不稳定时，提示用户改用键盘听写。

### 5.2 随手记保存 → AI 分类
```
客户端：写 notes（ai_status=pending，先用 classify-rules 给一个 category_id，category_source=rule）→ 进队列 → 同步
pg_cron 每 2 分钟 → fn ai-classify（x-cron-secret）
  ├ 取 ai_status=pending 的记录，按用户分组，每组最多 20 条，一次请求分完（省免费额度）
  ├ 带上这个用户现有的分类名单（最多 30 个），让 AI 选一个，或提议一个新分类
  ├ 校验：新分类名不超过 12 个字；这个用户的分类已经超过 30 个时不准新建，只能选已有的
  ├ 写回 category_id，category_source=ai，ai_status=done
  │   category_source=manual 的记录永远不改
  ├ 额度用完（429 或 quota）→ ai_provider_state.exhausted_until 设成下一次重置时刻，
  │   这批保持 rule 分类，ai_status=rule；第二天的第一轮把 rule 的记录重新排进队列
  └ 有 5 对以上分类名称很像（logic 里的相似度判断）→ 写一条 notice，提示“要合并分类吗”
隐私记：fn 解密后同样分类（按 R-46，好用优先），结果只写 category_id
```

### 5.3 到点提醒：pg_cron → Edge Function → Web Push
```
pg_cron（每分钟）── net.http_post + x-cron-secret ──► fn push-dispatch
  1. 查出 events、todos、anniversaries 里
     remind_at <= now + 60 秒、remind_at > now − 60 分钟（只发 60 分钟内的，沿用 v3 规则）、
     deleted_at is null、notified_for 不等于 remind_at
     （todos 还要 done = false），每次最多 500 条
  2. 逐条先写 notified_for = remind_at（条件更新 where notified_for 不等于 remind_at；
     返回 0 行说明别处已处理，跳过）→ 保证不重复
  3. 文案：“15:00 NEOX 会议”，纪念日写“明天是妈妈生日（60 岁）”，格式由 logic/format 共用
  4. 用 VAPID 私钥发给这个用户的每台设备（devices.push_endpoint）
     返回 404/410 → 删掉这个订阅；其他错误 → push_fail_count 加 1
  5. 纪念日：调 logic/anniv 算出下一次提醒（先 −7 天，再 −1 天，然后是明年），写回 remind_at
  6. 写一条 logs（act=push_ok 或 push_failed）
免打扰时段：放在第 1 步之后过滤，推迟到免打扰结束
桌面 exe（4.2）：WebView 里收不到 Web Push，靠程序内每分钟检查一次 + Tauri 本机通知；
  共用 notified_for，不会重复
```

### 5.4 纪念日：阴历换算 → 两次推送
```
保存时（客户端 data/anniv）：
  logic/anniv.nextDate(rec, today, variant) →
    阳历：今年的 month-day；已经过了就取明年；2 月 29 日在非闰年取 2 月 28 日
    阴历：lunar.toSolar(今年, month, day, is_leap, variant)；
          闰月当年不存在 → 用同号的平月；三十日不存在 → 用二十九日；已经过了就算明年
  remind_at = 下一个还没到的 (next_date − offset 天) 的 remind_time，按 profiles.current_tz 换算成毫秒
服务器：push-dispatch 推送以后滚动到下一个时刻（见 5.3 第 5 步）；
        fn anniv-roll 每天 00:10 兜底重算 next_date 已过期的记录（例如设备长期离线）
周岁：有 year 时 = 今年 − year，按阳历生日是否已过来定，阴历按换算后的日期
```
阴历版本：中国农历和韩国阴历个别年份会差一天，每条记录用 `lunar_variant` 记下按哪一种。默认值见第 13 节第 2 条。

### 5.5 隐私记：解锁、重设密码
```
第一次：ui/vault-lock → 设置 4 位以上数字 → fn vault {action: setup, pin}
        → 服务器存 bcrypt 哈希（cost 10）
解锁：
  密码：fn vault {unlock, pin}
        → 锁定中（locked_until > now）就拒绝
        → 校验；错一次 fail_count 加 1，满 5 次 locked_until = now + 15 分钟
        → 成功后 fail_count 清零，签发 vault_token（HMAC，内容 user_id + 过期时间，
          有效 10 分钟，每次调用续期）
  Face ID / Windows Hello：fn vault {webauthn_options} → navigator.credentials.get
        → fn vault {unlock_webauthn, assertion} → 校验公钥和 sign_count → 签发 vault_token
        （第一次要先在设置里“开启 Face ID”：用密码解锁后注册一个 credential）
  拿到 token → fn vault {list} → 服务器用 VAULT_KEY 解密 → 明文回到内存 → 能搜索、能编辑
上锁：切到后台，或 N 分钟（默认 3）没有操作 → 清空内存里的明文和 token
重设密码：“忘记密码” → 客户端重新发邮箱验证码登录（signInWithOtp）→ 拿到新 JWT
        → fn vault {reset, new_pin}：服务器检查 JWT 的签发时间在 10 分钟内，
          并且 amr 含 otp → 换新哈希，清零失败次数
        内容不受影响（因为是 VAULT_KEY 加密的，与密码无关）
```
- 风险：持有 Supabase 管理权限的人（只有你）理论上能解密，纪要第七节已接受。给朋友用之前要按第九节重新评估。
- iPhone 主屏幕 App 里能不能用 WebAuthn（Face ID）：**待真机实测**。

## 7. AI 服务商适配层

### 7.1 接口（`supabase/functions/_shared/ai/`）
```ts
interface AIRequest  { task: "parse" | "classify"; system: string; user: string;
                       schema: JSONSchema; maxTokens: number; temperature: 0 }
interface AIResult   { json: unknown; usage: { in: number; out: number }; provider: string; model: string }
interface AIProvider { name: string; complete(req: AIRequest): Promise<AIResult> }
// 失败时抛 AIError{kind: "quota" | "rate" | "timeout" | "bad_output" | "auth" | "other"}
```
- 第一版的服务商：`gemini.ts`，用免费额度，Flash 或 Flash-Lite，`responseMimeType: application/json` 加 `responseSchema`。另备 `claude.ts`、`openai.ts` 两个空实现，以后换服务商只改 `ai_config.provider_order`，不改代码。
- `router.ts`：按 provider_order 依次试，跳过 `exhausted_until > now` 的服务商。遇到 `quota` 错误，就把 exhausted_until 设成该服务商的下一次重置时刻（Gemini 按太平洋时间午夜重置，据第三方资料，**未核实**）；遇到 `rate` 错误，等 1 秒重试一次。所有服务商都不可用时返回 null，调用方改走本地规则。
- 每次调用都在 `ai_usage` 里记账：哪一天、哪个用户、什么任务、调用次数、token 数。

### 7.2 提示词放在哪里
- 放在 `supabase/functions/_shared/ai/prompts/parse.v1.md`、`classify.v1.md`，打包进函数，**不放数据库**，改动要走代码审查。
- 版本号写进 `notes.ai_meta.prompt`；改提示词就升版本号，并跑 `tests/ai/` 下的样例集（真实说法 50 条，中韩各半）对比准确率。

### 7.3 输出结构（JSON Schema，在 `logic/ai-schema.js` 里校验）
```json
parse:    {"items":[{"kind":"event|todo|note|anniv","title":"≤160字","date":"YYYY-MM-DD|null",
            "time":"HH:MM|null","duration_min":"int|null","due":"YYYY-MM-DD|null","important":false,
            "project":"≤40字|null","body":"≤2000字|null",
            "anniv":{"type":"birthday|anniversary|countdown","calendar":"solar|lunar","month":1,"day":1,"is_leap":false,"year":null}}]}
classify: {"results":[{"note_id":"uuid","category":"已有分类名或新名(≤12字)","is_new":false,"confidence":0.0}]}
```
校验规则：
- 只认上面列出的键，多出来的丢掉；
- kind 必须在白名单里；日期在今天前 1 年到后 5 年之间；items 最多 10 条；
- note_id 必须在本批输入里；confidence 低于 0.5 的当作“未分类”；
- 任何一项不合格就整条丢弃；整个响应解析不了，就返回 fallback。

### 7.4 防提示注入
1. 系统提示里写明：用户内容放在 `<data>…</data>` 里，那里面只是要处理的数据，不是指令；只输出 JSON。
2. 输入先去掉控制字符，再截到 2000 字；输入里出现的 `</data>` 先转义。
3. 模型**没有任何工具**，输出只当数据用，经过 schema 白名单。最坏的情况是归错分类或识别错日期，用户可以改，也可以撤销。
4. 函数写库时，`user_id` 一律取自 JWT 或令牌，与模型输出无关，所以碰不到别人的数据。
5. 分类结果只能落在这个用户自己的分类里。新建分类有数量上限，名称过滤 URL 和 HTML。
6. claude-intake 收到的内容同样当数据处理。

### 8.1 构建产物
- `python build/build.py --target web --env preview|prod` → `dist/web/`：
  - `index.html`，引用带哈希的文件名；
  - `app.<hash>.js`：沿用现在的 IIFE 拼接方式，`App.BUILD = {target:"web", env, version, build, supabaseUrl, anonKey, vapidPublic}`；这几个值从环境变量读，缺一个就构建失败；
  - `app.<hash>.css`；
  - `sw.js`：注入 `BUILD_ID` 和预缓存清单；
  - `manifest.webmanifest`、`icons/`、`fonts/`；
  - `version.json`：{version, build, commit}；
  - `_headers`：Cloudflare Pages 的响应头。index.html 和 sw.js 设 `no-cache`；带哈希的文件设 `immutable`；加 CSP（`default-src 'self'; connect-src 'self' https://<ref>.supabase.co wss://<ref>.supabase.co`）。
- 构建完照旧检查 A14（扫密钥）、发布版不能出现环境提示条。
- `--target fn`：把 manifest 里 `shared` 列出的 core、logic 文件包成 ESM，生成 `supabase/functions/_shared/logic.gen.js`（`export default App`）。这个文件不进 git，CI 部署前生成。这样提醒规则、阴历、一句话拆分、ai-schema 在前端和服务器上**是同一份代码**。
- `--target claude` 保持不变，另外加 `--readonly`，生成 3.0.1 只读版。

### 8.3 GitHub Actions
| 流水线 | 触发 | 步骤 |
|---|---|---|
| ci.yml | 每次 push 和 PR | 两个目标各构建一次 → `node tests/run-all.mjs` → `supabase start`（Docker）→ `db reset` → RLS 测试、适配器契约测试、函数测试（deno test）→ Playwright E2E（chromium + webkit）→ gitleaks |
| deploy-preview.yml | push 到 `develop` | 环境 `preview`：`supabase db push` + `functions deploy`，部署到**第二个 Supabase 免费项目** → `build --env preview` → Cloudflare Pages 预览分支（`develop.<项目>.pages.dev`） |
| deploy-prod.yml | 打 tag `v*.*.*` | 检查 tag 与 VERSION 一致 → 环境 `production`，要你在 GitHub 上点“批准” → 触发 backup-daily 并等待成功 → db push → functions deploy → build --env prod → Pages 正式分支 → 用 CHANGELOG 生成 GitHub Release |

数据库改动只做**向后兼容**的变更：先加列，旧列下一版再删。原因是旧版客户端（尤其是 exe）可能还在跑。`app_config.min_client_version` 高于当前版本时，客户端提示“请更新”。

### 8.4 密钥放在哪里
| 东西 | 放哪里 | 能不能进仓库 |
|---|---|---|
| SUPABASE_URL、anon（publishable）key、VAPID 公钥 | GitHub Environment **variables**，构建时注入前端 | 本身是公开的，但也不提交 |
| SUPABASE_ACCESS_TOKEN、DB 密码、项目 ref、CLOUDFLARE_API_TOKEN、账号 ID、TAURI_SIGNING_PRIVATE_KEY 及其密码 | GitHub Environment **secrets**（preview、production 各一套） | 不能 |
| GEMINI_API_KEY、ANTHROPIC_API_KEY（预留）、VAPID_PRIVATE_KEY、VAPID_SUBJECT（mailto:你的 Gmail）、VAULT_KEY（32 字节）、VAULT_TOKEN_SECRET、CRON_SECRET | `supabase secrets set`，即函数的环境变量；CRON_SECRET 另存一份到数据库 Vault | 不能 |
| service role key | 只在 Supabase 控制台里有；迁移或救急时临时放进本机环境变量，用完就删 | 不能 |
| 本地开发 | `.env.local`（写进 .gitignore）；本机备份脚本用的凭据放 Windows 凭据管理器 | 不能 |

**VAULT_KEY 一旦丢失，所有人的隐私记都打不开**，要离线另存一份（见第 13 节第 7 条）。密文带 `enc_key_id` 列，以后轮换密钥时可以新旧并存。

### 8.5 各端版本号统一
- `VERSION` 文件是唯一来源。build 把它写进 `App.BUILD.version`、SW 缓存名、`version.json`；CI 把它同步进 `tauri.conf.json`，并检查和 tag 一致；函数通过环境变量 `APP_VERSION` 拿到它。
- 预览环境的版本号写成 `4.0.0-preview.<run 号>`。
- “设置 → 关于”显示版本号和更新内容。
- 规则：修问题升第三位（4.0.1），加功能升第二位（4.1.0），要搬数据或不兼容的改动升第一位。

## 10. 备份

- **服务器端**：fn `backup-daily` 每天 00:30（首尔时间）逐张表导出 JSON（含已删除的条目），按用户分文件，gzip 压缩后放进私有桶 `backups/<日期>/`，只保留最近 7 天，免费版存储只有 1 GB。图片不放在服务器备份里。
- **拉回本机**：Windows“任务计划程序”每天 09:00 运行 `tools/backup/pull.ps1`。错过的话，开机后会尽快补跑。
  - 下载当天的备份包 → `D:\claude code\待办APP\data\backups\<日期>_每日\`（沿用 ADR-009 的位置，不进 git），写 `清单.json`（条数、版本、对应的服务器文件）；
  - 每周日增量同步一次图片（`images` 桶，用 S3 兼容接口）→ `D:\claude code\待办APP-备份\图片\`；
  - 每周一用 `supabase db dump` 导出整库 SQL → `D:\claude code\待办APP-备份\数据库\`；
  - 本机保留：每日的 30 天，每周的永久保留；
  - 凭据放在 Windows 凭据管理器。失败时写“失败原因.txt”，并在 App 的“设置 → 数据”里显示“最后备份时间”。
- **发版前**：deploy-prod 会先触发一次备份并等待它成功。
- **恢复演练**：4.0.0 上线前在预览环境里完整恢复一次，写进发布记录。

## 13. 需要产品负责人确认的架构问题

1. **AI 免费额度不够时怎么办**
   - 推荐：先按“0 元”上线，用上面的省额度办法：分类批量做；语音先用本地规则，说法复杂时才用 AI。用两周，看设置里的“AI 剩余次数”。如果天天不够用，再考虑每月花不到 1 美元，加 Claude Haiku 作为第二家服务商（价格未核实）。
2. **阴历默认按哪一套**
   - 推荐：默认按**中国农历**（家人的生日多半按农历过），每条可以改成“韩国阴历”。
3. **Claude 代记先支持哪里**
   - 推荐：4.0.0 先支持**电脑上的 Claude App**，它能直接调用接口。手机上的 Claude 聊天要另做一个“连接器”（MCP），放到 4.1 再评估，可行性未核实。
4. **预览环境用第二个 Supabase 免费项目**
   - 推荐：**用**。免费版正好能开 2 个项目，一个正式、一个预览，测试不会碰到真实数据。预览项目 7 天没人用会暂停，没有影响。
5. **4.0.0 的范围**
   - 纪要第十三节第 1 条写的是“直接做 4.0.0”，第七节则把随手记、隐私记、纪念日排在 4.1。
   - 推荐：**库表一次建好；功能仍分 4.0、4.1、4.2 三期交付**，先让日程、待办、推送、语音稳定跑起来。
6. **旧版改成“只读”需要发一个小版本**
   - 推荐：发 **3.0.1 只读版**。页面上能看、能导出，不能改，防止搬完数据以后又往旧版里记。
7. **隐私记总钥匙（VAULT_KEY）的保管**
   - 推荐：生成以后，你把它存进 iPhone 的“密码”App，再在纸上抄一份收好。我会写手把手的步骤。
8. **出差到别的时区时，日程怎么显示**
   - 推荐：**按手机当前的时区显示**。如果和记录时的时区不同，就加一个小标注，例如“14:00（首尔 15:00）”。提醒按真实时刻发。
