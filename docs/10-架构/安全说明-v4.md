## 一、本文件新登记的已接受风险

### S-1 Security Advisor 的 Leaked Password Protection 警告：按设计不适用

| 项 | 内容 |
|---|---|
| 出处 | B0 实测清单 P9（`docs/03-评审/B0/后端-B0实测清单.md` 第 46 行）；B1 接手清单 P-sec-b0；P9 签字条件 ⑤ |
| 现象 | Supabase 控制台 Security Advisor：0 错误、1 警告「Leaked Password Protection Disabled」（Auth 类）。截图 `docs/03-评审/B0/安全/预览-SecurityAdvisor-2026-10-28.jpg` |
| 结论 | **此警告按设计不适用，不开这个功能，不算待修项**。安全审查员 10-29 有条件通过 |
| 理由 | ① 这个功能是注册、改密码时拿密码去比对已泄露的密码库；**我们不用密码登录**，只用邮箱验证码，账号按设计不带密码。② 数据库层：`supabase/migrations/0001_core.sql` 第 109～115 行的触发器 `users_guard_no_password`，把写进 `auth.users` 的非空 `encrypted_password` 一律置成空串，设了也存不下。③ GoTrue 关不掉邮箱密码登录这条路，所以另有第二道防线：服务器认出 `amr` 含 `password` 的会话一律拒（`supabase/functions/_shared/auth.ts`、迁移 `20261029191000_auth_password_session.sql`；TC-B1-111，P0）。④ 登录方式只开 Email，手机、匿名、SAML、Web3、全部第三方登录和公开注册都关（10-29 预览和正式两个项目的截图 `预览-Auth登录方式-2026-10-29.jpg`、`正式-Auth登录方式-2026-10-29.jpg`）。开了“泄露密码检查”也不会多挡住任何东西 |
| 签字条件和进度（10-30） | ① 预览托管版补测：真令牌设密码后库里仍为空、`grant_type=password` 回 400（TC-B1-112）：**待做**，要登录令牌（接手清单 S2）；② 正式项目第一次 push 后复查：触发器状态为 `O`、带密码的行为 0、Advisor 只有这一条警告（换清晰截图）：**待做**，等正式项目第一次 push；③ 截图核实登录方式：**已核实**（10-29 06:21）；④ TC-B1-111 维持 P0：**维持**（测试用例-v4 第 275 行级别为 P0）；⑤ 安全说明写明：**本条即是** |
| 什么时候重新评估 | ① **升级 Supabase Auth（GoTrue）以后，重跑 Security Advisor**，看警告是否还是只有这一条、触发器和 `amr` 拒绝是否还在生效；② 正式项目每次 `db push` 改到 `auth` 相关的东西以后；③ Advisor 出现任何新的 Auth 类警告；④ 有人提议加密码登录、第三方登录或打开公开注册——那时这条结论作废，泄露密码检查要一并打开；⑤ `users_guard_no_password` 触发器或 `amr` 拒绝的代码被改、被删、改走 0.36 退路（`access_token_hook`）时 |

### S-2 `/files` 链接的查询串在 Cloudflare 实时日志流里看得到：接受

| 项 | 内容 |
|---|---|
| 出处 | B0 R2 任务单第五节第 7 项（`docs/09-路线图/B0-R2任务单.md` 第 136 行）；B1 接手清单 P-sec-b0、P-files-sig；架构未核实表第 19 项 |
| 现象 | 10-28 实测：预览 Pages 的“实时日志”（部署详情 › 函数 › 开始日志流）逐条显示**完整 URL，含查询串**（截图 `docs/03-评审/B0/安全/Pages-实时日志含查询串-2026-10-28.jpg`）。和 `docs/10-架构/方案-文件存储改用R2.md` 第 144 行“Cloudflare 不记查询串”的假设不符 |
| 结论 | **接受**“只有 Cloudflare 账号成员能看、不落盘的实时流里能看到查询串”。安全审查员 10-29 有条件通过 |
| 理由 | ① 实时流只有 Cloudflare 账号成员能看，不落盘；账号成员只有负责人本人（超级管理员），两步验证开（截图 `CF-账号成员与两步验证-2026-10-29.jpg`）。② 能看实时日志的人本来就能直接读 R2，查询串里的签名没有给他多出任何权限。③ 签名有效期短：`functions/_lib/files-rules.ts` 的 `TTL`，图片 view 120 秒、头像 60 秒、附件 60 秒、微软查看器 300 秒，**硬上限 600 秒**。④ 持久的地方都核实过不含查询串（10-29 06:15）：Logpush 没开（`CF-Logpush未开-2026-10-29.jpg`）；Observability › 日志（HTTP 请求）是持久记录，但只记路径、不记查询串（`CF-HTTP请求日志不含查询串-2026-10-29.jpg`）；数据分析 › 热门路径不含查询串（`CF-分析页热门路径不含查询串-2026-10-29.jpg`）；Pages 项目设置里没有 Workers Logs 开关 |
| 之后的变化 | B1 P-files-sig 已提交（8b766eb、a7722d5；第十批补安全审查中）：view、download 的签名改放请求头 `X-Files-Sig`，URL 不带查询串；**只有给微软查看器的 `ms` 用途还在查询串里**（微软那边只能拿一个 URL）。所以本条接受的范围实际缩小到 `ms` 链接，结论不变 |
| 守则 | ① **以后开任何持久日志之前（Workers Logs、Logpush、Observability 加字段、接第三方日志服务），先把查询串去掉**（日志里剔掉查询串，或先把 `ms` 的签名挪出 URL），安全审查员签字后再开；② 有效期上限保持 ≤600 秒，`ms` 按微软查看器实测的最短时长再缩；③ 不新增把凭证放在查询串里的用途 |
| 什么时候重新评估 | ① 打算开任何持久日志时（见守则 ①）；② Cloudflare 账号要加成员、或两步验证要关时；③ Cloudflare 的 Observability 日志或分析页开始记录查询串时（每次大版本上线前抽查一次）；④ `TTL.max` 或 `ms` 有效期要调长时；⑤ 新功能要把签名、令牌放进 URL 时 |
| 范围 | 本条只覆盖 `/files`。`/sb/*` 的查询串不在本条范围，按架构未核实表第 19 项另行核实 |
| 待同步 | 签字条件 ④ 要求架构里“未核实”改成“已核实：实时流可见，接受”：`docs/10-架构/方案-文件存储改用R2.md` 第 144 行和第 441 行（未核实第 6 项）、架构设计未核实表第 19 项：**已改（10-30）**，安全审查员代架构师；第 19 项只标了 `/files` 部分，`/sb/*` 部分仍未核实 |

## 二、待负责人定：`auth.audit_log_entries` 的保留期（OPS-mail-sugg ⑦）

> 这一节是**安全审查员的建议，不是结论**。保留期写进隐私说明属于面向用户的文字，**待负责人定**。

### 现状

- 表里是什么：Supabase Auth（GoTrue）每次登录、发验证码、刷新令牌、退出都记一行，含**邮箱**（`payload` 里的 `actor_username`）、**IP**、时间、动作。表归 `supabase_auth_admin`。
- 我们用它做什么：验证码发信量告警（`private.auth_mail_counts()`，只数过去 1 小时 / 24 小时，不回邮箱、IP）。
- 现在怎么清（上线与回滚手册第七节）：**到阈值才清**（100 万行、100 MB、一周 2 次 `auth_mail:timeout`，满足任一条），清的是 90 天前的旧行；手册写明“保留期待安全审查确认是否写进隐私说明”。
- 注销时：account-purge **删不到**这张表（service_role 没有这张表的权限：开发 10-30 在本机测试库实测（OPS-mail-sugg ⑤），审查员未复核），注销的人的登录记录会留在表里，直到被按时间清掉。
- 隐私说明：`site/zh/privacy.html` 还是占位页（“本页正在编写”），正文在 B7b 按架构 15.7 写。15.7 第 8 项“注销后还会残留什么”现在写的是“Supabase Auth 的审计日志（登录记录，按各家保留期）”；15.7 第 7 项“保存多久”没有这一条。

### 问题

照现在的手册，按现在的人数几年才到阈值，所以**实际保留期是“一直留着”**，不是 90 天。15.7 第 8 项“按各家保留期”也不准：Supabase 不替我们清，保留期是我们自己定的。

### 建议

1. **定为保留 90 天，并改成每月固定清一次**，不再只在到阈值时清（阈值留作“提前查看”的信号）。理由：
   - 发信量告警只要最近 24 小时；排查异常登录、刷验证码一类事件，90 天够用；再长只是多留邮箱和 IP。
   - 运维每月第一周本来就要查一次行数（手册第六节），顺手跑一遍手册里现成的分批删除语句，每月多几分钟；正式项目照旧由负责人在 SQL Editor 执行。
   - 不定期清，隐私说明里写的任何天数都兑现不了。
   - 每月清一次，一条记录最长约 90 + 31 天，对外写“最长约 4 个月”。
   - 这一条要改手册第七节的“什么时候清”（运维改，改动不涉及代码；`workers/lemo-ops/src/rules.ts` 引用的是第八节“验证码发信额度被耗尽”的标题，第七节改动不涉及）。
2. **写进隐私说明**：要写。表里有邮箱和 IP，属于个人信息，15.7 第 7 项“保存多久”要列出来（PIPA、PIPL 都要求写保存期限；未经律师核实）；第 8 项要如实写“注销时不会马上删”。**告知页不用改**：告知页（R-115 统一句、`ConsentPage`）讲的是 AI 处理和运营者能访问，不讲保存期；保存期只放隐私说明。
3. **不建议**另做“注销时按人删这张表”：表不归我们、service_role 没权限，要绕就得动 Supabase 自己的表权限，风险比多留几个月大。

### 建议文字（待负责人定）

> 以下是给 B7b 写隐私说明用的**建议文字**，**待负责人定**。韩文版由 B7b 按同一意思写，走韩文审校和负责人本人看（R-105、R-106）。架构 15.7 第 7、8 项由架构师按负责人的决定同步改。

- 15.7 第 7 项“保存多久”加一句：
  “登录记录（登录、发验证码、刷新登录状态、退出时的邮箱、IP 地址和时间）由我们使用的登录服务（Supabase）自动记下，用来排查异常登录和验证码被滥用。我们保留 90 天，每月清理一次，所以每条记录最长约 4 个月后删除。”
- 15.7 第 8 项“注销后还会残留什么”，把“Supabase Auth 的审计日志（登录记录，按各家保留期）”改为：
  “登录记录（邮箱、IP 地址、时间）注销时不会马上删除，按第 7 项的每月清理，最长约 4 个月后删除。”

如果负责人决定**不**改成每月固定清理，那隐私说明就不能写 90 天，只能如实写“登录记录会一直保留，直到我们按需要清理”，这一句同样待负责人定。
