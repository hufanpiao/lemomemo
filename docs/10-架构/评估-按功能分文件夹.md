# 评估：前端和数据是否按功能分模块

- 日期：2026-10-27　作者：架构师
- 状态：**已采纳（R-119，2026-10-27）**：按推荐的混合式 + 数据清单执行，已落进架构 0.22、架构约定 9.1、[ADR-019](../04-决策/ADR-019-前端按功能分文件夹与数据清单.md)
- 依据：[架构设计-v4](架构设计-v4.md) 0.21（第 2 节、3.3、3.4、4、6、10、附录 A）、[架构约定](架构约定.md) 第 9 节、[ADR-017](../04-决策/ADR-017-前端用React与TypeScript.md)
- 问题：负责人想知道两件事：
  - 前端代码要不要从“按层分”改成“按功能分文件夹”，好让以后加功能、删功能更方便；
  - 数据是不是也要按功能模块化。

---

## 0. 结论（给负责人的一句话）

**推荐“混合式”**：前端按功能分文件夹，但保留 shared、platform 两个基础层；数据也按功能各写一份“数据清单”，同步、备份、注销、清理都按清单处理，CI 比对数据库，没登记的就报错。现在还没写代码，改起来只要改文档；**工期加 1 人日（105 → 106）**，换来的是以后加一个功能大约少碰一半的地方，删一个功能能删干净。

---

## 1. 现状：一个功能的代码分散在哪里

现在按层分：shared → platform → data → ui（hooks → components → pages）→ app，另有 motion（架构 2.1、2.2）。下面按 2.2 和正文的模块名推算。

**纪念日（B5）**：

| 层 | 文件 |
|---|---|
| shared | `logic/anniv.ts`（下次日期）、`logic/lunar.ts`、`lunar-data.ts`（阴阳历）、`logic/notify-text.ts`（推送文案）、`schema/rows.ts`（anniversaries 的可写列）、`i18n/zh.ts`、`ko.ts`（词条混在一个大词典里） |
| platform | `image.ts`（头像裁剪，0.20）、`supabase/files`（上传头像） |
| data | `anniv.ts`、`reminders.ts`（纪念日提醒和日程待办共用）、`cache.ts`、`outbox.ts`、`sync.ts`（集合列表里登记一行） |
| ui | `hooks/useAnniv`（推算）、`components/` 里的纪念日卡片和头像、`pages/Anniv`、`pages/Settings/*`（默认提醒）、`pages/Today`（今天页的纪念日提示） |
| app | `routes.ts` |
| 服务器 | `supabase/functions/anniv-roll`、`push-dispatch`，触发器 `enqueue_anniv_defaults` |

一共大约 **6 个目录、12–15 个文件**。

**随手记附件（B4b-1）**：shared 的 `file-sniff.ts`、`media-path.ts`、`schema/api.ts`；platform 的 `supabase/files`、`desktop.ts`（save_attachment）；data 里新的附件模块（加上 outbox 和 sync 的登记）；ui 的 hooks、附件卡片、`pages/Notes`；`src/preview-frame/`；还有 file-check、vault-file 两个函数。大约 **7 个目录**。

**“＋”统一入口（B4b-3）**：shared 的 `logic/intent.ts`、`parse-*.ts`、`schema/ai.ts`；platform 的 `recorder.ts`、`speech.ts`；data 的 `capture.ts`、`ai.ts`；ui 的 `PlusButton`、`RecordPanel`、`TypeBar`、结果卡片、`state/ui-store.ts`（录音面板状态）；app 的快捷键；还有 ai-parse、ai-voice、ai-summarize、note-search 四个函数。也是 **6–7 个目录**。

**问题在哪里**：
- 改一个功能要在 5–7 个目录之间来回跳；
- 删一个功能很难确认删干净了（词典、ui-store、routes 里的残留，tsc 查不出来）；
- 几个“大家都要改”的文件（`routes.ts`、`zh.ts`、`ko.ts`、`ui-store.ts`、sync 的集合列表）是前端 A、B 并行时最容易冲突的地方。

**好处**：依赖方向一目了然，ESLint 规则写起来简单（A1、A8 只要按目录判断）。

## 2. 前端：三个可选结构

### 方案 A：完全按功能分

```
/shared/                       ← 仍然必须单独留着（Edge Functions 要用），见 3.3
/src/
├── app/                       main.tsx App.tsx router.ts
├── features/
│   ├── anniv/
│   │   ├── logic/             anniv.ts lunar.ts（纯 TS）
│   │   ├── data/              anniv-store.ts
│   │   └── ui/                AnnivPage.tsx AnnivCard.tsx useAnniv.ts
│   ├── notes/   attachments/   plus/   vault/   calendar/   today/   reminders/   settings/   auth/
│   └── …
└── （没有 platform、data 这些公共层，每个功能自己带）
```

**这个方案走不通**：
- 纪念日的推算、阴阳历、推送文案，服务器（anniv-roll、push-dispatch）也要用，**只能放在 /shared**，所以 `features/anniv/logic` 放不进去；
- 本机缓存、outbox、sync、登录、Supabase 客户端、录音这些不属于任何一个功能，最后只能另起一个公共目录。

所以它最后会变成方案 B，只是名字更乱。

### 方案 B：混合式（推荐）

```
/shared/                         前端和 Edge Functions 共用，纯 TS（结构不变，按领域分子目录）
├── core/  i18n/  schema/  db.types.ts
└── logic/  anniv/ (anniv.ts lunar.ts lunar-data.ts)  remind/  parse/ (parse-*.ts intent.ts)
            files/ (file-sniff.ts media-path.ts)  calendar/ (month-grid.ts holidays.ts) …
/src/
├── app/          main.tsx App.tsx router.ts features.ts（登记表：每个功能一行）
├── platform/     不变：supabase/ idb.ts recorder.ts speech.ts webauthn.ts desktop.ts …
├── core/         原来 data 里跨功能的：cache.ts outbox.ts sync.ts session.ts store.ts log.ts manifest.ts（读数据清单，见第 4 节）
├── kit/          通用界面：components/（Button Sheet Toast …）icons/ hooks/（useCollection useItem useSession useT）state/ui-store.ts
├── motion/       不变
├── features/
│   ├── anniv/
│   │   ├── index.ts             对外只暴露这一个：路由（React.lazy）、今天页的小卡片、设置页的分区、数据清单
│   │   ├── data.manifest.ts     数据清单（第 4 节）
│   │   ├── data/                anniv.ts（纯 TS，不准 import React）
│   │   ├── hooks/               useAnniv.ts
│   │   ├── ui/                  AnnivPage.tsx AnnivCard.tsx AnnivAvatar.tsx *.module.css
│   │   ├── i18n/                zh.ts ko.ts（这个功能自己的词条）
│   │   └── __tests__/
│   ├── today/  calendar/  todos/  notes/  attachments/  smart-search/  plus/  vault/  reminders/
│   └── settings/  auth/  onboarding/  desktop-shell/（exe 才有的：快捷键打字框、托盘设置）
├── preview-frame/  sw/  styles/  public/   不变
```

功能内部仍然分层：`data → hooks → ui`。功能之间只能经对方的 `index.ts` 引用。

### 方案 C：维持现状

保留 2.2 的目录树。只加两个小改动，就能缓解最主要的冲突：
- 词典按功能拆文件（`shared/i18n/zh/anniv.ts`…）；
- 路由按功能拆登记。

## 3. 三个方案的影响

| 方面 | A 完全按功能分 | **B 混合式** | C 维持现状 |
|---|---|---|---|
| 依赖方向和检查规则 | 要为每个功能重写边界规则，服务器共用的逻辑不知道放哪里 | 见 3.1，规则条数基本不变，A1 / A8 改写，新增“功能之间只能经 index.ts” | 不变 |
| 前端 A、B 并行 | 冲突少 | **冲突少**：各在自己的功能文件夹里改；共享文件只剩 `app/features.ts`（一功能一行）、`kit/` | 冲突点在 `routes.ts`、`zh.ts`、`ko.ts`、`ui-store.ts`、sync 集合列表 |
| /shared | 拆不开，要另想办法给 Deno 复制 | **不动**，只把 `shared/logic/` 按领域分子目录（anniv/、remind/、parse/…），CI 照旧把整个 /shared 复制进函数 | 不动 |
| 懒加载和体积 | 天然按功能分包 | 天然按功能分包；**要防 `index.ts` 把整页带进首屏**：index 只能导出 `React.lazy` 的页面和很小的卡片（ESLint 规则），check_size 照旧卡 150 KB | 按页面懒加载，和现在一样 |
| 测试放哪里 | 功能文件夹里 | 单元测试放 `features/*/__tests__/`；shared 的测试仍在 `/tests/shared/`（Node 和 Deno 都跑）；端到端、RLS、架构规则样例仍在 `/tests/` | `/tests/` 下按层分 |
| 加一个新功能（习惯打卡） | 1 个文件夹 + 服务器部分 | **前端：1 个文件夹 + `app/features.ts` 一行**；服务器和数据部分见第 4 节 | 前端 6 个目录、约 10 处：shared/logic、schema/rows、data、sync 登记、hooks、components、pages、routes、zh、ko、ui-store、设置页、今天页 |
| 删一个功能 | 删文件夹 | **删文件夹 + 删登记的一行**；tsc 会把残留的引用全部报出来 | 要在 6 个目录里逐个找，词典和 ui-store 的残留 tsc 查不出 |

| 规则 | 改法 |

## 4. 数据层的模块化

### 4.1 现状：加一种新数据要在哪里各登记一遍

以“习惯打卡”（假设新表 `habits`、`habit_checks`）为例，按现在的架构要逐处手写：

| # | 地方 | 现在在哪里 | 漏了会怎样 |
|---|---|---|---|
| 1 | 迁移：建表、公共列、`touch()` 触发器、`(user_id, synced_at)` 索引、行数上限触发器 `row_quota` | `supabase/migrations/0001_init.sql`（附录 A，一个大文件） | 不能同步、行数不受限 |
| 2 | RLS 四条策略 | 3.3 A 的表清单 | 别人的数据可能读到（有 Security Advisor 兜底） |
| 3 | 列级授权（insert、update 列清单） | 3.3 列级授权 | 客户端写不进，或者能写系统列 |
| 4 | `apply_patch` 的列白名单 | 4.4 | 离线补发失败 |
| 5 | Realtime publication | 15.6 第 4 条 | 别的设备不实时更新 |
| 6 | 本机缓存的 IndexedDB store、`schema_v` | `data/cache.ts`（4.1） | 离线看不到 |
| 7 | outbox 的集合、zod 校验 | `data/outbox.ts`、`shared/schema/rows.ts` | 离线写不进 |
| 8 | sync 的集合列表、整表重拉 | `data/sync.ts`（4.2–4.4） | 不同步 |
| 9 | 每天的 JSON 备份 | backup-daily（第 10 节） | **备份里没有这张表** |
| 10 | 本机拉取脚本、恢复脚本 | `tools/backup/pull.ps1`、导入脚本 | 恢复不出来 |
| 11 | 导出 | account export（6）、电脑 zip 导出（5.13 第 10 点） | 用户导不出自己的数据 |
| 12 | 注销清除 | account delete（6；public 表靠外键级联，private 表和桶要手写） | **注销后残留个人数据** |
| 13 | 30 天清理 | pg_cron（3.4） | 删除的东西永远留着 |
| 14 | 孤儿清理（有桶的才要） | 3.4 | 存储慢慢被占满 |
| 15 | 用量报告 | usage-report（6） | 监控看不到 |
| 16 | 数据字典 | `docs/05-数据字典/数据字典.md` | 文档过期 |
| 17 | zod schema、`db.types.ts` | `shared/schema/`、`supabase gen types`（2.5） | 有 CI 比对，漏了会失败 |
| 18 | （如果用 AI 或向量）同意检查、`embed_queue` 触发器、`note_vectors` 的 kind 和外键 | 5.13、5.14、附录 A | 未同意也送 AI；向量变孤儿 |
| 19 | （如果含隐私内容）不进本机缓存的明文、加密列 | 5.5、5.13 第 11 点 | 明文落到设备上 |

**一共 15–19 处**，散在迁移、5 个函数、前端 3 个模块、2 个脚本和 2 份文档里。现在只有第 17 项有 CI 兜底，其余靠人记。安全评审前几轮发现的“注销没删 X”“孤儿没清 Y”大多就是这样漏掉的（例如第四轮的 M3、L8）。

### 4.2 方案：每个功能一份数据清单

**每个功能写一份 `features/<功能>/data.manifest.ts`**。为了让 Edge Functions 也能读到，类型定义放在 `shared/schema/manifest.ts`，清单内容汇总到 `shared/manifests/<功能>.ts`（纯数据，前后端共用）。示例：

```ts
// shared/manifests/anniv.ts
export const anniv: DataManifest = {
  feature: 'anniv',
  tables: [{
    name: 'anniversaries', schema: 'public',
    sync: true, realtime: true, localCache: 'plain',      // plain / none（隐私记的明文写 none）
    clientWritable: ['kind','name','calendar', /* … */ 'avatar_id','avatar_bytes'],
    softDelete: true,                                     // 有 deleted_at，30 天清理
    backup: 'json', export: 'json',
    onAccountDelete: 'cascade',                           // 外键级联；private 表写 'explicit'
  }],
  buckets: [{
    name: 'images', pathPrefix: '<user_id>/anniv/',
    backup: 'weekly-s3', export: 'zip', countsToQuota: true,
    orphanSweep: { olderThanHours: 24, ownerColumn: 'avatar_id' },
  }],
  ai: { sendsToAI: false, vectors: false },
  usageReport: { rowCount: true },
};
```

**按功能拆迁移文件**：
- 第一版 `0001_init.sql` 拆成 `0001_core.sql`、`0002_events_todos.sql`、`0003_notes.sql`、`0004_attachments.sql`、`0005_anniv.sql`、`0006_vault.sql`、`0007_search.sql`；
- Supabase 按文件名顺序执行，所以**有跨功能外键的放后面**（例如 `note_vectors` 引用 events、todos、notes、note_files，必须在 0007）；
- 以后的改动照旧新建带时间戳的文件，文件名带功能名，例如 `20261120_habit_create.sql`；
- **删功能也是新写一个迁移去 drop，不删旧文件**。

**通用流程改成读清单**：

| 流程 | 现在 | 改成 |
|---|---|---|
| sync、cache、outbox | 手写集合列表 | `core/manifest.ts` 汇总所有清单，`sync: true` 的才同步，`localCache: 'none'` 的不落 IndexedDB |
| Realtime publication | 迁移里手写 | 生成脚本按 `realtime: true` 出 SQL，CI 比对 |
| 列级授权、apply_patch 白名单 | 手写，CI 比对三处 | 以 `clientWritable` 为准，CI 比对四处（清单、grant、apply_patch、`rows.ts`） |
| backup-daily、导出、pull.ps1 | 手写表清单和桶清单 | 读汇总清单（pull.ps1 读 backup-manifest 函数给的桶清单） |
| 注销 | 手写步骤 | 按 `onAccountDelete` 生成：cascade 的不用管，explicit 的逐个删，桶按 `pathPrefix` 删 |
| 30 天清理、孤儿清理 | 手写 SQL | 按 `softDelete`、`orphanSweep` 生成 |
| 用量报告 | 手写 | 读清单 |
| 数据字典 | 手写 | 从清单加 `db.types.ts` 生成表格部分，文字说明仍然手写 |

### 4.3 防漏：CI 检查

- **新增检查 D1**（`build/check_data_manifest.ts`，CI 在 `supabase db reset` 之后跑）：
  - 查 `information_schema` 和 `storage.buckets`，列出 public、private 两个 schema 的所有表和所有桶，和汇总清单比对；
  - **数据库里有、清单里没有 → 报错**；清单里有、数据库里没有 → 报错；
  - 再核对：`realtime: true` 的表都在 publication 里；`clientWritable` 和列级授权一致；`sync: true` 的表都有 `synced_at` 和索引；有 `deleted_at` 的必须 `softDelete: true`；`sendsToAI: true` 的功能，对应函数要调 `aiAllowed`（按清单里写的函数名查）。
- **注销测试按清单自动生成**：
  - 给测试账号在每张表、每个桶里各造一条数据，执行注销，逐项断言删干净；
  - 30 天清理和孤儿清理同样生成用例；
  - 新功能写了清单，用例就自动有了，不用另记。
- 列进 15.4 的 S-B0（P0）。

### 4.4 边界：哪些不拆，放进“核心”清单

下面这些跨功能，或者是基础设施，**不归任何一个功能**，统一写进 `shared/manifests/core.ts`。D1 检查照样覆盖它们，只是不随某个功能删除：

| 数据 | 为什么不拆 |
|---|---|
| `profiles`、同意记录（`consent_ai_at`、`consent_policy_ver`）、`devices`、`api_tokens`、`settings` | 账号本身，所有功能都依赖；settings 是“一项一行”的通用表，各功能的设置键在自己的清单里**声明 key 前缀**（例如 `anniv.*`），但表只有一张 |
| `app_config`、`user_limits`、`counters`、`ai_state` | 全局配置、限流、额度，跨所有 AI 功能 |
| `logs`、`applied_ops`、`heartbeat`、`remind_queue` | 运行和同步的基础设施 |
| `admins`、`invites`、`pending_signups`、`webauthn_challenges`、`deleted_accounts` | 账号和注册流程 |
| `vault`、`vault_credentials`，以及 `vault-images`、`vault-files`、`vault-preview` 三个桶、`vault_ai` | 隐私记的加密和解锁是一整套安全设计（ADR-014），**拆开容易让某个功能绕过 vault_token**；放进 vault 核心清单，其他功能只能声明“我的数据有隐私记版本”，由核心统一处理 |
| `embed_queue`、`note_vectors` | 一张表服务五种数据（note、image、file、event、todo）；各功能在清单里写 `vectors: true` 和要算向量的列，表本身归核心（智能查找） |
| `backups` 桶 | 备份本身 |

**一条原则**：表的“主人”只有一个。其他功能只能在自己的清单里声明“我用到它、用法是什么”，不能各自去改它的结构。

## 6. 推荐

**推荐方案 B（混合式）+ 数据清单。**

- **为什么不选 A**：服务器共用的逻辑必须留在 /shared，缓存、同步、登录也必须有公共层。完全按功能分做不到，最后还是变成 B。
- **为什么不选 C**：现在 10 来个功能还管得过来，但后面已经有加功能的需求（重复事项 4.0.1，以及习惯打卡这类）。按层分的话，每次要在 6 个目录、15–19 处数据登记点之间来回改；删功能时删不干净的风险，正好落在注销、清理、备份这些安全评审最容易挑出问题的地方。
- **为什么是现在**：代码还没开始写，改动只在文档里，**代价约 1 人日**；等 B1 以后再改，就要动真代码和测试。
- **不变的**：依赖方向、shared 前后端共用、所有安全规则（A12、A13、A22、A24、A25、vault 的隔离）都保留，只是换了组织方式。

**给负责人的一句话**：建议改成“按功能分文件夹、保留两层公共基础”，数据也让每个功能写一份清单、由 CI 核对；现在改只多 1 人日（合计 106），以后加一个功能大约少碰一半的地方，删功能能删干净，注销时也不会漏删。

**如果同意**：架构出 0.22，按第 5 节改第 2 节、数据部分、架构约定，新开 ADR-019，1.3 合计改成 106。
