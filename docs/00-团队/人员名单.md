# 人员名单

除“产品负责人”外，所有成员都是由主持人（Claude）按角色派出的 AI 助手（子代理）。每人只按分配的角色和任务独立工作，互相看不到对方写的内容，做完交一份报告。报告由主持人核实后再采纳，采纳和不采纳都有记录，见 [评审索引](../03-评审/评审索引.md)。

同一位成员可以接着追问或复查，复查时保持原来的评判标准。

**当前状态（2026-10-24）**：4.0.0 设计完成，架构 v4 已定稿（前端用 React + TypeScript，R-96）。开工前准备中：开工前 7 份交付物正在派人写（见第三节“B0 进门条件”）；账号注册定在 10-26。7 份交付物全部到位、签完字，并且 UI-4 的视觉评审签完，才开 B0。产品负责人要亲自做的事，见 [产品负责人待办-v4](产品负责人待办-v4.md)。

### 每一批都走这六环

| 环节 | 谁做 | 谁签字 | 签什么、签在哪 |
|---|---|---|---|
| ① 开发 | 按第二节的负责人；主持人整合 | 作者写“已完成、自测通过” | 本机测试和 CI 全绿；有界面改动的，前端先用 review-animations 自查 |
| ② 代码审查 | 代码审查员（作者不自审），按第五节加载 skill | **代码审查员本人**签“通过” | 记录按前端 / 后端 / 运维分节；不通过回到 ① |
| ②b 动效审查（R-93；有界面或动效改动的批次） | UI-4 用 review-animations 独立审：该不该动、时长和曲线、能否打断、退出、“减少动态效果”时是否关掉。**证据必须是录屏或性能分析截图**，不能只读代码。卡顿一项由代码审查员用 animation-performance 看性能截图后会签 | **UI-4 本人**签“通过”；卡顿项代码审查员会签 | 录屏、截图和结论一起存档；不通过回到 ① |
| ③ 安全清单核对 | 安全审查员，对照架构 15.4 的本批 S-Bx | **安全审查员本人**签“通过” | 逐项打勾；本批 P0 没过，不能进 ④ |
| ④ QA | QA：本批验收标准（架构 1.3）＋ 冒烟回归集 ＋ 新用例 | **QA 本人**签“通过” | 测试报告放 `docs/06-测试/` |
| ⑤ 产品负责人试用（真机批次：B2（含冷启动实测）、B3、B5、B7a；B1 没有这一环） | 产品负责人按 QA 给的清单在 iPhone 上试 | **产品负责人**在聊天里说“这批可以” | QA 写进报告，主持人记进过程记录 |

规则：
- **每一环的审查记录都必须存成文件**：放 `docs/03-评审/<批次>/`（例如 `docs/03-评审/B2/代码审查.md`），写明审查人、日期、结论、问题清单。**只在聊天里说过、没有文件的，算没签**。文档与配置管理每批结束时编进评审索引。
- **作者不自审**。谁写的代码，谁就不能签 ②。主持人整合时改过的代码，同样由代码审查员审。
- **审查结论只能由审查员本人签**。主持人不能代签“通过”，也不能把“有条件通过”写成“通过”。
- 没有界面动效的批次（如 B0 只有脚手架时），②b 写“本批不涉及”，由 UI-4 确认。
- 每批的冒烟回归集由 QA 在测试用例 v4 里标出来，**每批都跑**。前端 A 改了共用组件，前端 B 那条线的冒烟回归也要跑。

### 两条线并行（R-103 前端拆成两人后）

原来的规则是“这一批六环签完，才开下一批”。前端拆成两人以后，改成**两条线**：

| 线 | 批次顺序 | 谁 |
|---|---|---|
| 主线（App） | B0 → B1 → B2 → B3 → B4 → B5 → B6（皮肤与电脑布局） → B7a（搬家与发布准备） | 前端 A、后端、运维 |
| 副线（官网和 exe） | B0（官网路由骨架、语言分流，和主线 B0 一起验收） → **B6-exe**（exe 外壳） → **B7b**（文档与官网） | 前端 B、产品经理 |

- **同一条线内**，仍然是上一批六环签完才开下一批。
- **两条线之间**只在依赖点等待：
  - B6-exe 在主线 **B1 过了以后**才能开（exe 要用登录和同步），之后和主线 B2～B5 同时做；
  - B7b 在主线 **B5 签完以后**开工（官网截图和功能说明要用做好的界面），可以和主线 B6 同时做；**B7b 必须在 B7a 签字之前签完**（发布要用到隐私说明、官网和功能说明）。和架构 1.3 统一。
- B6-exe 和 B7b 各自单独走六环，单独签字。
- **上线前两条线都必须全部签完**。
- 具体日期和人日写进开发计划 v4。

## 七、密钥由本人生成，AI 不接触明文

VAULT_KEY、PIN_PEPPER（预览、正式各一套）和 exe 签名私钥，一旦泄露或丢失都很难补救。运维、主持人都是 AI，所以：
1. **运维只写生成脚本**，代码审查员和安全审查员审过才能用。脚本不把值写进任何文件或日志，也不发到网络上（除了写入下面的目标）。
2. **产品负责人本人在自己电脑上打开一个 PowerShell 窗口运行脚本**，不通过 Claude 运行。脚本生成随机值后：
   - VAULT_KEY、PIN_PEPPER：直接写入 `supabase secrets`（本人先 `supabase login`），屏幕只显示一次给本人抄进 iPhone“密码”App（R-90），然后清屏；
   - exe 签名私钥：私钥直接写入 GitHub production 环境的 secret，另存一份到本人选的 U 盘，私钥密码只显示一次给本人存进“密码”App。
3. **安全审查员在 S-B5、S-B6 各加一项核对**：生成过程中 AI 没有接触明文。核对办法：审脚本、查聊天记录和过程记录里没有这些值、本人确认是自己运行的。
4. Cloudflare 和 Supabase 的令牌、Gemini 密钥也一样：本人在网页上生成，直接粘贴到 GitHub 或 Supabase 的设置页，不经过聊天。
5. **要用正式令牌或 service role key 的手动操作**（不走 GitHub 流水线的那几步）：
   - 包括：搬家时的导入脚本（架构 5.8）、第 3 层回滚的恢复脚本、GitHub 用不了时手动部署函数（手册第四节第 2 层办法 B）；
   - **默认由产品负责人本人在自己的 PowerShell 窗口里执行**：运维事先写好完整命令（不含密钥值）、审查员审过；本人把密钥放进这个窗口的环境变量，运行命令，把屏幕上的条数等结果告诉运维，然后关掉窗口；
   - **例外**：确实只能由 AI 执行时（例如要边看报错边调整），本人临时生成一把新令牌或新密钥给这一次用，**用完立即在控制台吊销或轮换**，并记进过程记录（谁、什么时候、为什么、何时吊销）。安全审查员在 S-B7 核对这些记录。
