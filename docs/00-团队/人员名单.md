# 人员名单

除“产品负责人”外，所有成员都是由主持人（Claude）按角色派出的 AI 助手（子代理）。每人只按分配的角色和任务独立工作，互相看不到对方写的内容，做完交一份报告。报告由主持人核实后再采纳，采纳和不采纳都有记录，见 [评审索引](../03-评审/评审索引.md)。

同一位成员可以接着追问或复查，复查时保持原来的评判标准。

**当前状态（2026-10-27）**：4.0.0 设计补充中，需求到 R-171，架构到 0.29。手机和电脑（R-126 方案 B）的界面都已画完，最新画面以皮肤视觉稿为准；每条决定和它现在是否有效见[需求记录](../01-需求/需求记录.md)。R-148 起的三步整改已做完；R-159 起写下面 7 份交付物（需求澄清-v4 已通过，其余在写或在审）。工期约 152.25～166.25（0.29 加 B3 1～1.5、B4b-3 2.5～3.5；0.29 续加 B0 0.5、B1 4～5.25、B2 0.5、B6 0.25～0.5） 人日，日历时间约 157～180 个工作日（R-160，开发计划 v4 第四节）。

- **长期规则：新增表或桶，必须同时更新数据清单并过 D1**（R-119，架构 3.5）。哪一批加表、加桶（或桶里一段新的路径前缀），就在同一个合并里改对应功能的 `shared/manifests/<功能>.ts`；D1 比对不过不能合并。例如 B4b-1 的 `files`、`vault-files` 桶，B4b-2 的 `note_vectors`、`embed_queue`，B5 的纪念日头像。② 代码审查员每批核对清单跟着改了；③ 安全审查员核对注销、导出、备份跟着清单覆盖到了；④ QA 每批确认 D1 为 0 差异。

## 七、密钥由本人生成，AI 不接触明文

VAULT_KEY、PIN_PEPPER（预览、正式各一套）和 exe 签名私钥，一旦泄露或丢失都很难补救。运维、主持人都是 AI，所以：
1. **运维只写生成脚本**，代码审查员和安全审查员审过才能用。脚本不把值写进任何文件或日志，也不发到网络上（除了写入下面的目标）。
2. **产品负责人本人在自己电脑上打开一个 PowerShell 窗口运行脚本**，不通过 Claude 运行。脚本生成随机值后：
   - VAULT_KEY、PIN_PEPPER：直接写入 `supabase secrets`（本人先 `supabase login`），屏幕只显示一次给本人抄进 iPhone“密码”App（R-90），然后清屏；
   - exe 签名私钥：私钥直接写入 GitHub production 环境的 secret，另存一份到本人选的 U 盘，私钥密码只显示一次给本人存进“密码”App。
3. **安全审查员在 S-B5、S-B6 各加一项核对**：生成过程中 AI 没有接触明文。核对办法：审脚本、查聊天记录和过程记录里没有这些值、本人确认是自己运行的。
4. Cloudflare 和 Supabase 的令牌、Gemini 密钥也一样：本人在网页上生成，直接粘贴到 GitHub 或 Supabase 的设置页，不经过聊天。
5. **要用正式令牌或 service role key 的手动操作**（不走 GitHub 流水线的那几步）：
   - 包括：搬家时的导入脚本（架构 5.8）、第 3 层回滚的恢复脚本、GitHub 用不了时手动部署函数（手册第四节第 2 层办法 B）；
   - **默认由产品负责人本人在自己的 PowerShell 窗口里执行**：运维事先写好完整命令（不含密钥值）、审查员审过；本人把密钥放进这个窗口的环境变量，运行命令，把屏幕上的条数等结果告诉运维，然后关掉窗口；
   - **例外**：确实只能由 AI 执行时（例如要边看报错边调整），本人临时生成一把新令牌或新密钥给这一次用，**用完立即在控制台吊销或轮换**，并记进过程记录（谁、什么时候、为什么、何时吊销）。安全审查员在 S-B7 核对这些记录。
