# 人员名单

除“产品负责人”外，所有成员都是由主持人（Claude）按角色派出的 AI 助手（子代理）。每人只按分配的角色和任务独立工作，互相看不到对方写的内容，做完交一份报告。报告由主持人核实后再采纳，采纳和不采纳都有记录，见 [评审索引](../03-评审/评审索引.md)。

同一位成员可以接着追问或复查，复查时保持原来的评判标准。

**当前状态（2026-10-24）**：4.0.0 设计完成，开工前准备中。第七轮整体检查的整改进行中；前端改用 React + TypeScript（R-96），架构师正在同步改架构；账号注册定在 10-26；之后进入 B0（B0 含 React 脚手架）。产品负责人要亲自做的事，见 [产品负责人待办-v4](产品负责人待办-v4.md)。

## 三、每个版本的固定流程（4.0.0 起）

### 开工前
0. **备份**：开始新版本前备份云端数据和源码（[ADR-009](../04-决策/ADR-009-每个版本前备份数据和源码.md)），记进发布记录。执行：运维（4.0.0 上线前的 claude.ai 数据由主持人用 ArtifactData 导出）。
1. **需求**：产品负责人提出，主持人记入 [需求记录](../01-需求/需求记录.md)。
2. **设计和评审**：按需请产品经理、UI 设计经理评审，主持人汇总成修改清单，逐条问产品负责人。

### 每一批（B0～B7）都走这六环

| 环节 | 谁做 | 谁签字 | 签什么、签在哪 |
|---|---|---|---|
| ① 开发 | 按第二节的负责人（前端、后端、运维）；主持人整合 | 作者自己写“已完成、自测通过” | 本机测试和 CI（类型检查、ESLint、Vitest、Playwright 等）全绿；有界面改动的，前端先用 review-animations 自查动效 |
| ② 代码审查 | 代码审查员（作者不自审） | **代码审查员本人**签“通过” | 审查记录放 `docs/03-评审/` 对应批次；不通过就回到 ① |
| ②b 动效审查（R-93；本批有界面或动效改动时，B1～B7 基本都有） | UI-4 用 review-animations 独立审：该不该动、时长和曲线、能否被打断、退出动画、“减少动态效果”时是否关掉、会不会卡顿 | **UI-4 本人**签“通过” | 审查记录放 `docs/03-评审/` 对应批次；不通过回到 ① |
| ③ 安全清单核对 | 安全审查员，对照架构 15.4 的本批 S-Bx | **安全审查员本人**签“通过” | 逐项打勾；本批 P0 没过，不能进 ④ |
| ④ QA | QA：本批验收标准（架构 1.3）＋ 冒烟回归集 ＋ 新用例 | **QA 本人**签“通过” | 测试报告放 `docs/06-测试/` |
| ⑤ 产品负责人试用（涉及真机的批次：B2、B3、B5、B7） | 产品负责人按 QA 给的清单在 iPhone 上试 | **产品负责人**在聊天里说“这批可以” | QA 把结果写进报告，主持人记进过程记录 |

规则：
- **作者不自审**。谁写的代码，谁就不能签 ②。主持人整合时改过的代码，同样由代码审查员审。
- **审查结论只能由审查员本人签**。主持人只负责转交和核实，不能代签“通过”，也不能把“有条件通过”写成“通过”。
- 六环都签完，这一批才算过，才能开下一批。B0 只有脚手架和地基、没有界面动效时，②b 写“本批不涉及”，由 UI-4 确认。
- 不涉及真机的批次（B0、B1、B4、B6）没有第 ⑤ 环，但产品负责人随时可以在预览环境里试。
- 每批的冒烟回归集由 QA 在测试用例 v4 里标出来，**每批都跑**，防止新批次弄坏旧功能。

|---|---|---|
| B0 开工前 | 皮肤视觉稿和 10-24 当天改动的独立视觉评审 | UI-4（如果 UI-4 参与过皮肤稿，就换一位新的视觉评审员） |
| B1 开工前 | 中韩混排评审 | UI-3 |

### 发布
- 正式发布只走 GitHub 流水线：网页和服务器函数走 **deploy-prod**，exe 走 **desktop**。两条都要产品负责人在 GitHub 上点“批准”。不在本机手动发布正式版。
- 发布前按 [上线与回滚手册-v4](../08-发布/上线与回滚手册-v4.md) 的检查清单逐项打勾。执行：运维；审查：安全审查员、代码审查员；签字：产品负责人。
- 发布后写进 [发布记录](../08-发布/发布记录.md)，文档与配置管理同步更新 CHANGELOG、README、路线图。
- 上线后产品负责人自己先用 2–4 周，再开放给朋友（R-47）；开放前隐私说明和使用条款要签字。

## 四、单点和替补

代码审查员、安全审查员每批都要签，一个人卡住整批就停。所以各指定替补：

| 角色 | 替补 | 什么时候用替补 | 限制 |
|---|---|---|---|
| 代码审查员 | 首选：另派一位新的代码审查员，标准相同。临时：架构师 | ① 原审查员这一批积压的待审内容超过一批；② 原审查员参与过这段代码的编写或修改；③ 原审查员和作者意见僵持，需要第三人判断 | 架构师当替补时，只审“实现是否符合设计、代码质量”；不能审他自己写的设计文档 |
| 安全审查员 | 首选：另派一位新的安全审查员。临时：代码审查员 | 同上三条 | 代码审查员当替补时**只能签 P1、P2 项**；P0 项必须由安全审查员或新的安全审查员签 |

替补签字时写明“替补”和原因。原审查员回来后，抽查替补签过的内容。

## 五、工期

- 架构 1.3 的人日只算开发。**每批在开发人日之外，另加 20–30%**，用于评审、测试和返工。按 36–45 开发人日算，合计约 43–59 人日（示意）。
- B7 建议拆成 B7a（搬家与发布准备）和 B7b（文档与官网），见上线与回滚手册第一节。
- 前端改用 React + TypeScript（R-96）：原来的 v3 原生 JS 代码不能直接沿用，B0 要多出搭脚手架和迁移的工作，人日要由架构师和前端重新估。
- **开发计划 v4 里重新估算总工期后，告诉产品负责人。** B2 结束时再按实际进度估一次（架构 1.3）。

## 六、前端要不要拆成两人（**需产品负责人确认**）

建议拆成两人：

| | 前端 A：App 主体 | 前端 B：官网与 exe 外壳 |
|---|---|---|
| 做什么 | `/app/` 里的全部页面、离线和同步、录音、i18n、动效、Service Worker | 官网首页和 SEO、Pages Function 语言分流、Tauri exe 外壳（通知、单实例、托盘、自启、热键、CSP、最小权限、自动更新） |
| 主要批次 | B0～B5 | B0（路由骨架）、B6、B7b |

理由：
1. **工作量**：改用 React + TS 后，前端是全项目最大的一块，一个人从 B0 做到 B7，是新的单点和瓶颈。
2. **可以并行**：官网、exe 外壳和 App 主体相对独立，拆开后 B6、B7b 可以和 App 的收尾同时做，缩短工期。
3. **审查更清楚**：exe 的 CSP 和权限是 P0 安全项，交给专人做，安全审查员审起来范围明确。

代价和约束：
- 两人要共用一套组件和样式。约定**共用部分归前端 A**，前端 B 只用不改，需要改时提给 A。
- 多一个人，代码审查员每批审的量不变，但要分清作者，避免谁都不负责。

不拆的话：维持一人，工期按一人重估，B6、B7b 只能排在 App 之后。
