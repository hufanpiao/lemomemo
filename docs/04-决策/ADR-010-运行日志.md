# ADR-010 运行日志（操作日志 + 错误日志）

- 状态：**已采纳**（2026-10-23，产品负责人问“软件有log记录功能吧？”，选择“加进 v3”）
- 范围变更：v3 范围已冻结，这一项经产品负责人同意破例加入（需求 R-27）

## 背景
v2 和结构调整后的代码里一行日志都没有。提醒没响、保存失败、定时推送出错时，事后无从查起；QA 测试和代码审查也缺少依据。

## 决定
1. **两类记录**
   - 操作：新建、修改（只记改了哪些字段名）、完成 / 取消完成、改期、软删除、恢复、30 天清理。
   - 运行：保存失败、写入超时、断线和重连、提醒发出、提醒被确认或推迟、定时推送成功或失败、每日同步成功或失败。
2. **存储**：云端数据库新集合 `logs`。**每台设备每天一条文档**，文档 id 为 `<YYYY-MM-DD>_<设备号>`：页面的设备号是本机随机生成的（存在 `platform/prefs` 的 `pv-device`），Claude 写入时用 `claude`。这样多台设备同时写，也不会互相覆盖（数据库是“后写的覆盖先写的”）。
3. **每条记录的格式**：`{t: 毫秒, kind: "op"|"run", act: 动作, coll?: "events"|"todos", id?: 条目编号, fields?: [字段名], code?: 错误码, src: "page"|"chat"|"task"}`。
4. **隐私**：**不记标题、备注、原话、项目名等内容**，只记编号、字段名和错误码（和安全审查对推送的要求一致）。
5. **体量控制**：每条文档最多 500 条，超出时丢掉最早的；保留 90 天，页面打开时清理（每天最多一次，和最近删除的清理一起做）。页面先在内存里攒，每 30 秒或页面切到后台时写一次，不会每个动作都写一次库。
6. **本机**：每日同步（`planner-daily-snapshot`）和版本前备份都把 `logs` 一起导出到 `data/backups/`。
7. **代码位置**：`data/log.js`，只能由 data 层和 platform 层调用；界面要记的事件（比如提醒被确认）通过 data 层的接口记。日志写入失败不能影响正常功能，失败就静默丢弃。
8. **查看**：待办页底部加一个不显眼的“运行记录”入口，只读，显示最近 7 天；也可以直接让 Claude 读。

## 后果
- 好处：出问题能查到“什么时候、哪台设备、哪个动作、什么错误码”；QA 和审查有了依据。
- 代价：多一个集合、少量写入。按每天几十条估算，90 天、两三台设备，远低于数据库 25,000 条文档的上限。
- 不记录内容，所以日志只能回答“哪一条被改了”，要知道“改成了什么”，得对照每日备份。
