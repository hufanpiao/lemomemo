# ADR-020 编号与版本号规则

- 状态：**已采纳**（2026-10-27，需求 R-148：“按顺序来”；版本号选“改叫 4.1.0（推荐）”）
- 日期：2026-10-27
- 来源：整体结构检查（文档与流程）；[需求记录](../01-需求/需求记录.md) R-39、R-67
- 修订：R-67 的“4.0.1”改为 4.1.0

## 背景
- R-39 定了版本号“主.次.修”：大改升第一位、新功能升第二位、修问题升第三位。但 R-67 把新功能“重复事项”排成 4.0.1，路线图照抄，两条自相矛盾。
- 项目里同时有几套编号：需求 R 号、ADR 号、文件名里的“-v4”、架构文档的修订号 0.2x、评审轮次（出现了“第七轮第五轮复查”这种说法），没有写下它们之间的关系，以后迭代到 4.1、5.0 时容易混。

## 决定
1. **软件版本号**：按 R-39，`主.次.修`。
   - 主：大改（换架构、换形态），例如 3 → 4。
   - 次：加新功能，例如重复事项 → **4.1.0**。
   - 修：只修问题、不加功能，例如 4.0.1。
2. **需求编号 R-n**：全项目一条线连续往下编，换版本不重新从 1 开始；被改的需求不删，在“状态”列写明被哪条取代（需求记录说明）。
3. **ADR 编号**：同样连续不重开；被取代的 ADR 状态写“已被 ADR-x 取代”。
4. **文件名里的版本**只带主版本：`架构设计-v4.md`、`测试用例-v4.md`。4.1.0 不新开文件，在原文件里加节；到 5.0.0 才新开 `-v5`。
5. **文档修订号**（架构的 0.20、0.26……）只表示这份文档改到第几次，和软件版本号无关；在文档首页“状态”里写当前修订号和依据的最后一条 R 号。
6. **评审编号**从 4.0.0 开工起一律写成“版本-批次-第几次”，例如 `4.0.0-B4b-2-第1次`，放在 `docs/03-评审/` 下同名文件夹；开工前已有的“第一轮～第七轮”文件夹保持原样，不改名。

## 影响
- 路线图、CHANGELOG 里的“4.0.1 重复事项”改为 4.1.0。
- 需求记录加“状态”“影响”两列，`build/req_index.py` 维护和核对。
