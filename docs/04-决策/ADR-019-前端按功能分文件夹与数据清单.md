# ADR-019 前端按功能分文件夹，数据按功能写清单

- 状态：**已采纳**（2026-10-27，需求 R-119：“改，按推荐的混合式 + 数据清单”）
- 日期：2026-10-27
- 来源：[评估-按功能分文件夹](../10-架构/评估-按功能分文件夹.md)；[架构设计-v4](../10-架构/架构设计-v4.md) 0.22、2.1–2.3、3.5
- 修订：[ADR-017](ADR-017-前端用React与TypeScript.md) 的分层目录（技术栈不变）
- 关联：[ADR-016](ADR-016-备份按用户拆分与注销清除.md)（备份、导出、注销的范围改为读数据清单）

## 背景
- ADR-017 定的前端目录按层分：shared → platform → data → ui → app。一个功能（例如纪念日、附件、“＋”）的代码要分散在 6–7 个目录里，删功能时很难确认删干净；`routes.ts`、词典、`ui-store.ts`、同步的集合列表是前端两人并行时最容易冲突的文件。
- 数据方面，加一种新数据要在 15–19 个地方各登记一遍（迁移、RLS、列级授权、Realtime、本机缓存、outbox、sync、备份、拉取脚本、导出、注销、30 天清理、孤儿清理、用量报告、数据字典等），只有一处有 CI 兜底。前几轮安全评审挑出的“注销没删”“孤儿没清”，多数就是这样漏掉的。
- 代码还没开始写，现在改只需要改文档。

## 决定
1. **前端用混合式**：
   - 每个功能一个文件夹 `src/features/<功能>/`，里面分 `data/ → hooks/ → ui/`，另有 `i18n/`、`__tests__/`；
   - 对外只经 `index.ts`，它只能导出懒加载的页面、小卡片、类型和数据清单（A27）；
   - 保留公共层：shared（前后端共用，logic 按领域分子目录）、platform（不变）、core（原 data 里跨功能的缓存、队列、同步）、kit（通用组件、通用 hooks、跨功能界面状态）、motion（不变）；
   - 依赖方向和安全规则不变，ESLint 边界规则改写（A1 / A8、A18、A20），新增 A27。
2. **数据按功能写清单**：
   - 每个功能一份 `shared/manifests/<功能>.ts`，写明有哪些表和桶、是否同步、本机缓存方式（隐私记的明文不进）、备份和导出范围、注销和清理方式、是否用 AI 和向量；
   - 同步、本机缓存、备份、导出、注销、清理、用量报告都读清单；
   - 第一版迁移按功能拆成 7 个文件，以后的迁移文件名带功能名，删功能写 drop 迁移。
3. **防漏**：
   - CI 检查 D1 比对数据库里所有表、所有桶和清单，没登记的报错；
   - 注销、清理用例按清单自动生成；
   - 都列进 S-B0（P0）。
4. **核心清单不拆**：core（账号、配置、限流、日志、同步基础设施）、vault（隐私记一整套）、search（向量和重算队列）。一张表、一个桶只有一个主人。

## 考虑过、没采用的
- **完全按功能分**：服务器共用的逻辑必须留在 /shared，缓存和同步也必须有公共层，最后还是变成混合式。
- **维持按层分**：现在管得过来，但每加一个功能都要来回改 6 个目录和 15–19 处数据登记，漏登记的风险正好落在注销和清理这些安全要点上。

## 后果
- **好处**：
  - 加一个功能，前端只要一个文件夹加一行登记，数据只要一份清单加一个迁移文件；
  - 删功能能删干净，tsc 和 D1 会报出残留；
  - 前端两人并行时，共用的文件只剩 `app/features.ts` 和 `kit/`。
- **代价**：
  - B0 多 1 人日（边界规则、清单类型、D1、用例生成器），合计 106 人日；
  - 正文里的旧模块名不逐处改，靠架构 2.2b 的对照表对应，读文档时要多看一眼；
  - 要防功能的 `index.ts` 把整页带进首屏（A27 + 体积检查）。
