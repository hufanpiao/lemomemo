# ADR-009 每个版本前备份数据和源码

- 状态：**已采纳**（2026-10-23，产品负责人要求：“本地电脑要有完整的整个源码，每次做新版本前都要有备份”）
- 部分取代 ← R-105、R-208、R-209（2026-10-28 起，4.0.0 开工前备份起执行）：决定第 2 条（数据）按 R-208 停止——v3 数据不再备份；第 3、4 条的**存放位置**改到 `E:\柠檬记-备份\版本前\`（R-105），版本前源码备份**不加密**（R-209）；第 1、5～7 条不变。每日自动同步那一段已由架构设计-v4 第 10 节取代（R-25 → R-105），定时任务按 R-208 停用。

## 背景
- 真实数据只存在 claude.ai 的云端数据库里，本地没有副本。
- 源码在本机的 git 仓库里，但只有这一份；项目文件夹被误删或磁盘出问题时，就无法恢复。

## 决定
1. **时机**：每次**开始做新版本之前**、每次**发布之前**，都备份一次；产品负责人随时说“备份一下”时也执行。
2. **数据**：Claude 用 ArtifactData 把 `events`、`todos` 导出到 `data/backups/<日期>_<时机>/`，每条数据一个 JSON 文件。
3. **源码**：`python build/backup.py <时机>` 用 `git bundle --all` 把整个仓库连同全部历史，打包到项目文件夹**以外**的 `D:\claude code\待办APP-备份\源码\`，并校验 bundle 完整。工作区有未提交的改动时脚本会拒绝备份。
4. **清单**：脚本在数据备份文件夹里写 `清单.json`，记录条数、git 提交号和 bundle 路径，把数据和源码对上。
5. **隐私**：`data/backups/` 是真实个人数据，不进 git，只留在本机。
6. **记录**：每次备份记进 [发布记录](../08-发布/发布记录.md) 的“备份记录”。
7. **流程**：备份列为每个版本固定流程的第 0 步（[人员名单](../00-团队/人员名单.md)），也列进发布清单（[测试用例-v3](../06-测试/测试用例-v3.md) 第 7 节）。

## 后果
- 好处：数据和源码都能恢复到任何一个版本开始前的状态；源码备份放在项目外，误删项目文件夹也不怕。
- 代价：每个版本多两步操作，备份文件会逐渐占用空间。目前数据量很小，可以忽略；以后备份变大时再定保留策略。
- 还不够的地方：备份都在同一块硬盘上。需要的话，可以再把 `D:\claude code\待办APP-备份\` 同步到网盘或移动硬盘，这一步由产品负责人决定。

## 补充：每日自动同步（2026-10-23，产品负责人选择“每天 23:30”）
- 定时任务 `planner-daily-snapshot`（Claude App 的“定时任务”里可以看到和修改）：每天 23:30 左右（系统会错开几分钟，实际约 23:39），用 ArtifactData 把云端数据导出到 `data/backups/<日期>_每日/`，再运行 `python build/daily_snapshot.py` 写清单。
- 每日快照只保留最近 30 天；版本前、发布前的备份永远不删。
- 每日快照只备份数据，不打包源码（源码在版本前、发布前由 `build/backup.py` 备份）。
- 限制：电脑上的 Claude App 开着才会运行；没开时，下次打开时补做。失败时会在当天的快照文件夹里写“失败原因.txt”，能推送的话也会发通知。
- 这是云端 → 本机的单向快照，不是双向同步。

## 补充：R-105、R-208、R-209 起的新流程（2026-10-28，B0 开工前备份起）
- **R-105**：备份不再放 `D:\claude code\` 下面（开发工作区），改放 **`E:\柠檬记-备份\`**。
- **R-208**：v3（claude.ai 看板）的数据负责人全都不要了：不再备份 v3 数据，`data/backups/` 下的旧数据由负责人本人删除，脚本不负责。4.0.0 上线后含用户数据的备份另行设计（[架构设计-v4](../10-架构/架构设计-v4.md) 第 10 节）。
- **R-209**：版本前备份**只打包源码、不加密**（R-207 选的 WinRAR 加密不再需要）。

**流程**（运维 / 主持人运行，不需要负责人输密码）：
1. 先把改动全部提交；
2. 运行 `python build/backup.py <时机>`，例如 `python build/backup.py 4.0.0开工前`。脚本会：
   - 检查工作区已全部提交，时机名只允许文字、数字和 `. _ -`（不能有 `..`、不能以点结尾）；
   - `git bundle create --all`，再 `git bundle verify`；
   - **恢复测试**：用 `git -c core.longpaths=true clone` 把 bundle 克隆到临时目录，跑 `git fsck --full`，核对 HEAD、`HEAD^{tree}`、全部分支和标签；
   - bundle 和 `清单.json`（提交号、bundle 大小和 SHA256、恢复测试结果）直接写到 `E:\柠檬记-备份\版本前\<日期>_<时机>\`；这个文件夹已存在就停下，不覆盖；中途出错会删掉做了一半的文件夹。
3. **记录**：把路径、大小、SHA256、提交号记进[发布记录](../08-发布/发布记录.md)的“备份记录”。
4. **恢复演练**（QA，交付物 #7）：`git -c core.longpaths=true clone <bundle> 柠檬记APP`，再 `git -C 柠檬记APP config core.longpaths true`，确认能打开、能构建。仓库里有超过 260 字符的路径，不加 `core.longpaths=true` 会检出失败。

**还没处理的**：v3 时期 `D:\claude code\待办APP-备份\源码\` 里的两个 bundle 还留在 D 盘，要不要删或挪到 E 盘，由负责人决定。
