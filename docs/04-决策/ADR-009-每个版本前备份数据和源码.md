# ADR-009 每个版本前备份数据和源码

- 状态：**已采纳**（2026-10-23，产品负责人要求：“本地电脑要有完整的整个源码，每次做新版本前都要有备份”）
- 部分取代 ← R-105（2026-10-28 起，4.0.0 开工前备份起执行）：决定第 3、4 条的**存放位置和加密**改为下面“R-105 起的新流程”；第 1、2、5～7 条不变。每日自动同步那一段已由架构设计-v4 第 10 节取代（R-25 → R-105）。

## 背景
- 真实数据只存在 claude.ai 的云端数据库里，本地没有副本。
- 源码在本机的 git 仓库里，但只有这一份；项目文件夹被误删或磁盘出问题时，就无法恢复。

## 决定
1. **时机**：每次**开始做新版本之前**、每次**发布之前**，都备份一次；产品负责人随时说“备份一下”时也执行。
2. **数据**：Claude 用 ArtifactData 把 `events`、`todos` 导出到 `data/backups/<日期>_<时机>/`，每条数据一个 JSON 文件。
3. **源码**：`python build/backup.py <时机>` 用 `git bundle --all` 把整个仓库连同全部历史，打包到项目文件夹**以外**的 `D:\claude code\待办APP-备份\源码\`，并校验 bundle 完整。工作区有未提交的改动时脚本会拒绝备份。
4. **清单**：脚本在数据备份文件夹里写 `清单.json`，记录条数、git 提交号和 bundle 路径，把数据和源码对上。
5. **隐私**：`data/backups/` 是真实个人数据，不进 git，只留在本机。
6. **记录**：每次备份记进 [发布记录](../08-发布/发布记录.md) 的“备份记录”。
7. **流程**：备份列为每个版本固定流程的第 0 步（[人员名单](../00-团队/人员名单.md)），也列进发布清单（[测试用例-v3](../06-测试/测试用例-v3.md) 第 7 节）。

## 后果
- 好处：数据和源码都能恢复到任何一个版本开始前的状态；源码备份放在项目外，误删项目文件夹也不怕。
- 代价：每个版本多两步操作，备份文件会逐渐占用空间。目前数据量很小，可以忽略；以后备份变大时再定保留策略。
- 还不够的地方：备份都在同一块硬盘上。需要的话，可以再把 `D:\claude code\待办APP-备份\` 同步到网盘或移动硬盘，这一步由产品负责人决定。

## 补充：每日自动同步（2026-10-23，产品负责人选择“每天 23:30”）
- 定时任务 `planner-daily-snapshot`（Claude App 的“定时任务”里可以看到和修改）：每天 23:30 左右（系统会错开几分钟，实际约 23:39），用 ArtifactData 把云端数据导出到 `data/backups/<日期>_每日/`，再运行 `python build/daily_snapshot.py` 写清单。
- 每日快照只保留最近 30 天；版本前、发布前的备份永远不删。
- 每日快照只备份数据，不打包源码（源码在版本前、发布前由 `build/backup.py` 备份）。
- 限制：电脑上的 Claude App 开着才会运行；没开时，下次打开时补做。失败时会在当天的快照文件夹里写“失败原因.txt”，能推送的话也会发通知。
- 这是云端 → 本机的单向快照，不是双向同步。

## 补充：R-105 起的新流程（2026-10-28，B0 开工前备份起）
原来的做法有两个问题：源码 bundle 放在 `D:\claude code\待办APP-备份\源码\`，数据留在项目里的 `data/backups/<标签>/`，**都是明文**，而且都在 `D:\claude code\` 下面——开发工具和 AI 助手在这里工作时能读到。R-105 和[架构设计-v4](../10-架构/架构设计-v4.md) 第 10 节规定：放到 **`E:\柠檬记-备份\`**，用 **7-Zip AES-256 加 `-mhe=on`**（文件名也加密）。

**硬性规则：密码只由负责人本人保存，AI 不接触明文。** 密码不写进脚本、不放 Windows 凭据管理器（AI 跑的脚本能读到）、不发到聊天里；负责人存在 iPhone 的“密码”App 里。

1. **导出数据**（主持人）：照旧用 ArtifactData 把 `events`、`todos`、`logs` 导出到 `data/backups/<日期>_<时机>/`。
2. **打包和验证**（运维 / 主持人，AI 可以运行）：`python build/backup.py <时机>`（只备份源码时加 `--no-data`）。脚本会：
   - 检查工作区已全部提交；
   - `git bundle create --all` 并 `git bundle verify`；
   - **加密前的恢复测试**：把 bundle clone 到临时目录，核对 HEAD 和全部分支、标签一致（替 QA 做加密前的可恢复验证），结果写进清单；
   - 把 bundle、数据文件夹、`清单.json` 放进暂存目录 `E:\柠檬记-备份\暂存\<日期>_<时机>\`；
   - **不加密**，最后打印一条负责人要运行的命令。
3. **加密**（**负责人本人**在自己的 PowerShell 里运行）：`build/backup_encrypt.ps1 -Tag <日期>_<时机>`。脚本用 `7z a -t7z -mhe=on -p` 打成 `E:\柠檬记-备份\版本前\<日期>_<时机>.7z`，密码由 7-Zip 自己提示输入（脚本不接收、不保存）；再用 `7z t` 测试（再输一次密码）；测试通过后删掉暂存目录和项目内 `data/backups/<标签>/` 的明文；输出文件路径、大小、SHA256。
4. **记录**：负责人把路径、大小、SHA256 发给主持人（不含密码），记进[发布记录](../08-发布/发布记录.md)的“备份记录”。
5. **恢复演练**（QA，交付物 #7）：负责人解开 .7z（输入密码）到临时文件夹，`git -c core.longpaths=true clone <bundle> 待办APP`，确认能打开、能构建；用完即删明文。仓库里有超过 260 字符的路径，不加 `core.longpaths=true` 会检出失败。

**还没解决的**：v3 时期留下的明文——`D:\claude code\待办APP-备份\源码\` 里的两个 bundle、项目内 `data/backups/` 里的历史快照——要按架构第 10 节“旧的 data/backups/ 一并挪过去”另行加密搬走，由负责人决定什么时候做。
